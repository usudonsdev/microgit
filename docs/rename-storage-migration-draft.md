# 履歴・保存場所・同梱バイナリ名の「新旧両方を読む」移行設計（案）

> **案・未決定。決定は運営者。現行の正本は [design-policy.md §2.5](./design-policy.md)**（`refs/microgit/*`・`.microgit/`・同梱バイナリ名 `microgit-agent` / `microgit-vm` は**旧名のまま据え置き**。この決定は本書で覆さない）。
> 本書は、運営者が将来「新名へ移すか」を判断するための材料。実装・リリースの計画ではない。作成: 2026-11-08（夜間の自動作業）。事実を確かめていないものは【未確認】と書いた。
> 関連: [rename-vereve.md](./rename-vereve.md) §3・§5・§6（「`refs/microgit/*` の新旧両対応の移行設計」「同梱バイナリ名の改名（Mac の実機検証が先）」が未実施として残っている項目の、検討用の下書き）。

## 1. 先に結論（案の要点）

1. **今は移さない**（現行決定のまま）。移す価値（利用者に見えない内部名の統一）に対して、壊したときの被害（履歴が読めない・端末ごとに履歴が分裂する）が大きい。
2. 移すなら **3 つを別々の変更として、別々の時期に**扱う。データ（refs）・保存場所（`.microgit/` と `.git/microgit/repos/`）・同梱バイナリは、互換の相手も検証手段も違う。
3. データ（ref）は **段階案「読み取りだけ両対応 → 書き込み移行（一定期間は旧名にも書く）→ 旧名廃止」**。第 1 段階を出して**利用者の多くが更新してから**第 2 段階に進む（旧版は新名を読めないため）。ただし**段階ごとに戻せるのは ref だけ**。保存場所（`.microgit/`）は読み書き兼用の単一フォルダで「読み取りだけ両対応」が成り立たないので、別の手順で扱う（§5 の「保存場所」）。また**旧拡張 5.x（`usudonsdev.microgit`）は非推奨にして新拡張へ案内する対象で、第 1 段階の版を受け取れない**（§3 R1、§6）。
4. 旧名の**自動削除はしない**。廃止は利用者が明示的に行うコマンドにし、ここだけが不可逆な点として扱う。
5. 同梱バイナリ名は**利用者のデータと無関係**（VSIX の中で完結）なので、最も後回しでよい。**Mac 実機でビルド・署名・起動を確かめてから**。最悪、改名しなくても利用者への影響は無い。

## 4. 案の比較（データ = `refs/microgit/*`）

| 案 | 内容 | 利点 | 欠点 | 判定 |
|---|---|---|---|---|
| **A 据え置き**（現行） | 何も変えない | 互換の問題が無い。実装・検証の費用が 0 | 内部名に旧称が残る（利用者には見えない。文言と UI は verEve） | **現行の決定** |
| **B 段階案**（本書の推奨） | 読み取り両対応 → 書き込み移行 → 旧名廃止（§5） | **ref は**各段階で戻せる（保存場所は別手順。§5）。旧版との共存期間を作れる | 実装・テストが多い。期間が長い。第 1 段階を出して普及を待つ必要がある | 移すならこれ |
| **C 一括変換** | 起動時に旧名の ref を新名へ全部書き換え、旧名を消す | 実装が単純。移行期間が無い | R1・R4 が最悪の形で出る。旧版の端末の履歴が突然消えたように見える。戻せない | 却下 |
| **D 二重書きを永続化** | 新旧両方に書き続ける | 旧版と常に互換 | R2・R3 が恒常化。同期の失敗の面倒を永久に見る。改名の意味（旧名を無くす）が無い | 却下 |
| **E 全面改名**（refs・保存場所・バイナリを同時に） | design-policy §2.5 で却下済みの案 | 一度で終わる | 既存の履歴との互換が切れる。Mac で検証できない部分を同時に動かす。取りこぼすと静かに退行する | **却下済み（理由は §2.5）。再検討しない** |
| **F 別名 ref（symbolic ref）で新名を旧名の別名にする** | `refs/vereve/*` を `refs/microgit/*` への symref にする | 実体が 1 つで分裂しない（ように見える） | push / fetch は symref を転送せず、参照先の値を送る可能性が高い【未確認：実機で `git push` が symref をどう扱うかを確かめていない】。ホスティング側（GitHub など）の扱いも【未確認】 | 保留。確かめるなら安い実験（空リポジトリ 2 つ）で |

**案 B の読み取りの規則（R2 への対策案。本書での唯一の定義。§5 の各段階はこれを参照し、別の言い方をしない）**: 親リポジトリの `refs/microgit/*`（旧名）と新名の名前空間の両方から、同じブランチの `micro-history` を読むとき、

1. **片方にしか無い** → あるほうを採る。
2. **両方あり、同じ tip** → 新名を採る（同じなので違いは無い）。
3. **両方あり、一方がもう一方の祖先** → **先に進んでいる側（子孫の側）を採る**。新名が古く旧名が先に進んでいるときは、旧名の側を採る（新名を優先しない）。
4. **両方あり、どちらも祖先でない（発散）** → design-policy §4.1 の既存の動き（自分の tip に触れず、相手側を新しい `mb-N` タグとして追加）をそのまま使う。新しい規則を作らず、既存の「マージしない・分岐のみ」に乗せる。
5. **祖先関係を判定できない**（片方のオブジェクトが手元の bare に無い）→ 発散（4）として扱う。安全側（tip を動かさない）に倒す。【未確認】この場合が実際に起きるか、起きたときのオブジェクトの取得の流れは、コードを追って確かめていない。

「新名を先に、無ければ旧名」は 1 の特別な場合にすぎず、それだけを規則として実装すると 3 を満たさない（旧名だけが進んでいる状態で、古い新名を採って履歴が巻き戻って見える）。なお親の `refs/microgit/*` は bare の `refs/heads/micro-history` から作り直される派生ミラーで、ユーザーの作業を一意に持つのは bare 側（design-policy §4.1 の注記）。この規則は**取り込み（親 ref → bare）の向き**に適用する。

**途中で版が行き来したとき**: 第 2 段階の版 → 第 1 段階の版へ戻す → 戻した版が旧名にだけ書き進める（第 1 段階は書き込みを変えないので当然そうなる）→ 再び第 2 段階の版へ上げる、という経路では、新名は戻す前のまま古く、旧名だけが進んでいる。これは上の規則 3（新名が旧名の祖先）にそのまま当たり、**旧名を採って新名をそこまで進めてから**新名へ書く。戻している間に別の端末（第 2 段階の版）が新名を進めていれば、新旧は発散し、規則 4（`mb-N` として追加）に当たる。この経路を第 2 段階の完了条件に入れる（§5）。

## 5. 段階案（案 B の詳細）

### 第 0 段階：前提の確認（コードを変えない）

- Mac 実機の検証項目（§7）を済ませる。
- 旧版（5.x、および第 1 段階を入れる前の 6.0.0）が新名の ref に出会ったときの実機の挙動（無視されること）を確かめる（R1。コードの読みでは無視されるが【未確認】）。
- 案 F の実験（symref が push / fetch で転送されるか）。やるなら本段階。
- **新名の候補を決める**（例: `refs/vereve/*`。運営者の決定）。`refs/microgit-remote/*` は bare の中の一時 ref なので、改名しても利用者の履歴に影響しない（`shadowStore.ts` の 3 行。残った古い一時 ref の掃除は要る【未確認】）。

### 第 1 段階：ref の読み取りだけ両対応（書き込みと保存場所は旧名のまま）

- 親リポジトリの ref を読む箇所（`importFromParentRefs` と、その元の `parentMicroRefPrefix`）に、**§4 の読み取りの規則（1〜5）**をそのまま実装する。「新名を先に、無ければ旧名」だけの探索にしない（§4。旧名だけが進んだ状態で巻き戻る）。**書く側（`publishToParentRefs`、origin への push、fetch）は変えない**。
- **保存場所は第 1 段階では触らない**。`.microgit/`（shadow の gitfile・logs・overlay）は、読み取りと書き込みを同じフォルダで行う単一の場所で、ref のように「旧名と新名の両方を持ち、読むときだけ両方を見る」ことができない。「新フォルダ → 旧 `.microgit/` の順に探す」にすると、新フォルダができた時点で書き込み先が変わる（＝第 2 段階の変更になる）うえ、新旧に別々の内容があるときにどちらが正かを決める規則が要る（ref には §4 の祖先関係があるが、フォルダには無い）。したがって「読み取りだけ両対応」は **ref にだけ**当てはまる。
- 利点: この版が普及するほど、後続の段階で旧版の端末が減る。利用者に見える変化は無い。**ただし 5.x の利用者はこの版を受け取れない**（別拡張。§3 R1、§6.1）。
- 完了条件: 単体テスト（新名だけ・旧名だけ・両方で同じ tip・旧名だけが先に進んでいる・新名だけが先に進んでいる・発散・祖先を判定できない、の §4 の 1〜5 を網羅）と、旧データ（本物の 6.0.0 で記録した履歴）を読めること。**§4 の規則が一本であること**（コードの中に、この規則と別の優先順位の分岐が無い）。
- ロールバック: 無し（書き込みを変えていないので、版を戻すだけで元に戻る）。

### 第 2 段階：書き込み移行（一定期間は旧名にも書く）

#### 2a. ref（新名に書き、旧名へはミラー）

- 開始の条件（案）: 第 1 段階の版が一定期間出ていて、**Marketplace / Open VSX の更新状況から、verEve の利用者の大半が第 1 段階以上**と判断できる。**5.x の端末は母数に入らず、更新も届かない**ので、第 2 段階以降は 5.x が常に「旧版」として残る前提で、旧名のミラーをいつまで書くかを決める（第 3 段階の条件にも効く）。【未確認】利用者の版の分布を知る手段（Marketplace の統計に版別があるかを確かめる。無ければ、運営者の判断で期間を決める）。
- 新名に書く。旧名へは**ミラー**として書く（R3: 旧版の強制 fetch で巻き戻るので、ミラーを正本にしない）。ミラーの失敗は警告だけで止めない。
- 完了条件: 旧版と新版を同じ origin につないだ実機の往復（新→旧、旧→新）。発散時に履歴が失われないこと。**第 2 段階 → 第 1 段階 → 第 2 段階と版を行き来した経路**（第 1 段階の版が旧名だけを進めたあとで第 2 段階へ上げ直す。§4 の「途中で版が行き来したとき」）で、旧名が先に進んでいれば新名がそこまで進み、別の端末が新名を進めていれば発散として `mb-N` が付くこと。
- ロールバック（**ref だけに当てはまる**）: 第 1 段階の版へ戻せる（読み取り両対応なので、旧名のミラーを読める）。戻したとき、新名にしか無い最新の履歴が旧名のミラーに入っていることが前提なので、**ミラーが失敗していた期間の履歴は戻れない**。戻す手順に「新名から旧名へミラーを再作成するコマンド」を用意する。

#### 2b. 保存場所（`.microgit/` と `.git/microgit/repos/`）。ref の段階とは別の変更・別の時期にする

- **前提の整理**: 保存場所には 2 つある。(i) 実体の bare `.git/microgit/repos/<branch>.git`（親の `.git` の中。履歴の実体はここ。旧版が動いている別端末と共有しうる＝R5）。(ii) 作業ツリー側の `.microgit/`（`shadow/.git` の gitfile、`logs/`、`overlay/`。`shadowStore.ts` の冒頭コメントと `layout.ts` による）。新フォルダ名にするのは (ii) で、(i) は `.git` の中にあって利用者に見えず、名前を変える理由が薄い。
- 旧フォルダから新フォルダへの移行は、5.1.1 の `migrateLegacyMicrogitLayout` と同じ型（新しい場所が空ならフォルダごと移し、同名があるものは残し、移しきれない旧フォルダは消さない）で作れる。**ただし第 1 段階の版は新フォルダを知らない**ので、移した直後に版を戻すと、第 1 段階の版は旧 `.microgit/` が無いものとして空から作り直す（【未確認】bare は無傷で gitfile は `shadowStore.ts` が再生成する作りに読めるが、フォルダを消した状態からの復元は実機で確かめていない。`logs/` と `overlay/` の層が失われるかも【未確認】）。
- **ロールバックの手順（案。「戻せる」と言えるのはこの手順を用意したときだけ）**:
  - 案 S1（移す）: 第 2 段階の版に、**新フォルダを旧 `.microgit/` へ戻す逆方向のコマンド**を持たせ、版を戻す前にそれを実行する。逆移行の前に版だけ戻した利用者は、上の「空から作り直す」状態になる（履歴の実体は bare にあるので消えない見込み。【未確認】）。
  - 案 S2（移さずコピー）: 旧 `.microgit/` は触らず、新フォルダへコピーして新版は新フォルダだけを使う。版を戻しても旧 `.microgit/` が残っているので、戻した版はそのまま動く。代わりに、**コピー後に新版が書いた `logs/`・`overlay/` は旧側に反映されない**（古い内容に戻る。履歴の実体は bare で共通。【未確認】）。ディスクは二重になる。
  - 案 S3（保存場所は新フォルダへ移さない）: 据え置き。R10（利用者の `.gitignore` が新フォルダを除外しない）が出ない。本書は、**データ（ref）を移すことになっても、保存場所は S3 のまま残す案**を最小の選択肢として挙げる。移す動機（§6）が「利用者に見えない内部名の統一」だけなら、`.gitignore` への影響（R10）と引き換えに保存場所を動かす理由が薄い。
- どれを採っても、ミラーのような「旧新の両方に書く」ことはしない（`.microgit/` の中身は 2 つ書くと内容が割れる。R5）。
- R7 の対応（Boundary Guard の拒否リスト、フック、`.vscodeignore`、`.gitignore`）と R10 の対応（利用者の `.gitignore` の助言の更新、拡張側の除外）を**同じ変更セットで**行う。
- 完了条件: 旧 `.microgit/` を持つワークスペースを新版で開いて移行し、**逆方向（S1 の逆移行、または S2 の戻し）で第 1 段階の版が元どおり動く**こと。Windows（大文字小文字・パス長）でも動くこと（§7 の 9）。

### 第 3 段階：旧名の廃止

- 旧名を読まなくする。**旧名の自動削除はしない**。利用者が明示的に実行するコマンド（例: 「旧形式の履歴を整理」）で、新名に取り込み済みであることを確認してから旧名を消す。
- 開始の条件（案）: 第 2 段階の版が十分に普及。旧名にだけ履歴が残る端末が無い（利用者への告知とリリースノート。README が旧名を明記している＝R8）。**5.x の端末は更新されないので、旧名を読まなくした時点で 5.x の端末は新名の履歴を見られなくなる**。これを許容するか（5.x の非推奨から十分な期間を置くか）は運営者の判断（§8）。
- ロールバック（ref だけ）: **旧名を消したあとは戻れない**（R4）。消す前にバックアップ（旧名の ref を一覧にして保存）を取る手順を入れる。消さない限り、第 2 段階の版へ戻せる。保存場所は第 3 段階の対象ではない（旧名を消すのは ref だけ）。

### 同梱バイナリ（別の軸。データの段階とは独立に進められる）

- 互換の相手は**同じ VSIX の中のゲスト・ホスト・CI だけ**で、利用者のデータとは無関係。段階案のような共存期間は要らない。
- 進め方の案: (1) Mac 実機で §7 を確かめる。(2) `launchers.ts` の `resource()` が新名を先に、旧名を次に探す形にして、**ビルド側（Go・Swift・CI・`package-vsix.mjs`・NOTICES）の改名と同時に**出す。(3) ゲストの agent と `microgit-vm`、virtio-serial のポート名 `microgit`、環境変数 `MICROGIT_AGENT_STATE_DIR` は、**同じ名前でそろえて変える**（片方だけだと R6）。
- 利点が小さい（利用者に見えない）ので、**改名しない選択肢（据え置き続行）が妥当**。やるなら、データの移行とは別の時期・別の Issue。

## 6. トレードオフのまとめ

| 観点 | 据え置き（A） | 段階案（B） |
|---|---|---|
| 利用者のデータの安全 | 最も高い | **ref は**段階ごとに戻せるが、第 3 段階の削除は不可逆。**保存場所は戻す手順（§5 の 2b）を作って初めて戻せる** |
| 実装・検証の費用 | 0 | 大（ref・保存場所・テスト・旧版との実機の往復） |
| 期間 | なし | 複数のリリースにまたがる（普及待ち） |
| 旧版との共存 | 完全 | ref は第 1・2 段階で保つ。第 3 段階で切れる。**5.x とは第 1 段階の版を渡せないので、第 2 段階以降は常に旧名のミラー頼み** |
| 内部名の統一（改名の動機） | 満たさない | 満たす |
| Mac 実機が要るか | 不要 | バイナリ名のとき必須 |

「旧称が内部に残る」ことで利用者が困る場面は、現時点では見つかっていない（ログ・Publish の確認ダイアログは「技術名として `refs/microgit/*`」と書く方針。design-policy §2.5）。**移す動機が、検索性・商標・開発者の混乱のどれなのか**を、運営者が先に決めると、段階案を採る費用に見合うかを判断できる。

### 6.1 どの版に読み取り両対応を入れるか（5.x と 6.0.0 を分けて考える）

前提（確認済みの事実）: 6.0.0 は**未公開**（`CHANGELOG.md` の見出し、`package.json` の `version`）。旧 5.x は拡張 ID `usudonsdev.microgit` で、verEve（`usudonsdev.vereve`）は**新しい拡張**として出すので、5.x は更新の経路が違い、非推奨にして verEve へ案内する対象（`rename-vereve.md` §3・§5）。旧拡張の利用者は、第 1 段階の版を受け取れない。

| 選択肢 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| **X 公開前の 6.0.0 に第 1 段階（ref の読み取り両対応）を入れる** | 公開する最初の verEve から §4 の規則で新旧を読む | 「旧名しか読まない verEve」が存在しない。後から普及を待つ必要が、verEve の利用者については無くなる（範囲が最小）。5.x から乗り換えた人も最初から第 1 段階の版 | 6.0.0 の公開が、読み取りの実装・テスト（§5 第 1 段階の完了条件）の分だけ遅れる。**新名の候補が決まっていないと入れられない**（§8 の 3）。つまり「移すかどうか」を決めないまま 6.0.0 に入れることになり、据え置きの現行決定とずれる。公開前の最初の版に、効果のまだ無い分岐（新名は誰も書かない）を持ち込む |
| **Y 6.0.0 は現状のまま公開し、第 1 段階を後続の版（6.x）で出す** | 6.0.0 利用者は同じ拡張の更新で第 1 段階を受け取る | 6.0.0 の公開を遅らせない。移すと決めた時点で初めて実装する | 6.0.0 が「旧名しか読まない版」として一定数残る（R1）。自動更新の設定は利用者次第【未確認】で、更新されない端末が残る |
| **Z 何も入れない（案 A 据え置き）** | 現行 | 費用 0 | 移さないので R1 自体が起きない |

5.x の利用者はどの選択肢でも第 1 段階を受け取れず、**R1 の「旧版」は 5.x として必ず残る**。X は 6.0.0 を旧版の側から外す効果だけを持つ。

**費用対効果**: `rename-vereve.md` §3 は、旧拡張の「インストール 7」（2026-10-26 時点の記述。現在の数は【未確認】）で「出し直す費用が最も安い」と判断している。利用者が極少のうちは、(a) 第 1 段階の版の普及を待つ期間が、見積もりの手段（版別の利用者数）も無いまま長くなる、(b) 旧版と新版が同じ origin を共有する場面（R1・R2）自体がほとんど起きない、の両方が成り立つ。つまり**段階案の費用（§6 の表）が守る相手がほぼいない**。この推論は、現在の利用者数が 7 前後のままという前提に立つ（【未確認】）。数が増えるほど R1 の被害は大きくなるが、同時に X（公開前に入れる）の機会は 6.0.0 の公開で失われる。**「移すかもしれない」なら 6.0.0 の公開前に X を決める**、「移さない」なら Z で閉じる、が二択になる。Y は、移すと決めるのが遅れるほど費用が増える折衷。

## 7. 実機確認が必要な点（Mac を含む）

【すべて未確認】。この下書きは Linux 上でコードを読んで書いた。

Mac（バイナリ名・署名）:
1. `mac/build.sh` で、改名後の名前（例: `vereve-vm`）の Swift ヘルパーがビルドでき、ad-hoc 署名で起動する（design-policy / release.md の方針は ad-hoc、Developer ID・notarization なし）。
2. 名前を変えたヘルパーが、Gatekeeper・quarantine 属性の扱いで、旧名と同じように動く（署名が実行ファイル名・識別子に依存するか）。
3. `mac/run-golden.sh` と CI の `package.yml`（macOS）が、新名の成果物を見つけてゲストイメージ（arm64 の Image）と一緒に起動できる。
4. 新名を先に探し、無ければ旧名を探す `resource()` の順序が、macOS の `mac/.build/` の候補でも正しく働く。
5. R6 の検出: カーネル版が起動に失敗して Node.js 版へ落ちたことを、ログ（verEve Output）で利用者が気づけるか。

全 OS（データ）:
6. 旧版（5.x、および第 1 段階を入れる前の 6.0.0）が、新名の ref が入った origin に対して `Fetch` / `Publish` を実行しても、壊れず新名を無視する（R1）。
7. 案 F: symbolic ref を `git push` / `git fetch` が転送するか。GitHub など主要ホスティングでの扱い。
8. 旧名のミラーを旧版が強制 fetch したときの巻き戻り（R3）が、設計どおり安全側に倒れる。
9. 5.1.1 の `migrateLegacyMicrogitLayout` と同じ型で、新フォルダへの移行が Windows（大文字小文字・パス長）でも動く。

## 8. 運営者に決めてほしいこと

1. 移す動機（§6 の最後）。動機が弱ければ**据え置き続行（案 A）で閉じる**のが最も安い。
2. 移すなら、データ（refs・保存場所）とバイナリを**別々に**扱う方針でよいか。さらに、ref を移しても**保存場所は動かさない（§5 の案 S3）**でよいか。
2'. 読み取り両対応を、公開前の 6.0.0 に入れるか（X）、後続の版にするか（Y）、移さないか（Z）。6.0.0 の公開前に決める必要がある（§6.1）。
3. 新名（例: `refs/vereve/*`、新フォルダ名）。
4. 普及を待つ期間と、その見積もりの手段（版別の利用者数が見られるか）。
5. 旧名の廃止を、自動にせず明示コマンドにする方針でよいか（本書は明示コマンドを推奨）。
6. 5.x の端末（更新が届かない）を、第 3 段階で切り捨ててよいか。切るなら 5.x の非推奨からどのくらい待つか。
