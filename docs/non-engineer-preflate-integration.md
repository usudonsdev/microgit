# 非エンジニア版: preflate-rs の組み込み方(検討)

2026-11-23。前提は [計測メモ](./non-engineer-office-delta-measurement.md)(本物の Excel で、preflate-rs を使えば元のバイト列に戻せた)と、[設計メモ](./non-engineer-drive-sharing-design.md) §3・§9.4(独立した Windows アプリ、常駐、利用者単位のインストール)。試作は [scripts/research/office-delta/ooxml-split/](../scripts/research/office-delta/ooxml-split/)。ここに書くのは**案**で、確定は「確定」と書いたものだけ。

## 1. 結論(案)

1. **履歴の記録・保存・復元を受け持つ部分(以下「履歴エンジン」)を Rust で書き、preflate-rs はその中でライブラリとして直接使う。** 画面(トレイ、右クリック、版の画面)とは分ける。画面の技術は未決のまま進められる。
2. **補正データは、preflate-rs の実装そのものに依存する。版を固定し(`=0.7.6`)、版ごとの形式の番号を履歴に書き、古い版の補正データを読む部品を残し続ける。** これが組み込みで最も大事な決まりである(§4)。
3. **保存の瞬間は、ファイル全体をそのまま記録する。preflate で分ける処理は、後から裏で行い、組み立て直しが SHA-256 で一致したときだけ置き換える。** 保存を遅くせず、分ける処理が失敗しても履歴は失われない(§5)。
4. 試作で、ZIP の文書を「骨組み + 部品ごとの中身 + 補正データ」に分けて、元どおりに組み立て直すところまで動いた。Windows 向けの DLL と exe もビルドできた(実機では未実行)(§6)。

## 2. preflate-rs について確かめたこと(0.7.6)

- 提供元: Microsoft(`github.com/microsoft/preflate-rs`)。ライセンス Apache-2.0。配布するときは `THIRD_PARTY_NOTICES.md` に載せる。
- `#![forbid(unsafe_code)]`(unsafe を使わない)。依存は `bitcode`・`byteorder`・`cabac`・`default-boxed`・`deranged` ほか少数。
- Rust 1.89 以上、エディション 2024。
- 使い方は 2 つの関数で足りる: `preflate_whole_deflate_stream`(圧縮データ → 中身 + 補正データ)と `recreate_whole_deflate_stream`(中身 + 補正データ → 圧縮データ)。大きい入力向けに、少しずつ処理する口もある。
- 設定 `PreflateConfig`: `max_chain_length`(既定 4096。解析の手間の上限)、`plain_text_limit`(既定 128 MB。展開した中身をメモリに持つ上限。ZIP 爆弾の対策にもなる)、`verify_compression`(既定 true。解析の後に作り直して一致を確かめる)。
- 補正データの中身: 圧縮の設定の推定値を `bitcode` で書いたものと、予測と違った所を算術符号(CABAC)で書いたもの。**形式の版番号は入っていない。** 推定の仕組みや予測の手順が変われば、古い補正データからは元に戻せなくなりうる(§4)。
- README によれば、zlib・zlib-ng・libdeflate・miniz・Windows の zlib を見分ける。知らない圧縮でも往復はでき、補正データが大きくなる。Excel はこのどれかに近いと思われるが、どれと判定されたかは確かめていない。

## 3. 組み込み方の候補

アプリの形は「独立した Windows アプリ、常駐、利用者単位のインストール」(設計メモ §9.4)で、画面の技術(C#/.NET、Tauri、C++ など)は未決である。

| 案 | 内容 | 良い点 | 悪い点 |
|---|---|---|---|
| **A. 履歴エンジンを Rust で書き、preflate-rs を直接使う** | 監視・記録・分割・ストア・Fetch/Publish を Rust の 1 つの部品にする | 境界が無く速い。Rust の型でエラーを扱える。CDC(fastcdc)、SHA-256、zstd も Rust に揃っている | 画面の技術との境界は別に要る(下の B か C の形) |
| B. 別の言語のアプリから、Rust の DLL(C の口)を呼ぶ | .NET の P/Invoke や C++ から呼ぶ | 1 つのプロセスで済む | panic やメモリの使いすぎが、アプリごと落とす。データの受け渡しと解放の規則を C の口で書く手間がある |
| C. 別の言語のアプリから、Rust の補助 exe を常駐させて、標準入出力で話す | エンジニア版の `microgit-agent`(1 行 1 JSON)と同じ形 | 言語を問わない。エンジンが落ちても画面は残り、再起動できる。メモリの上限を OS で付けやすい | プロセスをまたぐ受け渡しの手間(大きいファイルはパスで渡せば軽い) |
| D. WebAssembly にして、画面の側で動かす | Electron や .NET の WASM 実行環境で動かす | 配布物が 1 種類 | 解析は計算が重い(711 KB の Excel で約 0.2 秒)。WASM では遅くなる。採る理由が乏しい |
| E. preflate を別の言語に移植する | C++ の元の preflate などを使う | なし | 補正データの互換を自分で守ることになる。採らない |

**推す形: A を基本にし、画面との境界は C(補助 exe)にする。** 理由:

- 履歴エンジンが扱うのは、他の人から Drive 経由で届いたファイルでもある。壊れたファイルや、展開すると巨大になるファイルが来ても、**画面ごと落ちない**ようにしたい。プロセスを分ければ、エンジンが落ちても画面が残り、再起動できる。
- エンジニア版で、補助プロセスと 1 行 1 JSON で話す形(`docs/agent-protocol.md`)に慣れている。同じ考え方を使える。
- 画面の技術を後で決めても、エンジンの作りは変わらない。画面が Rust(Tauri など)に決まれば、境界を無くして A だけにできる。
- 右クリックのメニュー(設計メモ §7.2)は、エクスプローラーに読み込まれる COM の DLL になる。**この DLL に preflate を入れない。** メニューは「対象のファイルか」を判定してエンジンに頼むだけにする(エクスプローラーの中で重い処理や panic を起こさないため)。

## 4. 補正データの互換を守る決まり(案。最重要)

補正データは、それを作った preflate-rs の実装でしか元に戻せないと考える。履歴は何年も残るので、次を守る。

1. **版を固定する。** `Cargo.toml` で `preflate-rs = "=0.7.6"` と書く(試作で済み)。依存先も `Cargo.lock` を履歴エンジンのリポジトリに入れて固定する。
2. **ソースを手元に置く。** `cargo vendor` などで、使った版のソースを保管する。crates.io から取り下げられても作り直せるようにする。
3. **履歴に形式の番号を書く。** 補正データごとに「どの形式で作ったか」(この試作では `FORMAT_VERSION = 1`、preflate-rs 0.7.6)を記録する。
4. **版を上げるときは、古い版も一緒に入れる。** Cargo は同じクレートの別の版を、名前を変えて同時に使える(例: `preflate_076 = { package = "preflate-rs", version = "=0.7.6" }`)。新しく作る補正データは新しい版で、古い番号の補正データは古い版で戻す。
5. **互換の試験を常に回す。** 小さな見本のファイル(利用者のファイルではなく、自分たちで作ったもの)と、その 0.7.6 の補正データをリポジトリに置き、ビルドのたびに「元のバイト列に戻るか」を確かめる。版を上げても、この試験が通り続けることを条件にする。
6. **戻すときも確かめる。** 記録したときのファイル全体の SHA-256 を持ち、組み立て直した結果と照らしてから書き出す。合わなければ書き出さず、画面で知らせる(設計メモ §7.1 の「置き換える前に確かめる」と同じ考え方)。

## 5. 保存の流れへの入れ方(案)

```
保存を検知
  └→ ① ファイル全体をそのまま履歴に記録(すぐ。ここで履歴は確定)
        └→ ② 裏で: ZIP の文書なら分ける(骨組み + 部品の中身 + 補正データ)
               ├ 組み立て直しが SHA-256 で一致 → 部品の中身を内容で分割して重複を省き、①の全体を置き換える
               └ 一致しない・失敗・時間切れ → ①のまま残す(節約しないだけで、戻せる)
```

- ① は、いまのエンジニア版の「保存のたびに記録」と同じ速さを目指す。② は、低い優先度のスレッドで、保存が落ち着いてから行う(連続して保存されている間は待つ)。
- 部品ごとに、作り直せなかったものは圧縮データをそのまま持つ(試作の `Raw`)。ZIP64・暗号化された ZIP・ZIP でないファイルは、分けずに全体を持つ(試作の `Whole`)。
- 対象は、まず docx・xlsx・pptx(中身が ZIP)。PDF の中の圧縮データや PNG にも同じ方法が使えるが、後回しにする。
- 解析の重さ: 試作で、711 KB の Excel を分けるのに 184 ms、戻すのに 32 ms(この Linux の環境。最適化ビルド)。zlib で圧縮し直した 572 KB の版は 405 ms かかった(知っている圧縮ほど予測の手間が増えるためと思われる。未確認)。数 MB の文書では秒単位になりうるので、② を裏で行う形が要る。

## 6. 試作(`scripts/research/office-delta/ooxml-split/`)

- `split(bytes) -> Split`: ZIP の中央ディレクトリを読み、部品ごとに preflate で分ける。**返す前に組み立て直して SHA-256 を比べ、合わなければ全体をそのまま持つ形にする。** 部品の解析で panic しても、その部品だけ `Raw` にする。
- `rebuild(&Split) -> bytes`: 骨組みに、作り直した圧縮データを差し込む。
- C の口 `vereve_ooxml_check`(分けられるかを確かめるだけ。B の形を試すため)。
- 結果(Linux、最適化ビルド):

| 入力 | 結果 |
|---|---|
| Excel 12 KB(本物) | 13 部品すべて preflate、補正 647 B、骨組み 3,438 B、一致 |
| Excel 711 KB(本物) | 11 部品すべて preflate、補正 13,301 B、骨組み 3,098 B、分ける 184 ms、戻す 32 ms、一致 |
| 同じ Excel を zlib 6 で圧縮し直したもの(572 KB) | 11 部品すべて preflate、補正 9,295 B、分ける 405 ms、戻す 69 ms、一致 |
| ZIP でないファイル(README.md) | 全体をそのまま持つ、一致 |

- Windows 向けのビルド(Linux から `x86_64-pc-windows-gnu` へクロスビルド): DLL 1.7 MB、exe 0.8 MB。DLL の外への口は `vereve_ooxml_check` のみ。依存する Windows の DLL は KERNEL32、ntdll、msvcrt など標準のものだけ。**Windows の実機では動かしていない**(この環境に Windows も wine も無い)。配布するときは MSVC 向け(`x86_64-pc-windows-msvc`)でビルドし、署名する(設計メモ §9.4)。
