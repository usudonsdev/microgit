## 1. 本質：Git を再定義する

MicroGit がやろうとしているのは、**保存形式は Git のまま、書き方と戻り方を作り直す** ことである。

- ふつうの Git は、人が区切りのよいところで `git add` と `git commit` を打つ前提で作られている。1 回の操作は数十 ms で、人の操作としては十分に速い
- MicroGit は保存のたびに記録する。1 日に数百〜数千回の記録と、その間の頻繁な行き来が起きる。Git のコマンドをそのまま使うと、この使い方の限界に当たる
- 保存形式（オブジェクト・ref）は Git のまま残す。ふつうの Git で履歴を読め、他デバイスと共有でき、既存の利用者の履歴を変換しなくてよい

したがって、速さの目標は「Git のコマンドより速い」ではなく、「**保存のたびに記録し、その間を自由に行き来しても、利用者が待たない**」である。そのための条件を 3 つに分ける。

| 条件 | 内容 | 5.0.0 の状態 |
|---|---|---|
| 残すのに手を止めない | Ctrl+S だけで記録される | 満たしている |
| 残すのを待たない | 記録が、次の保存より前に終わる。履歴が伸びても遅くならない | **5.0.0 までは満たしていなかった**（§3.2）。#32 で改善 |
| 戻るのを待たない | 過去の時点へ、`git checkout` と同じくらいの速さで戻る | 5.0.0 で満たした（§3.1） |

## 2. どこで何が動いているか

```
┌──────────── ホストの OS（Windows / macOS / Linux） ────────────┐
│ VS Code の拡張機能（MicroGit）                                  │
│  ① 記録：保存のたびに Git の形式のファイルを書く                  │
│     → ホストのファイルシステム（NTFS / APFS / ext4）              │
│  ② 層の作成：記録したコミットを層にして agent に送る              │
│  ③ 過去に戻る：agent から一覧と中身を受け取り、検証して書く        │
│     （Boundary Guard）                                          │
└────────┬───────────────────────────────────────────────────────┘
         │ 通り道：Windows は名前付きパイプ、macOS は virtio-console、Linux は標準入出力
┌────────┴── 最小の Linux（Windows・macOS は VM、Linux は VM なし） ──┐
│ agent ＋ OverlayFS。層はメモリ（tmpfs）上のキャッシュ               │
└──────────────────────────────────────────────────────────────────┘
```

**Linux の VM が担当しているのは、過去に戻るための層（OverlayFS）だけ**である。記録はホストで行う。OS ごとに速さが違うのは、主にこのため（§6）。

## 3. 計測で分かったこと

### 3.1 過去に戻る（5.0.0 で改善）　主張の強さ：確かめた

| 環境 | `git checkout` | v4（Node.js で模倣） | v5（カーネルの OverlayFS） |
|---|---|---|---|
| Mac（Apple M5） | 30.0 ms（`git gc` 後 24.8 ms） | 685.4 ms | **22.3 ms** |
| Linux（WSL2、VM なし） | 未計測 | 127.4 ms | **21.6 ms** |
| Windows（QEMU、WHPX） | 未計測 | 1,425.8 ms | **169.7 ms** |

ファイル 200 個・保存 40 回の履歴で、2 つの時点を 30 回行き来した中央値（`scripts/bench-backends.mjs`）。Mac の `git checkout` は同じ形の履歴を普通のリポジトリに作って測った。

- **言えること**：v5 は v4 より大幅に速く、Mac では `git checkout` と **同等**
- **言えないこと**：「Git より速い」。Git は毎回プロセスを起動しインデックスを書き直し、MicroGit は常駐して代わりに中身を検証しているので、仕事の中身がそろっていない

v4 → v5 の差の理由（**見込み**。段階ごとの計測はまだ）：v4 は過去の姿を作るたびにツリー全体をディスクにコピーしていた（`copyTreeBytes` と層の適用）。v5 は層を重ねて mount するだけで、ファイルのコピーが起きない。

### 3.2 記録（#32 で改善）　主張の強さ：確かめた

**5.0.0 までの記録は、使うほど遅くなっていた。** 保存 1 回で Git のプロセスを 16 回前後起動し、「過去に同じ変更があったか」を探すため、保存のたびに `git log --all` で履歴全体を読み、過去のコミットごとに Git を起動していた。

| 履歴の長さ（Windows） | 5.0.0 までの記録 p50 | Git の起動回数 | ふつうの Git（add＋commit） |
|---|---|---|---|
| 10 回 | 551.2 ms | 16.0 回 | 80 ms 前後 |
| 100 回 | 604.1 ms | 16.4 回 | |
| 300 回 | 872.3 ms | 20.9 回 | |
| 1,000 回 | **2,443.8 ms** | **62.5 回** | 78.1 ms |

（ふつうの Git は fsync なしの既定の設定。条件がそろっていない比較だが、履歴とともに遅くなることを示す。最後の区間は別の試験と同時に走っていた。`docs/paper/data/micro-commit-baseline-win32.json`）

#32 の速い記録（Git のプロセスを起動せず、Git の形式のファイルを直接書く）と、永続性の条件をそろえた比較（履歴 1,000 回、p50）：

| 環境 | 条件 | 5.0.0 まで | **速い記録** | ふつうの Git |
|---|---|---|---|---|
| Linux（WSL2） | fsync なし | — | **3.1 ms**（300 回で 2.1 ms） | 16.3 ms |
| Linux（WSL2） | 電源断でも失わない（既定） | 469.5 ms | **19.4 ms** | 30.7 ms |
| Windows | fsync なし | — | **44.5 ms** | 83.7 ms |
| Windows | 電源断でも失わない（既定） | 2,443.8 ms | **52.3 ms** | 168.1 ms |

- 速い記録は、履歴が 10 回でも 1,000 回でもほぼ一定
- **言えること**：記録が履歴に比例して遅くなる問題はなくなった。fsync なしの条件では、Linux で Git の約 5 倍速い
- **言えないこと（まだ）**：「既定の設定で Git より桁違いに速い」。既定では 1.6〜3.2 倍
- Windows の計測は回によるばらつきが大きい（同じ条件のふつうの Git が 84〜191 ms）

### 3.3 記録の残りの時間の内訳　主張の強さ：確かめた（Windows・Linux）

| 内訳 | Linux | Windows |
|---|---|---|
| fsync（保存 1 回で 7 ファイル） | 約 16 ms（記録の約 84%） | 回によって 8〜42 ms |
| fsync を除いた残り | 3.1 ms | 約 17.5 ms。うちファイルの作成（open 9 回・rename 8 回）で約 11 ms、保存したファイルの読み込みで約 3.5 ms |

Windows は、ファイルを 1 つ作るたびにウイルス対策の検査などが入り、1 つ 1 ms 前後かかる。

### 3.4 保存 1 回の処理全体（#37 で計測・改善）　主張の強さ：確かめた

§3.2 はコミットを作る部分だけの時間。保存 1 回の処理全体を段階ごとに計ると（`src/saveTiming.ts`）、**記録は全体の約 5% にすぎなかった**。

| 段階（Windows 11、カーネル版、保存 200 回の最後の 20 回の p50） | #37 の前 | #37 の後 |
|---|---|---|
| ブランチの確認 | 30.6 ms | 1.7 ms |
| 記録（コミット） | 20.6 ms | 22.5 ms |
| 層の作成 | 125.4 ms | 31.9 ms |
| timeline.log・画面の更新・Overlay の状態 | 223.3 ms | 0（保存の列の外へ） |
| **保存 → 記録が終わるまで** | 52.3 ms | **24.9 ms** |
| **保存 → その時点に戻れるまで** | 180.1 ms | **56.9 ms** |
| **処理全体** | 405.5 ms | **57.2 ms** |

- 画面の更新と timeline.log は、記録と関係のない後片付けだった。保存の列の外へ出し、保存が落ち着いてから 1 回だけ行う
- 層の作成は、保存 1 回で Git を 3 回起動して、直前に記録したばかりの中身を読み直していた。速い記録が知っている「親からの変化」をそのまま agent に渡すようにした（使えないときは今までどおり Git から）

CI の 5 つの環境（公開版と同じ形、保存 100 回の最後の 20 回の p50、run 36807397421、`docs/paper/data/ci-36807397421/`）：

| 環境 | 層 | 記録 | 層の作成 | Overlay の状態 | 記録が終わるまで | 戻れるまで | 処理全体 |
|---|---|---|---|---|---|---|---|
| Ubuntu 22.04 | カーネル | 6.0 | 8.3 | 0.1 | 6.8 | 15.6 | **15.8** |
| Ubuntu 24.04 arm | カーネル | 5.1 | 6.5 | 0.1 | 5.7 | 12.2 | **12.5** |
| Windows（CI） | カーネル | 62.7 | 31.0 | 0.1 | 65.0 | 95.7 | 96.1 |
| Ubuntu 24.04 | Node.js 版 | 5.1 | 16.4 | **487.6** | 5.7 | 22.5 | 512.0 |
| macOS（CI） | Node.js 版 | 10.6 | 15.2 | **641.1** | 11.1 | 27.1 | 666.6 |

- **言えること**：カーネル版の Linux では、保存 1 回の処理全体が 12〜16 ms、記録が終わるまで 6〜7 ms
- **残る課題**：Node.js 版（非特権の名前空間が止められた Linux、Intel Mac など）では、保存のたびに過去の姿のフォルダを作り直す処理が 0.5〜0.6 秒かかる（#41）。Windows の CI の機械では記録が 63 ms と、手元（22.5 ms）より遅い
- **確かめきれていないこと**：手元の計測の途中の 1 回だけ、記録の時間が保存を重ねるごとに 40 → 300 ms に伸びた。2 回測り直して再現せず、原因は未特定

#### Node.js 版の保存（#41 で改善）

Node.js 版は、保存のたびに「過去の姿のビュー」（その時点の完全なフォルダ）を作り直していた。次に過去に戻るときの下ごしらえで、保存（記録）そのものには要らず、しかも履歴とともに伸びていた。保存のときには作らず、過去に戻るときに作るようにした。

| 手元の Windows 11、Node.js 版、保存 40 回、p50 | #41 の前 | #41 の後 |
|---|---|---|
| 保存のたびの作り直し（最初の 20 回） | 512.3 ms | 0.3 ms |
| 同（最後の 20 回） | 1,190.2 ms | 0.3 ms |
| 保存 1 回の処理全体（最後の 20 回） | 1,317.5 ms | 124.0 ms |
| 過去に戻る操作（10 回） | 1,854.7 ms | 1,766.6 ms（遅くなっていない） |

CI（公開版と同じ形、保存 100 回の最後の 20 回の p50、run 36809764061、`docs/paper/data/ci-36809764061/`）：

| 環境 | 層 | 記録 | 層の作成 | Overlay の状態 | 保存 1 回の処理全体（#37 の後 → #41 の後） | 過去に戻る操作 |
|---|---|---|---|---|---|---|
| Ubuntu 22.04 | カーネル | 5.7 | 9.8 | 0.2 | 15.8 → 16.8 | 123.6 |
| Ubuntu 24.04 arm | カーネル | 5.5 | 5.9 | 0.1 | 12.5 → 12.4 | 77.7 |
| Windows（CI） | カーネル | 46.9 | 31.3 | 0.1 | 96.1 → 81.3 | 469.6 |
| Ubuntu 24.04 | Node.js 版 | 4.7 | 11.9 | 0.2 | 512.0 → **17.6** | 302.2 |
| macOS（CI） | Node.js 版 | 17.6 | 24.0 | 0.3 | 666.6 → **44.8** | 1,144.3 |

（単位は ms。過去に戻る操作は、途中の時点と最後の時点を 5 回ずつ行き来した 10 回の p50）

- **言えること**：保存 1 回の処理全体は、カーネル版の Linux で 12〜17 ms、Node.js 版の Linux でも 18 ms、macOS の Node.js 版で 45 ms
- **残る課題**：
  - Node.js 版の過去に戻る操作がもともと遅く、履歴とともに伸びる（手元の Windows で 40 回 1.8 秒、100 回 3.3 秒）（#43）
  - Node.js 版の保存の層の書き出し（`expandViewAfterExport`）に、**親のビューがあれば、そのフォルダを丸ごとコピーして新しいビューを作る** 処理が残っている。一度過去に戻った後の保存では毎回走るはず（ファイル数に比例）。今回の計測は「保存してから過去に戻る」順だったので表に出ていない（#43）
  - CI の Windows では記録が 47〜63 ms と、手元（22.5 ms）の 2〜3 倍遅い（#45 で理由を突き止めた。次の小節）

#### 記録の中の fsync（#45 で計測）

記録の中の段階ごとの時間と、fsync の回数・時間を、保存ごとに残すようにして（`src/fastGit/fsyncStats.ts`）、CI の 5 つの環境で取った（保存 100 回の最後の 20 回の p50、run 36882411545、`docs/paper/data/ci-36882411545/`）。

| 環境 | 記録 | うち fsync（7 回） | 割合 | 1 回あたり |
|---|---|---|---|---|
| Windows（CI） | 73.2 ms | **50.5 ms** | **69%** | 約 7.2 ms |
| macOS（CI） | 19.9 ms | 11.2 ms | 56% | 約 1.6 ms |
| Ubuntu 22.04・24.04・24.04 arm | 5.2〜6.1 ms | 2.3〜2.5 ms | 約 40% | 約 0.35 ms |
| 手元の Windows 11（保存 60 回） | 22.6 ms | 8.8 ms | 39% | 約 1.3 ms |

- **CI の Windows が遅い主な理由は fsync**。1 回の fsync が手元の約 5 倍遅い（クラウドの仮想マシンのディスクは、書き込みの確定が遅い）。fsync を除いた部分も手元の約 1.6 倍（約 23 対 約 14 ms）だが、差の大部分は fsync
- CI の Windows の記録の中の内訳：tree 28.8・ref 16.2・blob 9.3・commit 9.3・index 1.8 ms（どれも fsync を含む。fsync するのは blob・tree 3 つ・commit・ブランチ・タグの 7 ファイル。index は fsync しない）
- **見方**：同じコードでも、記録の速さはディスクの「書き込みの確定」の速さで大きく変わる。手元の PC で fsync が速くても、書き込みの確定が遅い PC（クラウドの仮想マシン、HDD、一部のノート PC など）では、記録の 6〜7 割が fsync になりうる

## 5. 各判断の理由

### D1：履歴の正本はホストの Git

- **判断**：マイクロ履歴の正本は、ホストの shadow の Git。VM の中の層は、Git からいつでも作り直せるキャッシュ
- **理由**（ADR-0013 で整理し直した）：
  - **可用性**：VM が起動していない・止まった・VM を使えない環境でも、記録を失わずに続けられる
  - **互換性**：ふつうの Git で履歴を読め、親のリポジトリへの push で他デバイスと共有できる。既存の利用者の履歴を変換しなくてよい
- **採らなかった案**：層（OverlayFS）そのものを正本にする。VM が消えると履歴が消える
- **引き受けること**：記録はホストのファイルシステムの速さに縛られる（§6）。層はホストの Git から作るので、その費用がかかる（§3.4）
- 当初の理由の 1 つだった「ゲストを信用しない」は、ADR-0013 で理由から外した（D6）

### D2：VM は OverlayFS のためだけ、Linux は VM なし

- **判断**：Linux 以外では、OverlayFS を持つ最小の Linux（カーネル 6.18 と agent だけ、ネットワークなし）を VM で動かす。Linux ホストでは VM を使わず、非特権のユーザー名前空間で同じ agent を動かす
- **理由**：Linux 以外にはカーネルの OverlayFS が無い。ユーザー空間での模倣（v4）は遅く（§3.1）、ゴールデンテストで本物との食い違いと不具合が見つかった。Linux には VM の存在理由が無い
- **採らなかった案**：WSL2・Docker Desktop に頼る（利用者に導入を求める）、各 OS の機能で近似する（ProjFS・APFS のクローン。挙動がそろわない）、LKL（保守状況が不明、保留）
- **引き受けること**：OS ごとに VM の動かし方と通り道が違い、それぞれ不具合が出た（Windows の標準入出力で 1 MiB が壊れた、macOS で 64 KiB を超えると止まった）

### D3：記録は Git のプロセスを起動せずに書く

- **判断**：blob・tree・commit・index・ref を、Git と同じ形式で拡張機能の中から直接書く（`src/fastGit/`、`src/fastMicroCommit.ts`）。前提から外れる設定（sha256、reftable、署名など）のリポジトリでは、自動で Git のコマンドに任せる
- **理由**：Git のプロセスの起動は、Windows で 1 回 30 ms 前後、Linux でも数 ms かかる。5.0.0 までは保存 1 回で 16 回前後起動していた
- **根拠**：§3.2。**Git のコマンドでの記録と 1 ビットも違わないこと** を、同じ保存の列（600 回。新しいコミット 445・変化なし 44・tree 全体が過去と一致 45・同じパスの同じ中身 22・途中の過去に戻る操作 44）を両方に流して確かめた。毎回の結果と HEAD・全部の ref・index が一致し、`git fsck --strict` が通る。CI で毎回流す。実際の VS Code（Windows）で、保存 5 回がすべて速い記録で行われた
- **採らなかった案**：Git のコマンドの回数を減らすだけ（最少でも 4 回で、Windows では 100 ms を超える）。libgit2 などのライブラリを同梱する（ネイティブの部品が OS ごとに要る）
- **引き受けること**：Git の形式の細部（tree の並び、index の形式、ref のロック）を自分で守る責任。Git の新しい形式（sha256、reftable、index の版 4）には追従せず、Git のコマンドに任せる
- **差分テストが見つけたこと**：同じ中身に戻したあと、Git のコマンドでの記録は HEAD だけを動かし index を残す。そのため次のコミットは、保存したファイル以外も親と違うことがある。最初の実装はこれを見落とし、66 回目で食い違った。仕様を読んでも気づきにくい振る舞いが、差分テストでは出てくる

### D4：探索は索引で

- **判断**：最初に 1 回だけ履歴を読んで索引（tree → コミット、パスごとの中身 → コミット）を作り、記録のたびに足す。ほかの処理が ref を書き換えたら（知らないコミットを指したら）読み直す
- **理由**：5.0.0 までは保存のたびに履歴全体を読んでいて、記録の時間が履歴の長さに比例して伸びた（§3.2）
- **引き受けること**：メモリに持った状態を、いつ捨てるか。ファイルの stat（更新時刻・大きさ・inode）で判断する。Git はファイルを「一時ファイルに書いて名前を変える」ので、書き換えられると必ず変わる

### D5：保存した中身をそのまま記録する（ADR-0012）

- **判断**：shadow では改行の変換・フィルタ（Git LFS など）・`$Id$` の展開・文字コードの変換を止める（`core.autocrlf=false` と `info/attributes`）
- **理由**：Windows 版 Git の既定（`core.autocrlf=true`）では、CRLF のファイルが LF に変えて記録され、**過去に戻ると改行が変わっていた**（5.0.0 までの不具合。空のリポジトリで確かめた）。以前の VS Code のテストは、この不具合のおかげで通っていた。スナップショットは保存したバイト列そのものであるべき。速い記録が変換の規則を真似なくてよくなる
- **利用者の方針（2026-10-01）**：最優先は保存のタイミングで最速になること。書き込み（過去に戻る）の時に変換が挟まるのは問題ない
- **他デバイスの記録に戻るとき（#36）**：保存の時はコミットのメッセージに `Saved-On: <OS>` を 1 行足すだけ。戻す時に、保存した OS と今の PC で改行が違うテキストのファイルだけ、今の PC の形（メインのリポジトリで `git checkout` したときと同じ）に変換する。同じ PC の記録は必ずそのまま戻る。**Git は「記録するときに正規化し、書き出すときに変換する」が、MicroGit は「記録するときは何もせず、書き出すときに必要な分だけ変換する」。変換の費用を保存の側から戻る側へ移した**
- **引き受けること**：これより前の記録は LF のまま。変更の後に同じファイルを保存すると、改行だけが違う中身として 1 回記録される。#36 が入るまでは、Windows で保存した記録を Mac・Linux で戻すと CRLF のまま書かれる

### D6：ゲストは間違えうるもの（ADR-0013）

- **判断**：ゲストは攻撃者としては扱わない。間違えうるものとして扱い、ゲストが返したものはワークスペースに書く前に検証する。ゲストに仕事を任せるかは、信頼ではなく速さ・可用性・互換性で決める
- **理由**：
  - ゲストへの入り口は、利用者が VS Code で保存したファイルの名前と中身だけ。外部のネットワークも、ほかのアプリとの通信も無い
  - 同じファイルを、ホストの VS Code・Git・言語サーバーが先に、利用者と同じ権限で読む。ゲストだけを特別に疑う理由は小さい
  - Linux の VM なしと、Windows の TCG では、そもそも隔離が無い
  - 一方で、ゲストと通り道の不具合は実際に起きた（D2）。検証はその備えとして役立ち、費用も小さい
- **この判断で変わること**：記録や層の作成をゲストに任せる設計を、安全性を理由に最初から外さなくてよくなる。**速さは検証を軽くすることで得るのではなく、仕事の置き場所を選べるようになることで得る**。Git のオブジェクトは中身とハッシュで照らせるので、ゲストが作ったものもホストで検証できる

### D7：永続性の既定は「電源断でも失わない」のまま

- **判断**：記録のオブジェクトと ref を fsync する既定（ADR-0002）を、今は変えない
- **理由**：記録は利用者の作業の履歴で、失うと取り戻せない
- **引き受けること**：fsync が記録の時間の大半を占める（§3.3）
- **見直しの材料（2026-10-01 に確かめた）**：VS Code は、ワークスペースのファイルを保存するとき、書き込みに使ったファイルハンドルを閉じる際に `fdatasync` を呼んでいる（`src/vs/platform/files/node/diskFileSystemProvider.ts`、失敗する環境では自動で止める）。保存したファイル本体は電源断にも耐えるので、MicroGit の記録だけ fsync をやめると「ファイルは残るのに履歴だけ消える」食い違いが生じる。**既定は保ち、fsync の回数を減らす方向で考える**（#38）

### D8：次の高速化の候補と、選ぶ基準

| 候補 | 何が速くなるか | 費用（見込み） | 引き受けること |
|---|---|---|---|
| **済み（#37）**：速い記録の結果（変わったファイルと中身）を、そのまま agent に渡して層を作る | 層の作成 125.4 → 31.9 ms（Windows） | 小さい | ほぼ無い（ADR の変更なし） |
| ジャーナル（1 回の保存を 1 つの追記ファイルに書き、fsync を 1 回に） | 既定の設定での記録（Linux で 19.4 ms → 5〜6 ms の見込み） | 大きい | 停電後の復元処理、同じ中身を 2 回書く、後片付け、排他。Windows ではファイル作成の費用が残る |
| 1 回の保存のオブジェクトを 1 つのファイル（pack）にまとめる | fsync とファイル作成の回数（とくに Windows） | 中 | 小さな pack がたまるので、ときどきまとめ直す |
| ~~既定を「fsync しない」にする~~（外した） | 既定の設定での記録（Linux で 3.1 ms） | 設定だけ | VS Code はファイルを保存するときに fdatasync している（`diskFileSystemProvider.ts`）。履歴だけ fsync しないと「ファイルは残るのに履歴だけ消える」食い違いが生じる（#38） |
| 記録も VM の中で行う | ホストのファイルシステムの差がなくなり、層もその場で作れる | 大きい | D1 の見直し（VM が無い・止まったときの記録、ホストの Git への書き戻し）、消えない仮想ディスク、記録の実装が 2 つになる |

**選ぶ基準**：(1) 保存 1 回の処理全体の内訳を 3 つの OS で測る。(2) いちばん安い候補（agent に直接渡す）から試す。(3) 残る差を見て、ジャーナル・pack・VM への移動を、速さ・可用性・互換性で比べる。

**(1)(2) の結果（2026-10-01〜02）**：(1) で、記録は保存 1 回の処理全体の約 5% にすぎず、画面の更新・ログ・Node.js 版のビューの作り直しのほうが大きいと分かり、先にそれらを外した（D9）。(2) で層の作成は 125.4 → 31.9 ms（Windows）。(3) は D10 のとおり保留。

### D9：保存の処理には、記録と、その時点に戻るのに要る最小限だけを置く

- **判断**：保存の処理の列の中でやるのは、shadow への書き込み・記録（コミット）・層の作成まで。画面の更新・timeline.log・log_latest.json は列の外で、保存が落ち着いてから 1 回だけ（#37）。Node.js 版のビューは、保存のときには作らず、過去に戻るときに作る（#41）
- **理由**：保存は何百回、過去に戻るのは数回。保存のたびに先回りして作ると、使わないものに何百回も費用を払う。利用者の方針は「最優先は保存のタイミングで最速」
- **根拠**：§3.4。手元の Windows（カーネル版）で保存 1 回 405.5 → 57.2 ms、CI の Node.js 版で 512.0 → 17.6 ms（Ubuntu）・666.6 → 44.8 ms（macOS）。費用を移した先（過去に戻る操作）も測り、遅くなっていない（1,854.7 → 1,766.6 ms）
- **採らなかった案**：後片付けを列の外で「すぐに」やる（保存が続くと、後片付けが次の保存と CPU を取り合う）。ビューを裏で先回りして作る（裏の処理が走っている間に保存されると、その保存を待たせる）
- **引き受けること**：画面の表示は保存から 300 ms ほど遅れて更新される。Node.js 版で、ビューの無い時点に初めて戻るときは、その場で作る分の時間がかかる。保存のときのビューのコピー（`expandViewAfterExport`）がまだ残っている（#43）

### D10：fsync の回数を減らす案は保留

- **判断**：ジャーナル（1 回の保存を 1 つの追記ファイルに書き、fsync を 1 回にする）は、今は作らない。先に CI の Windows で記録が遅い理由を段階ごとに調べる（#45）
- **理由**：CI の Linux では記録が fsync 込みで 5〜6 ms まで下がった。fsync を 7 回から 1 回にしても縮むのは数 ms の見込みで、停電後の復元処理・同じ中身を 2 回書く・後片付け・排他という複雑さに見合わない。手元の Windows で「fsync だけで 41 ms」と出た計測は、測り直し（7 回で 7.8 ms）では再現しなかった
- **再開する条件**：#45 で、Windows の遅さの主な理由が fsync だと分かったとき。ファイルの作成の数が理由なら、先に「1 回の保存のオブジェクトを 1 つの pack にまとめる」を検討する
- **#45 の結果（2026-10-02）**：CI の Windows では記録の 69%（7 回で 50.5 ms）、macOS では 56% が fsync だった。**再開の条件に当てはまる**。方式（ジャーナル／pack）は、見込みを示して利用者に確認してから進める
- **決めた人**：Claude が提案、利用者が了承（2026-10-02）
- **再開して作った（2026-10-02、ADR-0014、#38）**：利用者の方針「非常時の復元は遅くても復元が可能であればそれでいい。大切なのは復旧が可能であることと、通常時に高速でマイクロコミットが可能であること」で、ジャーナルを選んだ。保存 1 回の確定はジャーナルへの追記と fsync 1 回だけにし、Git のファイルは確定を待たずに書く。停電のあとは、起動時にジャーナルからオブジェクト・ref・index・reflog を作り直す（遅くてよいので、全部を確かめ直す単純な方法にした）。手元の Windows で記録が約 8 ms（25〜27%）短くなり、fsync は 7 → 1 回。停電を模した試験（4 つの場面、乱数の種 25 通り）で、作り直したあとの履歴が期待どおりで `git fsck --strict` が通ることを確かめた
- **CI の 5 つの環境（run 36902155146）**：記録は Windows で 70.4 → 20.6 ms、macOS で 19.0 → 12.3 ms、Ubuntu で 6.0〜6.6 → 3.0〜3.5 ms。fsync はどこでも保存 1 回に 1 回。保存 1 回の処理全体は Windows で 108.8 → 59.1 ms（ADR-0014 の表）
- **作ってから分かった、次の壁**：Windows では、fsync をしなくても Git のファイルを作るだけで保存 1 回に約 17 ms かかる（記録の 7 割）。記録を速くする次の候補は「ファイルを作る数を減らす」こと（#49）

### D11：正本は Git のまま、Git の形式のファイルは落ち着いてから書き出す

- **きっかけ**：利用者が「正本を OverlayFS の層にする」案を出した（2026-10-03）
- **比べた案**：A（正本は Git のまま。保存の直後はジャーナルが正本で、Git の形式のファイルは落ち着いてから書く）、B（層の保管場所を正本にし、Git は同期と互換のための書き出し先）、C（層だけ）
- **判断**：A。保存のときにすることは A と B でほぼ同じ（1 か所に書いて確定を 1 回待つ）。B・C は、層の保管場所・壊れたときの確かめ方・Windows と Mac での置き場所・層を重ねられる数の上限・同期・今の利用者の移行を、一から作る必要がある。B に進む価値があるのは、研究（マージレスブランチング）を層の上で作りたいときで、そのときも A のジャーナルが層の保管場所の原型になる
- **決めた人**：利用者（「1 で進めていきたいね。保存が高速ならそれで充分」）
- **結果（ADR-0015）**：保存 1 回の記録は、手元の Windows（ファイル 200 個、停電対策の設定をそろえる）で、普通の Git の `git add` → `git commit` の 0.090 秒に対して 0.010 秒。VS Code の中での保存の処理全体では、記録の段階は 0.003 秒で、残りの大半は戻るための準備（約 0.03 秒）
- **引き受けること**：隠しリポジトリを読む処理は、すべて「関所」（`flushPendingGitWrites`）を通す。保存が 0.3 秒の間もあけずに 64 回続くと、64 回目だけ約 0.4 秒かかる

## 6. OS ごとに速さが違う理由

VM の中の OverlayFS の振る舞いは、どの OS でも同じ（同じカーネル・同じ agent・同じ mount オプション。ゴールデンテストで確かめている）。違いは VM の外で生じる。

1. **記録はホストのファイルシステムに書く**（D1）。fsync の費用とファイル作成の費用は、NTFS・APFS・ext4 で大きく違う。Windows はファイルを作るたびにウイルス対策の検査などが入る
2. **ホストと VM の通り道が違う**。Windows は QEMU と名前付きパイプ、macOS は Virtualization.framework と virtio-console、Linux は VM なしで標準入出力
3. **VM を動かす仕組みが違う**。Windows は WHPX か TCG（仮想化機能が無効なとき）、macOS は Virtualization.framework

表の「Linux」の値は、Windows の PC の上の WSL2（これ自体が Linux の VM）で ext4 に書いて測った。同じ機械でも、ファイルシステムが違うだけで記録の速さが大きく変わる例になっている。

## 8. 記事・論文で書くときの注意

**書いてよい（確かめた）**
- 過去に戻る操作が、v4 から v5 で Mac 約 31 倍・Windows 約 8 倍・Linux 約 6 倍速くなり、Mac では `git checkout` と同等になった
- 5.0.0 までの記録は履歴とともに遅くなっていた。#32 で履歴の長さに関係なく一定になった
- 速い記録は、Git のコマンドでの記録と 1 ビットも違わない結果を作る（差分テスト）
- fsync なしの条件では、Linux で Git の約 5 倍速く記録できる
- Windows で過去に戻ると改行が変わっていた不具合を直した
- 保存 1 回の処理全体（保存してから処理が終わるまで）は、カーネル版の Linux で 12〜17 ms、Node.js 版の Linux で 18 ms（CI、公開版と同じ形）。手元の Windows（カーネル版）で 405.5 → 57.2 ms
- 部分（記録）だけを速くしても全体は速くならなかった。記録は処理全体の約 5% で、全体を段階ごとに計って初めてボトルネックが分かった（§3.4、学習用 12）

**書き方に気をつける（条件つき・見込み）**
- 「Git より速い」：過去に戻る操作は「同等」。記録は「fsync なしで 5 倍、既定では 1.6〜3.2 倍」と条件を必ず添える
- 「VM は隔離のため」：Linux の VM なしと Windows の TCG には隔離が無い。VM の目的は **本物のカーネルの機能をどの OS でも同じ形で使うこと**、と書く（D2・D6）
- v4 → v5 の速さの理由（物理コピーから mount へ）は、段階ごとの計測で裏付けるまでは「考えられる」と書く

**論文の主張の軸（提案）**
「保存のたびの履歴を、Git の保存形式を保ったまま、どの OS でも待たずに記録し、待たずに行き来できる。そのために、コミットの書き方を Git のコマンドから切り離し（D3・D4）、過去の姿の組み立てを本物のカーネルの OverlayFS に任せる（D2）」。機能単位の最小 VM の一般化は展望に留める。
