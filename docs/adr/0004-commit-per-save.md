# ADR-0004: 保存ごとに層を 1 枚作る（まとめない・mount を遅らせない）

| 項目 | 内容 |
|---|---|
| 状態 | 採用 |
| 日付 | 2026-09-26 |
| 決めた人 | Claude（利用者の「#19 まで自律的に進める」の指示のもとで） |
| 関係 | #12、補足 S-5、要件 FR-2・FR-4・NFR-2、[ADR-0001](./0001-source-of-truth.md)、[ADR-0003](./0003-layer-compaction.md) |

## 背景

要件 FR-2 の初期案は「upper を凍結して新しい lower にし、新しい upper を用意する」だった。補足 S-5 は、これは保存のたびに unmount と再 mount を伴い数 ms かかるので、FR-4（連続した保存を取りこぼさない）と NFR-2（メモリ転送と等速）に衝突すると指摘し、次のどちらかを選ぶよう求めた。

- 保存時は層を直接書き出し、mount は view を参照するときまで遅らせる
- 複数の保存をまとめて凍結する

## 決定

**初期案のまま、保存 1 回につき層を 1 枚作る**（mount → 書き込み → unmount で凍結）。まとめたり、mount を遅らせたりはしない。

## 理由

計測した（2026-09-26）。

| 処理 | 1 回あたり | 出典 |
|---|---|---|
| カーネルの層のコミット（WHPX、ゲストの tmpfs） | 0.1〜0.4 ms | [windows-backend.md](../windows-backend.md) §3、デモ |
| カーネルの層のコミット（TCG、エミュレーション） | 1.6〜1.9 ms（中央値） | 同上 |
| カーネルの層のコミット（WSL2、VM なし、ext4） | 6〜7 ms（中央値） | `check-guest.mjs` |
| **MicroGit の保存の Git の手順（add・write-tree・commit-tree・update-ref）** | **約 100 ms** | [ADR-0002](./0002-durability.md) |

保存 1 回の時間は Git の手順（主にプロセスの起動）で決まっていて、層のコミットはその数 % 以下にすぎない。保存はもともとバックグラウンドの列で順に処理されるので、FR-4 の取りこぼしも起きない。まとめる・遅らせる仕組みは、この程度の差のために複雑さ（まとめる単位、途中で落ちたときの扱い）を持ち込む価値が無い。

## 採らなかった案

- **mount を遅らせる**：保存時に lower の上へ直接ファイルを置くことになり、OverlayFS の whiteout や opaque を自前で作る必要がある。それはまさに Node 版がやっていることで、カーネルを使う意味が薄れる
- **まとめて凍結する**：まとめた保存のあいだの時点に戻れなくなる（マイクロコミットの粒度が落ちる）。戻れるようにするには層の外に差分を持つ必要があり、Node 版と同じ問題に戻る

## 引き受けること

- WSL2 の VM なしの経路（ext4 の上）では 1 回 6〜7 ms かかる。Linux ホストの VM なしの経路（#14）では、層を tmpfs（`$XDG_RUNTIME_DIR`）に置いて短くする
- 速さを本当に上げたいときは、層ではなく Git の呼び出しの回数を減らす（例：1 回の保存で 4 つ起動している Git をまとめる）。この ADR の範囲外

## 確かめ方

- `check-guest.mjs` と `windows/run-golden.ps1` の `commitUs`
- #14 で、MicroGit に組み込んだ経路の保存 1 回の時間を、Node 版とカーネル版で比べる
