# ADR-0001: マイクロ履歴の正本は shadow の Git、層はすべてキャッシュ

| 項目 | 内容 |
|---|---|
| 状態 | 採用 |

| 関係 | #11（O-10）、補足 S-7、要件 FR-2・FR-3、[ADR-0003](./0003-layer-compaction.md)、[design-policy.md](../design-policy.md) §5 |

## 背景

次期メジャーでは、OverlayFS の層（コミットごとの差分）を、Node.js 版（`.microgit_overlay/`）に加えて、カーネル版（最小ゲストの tmpfs、または Linux ホストの一時ディレクトリ）にも持つ。補足 S-7 は、既存の履歴（`git commit-tree` で作る shadow の Git）と層の置き場所との関係が決まっていないと指摘した。どちらを正本にするかで、次が変わる。

- デバイス間の同期（親リポジトリの `refs/microgit/*` での fast-forward／分岐）
- 既存の利用者のデータの移行
- 層の置き場所（ゲストのディスクイメージなど）が壊れたときの復旧
- 同じリポジトリを、別のバックエンドの環境で開いたときの互換性

## 決定

**マイクロ履歴の正本は、これまでどおり shadow の Git とする。** OverlayFS の層は、Node.js 版・カーネル版のどちらも、shadow の Git からいつでも作り直せる **キャッシュ** とする。

- 層は、コミット C について「親との差分（`git diff-tree -r -z --raw`）」から作る。親の層が無ければ、C の完全なツリーから「写しの層」を作る（[ADR-0003](./0003-layer-compaction.md)）
- 層のキャッシュが消えても（VM の再起動、形式の変更、壊れた場合）、必要になった時点で Git から作り直す
- 層の中のディレクトリの有無は、Git のツリーに合わせる。Git にディレクトリだけのエントリは無いので、「ファイルがあるディレクトリだけが存在する」

## 理由

| 観点 | Git を正本 | 層を正本 |
|---|---|---|
| デバイス間の同期 | 今の `refs/microgit/*` の仕組みがそのまま使える（design-policy §4） | 層を送る仕組みを新しく作る必要がある |
| 既存の利用者の移行 | 不要 | 既存の履歴を層に変換する必要がある |
| 壊れたとき | 層を捨てて作り直せば済む | 層の置き場所を守る仕組み（バックアップ・fsync）が要る |
| 別のバックエンドで開く | どのバックエンドも同じ Git から層を作るので互換 | 層の形式がバックエンドごとに違い（Node の `.json` の whiteout とカーネルの 0/0 デバイス）、変換が要る |
| ゲストを信用しない（SR-1） | ゲストの中に正本が無いので、ゲストが壊れても履歴は無事 | ゲストの中に正本があると、ゲストの侵害や誤動作が履歴の破損に直結する |

とくに最後の行は FR-3（ゲストの書き込みは upper に閉じ、ホストで検証してから反映）と同じ考え方で、正本をホスト側に置くことで、ゲストで何が起きても「捨てて作り直す」を選べる。

## 採らなかった案

- **層を正本にする**：上の表のとおり。加えて、ゲストの層は今 tmpfs（メモリ）にあり、正本にするならディスクイメージとその永続性が要る
- **両方を正本にして同期する**：食い違ったときにどちらを信じるかが決まらない

## 引き受けること

- **ディレクトリの意味論は Git の範囲になる。** カーネルの OverlayFS は「ファイルを 1 つずつ消した（ディレクトリは残る）」と「ディレクトリごと消した」を区別するが、Git からは区別できない。ゴールデンテストの N-1・N-2（[overlayfs-golden-test.md](../overlayfs-golden-test.md) §4）はこのためで、直さない。ワークスペースへの反映はファイル単位なので、利用者から見える影響は無い
- **別の環境で初めて開いたときは、層を作り直す時間がかかる。** 写しの層を 1 つ作るだけにして（ADR-0003）、履歴の全コミットを積み直すことはしない。時間は #14 で測る
- **保存の速さの上限は Git で決まる。** 計測（2026-09-26、Windows）では、保存 1 回の Git の手順（add・write-tree・commit-tree・update-ref）に約 100 ms かかり、そのほとんどは Git のプロセスの起動だった。カーネルの OverlayFS のコミットはゲストの中で 0.1〜0.4 ms（WHPX）なので、速さの課題は OverlayFS ではなく Git の呼び出し方にある（補足 S-5 の心配は当たらなかった）

## 確かめ方

- ゴールデンテスト（Git を通した Node 版の照合）と、#16 で作る「Node 版とカーネル版で、Git の同じ履歴からワークスペースに反映した結果が一致するか」の差分テスト
- #14 で、層のキャッシュを消してから過去に戻る操作をして、Git から作り直せることを確かめる
