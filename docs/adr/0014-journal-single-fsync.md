## 背景

ADR-0002 で、マイクロ履歴の既定は「電源断や OS の異常終了でも、保存ジョブが終わった記録は失わない」とした。#32 の速い記録は、これを守るために、保存 1 回で書く Git のファイル 7 つ（blob・tree 3 つ・commit・ブランチ・タグ）をそれぞれ fsync していた。

#45 の計測で、記録の時間のうち fsync の割合は、CI の Windows で 69%（7 回で 50.5 ms）、macOS で 56%、Ubuntu で約 40% だった。fsync 1 回の時間はディスクで大きく違い（CI の Ubuntu 約 0.35 ms、手元の Windows 約 1.3 ms、CI の Windows 約 7.2 ms）、書き込みの確定が遅い PC では記録の大半が fsync になる。

VS Code は、ワークスペースのファイルを保存するときに `fdatasync` している（`diskFileSystemProvider.ts`）。履歴だけ fsync をやめると「ファイルは残るのに履歴だけ消える」ので、確定させること自体はやめない（#38）。

## 決定

保存 1 回の記録を、**1 つの追記ファイル（ジャーナル）への追記と、その 1 回の fsync** で確定させる。Git の形式のファイルは確定を待たずに書き、停電などのあとは、次に起動したときにジャーナルから足りない分を作り直す。

### 通常時（保存 1 回）

1. 書くもの（新しいオブジェクトの中身、ref の「前の値 → 新しい値」、HEAD の向き）をメモリに集める
2. それを 1 つの記録としてジャーナルに追記し、**fsync を 1 回**
3. そのあとで、Git のオブジェクト・index・ref を、fsync せずに書く

**順番が要点**。ジャーナルを確定させる前に Git のファイルを書くと、停電で「名前は残ったが中身が壊れたオブジェクト」が、ジャーナルに記録の無いまま残りうる（次に同じ中身を保存しても「もうある」と判断され、壊れたオブジェクトを指すコミットができる）。ジャーナルが先なら、ディスクにある Git のファイルはどれも、確定したジャーナルの記録から作り直せる。

### ジャーナルの形

- 置き場所：shadow の Git のディレクトリの `microgit-journal/`。VS Code の窓（プロセス）ごとに別のファイル（`<pid>-<乱数>.log`）。複数の窓が同じリポジトリを開いても、鍵を取り合わない
- 1 つの記録：`MGJ1`（4 バイト）＋ 長さ（4 バイト）＋ 中身（JSON）＋ 中身の SHA-256（32 バイト）。中身には、新しいオブジェクト（種類・ハッシュ・中身）、ref の変更（名前・前の値・新しい値）、HEAD の向き
- 読むときは、先頭から順に、形と SHA-256 が合う記録だけを使う。最後の記録が書きかけ（停電で途中まで）なら、そこで止める（その保存は記録されなかったことになる。Git のファイルはジャーナルの後に書くので、ディスク上の状態とも矛盾しない）

### 非常時（起動時の作り直し）

MicroGit が shadow を最初に使うときに、すべてのジャーナルを読み、記録ごとに次をする。遅くてよい（利用者の方針）。

- **オブジェクト**：無いか、中身を展開してハッシュが合わなければ、ジャーナルの中身から書き直して fsync する
- **ref**：ref ごとに、ジャーナルに出てくる値の列（前の値・新しい値）と、最後の値・最後の記録の時刻をまとめてから、1 回だけ決める（実装の途中で、記録ごとに compare-and-swap を当てる案から変えた。下の「実装で分かったこと」）
  - 今の値が最後の値：何もしない
  - 今の値が読めない・指すオブジェクトが無い：書き込みが失われた → 最後の値に進める
  - 今の値がジャーナルに出てこない値：ほかの処理（過去に戻る操作、他デバイスからの取り込み）が書いた → 触らない
  - 今の値がジャーナルの途中の値：ref のファイル（無ければ packed-refs）の更新時刻が、その ref の最後の記録の時刻より**後**なら、ほかの処理がちょうどその値に戻した → 触らない。そうでなければ書き込みが失われて途中の値が残った → 最後の値に進める
- **index**：ジャーナルに入れない（Git でも index はキャッシュ扱い）。ref を進めたとき、または index が読めない・無いオブジェクトを指すときは、`git read-tree HEAD` で HEAD の tree から作り直す。古い index のまま次の保存をすると、最後の数回分の変更が消えた tree ができる
- **reflog**：fsync せずに追記しているので、行が途中で切れたり、無いオブジェクトを指したりしうる。ジャーナルに出てきた ref と HEAD の reflog から、形の合わない行と無いオブジェクトを指す行を取り除く（`git fsck` は reflog の壊れた行をエラーにする）
- 作り直したあと、持ち主のプロセスがもう動いていないジャーナルは消す。動いているもの（ほかの窓）は残す（中身はもう反映済みなので、読み直しても何も起きない）

### 後片付け（チェックポイント）

ジャーナルは放っておくと伸び続ける。記録が一定数（64 件か 8 MiB）たまったとき、または保存が落ち着いたときに、保存の列の外で次をする。

1. 次のジャーナルのファイルを裏で作り、名前も確定させる（その間の保存は今のファイルに追記し続ける）。できたら、保存と保存の間に切り替える
2. 古いジャーナルの記録で書いた Git のファイルを、まとめて fsync する（非同期。保存を待たせない）
3. 古いジャーナルのファイルを消す

途中で停電しても、古いジャーナルは消す前なので、起動時に作り直せる。

### 永続性の設定との関係

- `microgit.durability=power`（既定）：上のとおり
- `microgit.durability=process`：ジャーナルも fsync も使わない（今までどおり）
- ジャーナルを開けない環境では、今までどおりファイルごとに fsync する

### ファイルの名前も確定させる（ディレクトリの fsync）

Linux や macOS では、ファイルの中身を fsync しても、そのファイルの**名前**（ディレクトリの中身）は確定しない。ジャーナルは確定の唯一のよりどころなので、名前が消えると記録ごと失う。そこで、

- 新しいジャーナルのファイルを作ったら、`microgit-journal/` を fsync する（初めて作ったときは Git のディレクトリも）。チェックポイントでは次のファイルを裏で作ってから切り替えるので、保存のときにこれを払うのは、起動して最初の記録だけ（最初の実装は切り替えてから次の保存で作っていて、CI の Linux で 65 回目の保存の fsync が 2 回になった）
- チェックポイントでは、書いた Git のファイルの中身に加えて、それらが入っているディレクトリ（`objects/xx/`、`refs/heads/` など）も fsync してから、古いジャーナルを消す。作り直しも同じ
- Windows では、Node.js からディレクトリを開いて fsync できない。NTFS はメタデータを自分のジャーナルで守るので、何もしない

ADR-0014 の前（ファイルごとに fsync）も、ディレクトリは fsync していなかった（Git の既定も同じ）。ジャーナルにしたことで、むしろ名前の確定まで守るようになった。

### ほかの処理が ref を書き換える前のチェックポイント

ジャーナルに古い記録が残ったまま、MicroGit 自身が Git のコマンドで ref を書き換える（過去に戻る、ブランチを切り替える、速い記録が使えず Git のコマンドで記録する）と、そのあとの停電で、作り直しがその書き換えを古い値で上書きしうる。そこで、これらの前に**同期のチェックポイント**をして、ジャーナルを空にしておく。上の更新時刻での見分けは、別の窓（プロセス）や、利用者が手で Git を使った場合のための二重の守り。

### 拡張機能での呼び方

- 保存が 300 ms 途切れたとき（画面の更新と同じ予約、#37）：チェックポイント（非同期）
- 過去に戻る前、ブランチの shadow を切り替える前、Git のコマンドでの記録に切り替える前：チェックポイント（同期）
- shadow を開いたとき：作り直し（速い記録も、最初の保存のときに作り直す）
- 拡張機能を止めるとき：チェックポイント（同期）

## 理由

- 通常時の fsync が 7 回から 1 回になる。見込みは CI の Windows で記録 73 → 約 32 ms、macOS で 20 → 約 10 ms
- 復元の仕組みは、データベースの write-ahead log と同じ考え方で、よく知られている
- 復元は遅くてよい（利用者の方針）ので、起動時に全部の記録を確かめ直す単純な方法を取れる（速くするための工夫を入れない分、間違いにくい）

## 採らなかった案

- **1 回の保存のオブジェクトを 1 つの pack にまとめる**：Git の形式から外れないが、fsync は 7 → 4 回にしか減らず（pack・pack の索引・ブランチ・タグ）、小さな pack のまとめ直しも要る
- **既定を fsync なしにする**：VS Code が保存したファイル本体は確定しているのに、履歴だけ消えうる
- **ジャーナルだけを正本にして Git の形式に書かない**：ふつうの Git で履歴を読めなくなる（ADR-0001・互換性）

## 引き受けること

- **同じ中身を 2 回書く**（ジャーナルと Git のオブジェクト）。大きなファイルを頻繁に保存すると、ディスクへの書き込み量が約 2 倍になる（チェックポイントで消えるので、残る量は増えない）
- **停電の直後、作り直すまでの間**は、ふつうの Git やほかの道具から、最後の数回分の記録が見えないことがある（MicroGit が shadow を最初に使うときに作り直す）
- **作り直しの処理は、履歴を守るいちばん大事な部分に入る新しいコード**。停電を模した試験（Git のファイルを消す・壊す・ref を古い値に戻す・ジャーナルの最後を途中で切る・後からほかの処理が ref を書き換える）で確かめる
- loose object を、チェックポイントで fsync できるように書き込み可能（0644）で作り、fsync したあとで読み取り専用（0444）にする（Git は 0444 で作る）

## 実装で分かったこと（2026-10-02）

- **記録ごとの compare-and-swap では、過去に戻る操作と見分けられない**。ref を 5 つ前のコミットに戻す操作は、ジャーナルの 16 番目の記録の「前の値」と同じ値を書く。記録ごとに「今の値が前の値と同じなら進める」を当てると、戻した ref が最後の値まで進み直してしまった（停電の試験の external の場面で見つけた）。値だけでは「書き込みが失われて途中の値が残った」のか「ほかの処理がちょうどその値に戻した」のかが分からないので、ファイルの更新時刻で見分けることにした
- **更新時刻での見分けの限界**：FAT など、更新時刻の細かさが 1〜2 秒のファイルシステムで、ほかのプロセスが最後の保存と同じ秒のうちに ref を途中の値へ戻したあと停電すると、戻した操作が上書きされうる。MicroGit 自身の操作はチェックポイントで防ぐので、別の窓か手での操作に限る。この場合も Git として壊れた状態にはならない（指すコミットはどちらもある）
- **reflog と index も直す必要があった**。最初の停電の試験で、reflog の行が無いオブジェクトを指して `git fsck --strict` が失敗した。index も古いまま残り、次の保存で数回分の変更が消えた tree ができうる
- **手元の Windows での効果**（`scripts/bench-commit-phases.mjs`、ファイル 50、保存 200 回、SSD、2 回測った）：保存 1 回の fsync は 7 → 1 回、fsync の時間は 9.8 → 1.1 ms、記録全体は 30.5 → 22.2 ms と 32.6 → 24.4 ms（約 8 ms、25〜27% 短い）。ジャーナルの追記（fsync 込み）は 1.2 ms。この PC の fsync は速い（1 回約 1.4 ms）ので、fsync が遅い環境（CI の Windows で 1 回約 7.2 ms）ではもっと効くはず（CI の 5 つの環境の計測で確かめる）
- **次に大きいのはファイルを作る費用**：fsync をやめても、Windows では保存 1 回で Git のファイルを作る（オブジェクト 5 つ・index・ref・タグ・reflog）だけで約 17 ms かかる（オブジェクト 9.5 ms、ref 5.1 ms、index 2.3 ms）。これを減らす案は #49 で検討する

- 差分テスト（Git のコマンドでの記録と 1 ビット一致）：`scripts/test/micro-commit-diff.mjs`（既定でジャーナルを使う）
- 計測：`scripts/bench-micro-commit.mjs`、CI の 5 つの環境の保存の計測（fsync の回数が 1 になること）
