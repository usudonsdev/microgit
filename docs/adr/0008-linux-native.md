# ADR-0008: Linux ホストでは仮想マシンを使わない

| 項目 | 内容 |

| 日付 | 2026-09-26 |
| 決めた人 | 利用者（要件定義書 AD-2）。記録は Claude（#9） |

## 決定

Linux ホストでは、agent を `unshare -Urm` で非特権のユーザー名前空間と mount 名前空間の中に起動し、ホストのカーネルの OverlayFS をそのまま使う。層は、カーネル 6.6 以降で `$XDG_RUNTIME_DIR` があれば tmpfs に置く。

## 理由

- 仮想マシンを挟む理由（カーネルの機能を用意する）が、Linux にはそもそも無い
- 実測（WSL2、2026-09-26）で、起動 29 ms、過去に戻る操作 21.6 ms（Node.js 版 127.4 ms）。NFR-2 の Phase 0 の受け入れ基準を満たす
- 仮想マシンを使う経路と同じ agent・同じ命令・同じ mount オプションなので、挙動が揃う（FR-1。ゴールデンテストで 6.6・6.8・6.17・6.18 のカーネルが同じ結果）

## 引き受けること（補足 S-3）

- **動かない環境がある**：Ubuntu 23.10 以降は AppArmor で非特権のユーザー名前空間を止めている。起動して確かめる（probe）ので、止められていれば Node.js 版に切り替わる。GitHub Actions の Ubuntu 24.04 で、`unshare: write failed /proc/self/uid_map: Operation not permitted` の理由で 5 ms で切り替わることを CI で毎回確かめている
- **ホストのカーネルの攻撃面が増える**：仮想マシンの経路と違い、細工されたファイルの内容がホストのカーネルの OverlayFS に直接届く。ユーザー名前空間と OverlayFS を組み合わせた権限昇格の実例もある（CVE-2023-0386 など）。要件定義書 §7 の「侵害されても VM 内に閉じる」は、この経路では成り立たない（§7.4 に別項として書いた）。ホストのカーネルの更新は利用者（OS）の責任で、心配なら `microgit.overlayBackend` を `nodejs` にできる
- **agent はホストのファイルに触れる**：ユーザー名前空間の中の agent は、利用者と同じ権限でホストのファイルを読み書きできる。Linux の経路では Boundary Guard は「正しさの境界」で、「隔離の境界」ではない。agent は MicroGit と一緒に配る自前のコードで、層の置き場所（`$XDG_RUNTIME_DIR/microgit` か一時ディレクトリ）の外には書かない

## 採らなかった案

- Linux でも仮想マシン（QEMU）を使う：隔離は強くなるが、起動が遅く（CI の QEMU の TCG で ready まで 0.7〜1.3 秒。VM なしは 29 ms）、KVM の権限（`/dev/kvm`）が要る環境が多い。まず速さと動作要件を優先した。必要になれば設定で選べるようにする
