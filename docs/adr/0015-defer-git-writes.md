# ADR-0015: 保存のときはジャーナルにだけ書き、Git の形式のファイルは落ち着いてから書き出す

| 項目 | 内容 |

| 関係 | [ADR-0001](./0001-source-of-truth.md)（正本は Git）を保つ、[ADR-0014](./0014-journal-single-fsync.md)（ジャーナル）の上に作る、#49、[設計判断の理由](../design-rationale.md) D11、[保存が速くなった理由](../why-save-is-fast.md) |

## 背景

ADR-0014 で、保存 1 回の確定待ちはジャーナルへの 1 回になった。そのあとの段階ごとの時間で、記録の 7 割は **Git の形式のファイルを作ること** だと分かった（Windows で、オブジェクト 5 つ・index・ref・タグ・reflog を作るのに約 17 ms）。fsync をしなくても、Windows ではファイルを 1 つ作るたびに NTFS とウイルス対策の検査の費用がかかる。

利用者と、次の 3 つの案を比べた（2026-10-03）。

| 案 | 中身 |
|---|---|
| A | 正本は Git のまま。保存の直後はジャーナルが正本で、Git の形式のファイルは落ち着いてから書く |
| B | 層（OverlayFS）の保管場所を正本にし、Git は同期と互換のための書き出し先にする |
| C | 層だけにして Git を使わない |

保存のときにすることは A と B でほぼ同じ（1 か所に書いて確定を 1 回待つ）で、B・C は層の保管場所・壊れたときの確かめ方・同期・移行を一から作る必要がある。利用者は「保存が高速ならそれで充分」として A を選んだ。

## 決定

durability=power でジャーナルを使うとき（既定）、保存 1 回の記録は **ジャーナルに追記して確定させるだけ** にする。Git の形式のファイル（オブジェクト・index・HEAD・ref・reflog）は、メモリに貯めておき、次のときにまとめて書き出す（materialize）。

| 書き出すとき | 理由 |
|---|---|
| 保存が 0.3 秒落ち着いたとき（チェックポイントの前） | 画面の更新と同じ予約（#37）。ふつうはここ |
| ジャーナルが 64 件か 8 MiB たまったとき | 保存が続いても、貯める量に上限を設ける。この 1 回の保存だけ、書き出しの分だけ長くなる（下の「引き受けること」） |
| **隠しリポジトリを読む処理の直前**（関所） | Git のコマンドや、ファイルを直接読む処理は、書き出していない分を知らない |
| 拡張機能を止めるとき、MicroGit 自身が Git のコマンドで ref を書き換える前（過去に戻る・shadow の切り替え・CLI での記録） | ADR-0014 のチェックポイントと同じ場所 |

### 関所

`src/fastGit/pendingWrites.ts` の `flushPendingGitWrites(target?)` を、隠しリポジトリを読む Git の呼び出しの直前すべてに置いた（拡張機能の `runGit`、`overlay.ts`、`shadowStore.ts`、`kernel/layerFeeder.ts`、記録の部品の中の `git`）。`target` を渡すと、その場所に関係する隠しリポジトリの分だけを書き出す。ふつうのリポジトリ（利用者の作業フォルダ）に対する Git の呼び出しでは書き出さない。

ファイルを直接読む処理で、保存のたびに通るのは「HEAD に付いているタグ」を読むところ（`detectCurrentTag`）だけだった。ここで毎回書き出すと遅らせる意味がなくなるので、書き出し待ちのあいだは、記録の部品がメモリに持っている答え（`headTagFromMemory`）を使う。

### 書き出しの中身

- オブジェクト：貯めたものを全部書く（確定は待たない。チェックポイントでまとめて確定）
- index：今のメモリの index を 1 回書く
- ref：**最後の値だけ** を書く。reflog には、途中の更新も順に 1 行ずつ足す（Git で 1 回ずつ更新したときと同じ行になる）
- ほかの処理が、書き出すまでの間に ref や index を書き換えていたら（ref の今の値が、最初の更新の前の値と違う、index の更新時刻などが変わった）、**そちらを残す**。今までも「あとから書いた方が残る」結果だったのと同じ。こちらのコミットはオブジェクトとして残る

### 停電したとき

ジャーナルは保存のたびに確定しているので、書き出す前に停電しても、次に起動したときに ADR-0014 の作り直しがすべて書く。作り直しは、もともと「Git のファイルが何も書かれていない」場合を扱える（オブジェクトを書き、ref を進め、index を HEAD から作り直す）。

## 理由

- 保存のときにすることが、ジャーナルへの 1 回の追記と確定だけになる。手元の Windows（ファイル 200 個、保存 300 回、停電対策の設定をそろえる）で、普通の Git の `git add` → `git commit` が 0.090 秒のところ、0.010 秒
- 正本は Git のまま（ADR-0001）。同期・普通の Git での読み取り・今の利用者の移行は変わらない
- 停電への備えは ADR-0014 の仕組みをそのまま使える。新しく作る復元の処理は無い

## 採らなかった案

- **B（層を正本にする）・C（層だけ）**：上の背景のとおり。保存の速さはほぼ同じで、作るものと失うものが大きい
- **書き出しを裏の別スレッドで行う**：Node.js の拡張機能では、ファイルの書き出しを別スレッドに移しても、メインの処理との順番の管理が増える。落ち着いたときにまとめて書くので、待つ人がいない
- **durability=process でも遅らせる**：ジャーナルを確定させない設定では、書き出す前に VS Code が落ちると記録が消える。遅らせるのは、ジャーナルが確定しているときだけ

## 引き受けること

- **保存の直後、最大で 0.3 秒ほど、ディスクの Git の履歴が遅れる。** MicroGit の中の処理は関所で書き出すので影響しない。利用者がターミナルで隠しリポジトリを Git で読むと、最後の数回分が見えないことがある（落ち着けば見える）
- **関所を置き忘れた処理は、古い履歴を読む。** 隠しリポジトリを読む処理を足すときは、`flushPendingGitWrites` を呼ぶ（このファイルの「関所」と、`pendingWrites.ts` の説明）
- **保存が 0.3 秒の間もあけずに 64 回続くと、64 回目の保存だけ、書き出しの分だけ長くなる。** 手元の Windows（ファイル 50 個）で、63 回分の書き出しは約 0.4 秒（5 回測って 389〜426 ms）。人が手で保存する間隔（1 秒以上）や、VS Code の自動保存の既定（1 秒ごと）では、保存のあいだに毎回書き出しが済むので起きない。とても短い間隔で自動保存する設定の人には、64 回に 1 回の引っかかりになる。オブジェクトだけを少しずつ先に書く（ref は最後に 1 回）ことで均せるが、今は作らない
- **書き出すまでにほかの処理が ref を書き換えると、こちらの ref の更新は残らない**（コミットはオブジェクトとして残る）。MicroGit 自身の操作は関所で先に書き出すので、起きるのは利用者が手で Git を使ったときだけ

## 確かめ方

- 差分テスト `scripts/test/micro-commit-diff.mjs`：4 回に 1 回くらいだけ書き出して、Git のコマンドで記録した結果とディスクの状態（HEAD・ref・index）を比べる。何回分かを貯めてからまとめて書き出す場合も確かめる
- 停電の試験 `scripts/test/micro-commit-crash.mjs` の deferred の場面：30 回分を書き出す前に停電した写しを、ジャーナルから作り直し、書き出した場合と同じ履歴になるか
- 段階ごとの時間 `scripts/bench-commit-phases.mjs`（defer・journal・no-journal を並べる）、普通の Git との比較 `scripts/bench-micro-commit.mjs`
- Overlay Status の `materialized=<回数>/<保存の数>saves externalWins=<数>`
