## 背景

ADR-0009 は「ゲストは信用しない」とし、その理由を「乗っ取られたゲストの中の検査は、検査ごと書き換えられる」とした。この前提は、ゲストを **攻撃者** になりうるものとして扱っている。

#32 で速さを検討する中で、次のことを確かめた。

1. **ゲストへの入り口は 1 つしかない。** ゲストのカーネルはネットワークの仕組みを持たない（`CONFIG_NET` 無効、ADR-0010）。ホストとゲストの通り道は MicroGit だけが使う（Windows の名前付きパイプは起動ごとに 128 ビットの乱数の名前で、接続は 1 つだけ）。ゲストに届くのは、利用者が VS Code で保存したファイルの名前と中身だけ
2. **同じ入力を、ホストの道具はもっと無防備に扱っている。** 保存したファイルは、VS Code、Git、言語サーバー、ほかの拡張機能が、ホストで利用者と同じ権限で先に読む。ゲストの OverlayFS はファイルの中身を解釈せず、名前と構造だけを扱う。ゲストだけを攻撃の入り口として特別に疑う理由は小さい
3. **隔離が無い経路がすでにある。** Linux では VM を使わず、agent はホストで利用者の権限で動く（ADR-0008）。Windows で仮想化機能が無効なときの TCG は、QEMU の方針でセキュリティの境界ではない（要件定義書 §7.5）。「ゲストは隔離されている」という前提は、すべての環境では成り立っていない
4. **一方で、ゲストと通り道の不具合は実際に起きた。**
   - Windows の QEMU の標準入出力で、1 MiB の中身が壊れた（ADR-0006）
   - macOS の virtio-console で、約 64 KiB を超える 1 行を渡すとゲストが黙って止まった
   - 配布用の VSIX に古い agent が紛れ、「カーネル版」と表示されながら毎回 Node.js 版が肩代わりしていた

## 決定

- **ゲストは攻撃者としては扱わない。**
- **ゲストは間違えうるものとして扱う。** 不具合や通り道の故障で、正しくない一覧や中身が返りうる。ゲストが返したものは、ワークスペースに書く前にホストで検証する（Boundary Guard はそのまま残す）
- **ゲストに仕事を任せるかどうかは、信頼ではなく、速さ・可用性・互換性で決める。**
  - 可用性：VM が起動していない・止まった・VM を使えない環境でも、記録を失わずに続けられるか
  - 互換性：ふつうの Git や他デバイスとの共有を、今までどおり扱えるか

## 理由

- 検証の仕組み（パスの形、`.git` への書き込みの禁止、中身の sha256 の照合、全部受け取ってから書く順番）は、攻撃より不具合から利用者のファイルを守るものとして、実際に意味があった。費用も小さい（過去に戻る操作全体で 22 ms の中に収まる）
- ワークスペースに書く処理は、`.git/hooks` などへの書き込みでホストのコードの実行につながりうる、いちばん危ない操作。その 1 か所で検査するのは、信頼の前提に関係なく良い設計
- 「ゲストを信用しない」を理由に、ゲストに仕事を任せる設計（記録や層の作成をゲストで行うなど）を最初から外すと、速さの選択肢が不必要に狭まる。Git のオブジェクトは中身とハッシュで照らせるので、ゲストが作ったものもホストで検証できる

## 採らなかった案

- **ADR-0009 のまま（攻撃者として扱う）**：入り口の数と、ホストの道具との比較からみて、守っている危険に対して設計の制約が大きすぎる
- **検証をやめる（ゲストを信頼する）**：不具合は実際に起きた。検証の費用は小さい

## 引き受けること

- ゲストのカーネルの不具合を細工したファイル名で突かれる可能性は、ゼロではない。その場合も、ワークスペースへの書き込みは Boundary Guard が止める。ゲストが返す値を使って何かを決める処理を足すときは、その値の検証を同じ考え方で足す
- 前提が変わる条件：ゲストにネットワーク、ほかのアプリとの通信、利用者が保存したもの以外の入力（たとえば他人のリポジトリを丸ごと取り込む）を足すときは、この ADR を見直す
