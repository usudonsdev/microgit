# ADR-0003: 層キャッシュの深さに上限を設け、超えたら写しの層を作る

| 項目 | 内容 |

| 日付 | 2026-09-26 |

## 背景

保存のたびに層を 1 枚積むと、履歴が伸びるにつれて OverlayFS の限界に当たる（補足 S-6）。

- OverlayFS の lowerdir は最大 500 層（カーネルの `OVL_MAX_STACK`）
- mount のオプション文字列の長さ。補足 S-6 は「カーネル 6.5 より前」の制限としているが、agent が使う従来の `mount(2)`（Go の `syscall.Mount`）は、カーネルの版によらずオプションを 1 ページ（4096 バイト）までしか受け取らない。新しい mount API（`fsconfig`）に切り替えれば緩むが、Linux ホストで VM を使わない経路（AD-2）はカーネル 5.11 以降のどの版でも動かしたいので、従来の API の制限に合わせる
- 層が深いほど、ファイルを探すたびに見る層が増えて遅くなる

一方、MicroGit の履歴には数千のマイクロコミットがありうる。

## 決定

カーネル版の層キャッシュ（ゲストの tmpfs、または Linux ホストの一時ディレクトリ）について、次のようにする。

1. **深さの上限を 32 層にする。** コミット C の層を作るとき、親の層の深さが 32 以上なら、親への差分ではなく **C の完全なツリーの写しの層**（親を持たない層）を作る
2. **写しの層は Git から作る。** `git ls-tree -r -z C` の全ファイルを 1 枚の層にする。以降の保存は、この写しの上に積む
3. **キャッシュが空のとき（VM の起動直後など）は、目的のコミットの写しの層を 1 枚だけ作る。** 履歴の全コミットを積み直さない
4. **キャッシュの層の数にも上限（256 枚）を設ける。** 超えたらキャッシュを空にして、必要になった時点で作り直す（ADR-0001 により失うものは無い）
5. **agent の中の層の名前は短くする**（`/run/microgit/l/<番号>` など）。Git のハッシュ（40 文字）をそのまま使うと、32 層で約 1.9 KB になり、4096 バイトの制限に対して余裕が小さい

Node.js 版は今までどおり。ビュー（そのコミットの完全な写し）を保存時に作るので、層の深さの問題は起きない。

## 理由

- 32 層なら、短い名前（1 層あたり 20 バイト前後）で 700 バイト程度に収まり、4096 バイトの制限にも 500 層の制限にも十分な余裕がある
- 写しの層は「32 回の保存に 1 回、ツリー全体をゲストに送る」コストになる。MicroGit が記録するのは保存したファイルだけなので、ツリーは作業フォルダ全体より小さい
- 履歴は Git に全部あるので、層をいくら捨てても、どのマイクロコミットにも戻れる

## 採らなかった案

- **層を平らにまとめ直す（複数の層を 1 枚に合成する）**：OverlayFS には層を合成する機能が無く、agent の中で自前でやることになる。写しの層を Git から作るほうが単純で、正本（Git）と常に一致する
- **上限を 500 近くまで上げる**：6.5 より前のカーネルでは文字列の長さの制限に先に当たる。探索も遅くなる
- **LRU で古い層だけ捨てる**：層どうしに親子関係があるので、どれを捨ててよいかの判定が複雑になる。まずは「全部捨てて作り直す」で始め、必要になったら入れる

## 引き受けること

- 深さが 32 を超えるたびに、ツリー全体を境界越しに送る。ツリーが大きいと、その保存だけ遅くなる。#14 で測る
- 256 枚を超えるとキャッシュを空にするので、その直後の過去に戻る操作は写しの層を作る分だけ遅くなる

## 確かめ方

- #14 の単体テスト：深さ 32 で写しの層に切り替わる、キャッシュが空なら写しの層から始まる、キャッシュを空にしても同じ結果になる
- #14 の差分テスト：写しの層を挟んでも、Git のツリーとワークスペースへの反映結果が一致する
