# ADR-0007: 汎用の Linux 仮想マシンではなく、機能単位の部品として提供する

| 項目 | 内容 |
|---|---|

| 日付 | 2026-09-26 |
| 決めた人 | 利用者（要件定義書 AD-1）。記録は Claude（#9） |
| 関係 | 要件定義書 AD-1・NFR-3、補足 S-1、[guest-phase1.md](../guest-phase1.md) |

## 背景

Linux 以外のホストで Linux カーネルの機能を使う方法として、WSL2、Docker Desktop、Lima、Apple Containerization、libkrun などがある。どれも「Linux 環境」を丸ごと用意し、その中で任意のプログラムを動かせる。

## 決定

提供するのは OverlayFS という **1 つのカーネル機能** で、Linux 環境ではない。ゲストのユーザーランドは agent（Go の静的バイナリ）1 ファイルで、任意のプログラムは動かせない。ホストとは、OverlayFS の操作に絞った命令（[agent-protocol.md](../agent-protocol.md)）だけで話す。

## 理由

- 提供する範囲を絞ると、ゲストを削れる。実測で、カーネルと agent を合わせたゲストはダウンロードの大きさで 3.6 MB 以下（x86_64 3.55 MB、arm64 2.93 MB、gzip -9）
- 拡張機能に同梱して配れる。利用者に Linux 環境の導入を求めない（NFR-1）
- ホストとゲストの境界が「少数の単純な命令」になり、検証する側（Boundary Guard）を小さく保てる（SR-2）

## 補足 S-1 への答え：LKL・libkrun との違い

補足 S-1 は、LKL（Linux Kernel Library：カーネルをライブラリとしてプロセスの中で動かす）と libkrun（アプリに埋め込むライブラリとして提供される）に対しては、「既存の解決策は Linux 環境全体を提供する」という差分の主張が成り立たないと指摘した。そのとおりで、差分を次のように定義し直す。

| | LKL | libkrun | 本件 |
|---|---|---|---|
| カーネルの動かし方 | ホストのプロセスの中（仮想化なし） | 仮想マシン（KVM・HVF） | 仮想マシン（QEMU・Virtualization.framework）、Linux は仮想化なし |
| ゲストに入るもの | カーネル（ライブラリ） | Linux 環境（任意のプログラム） | カーネル＋OverlayFS の操作だけの agent |
| Windows | 保守状況が不明（2026-09-26 時点で調べていない） | 対象外 | QEMU（WHPX・TCG） |
| 境界の形 | 関数呼び出し（同じプロセス） | 仮想マシンの境界 | 仮想マシンの境界と、検証するホスト（Boundary Guard） |

本件の差分は「**1 つの機能だけを、仮想マシンの境界の向こうに置き、ホストが検証する**」ことにある。LKL は Windows で仮想化機能が要らない点で魅力があったが（補足 S-2）、QEMU の TCG が仮想化機能なしでも実用的な速さで動いたため（[windows-backend.md](../windows-backend.md)）、LKL の採否（O-9）は保留にした。

## 採らなかった案

- 汎用の軽量 Linux 仮想マシンを同梱する：実装は簡単だが、ゲストを削れず、既存の解決策との差分がなくなる
