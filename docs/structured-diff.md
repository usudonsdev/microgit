# 構造を理解した差分（xlsx のセル、動画のコマ）— 構想メモ・案

2026-11-23。利用者の提案：「バイナリファイルを、動画ならどのコマをどう変えたか、xlsx ならどのセルをどう変えたか、という単位で差分管理できれば、verEve はただの Git の入れ子より広く使える」。

ここに書くのは**案**であり、実装の正本にはしない。**2026-11-24 に第 0〜3 段階を実装した（未公開）。実装と、§7 の未決のうち実装で決めたことは [structured-diff-implementation.md](./structured-diff-implementation.md)。**容量の話（ZIP を展開して分割すると節約できる、など）は [non-engineer-history-storage-survey.md](./non-engineer-history-storage-survey.md) §6 に実験がある。本書は**差分の見せ方（意味のある単位での比較）**を主に扱う。

## 1. 結論（案）

1. **方向は良い。** 行単位の差分を持つテキストは Git で足りる。Git が「Binary files differ」としか言えないファイルに意味のある差分を出せれば、verEve が Git に足すものがはっきりする。
2. **記録（正本）は今のまま、保存したバイト列そのもの。差分は見るときに計算する派生物にする。** セル単位・コマ単位の変更を正本として持ち、そこから xlsx や動画を組み立て直す方式は採らない（§5）。[ADR-0012](./adr/0012-record-exact-bytes.md)（保存した中身をそのまま記録）と [ADR-0001](./adr/0001-source-of-truth.md)（正本は shadow の Git）をそのまま守れ、保存の速さ（最優先。ADR-0012 の利用者の確定）にも影響しない。
3. **先に解く前提がある。** 今の記録のきっかけは `vscode.workspace.onDidSaveTextDocument`（`src/extension.ts`）だけで、**Excel や動画編集ソフトが保存したファイルは記録されない**（§2）。
4. 形式ごとに「差分ドライバ」を足せる仕組みにし、**xlsx を最初の対象**にする。動画は計算が重く、外部の部品（ffmpeg）も要るので最後にする（§6）。

## 2. 前提：VS Code の外で保存されたファイルを記録する

- `onDidSaveTextDocument` は VS Code のエディタで保存したときだけ発火する。Excel が `book.xlsx` を保存しても、verEve は何も記録しない。
- 必要なのは、ワークスペースのファイル変更の監視（`vscode.workspace.createFileSystemWatcher` など）を記録のきっかけに加えること。
- 監視で起きる問題（要検証）：
  - **保存の途中を拾う。** Office は一時ファイルに書いてから改名する、と言われる（未確認）。動画の書き出しは数十秒〜数分かけて同じファイルに書き続ける。書き終わりを判定する（サイズと更新時刻が一定時間変わらない、ファイルを排他で開けるか確かめる、など）必要がある。
  - **一時ファイル・ロックファイルを記録しない。** `~$book.xlsx`（Office のロックファイル）、`*.tmp` など。除外の規則が要る。
  - **1 回の保存で複数回の変更通知が来る。** 同じ内容なら記録しない（今の saveChain の「直前と同じパス・同じ内容は足さない」と同じ考え）。
  - 記録の速さの設計（[why-save-is-fast.md](./why-save-is-fast.md)、[perceptible-delay.md](./perceptible-delay.md)）は、エディタの保存の直後に記録する前提で作っている。外部アプリの保存では「利用者が保存を押した瞬間」が見えないので、遅延の考え方を別に決める。
- これは差分の見せ方と独立に価値がある（xlsx を記録できるだけで、過去に戻れる）。**第 0 段階として先にやる。**
- **2026-11-23 実装（既定は無効、未公開）。** 判断・確かめたこと・未確認は [external-saves.md](./external-saves.md)。上の問題のうち、書き終わりの判定・一時ファイルの除外・二重の除外は実装した。実機のアプリでの確認はまだ。

## 3. 何を「差分」として見せるか

### 3.1 xlsx（セル単位）

xlsx は ZIP の中に XML が入った形式（OOXML、ECMA-376）。比較の手順：

1. 両方の版を展開し、シートごとの XML（`xl/worksheets/sheetN.xml`）、共有文字列（`xl/sharedStrings.xml`）、ブック（`xl/workbook.xml`、シート名と順序）を読む。
2. セルごとに「値・式・表示形式（スタイル番号）」の組にする。文字列は共有文字列の番号でなく中身で比べる（番号は保存のたびに振り直されうる）。
3. 比べて、変更の一覧を出す：

| 種類 | 例 |
|---|---|
| シート | 追加・削除・改名・並べ替え |
| 行・列 | 挿入・削除（§3.1.1） |
| セルの値 | `B3: 100 → 120` |
| セルの式 | `C3: =A3*B3 → =A3*B3*1.1` |
| 式の結果だけ変化 | `D10: 5,000 → 5,500`（式は同じ、参照先が変わった）。直接の編集と分けて表示する |
| 表示形式 | 太字、色、数値の書式（初期は「書式が変わった」だけでよい） |

初期は値と式に絞る。結合セル、条件付き書式、グラフ、ピボット、名前の定義、マクロ（xlsm）は後回し。

#### 3.1.1 難所：行・列の挿入

3 行目に 1 行挿入すると、それより下のセルの番地が全部ずれる。番地だけで比べると「下のセルが全部変わった」になり、役に立たない。

- 行ごとに内容のハッシュを取り、**行の列どうしを LCS（テキストの diff と同じ考え）で対応づけ**て、挿入・削除された行を見つける。列も同じことをする（2 次元を 1 次元ずつ、2 回）。
- 式の中の参照（`=A4`）は挿入で `=A5` に書き換わる。挿入による機械的な書き換えは「変更」に数えない（相対的な位置で比べる。R1C1 形式に直して比べるのが簡単）。
- 先行例：daff（表形式データの差分ライブラリ、行・列の対応づけを行う）、Microsoft の Spreadsheet Compare、xltrail（Excel 向けのバージョン管理サービス）。実装前に、これらの対応づけの方法を一次資料で確かめる（未調査）。

### 3.2 動画（コマ単位）

- 圧縮された動画は、少しの編集でも書き出し直すと**ほぼ全バイトが変わる**（再エンコード）。バイト列の差分には意味がない。
- 比較の手順（案）：
  1. 両方の版を復号し、フレームごとに小さな指紋（縮小画像の知覚ハッシュなど）を作る。
  2. 指紋の列どうしを対応づけ（3.1.1 と同じ LCS の考え）、**挿入・削除・切り詰め・差し替えられた区間**を出す。対応したフレームは、画素の差が閾値を超えたものを「変更あり」とする。
  3. 「どう変えたか」は、前後のサムネイルを並べる、差のヒートマップを重ねる、で見せる。「色調を補正した」「字幕を入れた」のような意味の言葉にするのは、この段階では目標にしない。
- 音声トラックも別に比べる（波形の指紋）。
- 重い：1080p・10 分・30fps で 18,000 フレーム。全フレームの復号は保存のたびには無理なので、**見るときに計算し、結果をキャッシュ**する。粗い比較（キーフレームだけ、低解像度）を先に出し、必要な区間だけ細かくする。
- ffmpeg（または libav）が要る。同梱するならライセンス（LGPL/GPL の構成次第）とサイズを決める必要がある。利用者が入れた ffmpeg を使う方式もある。
- **容量の問題が大きい。** 動画を保存のたびに丸ごと記録すると、すぐ肥大する。対象から外すサイズの閾値、残す版の数の上限などが要る（未決）。
- 補足：動画の編集では、**編集ソフトのプロジェクトファイル**（Kdenlive の XML、DaVinci Resolve・Premiere のプロジェクト）のほうが「何をしたか」を直接持っている。書き出した動画より先に、こちらの差分を構造的に見せるほうが効果が大きい可能性がある（要検討）。

### 3.3 その他の候補

| 形式 | 差分の単位 | 難しさ |
|---|---|---|
| docx | 段落・文字の挿入削除、書式 | 中（ZIP＋XML。段落の対応づけ） |
| pptx | スライドの追加・削除・並べ替え、スライド内の図形とテキスト | 中 |
| 画像（PNG、JPEG） | 変わった矩形の領域、前後の並置・ヒートマップ | 小〜中 |
| PDF | ページ単位のテキストと画像 | 中 |
| CSV | 行・列（3.1.1 と同じ） | 小（すでにテキストの差分は出るが、表として見せられる） |

## 4. 仕組み：形式ごとの差分ドライバ

```
差分ドライバ（形式ごと。拡張子と中身の先頭で選ぶ）
  入力：旧版のバイト列、新版のバイト列（shadow の Git の blob）
  出力：変更の一覧（JSON。種類・場所・前後の値）＋ 任意で表示用の画像
表示：Webview（既存の履歴 UI）に形式ごとの描画を足す
キャッシュ：(旧 blob ハッシュ, 新 blob ハッシュ, ドライバの版) をキーに .microgit/ の下へ保存
```

- **保存の経路には入れない。** 差分は、利用者が履歴を開いて 2 つの版を比べたときに計算する。保存の速さ（ADR-0012 の利用者の確定：最優先）に影響させない。
- 入力は blob のハッシュで決まるので、同じ組み合わせの計算は 1 回で済む。
- 一覧で「この保存で何が変わったか」の要約（例：「Sheet1 の 3 セル」）を出したいなら、保存の後に低い優先度で計算して貯めてもよい（後で検討）。
- 信頼できないファイルを読む部品になる（ZIP 爆弾、巨大な XML、壊れた動画）。展開後のサイズの上限、時間の上限、別プロセスでの実行を最初から入れる。

## 5. 採らなかった案

- **セル・コマの変更を正本にして、ファイルを組み立て直す。** xlsx を組み立て直しても、保存したときと同じバイト列にはならない（ZIP の圧縮、Excel だけが書く要素、属性の順序）。過去に戻ったときに別のファイルが出てくるのは、スナップショットとして正しくない（ADR-0012 と同じ理由）。動画は再エンコードで画質が落ちる。
- **shadow の Git に textconv・diff ドライバを設定する。** shadow は `info/attributes` で変換を止めている（ADR-0012）。差分の表示だけなら verEve 側で計算すれば足り、Git の設定に頼る必要がない。textconv はテキストに直すだけで、「セル B3」「区間 0:12〜0:15」のような構造は返せない。
- **保存のたびに差分を計算する。** 動画では不可能、xlsx でも大きいブックでは保存の体感を悪くする。§4 のとおり見るときに計算する。

## 7. 未決（利用者が決めること）

- **誰に使ってもらうか。** VS Code の利用者が xlsx や動画を同じフォルダで扱う場面はある（データ分析、ドキュメント、ゲームの素材）が多くはない。非エンジニア版の計画（[non-engineer-drive-sharing-design.md](./non-engineer-drive-sharing-design.md)、`origin/docs/release-5.1.0` の `docs/non-engineer-oss-plan.md`）と合わせるのか、VS Code 版に足すのか。
- 動画を記録の対象にするか（容量）。するならサイズの上限と残す版の数。
- ffmpeg を同梱するか、利用者が入れたものを使うか。
- xlsx の最初の対象範囲（値と式だけでよいか、書式も要るか）。
