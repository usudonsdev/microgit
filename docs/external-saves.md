# VS Code の外で保存されたファイルの記録（第 0 段階）

2026-11-23 実装（未公開）。構想は [structured-diff.md](./structured-diff.md) §2・§6 の第 0 段階。xlsx のセル差分・動画のコマ差分（第 1 段階以降）の前提として、**Excel や動画編集ソフトなど、VS Code の外で保存されたファイルも記録できる**ようにした。差分の表示はまだ無い（過去に戻ることはできる）。

## 1. 何をしたか

- 設定 `vereve.externalSaves.enabled`（既定 **false**）を true にすると、ワークスペースのファイルを `vscode.workspace.createFileSystemWatcher`（`**/*`）で監視し、変更・作成されたファイルを記録する。
- 記録の経路はエディタの保存と同じ（`enqueueRecordSave` → `saveChain` → `runShadowCommit`）。shadow には保存したバイト列をそのまま書く（ADR-0012）。
- 設定 `vereve.externalSaves.maxFileSizeMb`（既定 100、0 で上限なし）を超えるファイルは記録しない。

| ファイル | 役割 |
|---|---|
| `src/externalSave.ts` | VS Code に依存しない部品。一時ファイルの判定（`isTransientFileName`）、書き終わりを待つ（`SettleWatcher`）、最後に記録した中身（`RecordedContents`）、記録するかの判定（`decideExternalSave`） |
| `src/extension.ts` | `configureExternalSaves`（監視を作る・止める）、`handleSettledExternalFile`（記録するか決めて列に足す）、`enqueueRecordSave`（エディタの保存と共通の、列に足す処理）、`withWorkspaceWrites`（過去に戻る操作のあいだ監視を止める） |
| `src/test/unit/externalSave.test.ts` | 部品の単体テスト |
| `src/test/suite/overlayBackend.test.ts` | VS Code の中での確認（外で書いたバイナリの記録、書き出し途中を記録しない、一時ファイル・無視するファイル・二重・過去に戻る操作を記録しない） |

## 2. 記録までの流れ

```
監視の通知（変更・作成）
  ├ 落とす：verEve が過去に戻る操作で書いている最中 / 成果物（.microgit/ など）/ ワークスペースの外 / .git の中 / 一時ファイル名
  ├ 作成されたのがフォルダなら、中のファイル（最大 1000 個）を候補にする（§3.8）
  ▼
SettleWatcher：大きさと更新時刻が 1 秒（EXTERNAL_SETTLE_MS）変わらなくなるまで待つ
  ├ 待つあいだの通知は 1 回にまとめる。書き続けている（動画の書き出し）あいだは待ち続ける（上限なし）
  ├ 消えたファイル（一時ファイルを改名した場合など）は忘れる
  ▼
handleSettledExternalFile（externalChain で 1 件ずつ。git checkout などで大量に来ても Git を並列に大量起動しない）
  ├ 落とす：無効 / 大きすぎる / メインの Git が無視する（git check-ignore）
  ├ 中身を読み、ハッシュを取る
  ├ 落とす：最後に記録した中身と同じ（RecordedContents。エディタの保存の二重）
  ├ 落とす：shadow の HEAD と同じ中身（過去に戻る操作が書いたファイル）
  ├ 落とす：メインの HEAD と同じ中身（git checkout・pull・stash などの書き換え）
  ▼
enqueueRecordSave（エディタの保存と同じ。ブランチ・有効状態の確認、同じ中身の連続を畳む、saveChain へ）
```

## 3. 判断と理由

### 3.1 既定は無効にした

- 実機の Excel・Word・LibreOffice・動画編集ソフトで、一時ファイルの名前・保存の手順・書き終わりの判定が正しいかを確かめていない（§5）。
- 監視は、ワークスペースの中で動くすべての書き込み（ビルド、パッケージの導入、他のツール）を拾う。`.gitignore` で落とせない書き込みが多いプロジェクトでは、記録が増えすぎるおそれがある。
- 実機で確かめてから既定を見直す。

### 3.2 書き終わりは「大きさと更新時刻が 1 秒変わらない」で判定する

- 書き出しの途中のファイルを記録しないため。ファイルの排他を確かめる方法は OS ごとに違い（Windows の共有モード、POSIX の助言ロック）、Node.js から移植性のある形でできないので採らない。
- 1 秒は、エディタの保存の体感（[perceptible-delay.md](./perceptible-delay.md)）とは別の基準。外部アプリの保存では「保存を押した瞬間」が見えないので、記録が 1〜2 秒遅れることは許容した。
- 上限を設けない：動画の書き出しは何分も続く。途中で諦めて記録すると、壊れたファイルを記録する。

### 3.3 過去に戻る操作の書き込みは、中身で落とす（時間で区切らない）

- 最初は「verEve がワークスペースに書いた直後 1.5 秒は監視の通知を無視する」実装にした。VS Code の中のテストで、**直後の利用者の本当の保存が落ちた**（テストの最初の外部の保存が記録されなかった）。時間の区切りは、書き込みの量・マシンの速さで長さが変わり、正しい値が無い。
- 採った方法：書いているあいだ（`withWorkspaceWrites` の中）は通知を受け付けない。遅れて届いた通知は、書き終わりを待ったあと「shadow の HEAD と同じ中身」として落とす。過去に戻る操作は shadow の HEAD を戻した先に動かしてからワークスペースを書くので、書いた中身は HEAD と同じになる。仮に落とし損ねても、記録の側が「HEAD と同じ中身なら何もしない」（unchanged）ので誤りにはならない。

### 3.4 git checkout・pull の書き換えは「メインの HEAD と同じ中身」で落とす

- メインのブランチを切り替えると、Git がワークスペースのファイルを大量に書き換える。これを「保存」として記録すると、切り替え先のマイクロ履歴に、利用者が保存していない記録が並ぶ。
- 書き換えた後の中身はメインの HEAD と同じなので、それで落とす。
- **引き受けること**：利用者が Excel で編集して、最後にコミット済みの中身へ手で戻して保存した場合、その「戻した」保存は記録されない（メインの HEAD と同じ中身なので）。エディタの保存では記録される。差は小さいので許容した。

### 3.5 .gitignore で無視されるファイルは記録しない

- ビルドの出力（`out/`、`dist/`）、`node_modules/` などを記録しないため。メインの Git の判定（`git check-ignore`）に従う。
- エディタの保存では、無視されるファイルも記録している（今までどおり。変えていない）。エディタで開いて保存したファイルは利用者の意図した保存なので。

### 3.6 エディタの保存との二重を防ぐ

- エディタで保存すると、onDidSaveTextDocument と監視の両方から通知が来る。エディタの保存を記録するとき（`enqueueRecordSave`）、パスと中身のハッシュを `RecordedContents` に覚え、監視からの同じ中身の通知を落とす。
- 覚える数の上限は 4096 件。忘れても記録の側が unchanged にするだけ。

### 3.7 削除は記録しない

- 今の記録は「保存したファイル 1 つを、前の木に足す」形で、削除を記録する経路が無い（エディタの保存でも同じ）。監視の削除の通知は、待ちを取り消すだけにした。削除の記録は別の変更で考える。

### 3.8 新しいフォルダの作成の通知で、中のファイルも候補にする

- VS Code の中のテストで、フォルダを作ってすぐ中にファイルを書くと、ときどき（4 回に 1 回ほど）そのファイルの通知が来なかった。フォルダの通知は来ていた。【推測】再帰の監視が新しいフォルダを見張り始める前に書かれたため（inotify を使う再帰の監視で一般に起きる競合）。
- 対策：作成の通知がフォルダなら、その下のファイルを列挙して候補にする（`.git` と成果物のフォルダには入らない、最大 1000 個）。フォルダを丸ごとコピーしたとき・ZIP を展開したときにも効く。
- 候補にしたファイルが既に記録済みの中身なら、後段（`RecordedContents`、shadow の HEAD との比較）で落ちるので、二重には記録しない。
- 対策のあと、8 回続けて通った（§5）。

### 3.9 エディタの保存では、記録すると決めてからファイルを読む

- エディタの保存の経路と共通にした `enqueueRecordSave` は、中身を関数（`readSnapshot`）で受け取り、有効・ブランチ・`.git` の確認のあとで読む。無効のときの保存で、ファイルを読む仕事を増やさないため（共通化の前と同じ順序）。

## 4. 採らなかった案

- **時間で区切って過去に戻る操作の書き込みを無視する**：§3.3。利用者の保存を落とした。
- **保存のたびに記録の対象を拡張子で絞る（xlsx、docx など）**：対象を決めるのは利用者の用途しだいで、拡張子の一覧を拡張機能が持つと漏れる。`.gitignore` と大きさの上限で絞る。必要になったら含める・除くの設定を足す。
- **Node.js の `fs.watch` を直接使う**：VS Code の監視は、OS ごとの差（再帰の監視、Linux の inotify の上限）と `files.watcherExclude` を扱ってくれる。

## 5. 確かめたこと・未確認のこと

確かめたこと（この環境、Linux、Node.js 版の Overlay）：

- 単体テスト 13 件（`externalSave.test.ts`）。
- VS Code の中のテスト：外で書いたバイナリがそのままのバイト列で記録される。400 ms ごとに書き足すファイルは書き終わってから 1 回だけ記録される。`~$book.xlsx`・`~WRL0001.tmp`・`.gitignore` で無視されるファイルは記録されない。エディタの保存は二重に記録されない。過去に戻る操作で書いたファイルは記録されない。
- 速い記録（`fastMicroCommit`）と Git のコマンドの記録（`commit.gpgSign=true` のとき）の両方で通る。
- §3.8 の対策のあと、VS Code の中のテストを 8 回続けて流し、このテストは 8 回とも通った（速い記録 6 回、Git のコマンドの記録 2 回）。後者の 2 回では既存の「Overlay Status」のテストが落ちる。この環境の Git の設定（`commit.gpgSign=true`）で速い記録が使えないためで、この変更の前のコードでも同じように落ちる（今回の変更とは関係ない）。

未確認（実機で確かめる）：

- Excel・Word（Windows・macOS）が保存の途中に作るファイルの名前と、保存の手順（一時ファイルに書いて改名するか）。今の除外の規則は一般に言われている名前で、実機で見ていない。
- LibreOffice、Photoshop・GIMP、動画編集ソフト（DaVinci Resolve、Premiere、Kdenlive）の書き出し。
- Windows・macOS の VS Code の監視で、通知の遅れと取りこぼし。ネットワークドライブ・同期フォルダ（OneDrive、Google Drive）の上。
- 監視が動き出すまでの時間（テストでは、設定を変えてから 1.5 秒待っている。その前の変更は届かない）。
- カーネル版の Overlay での動作（この環境では agent が同梱されておらず Node.js 版で確かめた）。
- 大量の通知（数千ファイルの git checkout）のときの負荷。
