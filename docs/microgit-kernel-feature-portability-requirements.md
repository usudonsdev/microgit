## 1. 目的

### 1.1 一文での定義
**Linuxカーネルの機能としてのOverlayFSを、Linux以外のホストにも提供する部品**を作る。

### 1.2 解決したい課題
1. **OverlayFSはLinuxカーネルにしか存在しない。** MicroGitの設計思想（レイヤーの積み重ねによるマイクロコミット、CoWによる分岐）はOverlayFSと本質的に同じ構造だが、WindowsやmacOSでは使えない。
2. **現行実装はNode.jsによる仮想的なOverlayFSであり、遅い。** 連続セーブに追従するという速度目標に対し、ユーザー空間でファイルシステムの意味論を模倣する方式には性能の上限がある。
3. **既存の解決策はどれも「Linux環境まるごと」を要求する。** WSL2、Docker Desktop、Lima、Apple Containerization などはLinux環境全体を提供するもので、アプリに一機能だけを同梱する用途には重すぎる。

### 1.3 最終的な到達点
| 段階 | 形態 | 位置づけ |
|---|---|---|
| 初期 | MicroGitの内部機能としてVS Code Marketplaceで提供 | 最初の適用例・実証 |
| 最終 | AIを用いて、任意のアプリに必要なカーネル機能を部品として詰め込める仕組み | 汎用化 |

**判断理由：** いきなり汎用部品を作ると、要求が抽象的になり評価軸を失う。自分が保守しているMicroGitという具体的な利用者を最初に置くことで、性能・正しさ・配布のすべてを実利用で検証できる。汎用化はその知見を土台に行う。

### 1.4 非目的
- 収益化は目的としない。**無償で広く配布し、知名度と利用者数を最大化する**ことを優先する。
- 汎用のLinux実行環境を提供することは目的としない（§2.2）。

## 2. スコープ

### 2.1 対象範囲
- OverlayFSのマウント・レイヤー操作・差分取得を、Linux / macOS / Windows で同一の挙動で提供すること
- MicroGitからの利用に必要な境界インターフェース
- 最小ゲスト（カーネル・init・agent）の構築と配布
- ホスト側の検証機構（Boundary Guard）

### 2.2 対象外
| 対象外とするもの | 理由 |
|---|---|
| 任意のLinuxプログラムの実行 | 汎用VMになった瞬間にゲストを削れなくなり、差分（機能単位の部品）が失われる |
| ネットワーク機能 | MicroGitの用途に不要。含めると攻撃面・サイズ・保守要件がすべて増える（§5 NFR-4） |
| OverlayFS以外のカーネル機能 | 最終段階で扱う。初期に広げると評価軸がぼやける |
| ユーザーのOS・セキュリティソフトとの連携 | 環境ごとに有無が異なり、設計上の保証にならない（§7） |

## 3. 用語

| 用語 | 定義 |
|---|---|
| ホスト | ユーザーのPC上でVS Codeと拡張機能が動く側 |
| ゲスト | 最小VMの内部。最小カーネル・init・agentのみを含む |
| lower layer | OverlayFSの読み取り専用層。確定済みスナップショット |
| upper layer | OverlayFSの書き込み層。未確定の変更 |
| 境界 | ホストとゲストの間の通信・ファイル共有経路 |
| Boundary Guard | 境界を通るすべての要求と差分を検証するホスト側の実装 |
| TCB | Trusted Computing Base。安全性がその正しさに依存する最小限の部分 |
| バックエンド | ホストOSごとのOverlayFS提供方式 |

|---|---|---|

## 5. 機能要件

### FR-1：全ホストでOverlayFSの同一セマンティクスを提供する

**要件：** Linux / macOS / Windows のいずれでも、MicroGitから見たOverlayFSの挙動（層の重ね方、whiteout、コピーアップ、リネーム等）が同一であること。

**判断理由：**
- MicroGitは履歴を扱うツールであり、OSごとに挙動が微妙に違うと、同じリポジトリが環境によって異なる履歴を生む。これはバージョニングツールとして致命的である。
- 「本物のOverlayFS」を使う最大の価値は挙動の一貫性にある。性能だけが目的なら各OSのネイティブ機能で近似する選択肢もある（下記）。

**検討した代替案：**
| 代替案 | 採用しない理由 |
|---|---|
| 各OSのネイティブ機能で近似（WindowsのProjFS、macOSのAPFSクローン等） | 境界通過コストがなく高速になりうるが、OSごとに意味論が異なり、同一挙動を保証できない。3系統の実装を保守する負担も大きい |
| 現行のNode.js仮想実装を高速化 | ユーザー空間での模倣には性能上限がある。また「本物と同じ」ことを保証するには、結局カーネル実装との突き合わせが必要になる |
| LKL（Linux Kernel Library）によるプロセス内実行（第 2 版で追加、補足 S-1） | カーネルをライブラリとしてホストのプロセスの中で動かすので、Windows で仮想化機能も管理者権限も要らない利点がある。ただし Windows 対応の保守状況が分からない。QEMU の TCG が仮想化機能なしで実用的な速さで動いたので（NFR-1）、採否（O-9）は保留にした（ADR-0007） |

**トレードオフ：** 挙動の一貫性を取る代わりに、Linux以外ではホスト–ゲスト間の境界通過コストを負う。このコストの最小化が性能面の主課題となる（NFR-2）。

**受け入れ基準：** 同一のテストスイートが3 OSすべてで通過し、各操作後のマージ済みビューがビット単位で一致すること。

**範囲（第 2 版、補足 S-4）：** 「同一の挙動」は、カーネルの OverlayFS を使うバックエンド（Linux の VM なし、Windows・macOS の最小ゲスト）に求める。Node.js 版（フォールバック、NFR-5）には **ワークスペースへの反映の結果が同じ** であることを求め、ビューの中のディレクトリの有無（空のディレクトリ、ディレクトリごとの削除・rename）の違いは許す。どちらも Git がディレクトリを記録しないことから来る（ADR-0001、ゴールデンテストの N-1・N-2）。

**受け入れ基準（第 2 版）：** 2 段に分ける。
1. ゲストの中のビュー：ゴールデンテスト（本物のカーネルで記録した期待値、docs/overlayfs-golden-test.md）と完全に一致すること。Node.js 版は既知の食い違いの一覧どおりであること
2. ホストへの反映後：Git の同じ履歴から過去に戻ったワークスペースが、カーネル版・Node.js 版とも Git のツリーと一致すること（差分テスト、scripts/test/kernel-backend-e2e.mjs）

**固定する mount オプションと最低のカーネルの版：** ADR-0005（`userxattr,redirect_dir=nofollow,index=off,metacopy=off,xino=off`。VM なしは 5.11 以降、層を tmpfs に置くなら 6.6 以降、ゲストは 6.18.53）。

**ホストの FS で表せない変更（O-14）：** Boundary Guard が弾いて利用者に知らせる（変換はしない。SR-2、docs/boundary-guard.md）。

**結果（2026-09-28）：** ゴールデンテストはカーネル 6.6・6.8・6.17・6.18 で同じ結果。差分テストは WSL2（VM なし）・Windows（QEMU の WHPX と TCG）・macOS実機（Virtualization.framework）・CI の QEMU（arm64 / x86_64）で検証する。Mac実機では3 MiBと700ファイルを含む15シナリオ・126回の過去に戻る操作がすべてGitと一致した（Windows / CIは追加シナリオを次の実行で確認する）。

### FR-2：マイクロコミットのモデルをOverlayFS上で実現する

**要件：** MicroGitの基本操作を、OverlayFSの層操作として実現する。初期の操作候補：

| 操作 | 内容 | OverlayFS上の実現 |
|---|---|---|
| `commit` | 現在の変更をスナップショットとして確定 | upperを凍結して新しいlowerとし、新しいupperを用意 |
| `branch` | 既存履歴を共有したまま分岐 | 同じlower群の上に別のupperを作成（CoW） |
| `diff` | 2つの時点の差分取得 | 層の比較 |
| `view` | 任意時点のマージ済みビュー取得 | 指定した層構成でマウント |

**判断理由：**
- OverlayFSの「層を重ねる」「下の層は共有し、上の層だけ書く」という構造は、マイクロコミットと分岐のモデルにそのまま対応する。これはMicroGitの設計がOverlayFSへの関心から生まれたことの帰結でもある。
- `branch`がCoWで実現できることは、卒業研究（マージレスブランチング）の中心的な性質と一致する。

**備考：** 操作の詳細は既存MicroGitの内部モデルに合わせて内部設計で確定する。

**第 2 版で決めたこと：**
- **正本（補足 S-7）：** マイクロ履歴の正本は、これまでどおり shadow の Git。OverlayFS の層は Node.js 版・カーネル版とも、Git からいつでも作り直せるキャッシュ（ADR-0001）
- **commit の方式（補足 S-5）：** 保存ごとに層を 1 枚作る（まとめない・mount を遅らせない）。層のコミットは WHPX で 0.1〜0.4 ms、TCG で 1.6〜1.9 ms で、保存 1 回の Git の手順（約 100 ms）より小さい（ADR-0004）
- **コンパクション（補足 S-6）：** 層の深さが 32 を超えたら、そのコミットの完全なツリーの「写しの層」を作る。キャッシュが空なら写しの層を 1 枚だけ作り、256 枚を超えたら作り直す。履歴は Git に全部あるので、コンパクションの後もすべてのマイクロコミットに戻れる（ADR-0003）
- **操作の形（O-7）：** agent の命令の形 v1（docs/agent-protocol.md）

**結果：** 既存の MicroGit の機能（保存・過去に戻る）を、実際の VS Code の中でカーネル版・Node.js 版の両方で確かめた（src/test/suite/overlayBackend.test.ts）。

**受け入れ基準：** 既存MicroGitの機能テストが、新実装でも同一の結果で通過すること。

### FR-3：ゲストの書き込みはupper layerに閉じ、ホストの検証を経て反映する

**要件：**
- ゲストはワークスペースの実ファイルに直接書き込まない。
- ゲストの変更はすべてupper layerに蓄積される。
- ホスト側のBoundary Guardが差分を検証した後にのみ、実ファイルおよび履歴へ反映する。

**判断理由：**
- VMによる隔離が守るのは「共有範囲の外」だけである。ゲストがワークスペースに直接書ける構成では、ゲスト内のバグや侵害によって、共有範囲内のファイルや履歴が壊されうる。
- upperに閉じる構成であれば、ゲストで何が起きても「反映しない」という選択肢が常に残る。これは安全性とデータ保全の両方を、追加の仕組みなしに実現する。
- この構成は、OverlayFSでやりたいこと（レイヤーによる変更管理）そのものであり、**安全装置のために別の機構を作る必要がない**。

**検討した代替案：**
| 代替案 | 採用しない理由 |
|---|---|
| ワークスペースを読み書き可能で共有 | 実装は単純だが、ゲストの誤動作が即座に実データの破損につながる |
| ゲスト内で書き込みを検証 | 侵害されたゲスト内の検証は無効化されうるため、保証にならない（§7） |

**受け入れ基準：** ゲストを強制終了・異常な差分を返すよう改変した状態でも、ワークスペースの実ファイルと履歴が破損しないこと。

**第 2 版：** ゲストから受け取った一覧と中身は、ホストの Boundary Guard（src/boundaryGuard.ts、docs/boundary-guard.md）で検証してから反映する。中身を全部受け取って検証するまでワークスペースに触らないので、途中でゲストが落ちても半端な状態は残らない。一覧と違う中身が返ってきたら書かない（どちらも単体テストで確認）。履歴（正本）はホストの Git にあり、ゲストは触れない（ADR-0001・ADR-0009）。Linux の VM なしの経路では agent はホストのファイルに触れられるので、ここでの Boundary Guard は隔離の境界ではなく正しさの境界（§7.4、ADR-0008）。

### FR-4：連続セーブに追従する

**要件：** ユーザーが短い間隔で連続してセーブしても、コミットの取りこぼしや順序の逆転が発生しないこと。

**判断理由：** MicroGitの価値は「すべての変更を細かく記録する」ことにある。取りこぼしは価値の喪失に直結する。

**受け入れ基準：** 規定間隔（内部設計で決定）の連続セーブ負荷試験で、全セーブがコミットとして記録され、順序が保存されること。

**永続性の水準（第 2 版、補足 S-8）：** 既定は「電源断や OS の異常終了でも、保存ジョブが終わった記録は失わない」。shadow の Git のばらのオブジェクトと ref を fsync する（`core.fsync=loose-object,reference`、`core.fsyncMethod=batch`）。代償は計測のばらつき程度（保存 1 回 約 100 → 102〜107 ms）。設定 `microgit.durability` を `process` にすると Git の既定に戻る（ADR-0002）。保存は従来どおり列で順に処理し、層の記録も保存ごとに 1 枚（ADR-0004）。

### FR-5：ホストOSに応じてバックエンドを自動選択する

**要件：**

| ホスト | バックエンド |
|---|---|
| Linux | ネイティブOverlayFS（VMを使わない） |
| Apple silicon macOS | OS標準のVirtualization.frameworkによる最小VM（実機確認済み、#17） |
| Windows | OS標準のハイパーバイザAPIによる最小VM（方式は要検証）（第 2 版：同梱の QEMU。WHPX が使えればそれ、使えなければ TCG。通り道は名前付きパイプ。ADR-0006、docs/windows-backend.md） |
| 上記が利用不可 | 現行のNode.js仮想実装（フォールバック） |

**判断理由：**
- **Linuxでは VM が不要。** カーネル5.11以降、ユーザー名前空間の中であれば非特権でOverlayFSをマウントできる。VMを挟む理由（カーネル機能の提供）がそもそも存在しないため、境界コストをゼロにできる。
- **VMはLinux以外のためだけの手段である。** 目的はVMを作ることではなく、カーネル機能を持ち運ぶことにある。
- **フォールバックを残すことで、どの環境でも動く状態を常に維持できる。** 新方式の導入でMicroGitが一部環境で動かなくなる事態を避ける。

**受け入れ基準：** 各バックエンドが自動選択され、利用不可の場合はユーザー操作なしにフォールバックへ切り替わること。

**受け入れ基準（第 2 版で追加、補足 S-3）：** 非特権のユーザー名前空間が使えない環境（Ubuntu 23.10 以降の既定、Dev Containers、Codespaces など）で、自動的に Node.js 版に切り替わること。起動できそうかではなく、agent を起動して小さな層を 1 枚作れるかで判断する（probe）。GitHub Actions の Ubuntu 24.04 で、`unshare: write failed /proc/self/uid_map: Operation not permitted` の理由で 5 ms で切り替わることを CI で毎回確かめている。Dev Containers・Codespaces は未確認。

**実装（第 2 版）：** Backend Selector（src/kernel/backendSelector.ts）。設定 `microgit.overlayBackend`（auto・kernel・nodejs）、docs/kernel-backend.md。

## 6. 非機能要件

### NFR-1：対応環境はVS Code同等とする
**要件：** VS Codeが動作する全環境で動作し、動作要件もVS Codeと同等とする。

**判断理由：** VS Code拡張機能として配布する以上、利用者の期待は「VS Codeが動けば動く」である。追加の前提（WSLのインストール、Docker Desktopの導入等）を要求すると、導入の障壁が上がり、「広く配布する」という目的と矛盾する。

**判断上の含意：** WSL2やDocker Desktopへの依存は採用しない。これらはLinuxカーネルを前提ソフトウェアとして要求するためである。

**第 2 版（補足 S-2）：** Windows のハイパーバイザー API（WHPX）は、「Windows ハイパーバイザー プラットフォーム」が有効な PC でしか使えない（有効にするには管理者権限と再起動が要る）。同梱の QEMU は、WHPX が使えないとき CPU のエミュレーション（TCG）で動き、TCG は仮想化機能も管理者権限も要らない。GitHub の Windows のランナーで TCG だけに固定して、起動 1.8 秒、過去に戻る操作 平均 44 ms（WHPX では 36 ms）で、差分テストはすべて一致した。したがって Windows x64 では、仮想化機能の有無にかかわらず NFR-1 を満たす。Windows on Arm と Intel Mac は対象外で、Node.js 版で動く。

---

### NFR-2：性能
**要件：** 最終目標は、連続セーブに対してメモリ転送と等速。

**判断理由：** 連続セーブへの追従（FR-4）が性能で律速されてはならない。「メモリ転送と等速」は理論的な上限であり、方式選択の指針として置く。

**性能に関する見通し：**
- ゲスト内の処理（OverlayFS操作）自体は軽い。
- 支配的なコストは**ホスト–ゲスト間の境界通過**（ワークスペースをゲストに見せる経路、upperの差分をホストに戻す経路）になると見込む。
- したがって、ファイル共有方式の選定とupperdirの配置（§12）が性能を最も左右する。

**受け入れ基準（段階的）：**
1. Phase 0：Linuxネイティブ実装が現行Node.js実装より高速であること
2. Phase 1以降：メモリコピーをベースラインとした比率を計測し、改善の推移を記録すること（具体的な閾値は初回計測後に設定）

**結果（第 2 版、2026-09-26、scripts/bench-backends.mjs、ファイル 200・保存 40・行き来 30、中央値）：**

| 環境 | 保存 1 回ぶんの層 | 過去に戻る操作 |
|---|---|---|
| Linux（WSL2、VM なし） | Node.js 36.9 ms → カーネル 10.8 ms | Node.js 127.4 ms → カーネル 21.6 ms |
| Windows（QEMU、WHPX） | Node.js 271.0 ms → カーネル 135.0 ms | Node.js 1,425.8 ms → カーネル 169.7 ms |

Phase 0 の受け入れ基準を満たす。見通しにあった「支配的なコストは境界通過」は、Windows の QEMU の stdio の chardev で現実になり（毎秒 13 KB）、名前付きパイプに替えて解消した（ADR-0006）。また、保存 1 回の時間のほとんどは Git のプロセスの起動（約 100 ms）で、OverlayFS ではないことが分かった（ADR-0002・ADR-0004）。メモリコピー比の計測は未実施。

### NFR-3：サイズ
**要件：** 同梱するカーネルとゲストユーザーランドの合計で、一桁MBを目標とする。

**判断理由：**
- 拡張機能として配布する以上、ダウンロードサイズは導入の障壁になる。
- カーネル自体は障壁にならない見込みである。Linuxを最小構成でビルドすると圧縮後1MB前後、アプリ向けに特化したカーネルでも数MB程度（いずれも目安）。**VMの中ではデバイスがvirtioに統一されるため、実機向けのドライバを丸ごと除外できる**ことが、カーネルを小さくできる根本的な理由である。
- むしろサイズを支配するのはゲスト内のランタイムである。Node.jsをゲストに入れると本体だけで数十MBとなり、カーネルより大きくなる。

**判断上の含意：** ゲスト内agentはGoまたはRustの静的バイナリで実装する（AD-5）。

**第 2 版（補足 S-9）：** 目標は **プラットフォーム別の VSIX 1 つあたり** の大きさとする（x64 と arm64 で別のカーネルと agent が要るため）。実測（gzip -9 や zip の大きさ、ダウンロードの大きさに近い）：
- ゲスト（カーネル＋agent）：x86_64 3.55 MB、arm64 2.93 MB
- Windows の QEMU（#18、装置を絞った自前ビルド）：zip で 5.53 MB（配布版は 1.2 GB）
- Windows 用の VSIX の見積もり：約 9.6 MB（実物は #19 で測る）

見通しのとおり、カーネルより agent（Go のランタイム、約 3 MB）が大きい。

**結果（#19、VSIX の実物）：** 5.0.0 で win32-x64 9,444,940 バイト、linux-x64 1,429,604 バイト、linux-arm64 1,303,331 バイト、universal（部品なし）82,916 バイト（CI の run 36250700521。5 つの環境で VS Code の CLI で入れて確かめたもの）。どれも一桁 MB に収まる。10,000,000 バイト以上になると scripts/package-vsix.mjs が警告する（docs/release.md §1）。

### NFR-4：ネットワークを使用しない
**要件：** ゲストはネットワーク機能を持たない。ゲストカーネルからネットワークスタックを除外する。

**第 2 版（補足 S-10、ADR-0010）：** 補足 S-10 は、vsock は TCP/IP を使わないので「ゲストは IP スタックを持たない」に直し、制御チャネル（O-3）の第一候補を vsock にするよう勧めた。実装ではそれより一段強く、**`CONFIG_NET` 自体を無効にした**（ビルドで `CONFIG_NET=y` になったら止める）。制御チャネルは virtio-console の名前付きポートで、ネットワークの仕組みを使わない。下の「判断上の含意」の vsock の心配は、この構成では当たらない。

**判断理由：**
- MicroGitの用途（ローカルのファイル履歴管理）にネットワークは不要。
- 除外することで、**攻撃面・サイズ・保守要件が同時に下がる**。リモートから直接攻撃される経路が消え、ネットワーク関連のカーネル脆弱性の多くが無関係になる。
- 同梱カーネルのセキュリティ更新頻度を下げられるため、個人開発での保守負担（C-4）に適合する。

**判断上の含意：** ネットワーク系の設定に依存するホスト–ゲスト通信手段（vsock等）が使えない可能性があるため、制御チャネルは別経路（virtio-console等）を候補とする（要確認、§12）。

---

### NFR-5：互換性
**要件：** 現行のNode.js仮想OverlayFS実装を、フォールバックとして維持する。

**判断理由：** 新方式の成熟には時間がかかる。既存ユーザーの環境で動かなくなることは、知名度を上げるという目的に対して最も大きな損失である。

**第 2 版（補足 S-4）：** フォールバックの Node.js 版に求める「同じ挙動」の範囲は FR-1 の第 2 版のとおり（ワークスペースへの反映の結果が同じ）。ゴールデンテストとの違いは既知の食い違いの一覧（test/golden/overlayfs/node-known-diffs.txt）で管理し、一覧に無い違いが出たら CI が落ちる。差分テストでは、Node.js 版の不具合（N-3〜N-7）が見つかり、直した（CHANGELOG）。

---

### NFR-6：保守性
**要件：**
- ホスト側のBoundary Guardは小さく保ち、単独でテスト・監査可能な構成とする。
- ゲストのイメージは再現可能な手順でビルドできること（カーネル設定・ビルドスクリプトをリポジトリで管理）。

**判断理由：** ホスト側がTCBになる（§7）ため、その正しさの確認コストを下げることが安全性に直結する。再現可能なビルドは、GPL対応（NFR-7）と配布経路の完全性（§7）の両方の前提でもある。

**結果（第 2 版、#15・#16）：** Boundary Guard は VS Code に依存しない 1 つのモジュールで、単体テスト 21 件。ゲストは x64 と arm64 の両方で、別の出力先への 2 回のビルドが 1 バイトも違わないことを CI で毎回確かめている（カーネルのソースは sha256、Go は 1.27.1 に固定。gcc の版は未固定、docs/learning/05-reproducible-builds.md）。

---

### NFR-7：配布とライセンス
**要件：**
- 無償で配布する。
- 自作コードのライセンスは、他アプリへの組み込み障壁が低いもの（Apache-2.0またはMIT）を推奨とする（最終決定は§12）。
- 同梱するLinuxカーネルについては、GPLv2に従いソースコードとカーネル設定を公開する。
- OverlayFS部品は、MicroGitから独立したリポジトリとして公開することを目指す。
- （第 2 版）GPL の部品は Linux カーネルと QEMU。どちらもソースの tarball の sha256 と、使った設定・ビルド手順をリポジトリで管理し、配布のときにソースを一緒に提供する（#19）。x64 と arm64 の両方が対象（補足 S-9）

**判断理由：**
- 最終目標が「任意のアプリに詰め込める部品」である以上、利用者が増えるほど価値が上がる。緩いライセンスは組み込みの障壁を下げる。
- 無償配布であってもGPLv2のソース提供義務は免除されない。公開リポジトリで管理すれば、義務の履行と再現可能なビルド（NFR-6）を同時に満たせる。
- 独立リポジトリにすることで、「MicroGitの一機能」ではなく「誰でも使える部品」として認知される。

## 7. セキュリティ要件

### 7.1 脅威モデル

| 項目 | 内容 |
|---|---|
| 守る対象 | ユーザーのワークスペース外のファイル、ワークスペース内の実ファイル、MicroGitの履歴 |
| 想定する入力源 | ワークスペース内のファイル（インターネットから取得したリポジトリを含む） |
| 想定する攻撃 | 細工されたファイル名、シンボリックリンク、巨大ファイル等によるゲストの誤動作・侵害 |
| 想定しない攻撃 | ネットワーク経由の攻撃（ネットワークを持たないため）、ホストOS自体の侵害 |

### 7.2 要件

**SR-1：ゲストは信頼しない。** ゲスト内には検査機構を置かず、小さく正しく動くことに専念させる。

> **判断理由：** 侵害されたゲスト内の検査は攻撃者に無効化されうる。ゲスト内の検査は「ゲストが信頼できる間しか効かない」という前提から逃れられないため、保証の根拠にならない。隔離設計の定石として、検査は信頼できる側（ホスト）に置く。

**SR-2：検査はホスト側のBoundary Guardに集約する。**
- 共有範囲をワークスペースに限定する
- シンボリックリンクはホスト側で解決し、範囲外を指すものは拒否する
- ゲストからの要求の形式・サイズを検証する
- 差分の反映はFR-3に従い、検証後にのみ行う
- （第 2 版、補足 S-4・O-14）ホストの FS で表せない変更は、変換せずに弾いて利用者に知らせる。Windows と macOS の大文字小文字の違いだけの名前の衝突、Windows で使えない名前（`CON`、末尾の点や空白など）と文字、`.git` の中を指すパス、ファイルとディレクトリの取り違えなど（docs/boundary-guard.md）
- （第 2 版）シンボリックリンクはゲストから受け取らない（`unsupported-type` で弾く。MicroGit が記録するのは VS Code で保存したテキスト文書だけで、リンクが層に入る経路は今は無い。docs/overlayfs-golden-test.md）

> **判断理由：** 境界インターフェースを少数の単純な操作に絞ることで、検証範囲が小さくなり、テスト・監査が現実的になる。「ゲストは太っていても信頼しない、ホスト側は細く確実に」という分担とする。

**SR-3：ユーザーのOSやセキュリティソフトの存在は前提にしない。**

> **判断理由：** 環境ごとに有無・挙動が異なるため、設計上の保証にならない。

**SR-4：配布イメージの完全性を保証する。** ゲストイメージに署名し、ホスト側で起動前に検証する。更新経路も同様とする。

> **Marketplace の署名（#19 で確認）：** Marketplace は公開のときにすべての拡張機能に署名し、VS Code はインストールのときにその署名を確かめる（設定 `extensions.verifySignature`）。確かめるのはインストールのときだけで、入ったあとのファイルは、拡張機能の JavaScript と同じく確かめ直さない。

> **適用範囲（第 2 版、補足 S-11）：** ゲストのイメージを VSIX に同梱して配る場合、イメージを書き換えられる攻撃者は拡張機能の JavaScript も書き換えられるので、起動前にイメージの署名を確かめても上乗せの防御はほとんど無い。同梱配布では Marketplace の VSIX の署名検証に頼る。イメージを VSIX とは別の経路で配布・更新するときだけ、イメージの署名を検証する（今はその経路は無い）。

> **判断理由：** ネットワークを持たない構成では、ゲストカーネルの保守要件が緩和される代わりに、責任は「境界の設計」と「イメージの配布経路」に集中する。広く配布するほど配布経路は攻撃対象として魅力的になるため、知名度が上がる前に確立する。

### 7.3 緩和されるもの・されないもの

| 項目 | 緩和 | 理由 |
|---|---|---|
| ゲストカーネルの更新頻度 | される | ネットワークがなく、侵害されてもVM内に閉じる |
| ゲスト内の検査機構 | 不要 | SR-1 |
| 境界の設計と実装品質 | されない（重要度が上がる） | TCBになる |
| 配布経路の完全性 | されない（重要度が上がる） | SR-4 |
| ゲストの正しさ（データを壊さない） | されない | FR-3で被害は限定されるが、機能として正しく動く必要は残る |

### 7.4 Linux の VM なしの経路の脅威モデル（第 2 版で追加、補足 S-3、ADR-0008）

§7.1〜7.3 は仮想マシンの経路を想定している。Linux の VM なしの経路では、前提が次のように変わる。

| 項目 | 仮想マシンの経路 | Linux の VM なしの経路 |
|---|---|---|
| 細工されたファイルが届く先 | ゲストのカーネル（侵害されても VM の中） | **ホストのカーネル**の OverlayFS（ユーザー名前空間と OverlayFS を組み合わせた権限昇格の実例がある。CVE-2023-0386 など） |
| agent が触れる範囲 | ゲストの中だけ | 利用者と同じ権限で、ホストのファイル全部（mount 名前空間は見え方を分けるだけ） |
| Boundary Guard の意味 | 隔離の境界 | 正しさの境界（agent は自前のコードで、層の置き場所の外には書かない） |
| 「ゲストカーネルの更新頻度」の緩和 | される | 関係ない。ホストのカーネルの更新は OS（利用者）の責任 |

心配な利用者は `microgit.overlayBackend` を `nodejs` にできる。Ubuntu 23.10 以降の既定のように非特権のユーザー名前空間が止められていれば、この経路はそもそも使われない（FR-5）。

### 7.5 Windows で TCG（CPU のエミュレーション）で動くときの境界（#19 で追加）

QEMU のセキュリティの方針では、TCG で動かす使い方は「仮想化の使い方ではない」とされ、TCG の不具合はセキュリティの不具合として扱われない（ゲストの隔離を当てにしてはいけない）。WHPX が無効な PC で TCG に切り替わると（NFR-1 の第 2 版）、§7.3 の「ゲストカーネルの更新頻度」が緩められる理由（侵害されても VM 内に閉じる）が弱まる。

| 項目 | WHPX | TCG |
|---|---|---|
| ゲストの隔離 | ハードウェアの仮想化（QEMU のセキュリティの対象） | 当てにできない（QEMU のセキュリティの対象外） |
| ゲストに届くもの | どちらも、ワークスペースのファイルの名前と中身だけ。ゲストの OverlayFS は中身を解釈しない |  |
| ホストのファイルへの反映 | どちらも Boundary Guard が検証してから（ADR-0009） |  |

心配な利用者は `microgit.kernel.accel` を `whpx` にする（WHPX が使えなければ Node.js 版になる）か、`microgit.overlayBackend` を `nodejs` にする（docs/release.md §7）。

## 8. アーキテクチャ上の決定

### AD-1：汎用Linux VMではなく、機能単位の部品として提供する
- **決定：** 提供するのはOverlayFSという単一のカーネル機能であり、Linux環境全体ではない。
- **理由：** 提供範囲を絞ることで、ゲストを極限まで削れる（NFR-3）。アプリのライブラリとして同梱・配布できる。既存のWSL2、Lima、Apple Containerization、libkrun等はいずれもLinux環境全体を提供するものであり、この点が明確な差分となる。
- **代替案：** 汎用の軽量Linux VMを同梱する → 実装は容易だが、ゲストを削れず、既存ソリューションとの差分がなくなる。
- **差分の再定義（第 2 版、補足 S-1）：** LKL と libkrun は「アプリに埋め込む部品」として提供されており、「既存の解決策はどれも Linux 環境全体を提供する」は成り立たない。本件の差分は「1 つの機能だけを、仮想マシンの境界の向こうに置き、ホストが検証する」こと（ADR-0007）

### AD-2：LinuxホストではVMを使わない
- **決定：** Linuxでは非特権のネイティブOverlayFSを使う。
- **理由：** FR-5参照。VMの存在理由（カーネル機能の提供）がLinuxにはない。
- **第 2 版（補足 S-3、ADR-0008）：** 前提が 2 つ崩れる。(1) Ubuntu 23.10 以降の既定などで非特権のユーザー名前空間が止められていて、動かない環境が多い → 自動で Node.js 版に切り替える（FR-5 の第 2 版）。(2) 細工されたファイルがホストのカーネルに届く → 仮想マシンの経路とは別の脅威モデルを §7.4 に書いた。決定そのものは変えない

### AD-3：各OSネイティブ機能での近似ではなく、本物のOverlayFSを使う
- **決定：** Linux以外でもVM内の本物のOverlayFSを使う。
- **理由：** FR-1参照。挙動の一貫性を優先する。
- **トレードオフ：** 境界通過コストを受け入れる。
- **代替案（第 2 版、補足 S-1）：** LKL によるプロセス内実行 → FR-1 の代替案の表を参照（保留、O-9）

### AD-4：ゲストは信頼せず、検査はホストに集約する
- **決定：** §7参照。

### AD-5：ゲスト内agentはGoまたはRustの静的バイナリで実装する
- **決定：** ゲスト内のランタイムを持たない静的バイナリとする。
- **理由：** Node.jsをゲストに入れるとサイズの大部分を占める（NFR-3）。静的バイナリであれば共有ライブラリも不要となり、ゲストのユーザーランドをinitとagentだけにできる。
- **GoとRustの選定：** 内部設計で決定する。観点はバイナリサイズ、低レベルのシステムコール操作のしやすさ、クロスコンパイルの容易さ。
- **決定（第 2 版、#13）：** Go。init を兼ねる 1 つの静的バイナリで、Linux の VM なしの経路にも同じバイナリを使う。ビルドに使う Go は 1.27.1 に固定（ADR-0011）

### AD-6：ゲストはネットワークを持たない
- **決定：** NFR-4参照。

### AD-7：最小ゲストの構成
- **決定：**
  - カーネル：virtioデバイスのみ、ネットワーク無効、OverlayFS有効の専用構成
  - ユーザーランド：最小initとagentのみ。シェル等は含めない
- **理由：** VM内で必要な処理はOverlayFSとその操作だけである。シェルを含めないことで、侵害時に攻撃者が使える道具も減る。

## 9. 先行研究・既存技術との関係

| 分野 | 代表例 | 本件との関係 |
|---|---|---|
| Container debloating | Cimplifier、SlimToolkit、Confine、BAFFS | すべてLinuxカーネルを前提とし、ユーザーランドのみを削減する。動的解析による欠落が既知の課題。本件は「必要な機能を宣言的に組み立てる」方向で回避する |

| カーネルのライブラリ化（第 2 版で追加、補足 S-1） | LKL（Linux Kernel Library）、User-mode Linux | カーネルをホストのプロセスの中で動かす。本件と同じく「アプリに埋め込む」形。LKL は Windows で仮想化機能が要らない点が魅力だが、保守状況が不明で保留（O-9、ADR-0007） |

## 10. フェーズ計画と受け入れ

| Phase | 内容 | 受け入れ条件 | この順序にする理由 |
|---|---|---|---|
| 0 | Linuxネイティブ実装で境界インターフェースを確定し、現行実装と比較 | 既存テスト通過、性能比較の取得 | VMなしで検証できるため、インターフェース設計の誤りを最も安く発見できる |
| 0（第 2 版） | **最初の成果物は、本物のカーネルの挙動を記録したゴールデンテスト**（補足 S-13）。以降の全バックエンドの受け入れ基準をこれにそろえる | 済み（#10） | 「同一テスト」が未定義のままでは、FR-1・FR-2・NFR-5 の受け入れ基準が決まらない |
| 1 | 最小カーネル＋agentを作成し、macOSバックエンドで起動 | 起動時間・サイズ・スループットの計測 | macOSはOS標準APIでvirtio-fs等の共有機構が提供されており、VM方式の検証を始めやすい |
| 2 | Windowsバックエンドの方式確定・実装 | 3 OSで同一テスト通過 | 最大の不確定要素であり、Phase 0・1の知見を得てから着手する |

## 11. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| Windowsで実用的なVMM・ファイル共有が実現できない | 対応環境要件（NFR-1）を満たせない | Phase 2まで判断を遅らせる。フォールバック（NFR-5）で動作は維持する |
| 境界通過コストが性能目標を大きく下回る | NFR-2未達 | upperdirの配置と共有方式を複数案で計測。最悪の場合、AD-3の再検討材料とする |
| ゲストの最小化で必要な機能を削りすぎる | 特定操作で誤動作 | 3 OS共通のテストスイートを常時実行。削る対象は宣言的に管理する |
| 同梱カーネルの脆弱性対応が滞る | 配布物の信頼性低下 | ネットワーク除外で対象を限定。再現可能なビルドで更新コストを下げる |
| GPL対応の不備 | 配布継続が困難になる | カーネルソース・設定を公開リポジトリで管理 |
| （第 2 版、補足 S-2）Windows VM バックエンドを実現しても、仮想化が無効な既定環境ではフォールバックになる | 恩恵を受ける利用者が少ない | **解消**：同梱の QEMU は TCG でも動く（NFR-1 の第 2 版） |
| （第 2 版、補足 S-3）Ubuntu 23.10 以降や Dev Containers 等で Linux ネイティブが動作しない | Linux でもフォールバックの比率が高くなる | 自動フォールバックを受け入れ基準に含め、CI で確認（FR-5）。仮想マシンの経路を Linux でも選べるようにするかは今後 |
| （第 2 版、補足 S-3）Linux ネイティブ経路でホストカーネルの攻撃面が増える | ゲスト隔離を前提とした安全性の主張が Linux では成り立たない | §7.4 に別の脅威モデルとして書いた。設定で nodejs を選べる |
| （第 2 版、補足 S-6）積層上限への到達 | 長期利用で動作不能になる | **解消**：コンパクション（ADR-0003） |
| （第 2 版）ホストとゲストの通り道の実装差（Windows 版 QEMU の stdio が遅く、大きなデータで壊れた） | 性能と正しさ | **解消**：名前付きパイプ（ADR-0006）。実際の大きさのファイルを流す差分テストを CI に入れた |
| （第 2 版）道具の不具合（Windows 版 Node 25.1.0 の fs.rmSync が、ASCII 以外の名前のディレクトリの再帰削除で落ちる） | VS Code の Node が上がったときに、キャッシュの削除で拡張機能が落ちうる | 自前の removeTree（#21）。VS Code 1.139.1 の Node は 24.20.0 で、この不具合は無い |
| （第 2 版）同梱する部品（QEMU、glib などの DLL）のライセンス対応 | 配布を続けられなくなる | #19：THIRD_PARTY_NOTICES.md、VSIX にライセンスの文書、DLL の出どころとソース RPM をビルドのときに記録、リリースごとにソース一式を GitHub Release に置く |
| （#19）Windows の Smart App Control が、署名の無い同梱の QEMU を止める | その PC ではカーネル版が使えない（Node.js 版に切り替わるので機能は失われない） | 起動後に agent の応答を待つので、止められれば切り替わる。避けるにはコード署名（利用者の判断、docs/release.md §6） |
| （#19）TCG で動くときは、ゲストの隔離を当てにできない | §7.3 の緩和の理由が弱まる | §7.5。設定で WHPX だけ、または Node.js 版にできる |
