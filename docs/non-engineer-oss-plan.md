「OSS」という語は、製品説明としての明記が現行の配布文書には見つかっていない（`docs/release.md` は VS Code Marketplace と Open VSX の VSIX を配る、と書いている）。ソースのライセンス本文は MIT である（`LICENCE.md` の 1 行目）。配っている VSIX には GPL・LGPL の部品が入る。`docs/release.md` 114 行目は、GitHub Release `v5.0.0` を、GPL・LGPL の部品のソースを同時に取れるようにするために公開した、と書いている。同 142 行目は、GPL / LGPL のソースを各 GitHub Release に置く、と書いている。製品全体が MIT だけ、ではない。この計画の「OSS として展開する」は、MIT のソースを、Git と VS Code を前提にしない利用者へ届ける、という意味に限る。ライセンスの変更や、新しい配布先の決定は含まない。

## 1. 状況と目的

2026-10-18 時点の決定である。コードはまだ無い。

依頼の言葉はデータであり、仕様の全文ではない。「ファイルそのものの中にメタデータとしてバージョン管理を埋め込むか、1 つファイルを作り、そこにすべてのファイルを詰め込む」。この二案を、下の四つの置き場に分けて比べた。混ぜて一つの案にしない。

依頼の「すべてのファイルを 1 ファイルに詰める」は置き場 B である。B はライブの正本として却下したままである（§6.3）。置き場 D は、この第二案の充足ではない。D は履歴ストアの安全な複製であり、作業中のファイルは入らない。

目的は、非エンジニアが普通のアプリ（メモ、表計算、画像、PDF、テキスト）でファイルを開き、保存する作業を崩さずに、フォルダ単位のタイムトラベルを残すことである。Git も VS Code も、その利用者の前提にしない。

採用するのは次の二つを同時に使う形である。役割は別である。

- **ライブの正本**は、置き場 C。作業ツリーは普通のファイルのまま、履歴だけを作業ツリーの外の SQLite に置く（Fossil では、concepts.wiki の §2.0 の文 "A repository in Fossil is a single file on your disk." と、作業ツリーが普通の階層であること、に近い。出典の切り分けは §4.1）。
- **持ち出し**は、置き場 D。Backup API または `VACUUM INTO` で作る、一時点の複製だけを 1 ファイルにする。ライブの書き込み中の正本にはしない。

置き場 A（各ファイルへ埋める）と置き場 B（作業ファイルごと 1 ファイルに詰めてライブの正本にする）は却下する。理由は §6。

## 2. 非エンジニアの作業と、この計画が引き受けないこと

リポジトリに「非エンジニア」という語の直接の記述は無い。近い決定は、Word などの文書を使う人向けの版でも戻す単位はフォルダである、というもの（[design-policy.md](./design-policy.md) §2.3、2026-10-05）と、「ソフト制作者以外へ広げるときも、タイムトラベルの意味を変えない」という一文である。この計画はその二人称を、次の作業として引き受ける。

利用者がやること:

1. フォルダの中のファイルを、普段のアプリで開く。
2. 編集して、そのアプリの保存をする。
3. あとから「あの時点のフォルダに戻す」。

この計画が引き受けること:

- 保存のきっかけは、VS Code の保存イベントではなく、フォルダを見る別プロセスである。アプリがディスクへ書き、書き込みが落ち着いたら、その時点のフォルダのツリーを 1 件記録する。
- 記録の前後で、利用者のファイルのバイト列は変えない。
- `.git` が無いフォルダでも記録する。Git の実行ファイルを起動しない。

この計画が引き受けないこと:

- 非エンジニアの範囲をアンケートやペルソナで確定すること。語の定義がリポジトリに無いので、上の作業以外へ対象を広げない。
- Word、LibreOffice、表計算、画像、PDF の保存手順を、それぞれの仕様として再現すること。実アプリが一時ファイルをどう置くかは、§4 の未確認に入れる。段階 1 が確かめるのは、テストが注入する「一時ファイルへ書いてからリネーム」までである。
- クラウドの版履歴（Dropbox、OneDrive、Office）の置き換え。それらがファイルの中かサーバ上かは未確認である。
- ファイル 1 つだけを戻すことを既定にすること。部分的に取り込む操作は、エンジニア版でも将来の明示操作（Cherry-pick）であり、この計画の段階には入れない。
- VS Code 拡張、shadow の Git、`refs/microgit` の置き換え。Issue #8 を止めること。
- 利用者の通常 Git への自動コミット（[design-policy.md](./design-policy.md) の §2。エンジニア版と同じ禁止）。
- `skills/use-microgit` の変更。あのスキルは「エディタの保存で記録される」前提で、履歴がファイルの中にあることには依存していない。非エンジニア版の記録は監視プロセスが見た変更であり、別経路である。
- 新しい GUI、新しいライセンス、Marketplace 以外の配布先。配布先は §10 の未決である。
- Office の COM アドイン。[design-policy.md](./design-policy.md) §2.3 の未決は、この計画では解消しない。

## 3. 四つの置き場の定義

同じ「1 ファイル」という言葉でも、中に何があるかで別物である。実装も文書も、この四つの名前で呼び分ける。

### 置き場 A: 各ファイルの中に埋める

利用者が開くファイルのバイト列の中に、履歴や版の印を書く。保存のたびに、そのファイルを書き換えて注入する。PDF の末尾追記、JPEG の Exif、文書の見出しの下の履歴リスト、`$Id$` の展開は、すべてこちらに属する。

作業ツリーの外のデータベースは、置き場 A ではない。

### 置き場 B: 作業ファイルごと含めて 1 ファイルに詰める（ライブ形式）

メモ、表、画像、PDF の実体が、常時 1 つのコンテナの中にだけある。普通のアプリは、そのコンテナを直接開いて保存する、という形がライブの正本になる。ZIP に部品を入れる、SQLite の `files` 表に作業中の実体だけを入れる、がこちらである。

履歴だけのデータベースは、置き場 B ではない。持ち出し用に固めた複製も、置き場 B ではない。

### 置き場 C: 履歴だけを 1 ファイルにする

作業ツリーは、今までどおり普通のファイルの階層である。アプリが開くのはそのファイルである。履歴の正本だけが、作業ツリーの外にある 1 つの SQLite ファイルである。Fossil がリポジトリを単一ファイルにし、作業ツリーを別に持つ形に近い。

落ち着いたあとの正本は、その SQLite ファイル 1 つである。トランザクションの途中には、回復用のジャーナルが隣に出る。WAL を選んだ場合は `-wal` と `-shm` が付く。この付随ファイルは置き場 C の既知の制限であり、置き場 B や置き場 D に吸収して呼んではならない。段階 1 は WAL を使わず、SQLite の既定であるロールバックジャーナルにする。理由は §7。

### 置き場 D: 持ち出し用に 1 ファイルへ固める

ライブの書き込み先とは別の、一時点の複製である。中身は履歴ストアの一貫したコピーであり、作業中のファイルは入らない。作業ツリーをこのファイルだけに移すのではない。依頼の「すべてのファイルを 1 ファイルに詰める」の充足ではない（それは置き場 B）。作る手段は SQLite の Backup API か `VACUUM INTO` に限る。利用者がライブの DB ファイルをコピーすることは、置き場 D ではない。複製には、その時点までの履歴が入るので、秘密が残りうる（§10）。フォルダと履歴を一つの ZIP に固めた配布用アーカイブは、置き場 D ではない。ライブ形式でもない（§6.4）。

置き場 D を、監視プロセスが書き込む正本にしてはならない。

```
[普通のアプリ] --保存--> [監視フォルダの普通のファイル]     ← 作業ツリー。置き場 B にしない
                                |
                           監視プロセス（落ち着いたら 1 件）
                                |
                                v
                      [フォルダの外の SQLite]               ← 置き場 C。ライブの正本
                                |
                 Backup API または VACUUM INTO（書き込みの正本ではない）
                                |
                                v
                      [持ち出し用の 1 ファイル]             ← 置き場 D
```

## 4. 先行事例から言える制約

数値や、開いていない仕様の本文は、ここから足さない。

### 4.1 この文書を書くときに開いたもの

Fossil（2-clause BSD。https://fossil-scm.org/home/doc/trunk/www/index.wiki の第 8 項）:

- index.wiki の第 7 項は、内容を SQLite に置き、停電やクラッシュでもトランザクションが原子的である、と書いている。単一ファイルとは書いていない。第 3 項は実行ファイルが単体である話であり、リポジトリの話ではない。
- 「A repository in Fossil is a single file on your disk.」は、https://fossil-scm.org/home/doc/trunk/www/concepts.wiki の §2.0 の文である。リポジトリがディスク上の単一ファイルである、という記述はこちらに付ける。この改訂では、その文を超えて引用しない。
- 作業ツリー（source tree）は普通のファイル階層で、リポジトリとは別である。根の `_FOSSIL_`（または `.fslckout`）がリポジトリのパスを指す。リポジトリ側は作業ツリーの一覧を持たない（同 concepts.wiki の §2.0。初稿で開いた範囲として残す。上の一文の外側を、この改訂で引き写してはいない）。
- ディスク上の中身は、現行実装では delta と zlib で圧縮した blob を SQLite に入れる。fileformat.wiki は、これは実装の詳細であり、将来変わりうる、と書いている。耐久させると宣言しているのは artifact の形式の方である（https://fossil-scm.org/home/doc/trunk/www/fileformat.wiki の §2.0 の前置き）。この計画は Fossil のカード形式も delta 圧縮も採用しない。分けるのは「作業ツリーと、履歴の単一ファイル」だけである。
- 同期は、artifact のハッシュのリストを交換し、足りない中身だけを送る（https://fossil-scm.org/home/doc/trunk/www/sync.wiki の §1.0）。この計画の段階 1〜3 は同期を作らない。

Git bundle（https://git-scm.com/docs/git-bundle）:

- bundle は refs と、そこから届くオブジェクトの pack である。作業ツリー、index、stash、リポジトリ設定、hooks は含まれない。例の全文バックアップも「refs と、そこから届くコミットだけ」と書いている。
- bundle への push は無い。
- リポジトリを素朴に `cp -r` すると、書き込み中のコピーが壊れうる、と DISCUSSION が書いている。

SQLite をアプリのファイル形式にすること（https://www.sqlite.org/appfileformat.html）:

- ファイル群は `CREATE TABLE files(filename TEXT PRIMARY KEY, content BLOB)` で 1 つの DB に入れられる、と例示している。
- `grep` や `awk` では中を搜せない、と書いている（SQL の方が手段になる、という文脈）。
- ZIP のような包んだファイルの山は、部品を 1 つ変えるとき、通常ファイル全体を書き直す、と書いている。SQLite は変わったページだけを書く、とも書いている。
- トランザクションは、システムのクラッシュや停電でも、完全に起きるか全く起きないかである、と §3 の第 6 項が書いている。同じページのセキュリティ節は、信用できない DB ファイルを開く攻撃があり、防御の文書を読むよう求めている。
- この執筆で開いた appfileformat.html には、パブリックドメインというライセンス文は無かった。依頼時の確認はパブリックドメインである。依存や同梱を足す段階で、使うファイルのライセンス文をその場で確認する。この計画は確認前にライセンスを断定しない。

WAL（https://www.sqlite.org/wal.html の §1）:

- 原子的なコミットの既定はロールバックジャーナルである。WAL は 3.7.0（2010-07-21）以降の選択肢である。
- WAL には `-wal` と `-shm` が付く。アプリのファイル形式としては魅力が下がる、と欠点の 6 に書いている。
- WAL はネットワークファイルシステムでは動かない（欠点の 1。プロセス間で少量のメモリを共有するため）。
- ロールバックジャーナルでは、COMMIT はジャーナルファイルを消すことである（§2）。

壊し方（https://www.sqlite.org/howtocorrupt.html）:

- アプリのクラッシュ、OS のクラッシュ、停電がトランザクションの途中で起きても、次に開いたときに部分的なトランザクションは自動で巻き戻る、と概要が書いている。同時に、免疫ではない、とも書いている。
- トランザクションの途中のバックアップコピーは、古い内容と新しい内容が混ざって壊れうる（§1.2）。
- 直前の書き込みトランザクションが失敗したあとにコピーするなら、`-journal` または `-wal` をデータベースファイルと一緒にコピーする（§1.2）。ジャーナルを別の DB と取り違える、ジャーナル無しで DB だけコピーする、は壊れうる（§1.4）。
- 落ち着いた状態ではジャーナルファイルは無く、意味を持つのはデータベースファイルだけである（§1.4）。
- 安全な複製として、同 §1.2 が sqlite3_rsync、`VACUUM INTO`、Backup API の三つを挙げている。
- `PRAGMA synchronous=OFF` や `journal_mode=OFF` / `MEMORY` は、クラッシュや停電で壊しうる（§7）。既定の synchronous は FULL であり、最大の信頼性のためには FULL のままにせよ、と §3.2 が書いている。
- 民生用のディスクは sync を偽ることがある。停電で、コミット済みのトランザクションが失われる、または壊れる、と §3.1 が書いている。WAL の方が sync の失敗に寛容、とも書いている。この寛容さは、段階 1 で WAL を採用する理由にはしない。付随ファイルとネットワークファイルシステムの欠点の方が、非エンジニアの「1 ファイルを持ち歩く」誤解に近いためである。
- この執筆で開いた howtocorrupt.html と backup.html に、「通常の rsync」という語は無かった。依頼時の「通常の rsync は壊れたコピーを作りうる」は、上の「素のコピー」と「ジャーナル無しのコピー」としてこの計画に取り込む。rsync というコマンド自体の挙動は、開いたページからは断定しない。

Backup API（https://www.sqlite.org/backup.html）:

- 完了すると、コピー開始時点のソースとビット単位で同じスナップショットが宛先にできる、と §1 が書いている。
- ファイルコピーの途中で停電や OS の障害が起きると、そのバックアップは壊れていることがある、とも書いている。
- §1.1 は、同じ目的のより新しい手段として `VACUUM INTO` と sqlite3_rsync を挙げている。

### 4.2 依頼時に確認済みで、この執筆ではページを開き直していないもの

引用は依頼時の範囲を超えない。

- PDF の incremental update は、ファイル末尾への追記で、小さな変更を全体の書き直し無しに入れられる（Wikipedia の PDF。ISO 32000 の §7.5.6 の本文は未取得）。PDF のコメントは、編集アプリが必ず保持するとは限らない（PDF 32000 の §7.2.3）。
- JPEG の Exif は 64kB の制限があり、ほとんどの画像エディタは保存時に Exif を損なうか消す（https://en.wikipedia.org/wiki/Exif 。二次情報）。非標準の拡張も再保存で失われやすい。
- PNG は、編集ツールに補助情報を可能なら保持するよう求める（https://www.w3.org/TR/PNG/ の “wherever possible”）。必ず保持、ではない。
- Apple の NSFileVersion は、version store から版を削除する API である。履歴がファイル本体の中にある、とは書かれていない（https://developer.apple.com/tutorials/data/documentation/foundation/nsfileversion.json）。
- RCS はチェックインすると本文が `,v` ファイルに置き換わる。履歴本体はファイルの外である。キーワード展開は checkout のときに本文を書き換える（man co）。履歴は利用者が編集できる（Wikipedia の RCS）。
- Git の ident は、checkout のときに `$Id$` を書き換える（https://git-scm.com/docs/gitattributes）。MicroGit の shadow はこれを止めている。
- Org-mode は、見出しの直下に履歴リストを挿入する。本文と混ざる。
- Google ドキュメントの改訂は統合されることがあり、スプレッドシートを古い版に戻すとセル単位の履歴が消える（https://support.google.com/docs/answer/190843）。履歴がファイルの中かサーバ上かは、この出典には無い。

### 4.3 未確認（この計画の採用理由に使わない）

- Word と LibreOffice が、未知の OOXML パーツを保存時に保持するか。
- ODF の変更履歴仕様の一次情報。Wikipedia は「仕様が限定的」とする、という二次情報がある、と依頼時に分かっている。一次情報は未確認。
- Dropbox、OneDrive、Office の版履歴が、ファイルの中かサーバ上か。
- PDF の §7.5.6 の本文。
- クラウド同期がファイルを正規化して、埋め込みを落とす一次情報。
- クラウド同期フォルダが、SQLite の言うネットワークファイルシステムに当たるか。
- Fossil が WAL とロールバックジャーナルのどちらでリポジトリを開いているか。index.wiki は原子性を主張しているが、ジャーナルモードは開いたページには無かった。
- Office が保存時に使う一時ファイルの名前。段階 1 は特定の製品の名前に依存しない。

## 5. 現行の不変条件との衝突

この計画は、エンジニア版の不変条件を緩めて解決しない。衝突するものは、非エンジニア版の側の形を変えて避ける。

| 現行 | 場所 | この計画での扱い |
|---|---|---|
| 正本は shadow の Git。層は作り直せるキャッシュ | [ADR-0001](./adr/0001-source-of-truth.md) の決定（21 行目） | エンジニア版では維持する。非エンジニア版の正本は別の SQLite であり、ADR-0001 を覆す ADR は書かない |
| 記録単位は保存イベント。通常 Git へは自動コミットしない | [design-policy.md](./design-policy.md) 23 行目 | 非エンジニア版も、利用者の Git にコミットしない。きっかけだけがフォルダ監視になる |
| タイムトラベルは、その時点のツリー全体 | 同 24 行目、31〜34 行目 | 守る。既定の戻す単位はフォルダ |
| 文書ファイルだけ記録してそれだけ戻す案は却下。ソフト制作者以外でも意味を変えない | 同 50〜59 行目 | 守る。置き場 A を却下する理由の一つ |

## 6. 比較と採否

戻す単位はフォルダのままにする。性能や、1 ファイルでメールできることと、天秤にかけない（[design-policy.md](./design-policy.md) §2.3 の「天秤にかけない」と同じ理由）。フォルダの中の他のファイルが、その時点の組み合わせから外れるからである。

Google のスプレッドシートの例は、履歴の置き場の証拠には使わない（ファイル内かサーバかが出典に無い）。使うのは、「古い版へ戻すと、より細かい履歴が消えることがある」という操作の注意だけである。この計画の戻す操作は、その時点のファイルのバイト列へフォルダを戻す。セル単位の履歴を `.xlsx` の中に作る、とは約束しない。

### 6.1 トレードオフ

| 観点 | A 各ファイルに埋める | B 作業ファイルごと 1 ファイル（ライブ） | C 履歴だけ 1 ファイル | D 持ち出しの 1 ファイル |
|---|---|---|---|---|
| 普通のアプリで開いて保存できるか | 形式ごとの運次第。保持は保証されない（§4.2） | コンテナを直接開けない。中の部品を文書アプリが編集できる、という出典は無い | 作業ツリーは普通のファイルのまま | 複製はアプリの編集対象ではない。戻してから開く |
| 戻す単位をフォルダにできるか | ファイルごとの履歴になり、組み合わせが外れる | コンテナ 1 つが単位になり、フォルダの階層が消える | スナップショットがフォルダのツリーを持つ | ライブと同じツリーを、その時点の分だけ持つ |
| 保存のたびに利用者のファイルを書き換えるか | 書き換える | 利用者のファイルはコンテナの中にしか無い | 書き換えない。コピーを履歴へ足すだけ | ライブのファイルは触らない |
| Git が要るか | 要らない | 要らない | 要らない | 要らない（git bundle にはしない） |
| 素のファイルコピーは安全か | ファイル自体のコピーは、そのファイルの問題になる | 書き込み中の全体コピーは、ZIP の書き直しと重なる | 落ち着いていれば DB 1 つ。途中やジャーナル欠落は壊れうる（§4.1） | Backup API か `VACUUM INTO` の結果だけを渡す |
| ふつうの Git で読めるか | 読めない | 読めない | 読めない。エンジニア版では不採用の理由だが、ここでは要求しない | 読めない |
| メールや受け渡しで旧版が付いていくか | 付いていく。秘密も付いていく | 作業中の実体ごと付いていく | 作業ファイルだけ渡すなら履歴は付かない | 渡した複製には、その時点までの履歴が入る。明示の操作である |

### 6.2 採用

**ライブの正本は置き場 C。持ち出しは置き場 D。D は C とは別のファイルであり、ライブの書き込み先ではない。**

依頼の「すべてのファイルを 1 ファイルに詰める」は置き場 B である。B はライブの正本として却下したままである。置き場 D は依頼の第二案の充足ではない。D は履歴ストアの安全な複製であり、作業中のファイルは入らない。フォルダと履歴を一つの ZIP に固める配布用アーカイブもライブ形式ではない。段階 1〜3 では作らない（§6.4）。

採用する理由:

- 普通のアプリは、今までどおりファイルを開いて保存する。履歴の注入も、コンテナの中だけに実体を置くことも、この作業を崩す。
- 戻す単位は、スナップショットが持つフォルダのツリーにできる。[design-policy.md](./design-policy.md) の §2.1 と §2.3 を、利用者の種類で捨てない。
- Fossil が、作業ツリーと単一ファイルのリポジトリを分けている。リポジトリが作業ツリーを含まない、という先例が、置き場 B をライブにしないことと一致する。
- 持ち出しだけを 1 ファイルにするなら、SQLite が安全だと書く手段（Backup API または `VACUUM INTO`）が使える。ライブの DB を利用者がコピーする手順にはしない。
- Git 未インストールで動く。現行の記録経路は `git cat-file` を呼ぶので、そのままではこの条件を満たさない（§5）。
- エンジニア版の正本、共有、Issue #8 に書き込まないので、第 1 段階で ADR-0001 を壊さない。

前提:

- 監視プロセスが動いているあいだだけ、履歴が増える。止まっているあいだの編集は、次に動くまで記録されない。
- 利用者には、戻す前にフォルダを開いているアプリを閉じることを求める。開いたまま戻したときの Word 等の振る舞いは未確認なので、完了条件に入れない。実装は、アプリを閉じたことだけには頼らない。上書きと削除の前に、直前の snapshot との一致を確かめる（§7.4）。
- ライブ DB の既定の場所は、監視フォルダの外のローカルなディレクトリである。クラウド同期フォルダを既定にしない（ネットワークファイルシステムかどうかは未確認。未確認の場所へは置かない）。
- 「ふつうの Git でこの履歴を読める」ことは、非エンジニア版の完成条件にしない。

既知の制限:

- 落ち着いた状態の正本は 1 ファイルだが、トランザクション中は回復用ジャーナルが隣にある。ジャーナルを消すと、停電後の回復ができない（howtocorrupt §1.3）。
- 民生用ディスクが sync を偽ると、停電でコミットが失われるか壊れる、と SQLite が書いている。この計画はそれを超える保証をしない。
- 同じバイト列は 1 回だけ格納する。変わったファイルは、新しいバイト列をそのまま足す。Fossil の delta 圧縮は採用しない。大きなファイルを繰り返し保存すると、履歴のファイルは伸びる。
- `grep` は履歴 DB の中を搜せない。搜す対象は作業ツリーの方である。
- エンジニア版と同時に同じフォルダを見ると、履歴が二つ残る。それは失敗ではない。合わせる処理は作らない。
- ドットファイル（`.env` を含む）も記録する。除外リストの実装は後回し（§6.4）。置き場 C と置き場 D に秘密が残りうる（§10）。

### 6.3 却下

**置き場 A を却下する。** 保存のたびに利用者のファイルへ履歴を注入すると、次と衝突する。

- 画像エディタは Exif を損なうか消し、PNG の補助情報の保持は “wherever possible” で必ずではない。注入した履歴は、次の普通の保存で消えうる。消えたあとのファイルは、履歴が無いバイト列としてもう一度記録される。
- PDF のコメントも、編集アプリが必ず保持しない。incremental update は PDF の末尾追記としては成り立つが、メモ、表計算、画像、テキストへ一般化できない。PDF だけ別形式にするのは、戻す単位をフォルダにする方針と合わない。
- Git の ident と RCS のキーワード展開は、checkout のときに本文を書き換える。MicroGit は ident を止め、保存したバイト列を正としている（ADR-0012）。注入は、この「保存したバイト列」をアプリの次の保存まで保てない。
- Org-mode は履歴を本文へ混ぜる。非エンジニアのメモの本文が、履歴リストで変わる。
- ファイルをメールすると、旧版が全部付いていく。[design-policy.md](./design-policy.md) 271 行目は「マイクロ履歴に秘密情報が残りうる。PR 添付はオプトイン。除外／redaction を設計に含める。」と書いている。埋め込みは、その注意をファイルのコピーごとに広げる。段階 1〜3 は redaction を実装しない。
- Word が未知のパーツを保持するかは未確認である。未確認の保持に依存して採用しない。
- NSFileVersion は、履歴がファイルの中にあるとは書かれていない。OS の version store は置き場 A の先例ではない。
- RCS の `,v` は履歴がファイルの外であり、置き場 A の成功例ではない。チェックインで作業ファイルが `,v` に置き換わるのは、普通のアプリが開くファイルを崩す。

**置き場 B をライブの正本として却下する。**

- 普通のアプリは、ZIP や SQLite の中の部品を直接開いて保存できない。EPUB は unzip できる、と依頼時に確認されている。中の部品を文書アプリがそのまま編集できる、という出典は無い。
- ODF と EPUB と Office 文書は ZIP である。部品を変えるとき、ZIP は通常ファイル全体を書き直す（appfileformat.html）。フォルダの中の 1 ファイルの保存が、コンテナ全体の書き直しになる。
- ライブの SQLite に作業中の実体だけを入れると、WAL またはホットなジャーナルが付く。コピーはジャーナルと揃っていないと壊れる。利用者に「この 1 ファイルが文書です」と渡す形と衝突する。
- macOS の bundle は、ディレクトリを 1 つの書類に見せるだけで、単一ファイルではない。Windows の利用者へ「1 ファイル」として渡せない。
- Notion の書き出しは HTML / Markdown / CSV と添付の固まりで、ライブの正本ではない。ライブ形式の先例にしない。

**置き場 D をライブの正本にすることを却下する。** D は複製である。監視プロセスが D に追記し始めると、C と D の区別が消え、書き込み中のファイルを持ち歩く問題に戻る。

**git bundle を、C の代わりにも D の代わりにもしない。** 受け手に Git が要る。作業ツリーは入らない。bundle への push は無い。エンジニア版は、双方 MicroGit があるときの bundle 共有を、差分肥大と展開コストで既に不採用にしている。

**青谷らの persistent signals を、非エンジニア版のライブの正本にはしない。** 理由は §11。データベースを持たない方式ではない。

**現行の shadow Git を、見えない `.git` ごと文書フォルダに自動で作る案を却下する。** 拡張は `.git` が無いとスキップする。bare の置き場は親の `.git` の下である。速い記録の回復経路は `git` を起動する。文書フォルダに `.git` を作ると、あとから Git を覚えた利用者のリポジトリと取り違える。エンジニア版のエンジンを文書フォルダへ分岐させることでもある。design-policy §5 が再構築を採らなかったのはエンジニア版の話で、そのエンジンを非エンジニア版へコピーする理由にはならない。

### 6.4 後回し

次は却下ではない。この計画の段階 1〜3 では作らない。

- デバイス間の共有。Fossil はハッシュリストを交換するが、非エンジニア版の運び方は未決である。エンジニア版の `refs/microgit` とは混ぜない。
- エンジニア版の履歴との相互変換、git bundle への書き出し。
- WAL。段階 3 の計測のあとでも、付随ファイルを利用者へ見せずに済む理由が無ければ採用しない。
- Fossil の delta / zlib。伸びるディスクは既知の制限として残す。
- 監視フォルダの中のポインタファイル（Fossil の `_FOSSIL_` に相当するもの）。段階 1 は DB のパスを引数で渡す。
- GUI、配布、Office の実機を完了条件にすること。
- フォルダと履歴を一つの ZIP に固める配布用アーカイブ。ライブ形式ではない。
- 秘密やドットファイル（`.env` を含む）を記録から外す除外リスト。段階 1 が記録しないのは、どの階層にあっても、`.git`、`.microgit_shadow`、`.microgit_overlay`、`.microgit_logs`、シンボリックリンクだけである（§7.1）。それ以外のドットファイルを外す除外リストは、この後回しのままである。
- 秘密の redaction。段階 1〜3 は実装しない（§10）。
- 言語の persistent signals（時系列データベースをランタイムに置く方式）を、普通の文書アプリの履歴に使うこと。段階 1〜3 では作らない（§11）。

## 7. 採用案の形

### 7.1 作業ツリー

監視対象は、利用者が指定した 1 つのフォルダである。中のファイルは普通のファイルのままである。記録処理は、読んだバイト列を履歴へコピーするだけで、元のファイルを開いて書き戻さない。

記録するパスは、フォルダからの相対パスである。区切りは `/`。絶対パス、`..`、空の要素は拒否する。

次は、どの階層にあっても記録しない。restore はそれらを消さない。シンボリックリンクは辿らない。段階 1 は、スキップしたリンクの数を、その回の結果の数として返す。

- `.git`
- `.microgit_shadow`
- `.microgit_overlay`
- `.microgit_logs`
- シンボリックリンク

シンボリックリンクを記録しない理由は、フォルダの外へ出るためである。残りの四つはエンジニア版と通常 Git の置き場である。戻す単位から外す理由は、文書同士の組み合わせを守るためではなく、この計画が ADR-0001 と利用者の Git を壊さないためである。それ以外のドットファイル（`.vscode`、`.env` を含む）は、フォルダにあれば記録する。これは既知の制限である。除外リストの実装は後回し（§6.4）。

空のディレクトリも記録する。根拠は ADR-0001 の決定にある「Git にディレクトリだけのエントリは無い」（[ADR-0001](./adr/0001-source-of-truth.md) 25 行目）である。このストアは Git ではないので、その制限を引き継がない。同 ADR の「引き受けること」（44 行目）は、ファイルを消したこととディレクトリごと消したことを Git が区別できない、という記述である。空ディレクトリを持てる根拠としては、その節を引用しない。非エンジニアのフォルダでは、空のフォルダも作業の一部になりうる。

同じバイト列は 1 回だけ持つ。ハッシュのアルゴリズムは段階 1 の実装が選び、`src/plainstore/` の先頭コメントに 1 行で固定する。この文書は桁数もアルゴリズム名も決めない。テストは、同じバイト列を 2 回記録しても blob の行が 1 つのままであることで確かめる。

他の OS へ戻すときの改行変換はしない。Windows で保存した CRLF は、どの OS で戻しても CRLF のままである。

### 7.2 正本ファイル

ライブの正本は、監視フォルダの外にある SQLite ファイル 1 つである。段階 1 は、フォルダの中にライブ DB もポインタも置かない。DB のパスは引数で渡す。既定のパスを実装するなら、OS のユーザー領域で、監視フォルダのフルパスから決めた名前にする。クラウド同期されがちなディレクトリを既定の計算に使ってはならない。どの API でユーザー領域を取るかは実装が選び、コメントに書く。

ジャーナルモードは、SQLite の既定（ロールバックジャーナル）のままにする。`PRAGMA journal_mode` を WAL、OFF、MEMORY にしない。`PRAGMA synchronous` を OFF にしない（既定の FULL のまま）。落ち着いたあとは、隣に `-journal`、`-wal`、`-shm` が残っていないことを、段階 1 のテストが見る。

スキーマの概要（バイト列互換の仕様書ではない。表の名前は変えてよい）:

- blob: バイト列そのもの。同一性はハッシュ。
- snapshot: 単一の親（最初の 1 件は親が無い）、時刻、きっかけ（監視か、手動の 1 回か）。
- entry: ある snapshot に含まれる相対パスと、ファイルなら blob への参照、ディレクトリならディレクトリであること。
- tip: 先端の snapshot を 1 つだけ示す場所。表でも 1 行でもよい。書き込めるライブ DB の restore は、ここを対象の snapshot へ移す。

ファイルとディレクトリの置き換えは、いずれの階層もシンボリックリンクでもジャンクションでもないときだけ、既存を消してから作る。リンクまたはジャンクションがあるときは §7.4 のとおり、フォルダを変える前に 0 以外で終わる。

大文字小文字だけが違う二つのパスが同じ回にあるときは、段階 1 では snapshot を確定しない。どちらを残すかは決めない。先端とバイト列もエントリも同じなら、新しい snapshot は作らない。

アプリが書く SQL は、アプリが組み立てる。DB ファイルの中に入っている SQL 文字列は実行しない。これは確定の禁止である。view やトリガを読んで、次の SQL を組み立てない。信用できない DB、特に持ち出しファイルを開くときの照合は、段階 2 に書く。照合は表名ではなく、アプリが書く CREATE 文と `sqlite_schema` の `sql` の一致である。

書き込むプロセスは 1 つに限る。SQLite のトランザクションロックだけでは足りない。フォルダを読んでから DB へ書くあいだを、トランザクションロックだけでは 1 プロセスにできない。段階 1 は、DB とは別のロックを、プロセスが生きているあいだハンドルで排他に持つ。2 つ目は取得に失敗したら 0 以外で終わり、snapshot を増やさない。クラッシュでハンドルが閉じたあとは、次のプロセスが取得できる。残ったファイルを手で消す手順にはしない。どの Node API かは実装が選び、`src/plainstore/` のコメントに書く。`list` はロックを取らない読み取りである。watch がロックを持っているあいだ、別プロセスの restore は失敗する。同じプロセスが watch を止めてから restore する。

読み取りに失敗したパスが 1 つでもある回は、スナップショットを確定しない。部分的なツリーを先端にしない。次に全部読めたときだけ確定する。

### 7.3 耐久性

目指すのは ADR-0002 の `power` と同じ方向である。手段は SQLite のトランザクションである。1 件のスナップショット（blob の追加、entry の追加、snapshot の行）は 1 つのトランザクションで確定する。途中でプロセスが死んだとき、次に開いた先端は、確定した最後の完全なスナップショットである。半分だけの entry が先端に残ってはならない。

これはプロセスの強制終了について、段階 3 のテストで言う。電源プラグを抜いた結果は、SQLite がディスクの sync の偽りを限界として書いているので、この計画の保証文にしない。

ホットなジャーナルが存在するあいだに、DB ファイルだけを別の場所へコピーする手順は作らない。利用者向けの複製は置き場 D だけである。

### 7.4 戻す操作

引数は、DB のパス、監視フォルダ、snapshot の id である。

restore の最初に、今のフォルダと、開いている DB の先端の違いを見る。未記録かどうかは、その DB の先端と比べる。export を `--db` にして restore するときは、その DB（export）の先端と比べる。§7.1 で記録しないもの（`.git`、`.microgit_shadow`、`.microgit_overlay`、`.microgit_logs`、シンボリックリンク）は、どの階層にあっても未記録の子に数えない。

違いがある、または消すと記録対象の未記録の子が巻き込まれるなら、書き込めるライブ DB では先に snap する。その snap が確定しなかったときは、読めなかった場合に限らず、大文字小文字の衝突を含むどの理由でも、restore は 0 以外で終わり、フォルダも DB の先端も変えない。snap が成功したあとなら、未記録だった記録対象のファイルは新しい snapshot に入っている。先に成功した snap は残してよい。古い snapshot へ戻すときに消えても、その新しい snapshot から戻せる。

消す対象のディレクトリの下に、記録対象なのにどの snapshot にも無い子が残っているなら、restore は何も消さずに失敗する（snap をすり抜けた場合の保険）。その下にあるのが §7.1 で記録しないものだけであることは、この失敗にしない。例は、後の snapshot にだけある空の `inbox/` の中に、監視を止めたあと `letter.txt` を置いたときである。`inbox/` を消すと `letter.txt` も消え、残すとツリーが一致しない。先に snap が成功していれば、`letter.txt` は新しい snapshot に入っているので、古い snapshot へ戻すときに消してよい。その新しい snapshot を restore すると戻る。

書き戻しの意味は次で固定する。成功条件は、記録対象のパスが対象 snapshot と一致することである。除外パスとリンクが余分に残ることは失敗にしない。

- 対象の snapshot に含まれる記録対象のパスは、そのバイト列にする。ディレクトリならディレクトリにする。無ければ作る。
- いずれかの snapshot に含まれ、対象の snapshot に含まれない記録対象のパスは、フォルダから消す。消す前の snap が成功していれば、未記録だったファイルはその新しい snapshot から戻せる。ディレクトリ自体を消すと §7.1 で記録しないものも消える場合は、ディレクトリを消さず、記録対象の子だけを消す。そのためにディレクトリが残ることは、失敗にしない。
- §7.1 で記録しないものは、どの階層にあっても記録にも復元にも含めない。restore はそれらを消さない。
- 対象より後の snapshot の行は、DB から消さない。書き込めるライブ DB では、書き戻しが全部成功したあとだけ、先端の印を対象へ移す。途中で書き込みが失敗したら、先端は移さない。親は単一のままなので、移した先端から次に記録する snapshot の親は、その対象である。エンジニア版の「過去へ戻したあと、新しい記録は戻した先端から続く」と同じ向きである。分岐の一覧 UI は作らない。

書き込みと削除の前に、次の二つを、フォルダをまだ変えていないうちに行う。先に成功した snap は残してよい。ここで 0 以外で終わるときは、フォルダの中身は変えない。

- 監視フォルダの根から、書き込みまたは削除をしようとしているパスの各階層を lstat する。途中も含め、シンボリックリンクまたはジャンクションが 1 つでもあれば、その restore は 0 以外で終わる。残すだけの除外パスとシンボリックリンクは、この失敗の理由にしない。親から子の順で処理する。ディレクトリを消すときもリンクの先は辿らない。リンク先のファイルは残る。フォルダの外のファイルは消えない。リンク自体を unlink してから通常のファイルやディレクトリに置き換える、とはしない。それはフォルダを変えるからである。
- 上書きと削除の対象について、今のバイト列（ディレクトリなら種類）が、直前の snapshot と一致するかを全部読んで確かめる。直前の snapshot は、保護の snap が成功したならその snap、そうでなければ書き戻し前の先端である。1 つでも違えば、0 以外で終わる。アプリを閉じる前提だけには頼らない。順序は、必要な snap の確定、そのあと lstat とこの照合、そのあと親から子の順の書き込みと削除、である。この照合のあと、違いを取り込む snap はもうしない。

パスは、記録時だけでなく restore でも、絶対パス、`..`、空要素を拒否する。いずれの階層もシンボリックリンクでもジャンクションでもないときだけ、ファイルとディレクトリの置き換えは既存を消してから作る。フォルダの外へ出る書き込みはしない。

先に snap するのは、書き込めるライブ DB を開いているときである。先端を移すのは、書き戻しが全部成功したあとの、書き込めるライブ DB だけである。export は読み取り専用なので、export へ snap せず、先端も移さず、export ファイルへは書き込まない（段階 2）。export を `--db` にした restore で、記録対象の未記録のファイルがある、または消すと記録対象の未記録の子が巻き込まれるなら、フォルダも export も変えずに 0 以外で終わる。その保護の snap は export へ書けないからである。未記録の判定は、その export の先端と比べる。空のフォルダには未記録の子が無い。段階 2 の完了条件 2 は、その空のフォルダへ読み取り専用のまま書き戻し、export の件数を変えない。未記録のファイルを snap に残すことは、import したライブ DB で確かめる。

watch が §7.2 のロックを持っているあいだ、別プロセスの restore は失敗する。同じプロセスが watch を止めてから restore する。

戻す操作は、フォルダを開いているアプリがロックしているかは見ない。restore の書き込みが途中で失敗したら、0 以外で終わり、成功したことにしない。先端は移さない。移すのは、全部書けたあとだけである。既知の制限として、途中まで書いたフォルダは自動では戻さない。回復は、残っている直前の snapshot へ、利用者がもう一度 restore すること。

### 7.5 共有

段階 1〜3 に共有は無い。`refs/microgit` を読まない、書かない。git bundle を作らない。Fossil の sync も作らない。

### 7.6 エンジニア版との並存

並存する。履歴ストアは共有しない。エンジニア版を、この SQLite へ移行しない。

同じフォルダで VS Code 拡張と監視プロセスが両方動くと、shadow の Git と SQLite の両方に履歴が残る。ディスクを二重に使う。失敗としては扱わない。どちらかを止める処理は作らない。

非エンジニア版は、フォルダに `.git` があっても無くても、同じように記録する。`.git` の有無でスキップしない。`.git` の中へは書かない。

製品の表面は、VS Code 拡張の置き換えではない。同じリポジトリの中のライブラリと、それを起動する別プロセスである。

コードの置き場所:

- `src/plainstore/` にライブラリと CLI を置く。役割が同じならファイルを分けてよい。
- エントリは `src/plainstore/cli.ts`。コンパイル後は `node out/plainstore/cli.js`。
- 単体テストは `src/test/unit/plainstore.test.ts`。既存の `npm run test:unit` が `out/test/unit/**/*.test.js` を拾う。
- `src/extension.ts`、`src/shadowStore.ts`、`src/fastMicroCommit.ts`、`src/fastGit/` に処理を足してはならない。
- `package.json` の script を 1 つ足すのはよい。README は段階 1〜3 では書き換えない。

SQLite の入り方: 段階 1 の最初に、開発に使う Node で `node:sqlite` が記録と復元に使えるかを確かめる。使えるなら依存を足さない。使えないなら、依存を 1 つ足す。足す前に、そのパッケージのライセンス文をファイルで確認する。依頼時の「パブリックドメイン」は、開いた appfileformat.html では裏が取れていない。`THIRD_PARTY_NOTICES.md` に載せる必要があるかは、足した依存のライセンスが既存の同梱物と同じ扱いを要求するかで決める。秘密は書かない。

`npm run compile` は `tsc -p ./` である。`tsconfig.json` は `rootDir` が `src`、`outDir` が `out` で、plainstore を外す include も exclude も無い。tsc は `src` 全体を `out` へ出す。plainstore が型で失敗すると、拡張の compile も失敗する。`node:sqlite` の型が無い場合は、段階 1 の最初の関門で、依存を足すか、その API を使わないかを決める。拡張の compile を壊したまま完了にしない。npm の依存を足しても `scripts/package-vsix.mjs` は `--no-dependencies`（同ファイル 224 行目）なので、VSIX に `node_modules` は入らない。入るのは compile 結果である。だから `.vscodeignore` に `out/plainstore/**` を足す。これは段階 1 の作業である。この計画を直した時点では、`.vscodeignore` はまだ変えていない。

CLI の引数（名前は実装で揃っていればよい）:

- `init --folder <dir> --db <path>`: DB を作り、フォルダの今のツリーを 1 件記録する。
- `snap --folder <dir> --db <path>`: 今のツリーを 1 件記録する。
- `watch --folder <dir> --db <path>`: 変更が落ち着くまで待ち、落ち着いたら 1 件記録する。落ち着きの待ち時間は実装が選ぶ。この文書はミリ秒を決めない。現行拡張の 0.3 秒（ADR-0015 の画面更新と同じ予約）を流用してよいが、Office の保存に足りるかは未確認であり、採否はこの数値に依存しない。
- `list --db <path>`: snapshot の id、親、時刻を出す。ロックは取らない。
- `restore --folder <dir> --db <path> --snapshot <id>`: §7.4。

時計は注入できるようにする。テストは実時間の `fs.watch` に依存しない。

24. `src/plainstore` の import 行が、`child_process`、`node:child_process`、`shadowStore`、`fastGit`、`fastMicroCommit`、`extension` を import していない。テストは import 行だけを見る。コメントに単語が出ることは失敗にしない。文字列を分割して起動する抜け道は、このテストの目的外である。
25. 親ディレクトリを、フォルダの外へのシンボリックリンクまたはジャンクションに差し替えたとき、外のファイルが残り、フォルダの外のファイルが消えない。restore はフォルダを変える前に 0 以外で終わる。作れる環境だけでこの 1 件を走らせ、作れない環境ではスキップしたとテストが明示する。
26. snap のあと、書き戻しに入る前にファイルを 1 バイト変える。restore は 0 以外で終わり、その書き戻しではフォルダを変えない。テストは注入でよい。

`npm test`（VS Code を起動する拡張機能テスト）は、段階 1 の完了に必須にしない。上のブランチ差分に拡張の経路が無いので、拡張の経路は変わっていない。`npm run compile` は完了に含める。plainstore の型が壊れていると、`src` 全体を出す tsc が拡張も失敗させる。

### 段階 2: 持ち出し用の 1 ファイル

作るもの:

- CLI の `export --db <path> --out <path>`。実装は Backup API か `VACUUM INTO` のどちらか一方。選んだ方を `src/plainstore/` のコメントに 1 行書く。sqlite3_rsync は使わない（別の実行ファイルを配ることになるため）。export は履歴の複製であり、作業中のファイルは入らない。秘密が残りうる（§10）。
- CLI の `import`。import の前にスキーマを照合する。トリガ、ビュー、またはアプリが書く CREATE 文と違う CREATE 文があるファイルは import しない。照合前に Backup API で写さない。照合が通ったときだけ、Backup API で export を新しいライブ DB へコピーし、そのライブ DB へ snap する。export 自体へは snap しない。照合に失敗したときは、新しいライブ DB を作らない。使う API が Backup API を出せるかは未確認なので、段階 2 の開始時に見る。出せなければ、その API では import しない。
- export を開く処理。読み取り専用である。export に snap しない。先端を移さない。export ファイルへは書き込まない。開いた直後、操作に使う前にスキーマを照合する。アプリが書く CREATE 文と `sqlite_schema` の `sql` が一致しなければ開かない。表名が同じだけでは開かない。生成列、CHECK、DEFAULT の式が違えば開かない。トリガとビューが 1 つでもあれば開かない。アプリが書く照合の SQL は実行する。ファイルの中に入っている SQL 文字列は実行しない。
- export を開く API は、`trusted_schema` を切ること、トリガとビューを無効にすること、`integrity_check`、書く前の blob のハッシュ照合を、出せなければならない。1 つでも出せなければ、その API では export を開かない。出せるときだけ行う、という緩和はしない。`node:sqlite` がこれらを出せるかは未確認である。段階 2 の開始時に API を見る。この改訂では security.html を開いていない。開いていない細目を、できるとは書かない。

作らないもの:

- ライブ DB のファイルコピーを、公式の複製手順にすること。
- 作業ツリーを export ファイルの中だけに移すこと。
- export ファイルを、動いている監視プロセスの書き込み先にすること。export へ snap すること。export の先端を移すこと。
- git bundle。
- ファイルの中の SQL 文字列を実行すること。

完了の判定:

1. 記録が 2 件ある DB から export する。出力の隣に `-wal` と `-journal` が無い。出力ファイルは 1 つである。
2. 空のフォルダへ、export を `--db` にして 1 件目を restore する。バイト列が元の 1 件目と一致する。export の件数は 2 のままである。export へは書き込まない。
3. 照合が通った export を Backup API で新しいライブ DB へ import し、そのライブ DB へ snap すると、新しいライブ DB の件数は 3 になる。export の件数と元のライブ DB の件数はどちらも増えない。照合の前には Backup API で写さない。
4. テストは、ライブ DB のファイルを `fs.copyFile` したものを正の複製として比較しない。
5. トリガ、ビュー、またはアプリが書く CREATE 文と `sqlite_schema` の `sql` が違うファイルは開かない。生成列、CHECK、DEFAULT の式が違うものも開かない。そのファイルの件数は増えない。
6. トリガが入った DB の import は拒む。照合の前に Backup API で写さない。新しいライブ DB は作られない。

### 段階 3: 強制終了と、ファイル作成回数の計測

作るもの:

- コミット直前に必ず止まる注入点を 1 つ用意し、そこでプロセスを止める試験。既存の停電模擬（`scripts/test/micro-commit-crash.mjs`）のやり方を読んで、非エンジニア版用に別に書く。エンジニア版の試験を書き換えない。注入が無い試験は完了条件にしない。
- Windows で、`snap` 1 回のあいだに新規作成されたファイルの数を数える計測スクリプト。目標ミリ秒は置かない。

作らないもの:

- 現行ジャーナルと同じ 1 回の fsync である、という主張。
- `microgit.durability` や ADR-0015 の遅延書き出しを変えること。
- 電源プラグを抜く試験を完了条件にすること。
- 遅いことを段階 3 の失敗にすること。失敗は、確定した記録が消えること、または半分だけの記録が先端に残ることである。

完了の判定:

1. 完全な snapshot が N 件ある状態で、次のコミット直前の注入点でプロセスを止める。再開後に読める snapshot は、0 件目から N 件目までの接頭辞である。N+1 件目の entry だけが残っていない。注入点を使わない試験は、この完了条件に数えない。
2. 計測の数字を `docs/paper/data/` か、段階 3 の作業で既存の計測の置き方に合わせて残す。比較文を書くなら、条件が違うことは文に含める。ADR-0015 の「手元の Windows で 0.010 秒」は、エンジニア版の別経路の数字であり、段階 3 の合格線にしない。
3. 段階 1 のブランチ差分の条件（指定したパスが無いこと）が、まだ成り立っている。

段階 4 は無い。共有、GUI、配布、相互変換は §6.4 の後回しであり、完了条件を持つ段階にしない。

## 9. 移行と、やらないこと

移行はしない。

- 既存の shadow Git の履歴を、SQLite へ移すツールは作らない。
- 非エンジニア版の履歴を、`refs/microgit` へ上げるツールは作らない。
- VS Code 拡張の保存経路を、SQLite へ切り替える変更はしない。
- 利用者の文書フォルダに `.git` を自動で作らない。
- 段階 1 の実装が ADR-0001 を「正本は場合による」へ書き換えてはならない。正本が二つある、と書くなら「製品が二つある」と書く。エンジニア版の正本は Git のままである。

やらないこと（段階を超えて）:

- 利用者ファイルへのメタデータ注入。キーワード展開。本文への履歴リスト。
- 作業中のファイルを ZIP か SQLite の中だけに置き、普通のアプリの対象から外すこと。
- `.docx` を XML に分解して記録すること。バイト列のまま記録する。[design-policy.md](./design-policy.md) §2.3 の「分割するか」は未決のまま残し、この計画は分割を実装しない。
- ファイル 1 つだけの復元を既定にすること。
- マージ、複数親、Cherry-pick。
- 監視プロセスが止まっているあいだの編集を、あとから推測して埋めること。
- `skills/use-microgit` を、監視プロセス前提へ書き換えること。
- README の利用者向け説明を、段階 1〜3 で書き換えること。計画の導線は [design-policy.md](./design-policy.md) の §2.4 と、§9 の関連一覧の 1 行である。

未決（決まるまで、それに依存した実装をしない）:

残リスク:

- 監視が止まっていれば、履歴は歯抜けになる。利用者には「プロセスが動いているあいだのフォルダ」としか言えない。
- 戻す操作の書き込みが途中で失敗する（ディスクが満杯になったときを含む）と、フォルダが対象のツリーと一致しないまま残ることがある。先端は移さない。途中まで書いたフォルダは自動では戻さない。回復は、残っている直前の snapshot へ、利用者がもう一度 restore することである。
- ホットなジャーナルが残っているときに、利用者が DB だけを手動でコピーすると、そのコピーは壊れうる。公式手順は置き場 D だけである。UI が無い段階では、CLI の `export` 以外を文書で禁じることしかできない。
- sync を偽るディスクでは、停電の保証は SQLite の文書の限界を超えない。
- 同じフォルダでエンジニア版と併用すると、ディスクを二重に使う。利用者への警告 UI は、この計画の段階に無い。
- 信用できない持ち出しファイルを開く攻撃は、appfileformat.html の §4 が別文書の確認を求めている。この改訂では security.html を開いていない。段階 2 で確定しているのは、export を読み取り専用で開くこと、ファイルの中の SQL 文字列を実行しないこと、アプリが書く CREATE 文と `sqlite_schema` の `sql` が一致しないもの、トリガ、ビューがあれば開かないこと、生成列、CHECK、DEFAULT の式が違えば開かないこと、export へ書き込まないこと、import の前にスキーマを照合し、照合前に Backup API で写さないことである。`trusted_schema` を切ること、トリガとビューの無効化、`integrity_check`、書く前のハッシュ照合について、export を開く API は、これらを出せなければならない。1 つでも出せなければ、その API では export を開かない。出せるときだけ行う、という緩和はしない。出せるかは未確認である。開いていない細目を、できるとは書かない。
- 置き場 C と置き場 D に秘密が残りうる。[design-policy.md](./design-policy.md) 271 行目は「マイクロ履歴に秘密情報が残りうる。PR 添付はオプトイン。除外／redaction を設計に含める。」と書いている。段階 1〜3 は redaction を実装しない。export は履歴ストアの複製なので、その時点までの秘密も入りうる。ドットファイル（`.env` を含む）も記録する。
- 大きなファイルの全文コピーで、履歴 DB が伸びる。上限バイト数は、測る前に決めない。

未確認のままのリスク（断定しない。Office や OneDrive がそうする、という確認ではない）:

- Office のロックファイルの読み取りが失敗すると、§7.2 の「1 つでも読めなければ確定しない」により、同じ回の他のファイルも記録されない。
- 落ち着き待ちより長く一時名のままの保存は、一時名だけの snapshot になり、戻すと元の名前が消えうる。
- クラウドのプレースホルダを空のバイト列として読んでしまった場合は、その空が履歴になる。

## 11. Persistent signals（2026-10-18 に読みを訂正）

同じ日の追加の検討である。置き場 C をライブの正本にする決定は変えない。段階 1〜3 に実装は足さない。

依頼は、signal 型のデータベースレス運用を、非エンジニア向けの履歴の正本にできるか、だった。指している発表は、TC39 TG5 のワークショップ（東京、2026-09-28）で Tomoyuki Aotani（芝浦工業大学）が話す「Persistent Signals: Reactive State That Outlives the Program」である。プログラムと要旨は [tc39/tg5 の workshops/2026/116.md](https://github.com/tc39/tg5/blob/main/workshops/2026/116.md) にある。

最初の文書は、この発表を特定する前に、signal を「データベースを持たず、操作や差分の列だけを残す方式」と読んでいた。その読みは撤回する。btrfs の send、ZFS の send、event passing、操作配送型の CRDT は、この signal ではない。それらの採否は、この節の決定に使わない。

### 11.1 公開されている定義

ワークショップの要旨は、次のように書いている。

- Signal は、時間とともに変わる状態の標準的な抽象である。ただし一時的で、過去の値は捨てられるかメモリに漏れ、プロセスの境界で止まる。
- Persistent signals は、時系列データベースを言語ランタイムの一部として扱う。更新はすべて記録され、過去の値を問い合わせられる。
- Signal classes は、persistent signals を、動的に実体化でき、同期する単位へまとめる。
- 情報源は分散してよく、パケット損失のあとで時刻の一貫性を回復する。データ構造はスキーマの版をまたいで変わりうる。トランザクションは signal ごとに一貫性の水準を混ぜうる。

論文としての先行は、Kamina、Aotani、Masuhara「Signal Classes: A Mechanism for Building Synchronous and Persistent Signal Networks」（ECOOP 2021、LIPIcs、[10.4230/LIPIcs.ECOOP.2021.17](https://drops.dagstuhl.de/entities/document/10.4230/LIPIcs.ECOOP.2021.17)）である。今回開いたのは要旨のページであり、30 ページの PDF 本文は開いていない。要旨が書いていることは次である。

- Persistent signals は、時間変化する値と、その実行履歴の抽象である。過去の値の蓄積によるメモリの漏れを、データベースシステムに管理させることで扱う。
- 計算は、下にあるデータベースシステムと関係代数でやり取りするように定義している。
- 実装は、コンパイラと、時系列データベースに基づくランタイムライブラリである。

どちらも、履歴の置き場をデータベースにしている。アプリケーションが SQL を書かない、という意味での「データベースを意識しない」は、要旨には書かれていない。書かれているのは、時系列データベースをランタイムの一部にし、履歴の管理をデータベースへ渡すことである。したがって、この方式をデータベースレスとは呼ばない。

### 11.2 この計画との違い

似ているのは、プロセスが終わったあとも過去の値を残し、あとから問い合わせる、という目的だけである。置き場 C の snapshot も、その目的でフォルダの外に履歴を置く。

単位が違う。Persistent signals の 1 件は、言語の中の反応的な値の更新である。この計画の 1 件は、普通のアプリがフォルダへ保存したあとの、ファイルのバイト列の木である。Word や表計算や画像や PDF は、青谷らの signal class のランタイムの上では動いていない。監視プロセスが見るのは、保存後のバイト列であり、言語の signal の更新ではない。ランタイムが無いアプリへ、時系列データベースを言語の一部として差し込むことは、段階 1 の範囲に無い。

戻す単位も違う。Signal class は、関連する signal を同期する単位である（ECOOP 2021 の要旨）。この計画が守る単位は、design-policy §2.3 のフォルダである。signal の過去の値へ戻しても、同じ時点のフォルダの他のファイルは戻らない。

履歴のエンジンも、すでにデータベースである。ECOOP 2021 の実装は時系列データベースに基づく、と要旨が書く。ワークショップの要旨も、時系列データベースをランタイムに置く、と書く。置き場 C が SQLite を使うことと、データベースを持たないこととの二者択一にはならない。違うのは、データベースが言語ランタイムの裏にあるか、フォルダの外のファイルとして監視プロセスが持つか、である。非エンジニアの文書フォルダには、後者しか接続点がない。

### 11.3 別ファイルを管理しない、は要旨のメリットか

問いの言葉はデータである。「データベースを別ファイルで管理しなくていいのがメリットじゃないの」。

プログラムを書く人から見ると、その読みは要旨に近い。ワークショップの要旨は、時系列データベースを言語ランタイムの一部として扱う、と書く。利用者が signal を更新すると、ランタイムが記録する。ECOOP 2021 の要旨は、過去の値の管理をデータベースシステムに任せる、と書く。アプリケーションのコードが、DB のパスを渡し、SQL を書き、Backup API を呼ぶ、とは書いていない。

ただし、別ファイルがディスク上に無い、とはどちらの要旨も書いていない。書いてあるのは、履歴の管理を時系列データベースへ渡すことである。ECOOP 2021 の実装は、そのデータベースに基づくランタイムライブラリである。データベースがどのファイルに置かれるかは、開いた要旨には無い。PDF 本文は開いていない。したがって「ファイルが一つも増えない」とは書かない。増えないのは、アプリケーションが自分で名前を付けて管理するファイルである。ランタイムの裏のデータベースは残る。

要旨がメリットとして書いているのは、別ファイルを見せないことではない。過去の値がメモリに溜まって漏れないこと、プロセスが終わったあとも過去の値を問い合わせられること、関連する signal を signal class でまとめて同期すること、である。

この計画へ取り込むなら、取り込むのは置き場の種類ではなく、利用者に DB のパスを扱わせないことである。§7.2 は、既定のパスを実装するなら、監視フォルダの外の OS のユーザー領域に、フォルダのフルパスから決めた名前で置く、と既に書いている。段階 1 の CLI は、テストがパスを渡せるように `--db` を残す。既定のパスは、利用者がパスを意識しないためのものであり、データベースを消すものではない。

別ファイルを消す読みは、ここでは採らない。

- プロセスのメモリだけに履歴があると、プロセスの境界で止まる。それはワークショップの要旨が、通常の signal の限界として書いていることであり、persistent signals が避けることである。
- 履歴を利用者の文書ファイルの中へ入れると、置き場 A である。§6.3 で却下済みである。
- ファイルをユーザー領域へ隠しても、停電、持ち出し（置き場 D）、フォルダの改名（§10）では、そのファイルが正本であることに変わりはない。隠し場所は、利用者が履歴をコピーする手順を難しくする。公式の複製は、パスを指定する `export` のままである。

非エンジニアの Word などには、signal のランタイムが無い。監視プロセスがランタイムの役を代行しても、履歴のファイルは監視プロセスの側に残る。別ファイルを利用者の作業から隠すことは、signal class へ乗り換えなくても §7.2 の既定パスでできる。

### 11.4 採否

**非エンジニア版のライブの正本には採用しない。** 置き場 C を維持する。エンジニア版の shadow Git（ADR-0001）も変えない。別ファイルを利用者に管理させないことは、signal の採否とは別に、§7.2 の既定パスで扱う。段階 1 の完了条件は変えない。

段階 1〜3 で作らないもの:

- Signal class、時系列データベースを埋め込んだ言語ランタイム、signal ごとの一貫性水準。
- 文書アプリの内部状態を signal として記録すること。
- パケット損失後の時刻合わせ。ワークショップの要旨が将来の性質として書いている範囲であり、この計画の共有（§6.4）の完了条件にはまだできない。

後で見直す条件は、利用者がその言語の signal で書いたプログラムの状態履歴を残す製品を、文書フォルダのタイムトラベルとは別に作るときである。そのときは、ECOOP 2021 の PDF 本文と、ワークショップ当日の資料を開いてからにする。今回の採否は、開いた二つの要旨で足りる。PDF 本文に「データベースを使わない」と書いてあっても、非エンジニアのアプリにランタイムが無い、という理由は残る。
