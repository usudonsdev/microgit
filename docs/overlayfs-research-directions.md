## 1. 前提：保存 1 回の時間の内訳（確かめた）

CI の 5 つの環境で、VS Code の中で保存を繰り返して測った値（[paper/data/ci-36902155146](./paper/data/README.md)、ジャーナル導入後、新しいコミットを作った最後の 50 回の中央値、ms）。

| 環境 | 層の作り方 | 記録（commit） | うち Git の形式の計算 | うちファイルの作成 | うちジャーナル（fsync 1 回） | 層づくり（layer） |
|---|---|---|---|---|---|---|
| Windows（windows-latest、WHPX） | カーネル版 | 20.6 | 1.5 | 15.1 | 3.0 | **35.1** |
| Ubuntu 22.04 x64 | カーネル版 | 3.0 | 0.4 | 1.7 | 0.4 | **7.5** |
| Ubuntu 24.04 arm64 | カーネル版 | 3.5 | 0.6 | 1.9 | 0.5 | **6.5** |
| Ubuntu 24.04 x64 | Node.js 版 | 3.3 | 0.5 | 1.9 | 0.4 | **18.0** |
| macOS 14 | Node.js 版 | 12.3 | 1.3 | 5.2 | 2.9 | **34.4** |

- 「Git の形式の計算」は commitPhases の readFile・blob・index・tree・past・flat・commitObject・refs・refsAndIndex・load・historyIndex・restamp の和。ハッシュと圧縮を含む
- 「ファイルの作成」は writeObjects・writeIndex・writeRefs の和
- macOS の layer は計測ごとのぶれが大きい（ADR-0014 の注記）

ここから言えること：

1. **Git の形式の計算（ハッシュと圧縮）は 0.4〜1.5 ms で、記録の主な費用ではない。**
2. **記録の費用の大半はファイルの作成で、特に Windows（NTFS）で重い**（15.1 ms）。次が fsync。
3. **保存 1 回の処理全体でいちばん重いのは、記録ではなく層づくり（過去に戻るための準備）。** カーネル版でも、Linux で記録の約 2 倍、Windows で約 1.7 倍かかる。仮想マシンの中で層を 1 枚確定させること自体は 0.1〜0.4 ms（ADR-0004）なので、Windows の 35 ms の大半は境界を越える通信と、層ごとの mount・unmount だと考えられる（**見込み**：内訳はまだ測っていない）。

## 2. 案 2：OverlayFS の層を記録の正本にする

### 2.1 何が置き換わるか

保存の経路から Git の形式を外し、「層を作ること」を記録とする。Git の形式は、保存が落ち着いたときに層から作る（遅延）。

削れるのは、表の「Git の形式の計算」と「Git のファイルの作成」だけである。

### 2.2 速くなるか（見込み）

| 削れるもの | 見込み |
|---|---|
| Git の形式の計算 | 0.4〜1.5 ms。削っても小さい |
| Git のファイルの作成 | 層も、停電で失わないためにはディスクにファイル（層のディレクトリ、中身、メタデータ）を作る必要がある。作るファイルの数は大きく減らない |
| 停電への備え | 層を正本にしても、fsync は少なくとも 1 回要る。ジャーナルと同じ |

さらに、**今の層づくりは保存の中でいちばん重い**（§1 の 3）。層づくりを「記録が終わるまで」の経路に乗せると、記録はむしろ遅くなる。たとえば Windows では、今の記録 20.6 ms に対して、層づくりだけで 35.1 ms かかっている。

したがって、**今の設計のまま層を正本にしても、記録は速くならない見込みが高い。** 速くするには、層づくりの境界越えと mount・unmount の費用そのものを、メモリ転送に近い速さまで下げる必要がある（要件定義書 NFR-2 の最終目標「メモリ転送と等速」と同じ問題）。

### 2.3 Windows のファイルの作成を消すだけなら、OverlayFS は要らない

Windows の記録の大半（15.1 ms）は NTFS でのファイルの作成である。これを保存の経路から外すには、「保存の経路ではジャーナルへの追記だけを確定させ、Git のファイルは保存が落ち着いてから書く」で足りる（記事の「まだ残っていること」で検討中の方式）。OverlayFS は関係しない。

### 2.4 OverlayFS が原理的に記録を速くできる形：保存を「捕まえる」側に回す

OverlayFS が得意なのは、**書き込みを upper に集め、upper を凍結すれば、その時点の差分がコピーもハッシュも無しに確定する** ことである。これを記録に使えるのは、**ワークスペースそのものを OverlayFS の合成したフォルダにし、エディタの書き込みが最初から upper に落ちる** 場合だけである。そのとき、記録は「upper を凍結して lower に積み、新しい upper を用意する」という、ファイルの大きさや数によらない操作になる（要件定義書 FR-2 の初期案）。

| 障壁 | 内容 |
|---|---|
| Windows・macOS | ワークスペースはホストのファイルシステムにある。ゲストの中の mount は VS Code から見えない。成り立たない |
| Linux（非特権） | 利用者の名前空間の中の mount は、その名前空間の中でしか見えない。外で動く VS Code や言語サーバーからは見えない。全体から見せるには root の mount か FUSE（fuse-overlayfs など）が要り、FUSE はすべてのファイル操作に費用が乗る |
| 凍結の操作 | upper を凍結するには unmount と mount が要る。その間、エディタや言語サーバーが開いているファイルの扱いが問題になる |
| 要件 | NFR-1（VS Code が動く環境ならどこでも動く）と衝突する |

**Linux に限った研究用の試作** としてなら、「保存＝凍結」にしたときの記録の下限を測れる。これが、案 2 で OverlayFS 自身が記録を速くすることを示せる唯一の筋道である。

### 2.5 既存の判断との関係

- ADR-0001 は、層を正本にする案を「デバイス間の同期・既存の利用者の移行・壊れたときの復旧・別のバックエンドで開いたときの互換・ゲストを信用しない」の 5 つの観点で退けた。このうち「ゲストを信用しない」は、ADR-0013 で「ゲストは間違えうるもの」に置き換わり、ゲストに記録を任せる設計を最初から外さない、と明記された
- ADR-0014 で、停電のあとに履歴を作り直す元はジャーナルになった。「Git だけが正本」は、すでに実質的に「保存の経路ではジャーナル、落ち着いたら Git」に緩んでいる。案 2 は、ADR-0001 を覆すというより、**ADR-0014 の延長** として書ける
- デバイス間の同期は、Git の形式ができてからでよい（publish は今も保存とは別に予約して行っている）。壊れたときの復旧は、ジャーナルから作り直す ADR-0014 の仕組みがそのまま使える。移行と互換は、Git の形式を遅れて作る限り今と変わらない

### 2.6 研究にするなら

1. **否定的な結果としてまとめる**：§1 の内訳から、「Git の形式の計算は支配的でない。記録の費用はファイルの作成と fsync で、層を正本にしても減らない」ことを示す。記録の高速化の研究としては、それ自体が結論になる
2. **2.4 の試作**：Linux で、ワークスペースを OverlayFS（root か FUSE）にして、記録を「凍結」にしたときの下限と、エディタとの共存の問題を測る。成り立てば強い主張になるが、配布できる MicroGit には戻せない

## 3. 案 3：卒業研究のビルドキャッシュに OverlayFS を使う

卒業研究（[build-verification-engine.md](./build-verification-engine.md)）は、ビルドキャッシュをマイクロブランチ（lane）ごとに持ち、分岐に合わせて Copy-on-Write で複製する。設計書は reflink（btrfs・XFS）を前提にし、レビューの R-05 で主評価環境を「reflink できる Linux」と決めた（§15）。

### 3.1 OverlayFS で置き換えたときの利点（見込み）

| 点 | reflink | OverlayFS |
|---|---|---|
| 必要なファイルシステム | btrfs・XFS など reflink できるもの | ext4 を含む、ふつうの Linux |
| 複製したキャッシュの場所 | 分岐ごとに別のパスになる | **どの lane も同じパスに mount できる** |
| 分岐の費用 | ファイルの数に比例する複製 | upper を凍結して lower にし、新しい upper を 2 つ用意するだけ（ファイルの数によらない） |
| 書き換えの単位 | ブロック | ファイル（初めて書き換えたときに、ファイルを丸ごと upper にコピーする） |
| containerd snapshotter | btrfs・zfs バックエンド | overlayfs バックエンドがある（ADR-004 の「部品として使う」と合う） |

いちばん大きいのは **パスの固定** である。設計書のクリティカルパス②（複製したキャッシュを、コンパイラが別のパスでも正しく再利用できるか。`.tsbuildinfo` や sourcemap が絶対パスを持つ問題、§12）は、reflink では「固定パスにリンクして見せる」追加の設計が要った。OverlayFS なら、検証する lane の合成フォルダを毎回同じパスに mount すればよく、問題が構造ごと消える見込みがある。

### 3.2 MicroGit 5.0 と一本の線になる

lane を分岐するときの操作（いまの upper を凍結して lower にし、両方の lane に新しい upper を載せる）は、MicroGit 5.0 が保存のたびにやっている「凍結して積む」操作と同じである。ソースの側（コミットごとの完全なツリー）も、レビュー §15 の T-2（エンジンが Git のオブジェクトから自分で展開する）で、コミットごとに層として積めば、固定のパスに安く用意できる。

卒業研究を「MicroGit で実証した、履歴の分岐に合わせて層を凍結して積む仕組みを、ソースとビルドキャッシュの両方に使う」と書ける。新規性 A（VCS の動的な分岐に CoW キャッシュを追従させる）の実現手段に、OverlayFS が正面から入る。

### 3.3 注意点

| 注意点 | 内容 |
|---|---|
| ファイル単位の複製 | 大きいファイルの一部だけを書き換えるキャッシュ（SQLite を使うもの、追記型のもの）は、初めての書き換えでファイル全体をコピーする。reflink はブロック単位。ツールごとに測る |
| 層の深さ | lane からさらに lane を分岐すると層が積み上がる。重ねられる層の数には上限があり、mount も遅くなる。ADR-0003 と同じく、深くなったら写しの層にまとめる |
| lower の凍結 | mount 中の lower を書き換えてはいけない（結果が定まらない）。分岐の元の lane も、凍結して新しい upper に移す必要がある |
| 非特権 | root なしで使うには、エンジンが user namespace を作り、コンパイラをその中で起動する。mount はその名前空間の中でしか見えないが、コンパイラを中で動かすので問題にならない見込み |
| Windows・macOS | ビルドツールはホストで動くので、ゲストの中の mount は使えない。P-2 の「主評価環境は Linux」と合う。Windows・macOS は対象外（フルコピーに落とす） |
| R-01 | ソースのツリーが部分的になる問題は、OverlayFS では解決しない。全量のシード（A-1）か T-2 が別に要る |

### 3.4 測るもの

- 設計書 E-02 に「OverlayFS」を加え、**OverlayFS・reflink・素朴なコピー** の 3 つで、分岐の回数に対する複製の時間とディスクの使用量を比べる
- クリティカルパス②（M1）を、OverlayFS の固定パスで行い、`tsc --incremental` と cargo のキャッシュが分岐をまたいで再利用されるかを確かめる
- ファイル単位の複製が効いてしまうツール（SQLite 系など）で、初めての書き換えの費用を測る

### 3.5 構成の具体案：1 つの固定パスに 3 種類の層を重ねる（見込み）

レビューの R-01 の副次論点は、粒度を「ソース＝コミット単位 / 依存物＝ロックファイル単位 / ビルドキャッシュ＝lane 単位」の 3 つに分けることを提案していた。OverlayFS では、この 3 つをそのまま 1 つの mount の層にできる。

```
/work（固定のパス。検証のたびに mount し直す）
  upper  : lanes/<lane>/upper          ← その lane のビルドが書いたもの（.tsbuildinfo、target/、出力）
  lower  : cache/<凍結した祖先の層>…    ← 分岐の元の lane から受け継いだキャッシュ（lane 単位）
           deps/<ロックファイルのハッシュ>  ← node_modules など（ロックファイルが変わったときだけ作る）
           src/<コミットの差分の層>…      ← ソース（コミット単位。MicroGit と同じ差分の層）
```

**保存のたびの検証**（lane B のコミット C）

1. C のソースの層を、親との差分から作る（MicroGit の記録がすでに差分を持っている）
2. `/work` を unmount し、lower を「B のキャッシュの祖先＋依存物＋C までのソース」、upper を `lanes/B/upper`（前回のものをそのまま）にして mount し直す
3. 前回 B で検証したツリーから中身が変わったファイルの更新時刻をそろえる（§3.6 の 2）
4. エンジンが作った user namespace の中で、`/work` で `tsc --noEmit` や `cargo check` を動かす
5. 結果を記録する

ソースが変わっても upper（キャッシュ）は引き継がれる。これは、開発者が同じフォルダでソースを書き換えながらインクリメンタルビルドを繰り返すのと同じ状況で、差分の判断はコンパイラに任せる（設計書 ADR-001）。

**分岐**（lane A のある時点から lane B を作る）

1. A の upper を凍結して、キャッシュの層にする（A は mount していない状態で行う）
2. A には新しい空の upper を、B にも新しい空の upper を用意する。どちらも、凍結した層を lower の先頭に置く
3. 費用は、ディレクトリの rename と mkdir だけで、キャッシュの大きさやファイルの数によらない

**実装の土台**：MicroGit の agent（`guest/agent/overlay.go`、Go）は、層の凍結・積み上げ・非特権の mount・lowerdir の長さの対策（ADR-0003）をすでに持っている。containerd の snapshotter（設計書 ADR-004）は、active な snapshot の親が固定で、「同じ upper を別のソースの lower と組み合わせ直す」使い方を想定していない。エンジンは agent の層の扱いを土台にするほうが素直な見込み。

### 3.6 確かめるべき点

1. **upper を別の lower と組み合わせ直してよいか。** カーネルの OverlayFS の文書では、前に別の lower と使った upper を、別の lower と組み合わせて mount することは、`index` と `metacopy` が無効なら許される。MicroGit はこの 2 つを無効にした設定で固定している（ADR-0005：`userxattr,redirect_dir=nofollow,index=off,metacopy=off,xino=off`）。ただし、upper に入った古いコピー（ビルドツールがソースや依存物を書き換えた場合）や whiteout は、新しい lower を隠す。ビルドツールがソースや依存物を書き換えないことを前提にし、書き換えを検出したら upper を捨てる
2. **更新時刻で作り直しを判断するツールで、偽の緑が出ないか。** cargo や make は、ソースの更新時刻が前回のビルドより新しいかで作り直しを決める。古い時点へ分岐すると、中身は古い版に戻るのに、更新時刻も古いので「変わっていない」と判断され、古い成果物のまま緑になりうる（設計書 ADR-006 の「本当は壊れているのに緑」）。対策の案：前回その lane で検証したツリーと中身が違うファイルだけ、検証の前に更新時刻を今に変える（変えたファイルだけ upper にコピーされる）。差分の層でソースを積むと、変わっていないファイルの更新時刻は保たれるので、作り直しが最小になる。tsc は `.tsbuildinfo` に中身のハッシュを持つので影響を受けにくい見込み（要確認）
3. **キャッシュが絶対パスを持っていても再利用されるか。** 固定パスで mount すれば、パスは毎回同じになる。tsc と cargo で、分岐をまたいでキャッシュが実際に再利用されるか（作り直したファイルの数）を測る
4. **ファイル単位の複製の費用。** §3.3 のとおり、SQLite 系のキャッシュを使うツールで測る
5. **コミット単位でキャッシュを凍結する案。** 設計書 ADR-002 は、キャッシュ全体を複製する費用からコミット単位の保持を退けた。OverlayFS なら、検証のたびに upper を凍結しても、増えるのはそのビルドが書いたファイルだけになる。「分岐の元にした時点のキャッシュ」から正確に始められる利点と、層の数・ディスクの増え方を測れば、ADR-002 を見直す材料になる

### 3.7 最初の実験（数日、Go もエンジンも要らない）

小さな TypeScript のプロジェクトと Rust のプロジェクトで、シェルスクリプトと `unshare -Urm` だけで試す。

| 段階 | やること | 分かること |
|---|---|---|
| 1 | lane A でコミットを数個積み、`/work` に mount して検証を繰り返す | upper の引き継ぎでインクリメンタルビルドが効くか（§3.6 の 1・3） |
| 2 | A の途中の時点から lane B を分岐し、`/work` に mount し直して検証する | 分岐の費用と、分岐をまたいだキャッシュの再利用（作り直したファイルの数） |
| 3 | B で、A の先端より古い中身に戻したファイルを含めて cargo で検証する | 更新時刻による偽の緑が出るか、§3.6 の 2 の対策で消えるか |
| 4 | 同じことを reflink（XFS か btrfs の上の `cp --reflink`、分岐ごとに別のパス）と素朴なコピーでもやる | E-02 の比較の予備値と、パスが変わることによる再利用の差 |

1〜3 が崩れなければ、案 3 の前提は立つ。3 で偽の緑が対策できない場合は、更新時刻で判断するツールを適用の範囲から外すか、検証のたびにそのツールのキャッシュの確認を強める必要がある。

## 4. まとめ

| 案 | OverlayFS が速くするもの | 見込み | 位置づけ |

| 2（層を記録の正本に） | 今の設計のままでは、記録は速くならない。Git の形式の計算は支配的でなく、費用はファイルの作成・fsync・層づくり | 低い。ただし「保存＝凍結」の試作（Linux 限定）は唯一の筋道 | 否定的な結果の分析、または Linux 限定の試作 |

「保存ごとの記録を速くする」という目的は、案 3 では「保存ごとのビルド検証を、実用的な速さで回す」（設計書 §2.2 の前提）に形を変えて残る。OverlayFS は、記録そのものではなく、記録の **次** に来る処理（戻る・ビルドする）を、履歴の分岐に追従させながら安くする道具として効く。
