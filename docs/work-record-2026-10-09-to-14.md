## 3. うまくいかなかったこと・誤り（と、どう扱ったか）

私（Windows 側のエージェント）の誤りを含む。同じことを繰り返さないための記録。

### 3.1 計測に使っていたテスト自身が、結果に混ざっていた（#61、10-09）

- 何が起きたか：拡張機能テストは拡張機能と**同じプロセス**で動く。保存の直後にテストが `execFileSync` で Git を起動して HEAD を確かめていたので、そのあいだ MicroGit が agent の応答を読めず、層づくりの「通信」が長く測られた。#37 以降の CI・手元の「層の作成」「保存 1 回の処理全体」の値は、この待ちを含んでいた
- 見つけ方：同じ往復を VS Code の外で測ると 60 倍以上違った。通信を分け、往復のあいだのイベントループのすき間を測ると、ループが 1 回の長い処理でふさがれていた
- 対処：テストは保存の最中に Git を起動せず、内部コマンド `microgit.internal.lastSave` で待つ。master へは 5.1.3（PR #71）で入った。研究の現状の文書（§2.2 の「層づくりがいちばん重い」）を訂正した
- 注意：**非同期の `execFile` にしても、Linux の CI では数 ms 止まった**（子プロセスを作る瞬間）。測り方の落とし穴として §6 に残す

### 3.2 5.1.2 が公開済みなのを確かめずに、「出さずに取りやめた」と書いた（10-14）

- 何が起きたか：10-09 に Windows の機械から公開に失敗したままだと思い込み、PR #76・#77 で「5.1.2 は出さずに 5.2.0 にまとめた」「Marketplace は 5.1.1 のまま」と書いて master に入れた。実際は**利用者が 10-12 に Mac から公開済み**だった
- 見つけ方：最後にストアの版を確かめた（Marketplace の API、`gh release view`、Open VSX の API）
- 対処：PR #78 で、観測できた事実だけに直した。公開のときの sha256 の確認など Mac 側で何をしたかは、リポジトリに記録が無いので書いていない
- 教訓：**公開の事実を文書に書く前に、ストアの今の版を確かめる**（§6）

### 3.3 エージェント（サブエージェント）が、利用回数の上限で止まった

- 10-10（セッションの上限）と 10-11（週の上限）に、実行中の作業が途中で止まった。10-10 のものは `SendMessage` で再開できた。週の上限で止まった #72・#73 は、書きかけの変更が作業フォルダに残っていたので、10-14 に私が引き継いだ
- 止まった作業の変更は、**テストが通っているとは限らない**（#72 は単体テストが 1 件失敗していた）

### 3.4 書きかけの変更に、デバッグ用の出力が残っていた（#73）

- 何が起きたか：#73 の作業者が、画面の更新の呼び出し元を調べるため、**ホームフォルダ（`C:\Users\ssliv\refresh-trace.log`）にファイルを書くデバッグ用の出力**（`TRACE-TMP`）を製品のコードに入れたまま止まっていた。さらに、編集の都合で `'\n'` を `String.fromCharCode(10)` に書き換えた意味のない差分も 5 か所あった
- 見つけ方：コミットの前に、差分から `console.log`・`TRACE`・`debugger` などを検索した
- 対処：取り除いた。ログのファイルも消した。`'\n'` に戻す途中で、置換の書き方の誤りでコンパイルが壊れたが、コミットの前に気づいて直した
- 教訓：書きかけを引き継いだら、**コミットの前に、差分を検索して名残を確かめる**

### 3.6 作業の進め方での失敗

- **#66（Node.js 版）の最初のコミットのメッセージが、事実と違う。** 変更履歴と調査の文書の更新が、改行コード（CRLF）の違いで置き換えに失敗していたのに、メッセージには「更新した」と書いた。抜けた分は次のコミットで入れた（最初のメッセージは直していない）。**書いたことが入っているかを、コミットの前に `git show --stat` で確かめる**
- **#72 を master に入れる直前に、合わせたコミットの CI を待たずにマージした。** 手元の単体テスト（81 件成功）と拡張機能テストは通っていた。全環境の確認は、版を上げる PR #76 の CI で後から行った（通った）
- **文書の一括置換で、意図しない箇所まで書き換わった。** 引き継ぎの文書の `v5.1.2` を全部 `v5.2.0` にして、「古いタグ `v5.1.2`」が意味の通らない文になった。気づいて直した
- **複数ブランチを 1 回のコマンドでマージしようとして失敗した**（octopus マージは衝突する変更では使えない）。ブランチは更新されなかったが、同じコードをもう 1 回測ることになり、ばらつきの確認になった
- **ヒアドキュメントに長いスクリプトを入れたら実行されなかった。** 以後は、ファイルに書き出してから実行した
- **CI の VS Code のダウンロードのチェックサム不一致で、拡張機能テストが 1 回落ちた**（コードの問題ではない）。失敗した分だけ流し直して通った
- **利用者の指示「コストを重視して Haiku を優先」**：実際には Haiku を使わなかった。作業の中心が、正しさの判断が要るレビュー（Opus・Sonnet）と、私が直接できる小さな修正だったため。コストを抑えるために、エージェントではなく、私が手元でテスト・計測を流した場面が多い

## 6. 学んだこと（次から守ること）

- **測る道具も、測られる側と同じ場所で動いていれば、結果に混ざる。** VS Code の拡張機能テストは拡張機能と同じプロセスで動く。テストの同期処理（`execFileSync`・`spawnSync`・大きな同期の読み書き）は、拡張機能の待ちとして測られる。非同期の `execFile` でも、子プロセスを作る瞬間は止まりうる（Linux の CI）
- **外と中で同じものを測る。** 外（VS Code の外）の値を基準にすると、混ざりものが分かる
- **合計だけでなく、待っているあいだに何が起きていたかを測る。** イベントループのすき間の最長が、決め手になった
- **公開の事実（ストアの今の版、Release の状態）は、文書に書く前に、ストアで確かめる。** 手元の記憶や、前の文書の記述で書かない
- **書きかけを引き継いだら、コミットの前に、差分を検索して名残（`console.log`・`TRACE`・ファイルへの書き込み・意味のない書き換え）を確かめる**
- **コミットのメッセージに「した」と書いたことが、実際の差分に入っているかを確かめる**（`git show --stat`）
- **文書の置換は、置換する語の周りの文脈を確かめる**（`v5.1.2` を全部書き換えて、意味が通らなくなった）
- **まとめた操作は、1 本の失敗が全部を止めないかを確かめる**（まとめた `push` と壊れたタグ）。前の方法の失敗の扱いを、新しい方法でも守る
- **レビューには、実際に動かして反例を探すもの（敵対的レビュー）と、読んで正しさを見るもの（独立レビュー）の両方が効いた。** 独立レビューは、まとめた `push` の失敗の扱いを見つけた。敵対的レビューは、修正が効いていることを、タグ 0〜1000 本・変わった名前・壊れたタグ・保存との並行で確かめた
- **CI の数字は 1 回でなく、2 回見る。** Windows の CI は、1 回目に悪化して見えたものが、2 回目では消えた
