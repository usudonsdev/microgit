# 非エンジニア版: Google Drive 共有フォルダでの履歴共有(設計メモ・案)

2026-10-18。調査の根拠は [non-engineer-history-storage-survey.md](./non-engineer-history-storage-survey.md)。非エンジニア版の全体計画は `origin/docs/release-5.1.0` の `docs/non-engineer-oss-plan.md`(このブランチには無い)。ここに書くのは**案**であり、未実装・未検証の前提を含む。実装の正本にはしない。

## 1. 前提(利用者が確定させたもの)

- 相手に Git を入れさせない。
- **対象は Git の使い方を知らない人である。版の管理は GUI だけで完結させる。Git のコマンドや考え方(コミット、ブランチ、マージ、push など)を再現しない、見せない。**(確定: 利用者の方針、2026-11-23。画面と言葉の原則は §7.3)
- 共有の相手は、同じ会社やチームの人で、**Google Drive の共有フォルダ**で文書を共有する。
- 全員が、この OSS(専用の拡張機能)と Google Drive(Drive for desktop)を入れている。それ以外のソフト(Word、Excel、PDF ビューアなど)は問わない。
- **保存のたびの版管理は、ローカル環境だけで行う。** Drive への履歴のアップロードは、**利用者が明示的に押したときだけ**行う。
- 現行の verEve(エンジニア版)も同じ形である。保存のたびにローカルへ記録し、共有は `Publish Micro History` と `Fetch Micro History` の明示操作で行う(`design-policy.md` §4、README)。非エンジニア版も、この操作の対応を引き継ぐ。運び手が Git ではなく Drive になる。

## 2. 結論(案)

- **ローカルの履歴ストア**は、共有フォルダの外(OS のユーザー領域)に置く。保存のたびに自動で記録する。Drive には一切触れない。
- **Publish(共有に出す)** を押したときだけ、履歴のうち共有フォルダに無い分を、共有フォルダ内の専用フォルダへ普通のファイルとして書く。Drive for desktop が従来どおりそれを同期する。
- **Fetch(共有から取り込む)は自動で行う**(確定: 利用者の方針、2026-11-23。改訂前は「押したときだけ」)。他のメンバーが Publish した履歴を、自分のローカルの履歴ストアへ取り込む。手順と時機は §4.1。Publish(出す側)は、これまでどおり利用者が押したときだけ行う。
- **拡張機能は Drive API を使わない。** 運び手は Drive for desktop(ファイルシステムの同期)である。

Drive API を使わない理由:

- appDataFolder は共有できない(公式本文で確認)。
- `drive.file` は「アプリが作ったファイル」と「利用者が開いたファイル」に限られる(公式本文)。【推測】A さんの拡張機能が作った履歴を、B さんの拡張機能が自動で見つけるには、Picker で開く操作が要りそうで、使いにくい。実機で未検証。
- ファイルシステム経由なら、OAuth、スコープの審査、クォータの課金方針の未確定を、すべて避けられる。

## 3. 構成

ローカル(共有フォルダの外):

```
<OS のユーザー領域>/microgit/<フォルダのフルパスから決めた名前>/
  履歴ストア(保存ごとに更新。形式は計画 §7 の置き場 C に従う)
```

共有フォルダ F の中(Publish が書く):

```
F/
  (利用者の文書。Drive for desktop が従来どおり同期)
  .microgit-history/
    chunks/<hash 先頭2桁>/<hash>      内容アドレス型の不変チャンク
    log/<deviceId>/<連番>-<hash>      その端末だけが書く、追記専用のスナップショット記録
```

- **チャンク**: 展開した文書の中身(ZIP 形式なら部品ごと)を内容定義チャンク分割し、ハッシュで名付ける。ZIP 形式は、元のバイト列に戻すために、部品ごとの preflate の補正データと ZIP の骨組みも持つ(計測で確かめた第一候補。[計測メモ](./non-engineer-office-delta-measurement.md) §5)。preflate-rs の組み込み方と、補正データの互換を守る決まりは [non-engineer-preflate-integration.md](./non-engineer-preflate-integration.md)。一度書いたら変更しない。誰が書いても同じ内容は同じファイルになるので、重複しても害がない。
- **スナップショット記録**: 保存の時点のフォルダの木(パスとチャンクの一覧)。親の記録のハッシュを持つ。各端末は**自分の `log/<deviceId>/` にだけ**書き、他の端末の記録は書き換えない。
- Publish の手順: ①共有フォルダに無いチャンクを書く。②全チャンクが書けたことを確認する。③記録を一時名で書いて改名する。この順序は、最後の記録が見えた時点で、参照先が揃っていることを保証するためである。
- Fetch の手順: ①他端末の `log/` の記録を読む。②参照先のチャンクが全部あることを確認する。無ければその記録は「保留」にして、取り込まない。③揃った記録とチャンクを、ローカルのストアへコピーする。他端末の履歴は、その端末の系列として別に表示する。

### 3.1 共通の履歴パス(確定: 利用者の方針)

全員に、**同じ履歴フォルダ**を使うことを求める。履歴フォルダの置き場は、共有フォルダ F の中で**全員が同じ相対パス**とする。

- **パスは相対で決める。** 絶対パスは端末ごとに違う(Drive のドライブ文字や、マウント先、ショートカットの有無が人によって異なる)。「F の中の `.microgit-history/`」のように、F からの相対位置で揃える。F そのものの場所は、各自の PC で選んでもらう(9.2 の確認 3)。
- **目印ファイルを置く。** 履歴フォルダの直下に、チーム ID と形式の版を書いた小さなファイル(例: `team.json`)を置く。最初に Publish する人が作る。他の人は、フォルダを選んだ時点で目印を読み、**チーム ID が一致しないフォルダ、または形式の版が合わないフォルダは、書き込まずに警告する。** 違うフォルダに履歴を書いて、共有が噛み合わなくなる事故を防ぐ。
- **名前は利用者に見える通常の名前も許す。** 先頭ドットや隠し属性が Drive for desktop で同期されるかは未確認(§6 の検証 1)。全員が同じ名前に揃えるので、同期されない名前を避けて決められる。
- 保証できるのは「全員が同じ場所を指す」ことである。**Drive の同期の遅れ、順序の入れ替わり、重複は、これでは防げない。** それらへの対策は §4 の規則に残る。したがって「共有の安定性を保証する」とは書かない。パスを揃えることで防げるのは、場所の取り違え、書き込み先の食い違い、目印の見つけ損ねである。

## 4. 明示操作にしたことで変わること

- **同期の順序と重複の問題は、Publish と Fetch の瞬間に限られる。** 保存のたびに共有フォルダを書く案より、起きる回数がずっと少ない。残る問題への対策は次のとおり。

| 問題 | 対策(案) |
|---|---|
| 記録がチャンクより先に届く | Fetch は、参照先が全部あることを確認する。足りなければ保留にして、次の自動実行で取り直す(§4.1) |
| 書きかけのファイルが見える | 一時名で書いてから改名する。Fetch は一時名を無視する。ハッシュと一致しないチャンクは捨てる |
| 重複ファイルや競合コピー(`... (1)` など) | 書き手が 1 端末なので同名を 2 台が書かない。出た重複は、ハッシュが同じなら無視し、違えば警告する |
| 2 人が同じ文書を別々に編集して分岐する | 統合しない。系列ごとに別の枝として見せる。現行の `diverged` の扱いに合わせる(`design-policy.md` §4) |
| 古い履歴の整理 | ローカルのストアは自由に整理できる。共有側は追記のみで、段階 1 では削除しない。restic の prune が使う排他ロックは、Drive では信頼できない |
| 取り込んだ他人の本文を、自分の保存と誤認する | 本体の文書は Drive が従来どおり同期する。自分の端末の監視が、その変更をローカルの保存として記録する。内容のハッシュが、取り込み済みの他端末の記録に既にあれば、新しい記録を作らず参照だけにする |
| ストリーミング(オンライン専用)で未ダウンロード | 取得できない間は保留にする。案内は版の画面を開いたときに出す(§4.1) |

- **途中経過の秘密はローカルに留まる。** 下書きの途中、消した内容、機密を含む過去の版は、Publish を押すまで共有フォルダの人に見えない。ただし Publish は、前回の Publish 以降の連鎖を丸ごと出すので、途中の版も共有される。選んだ版だけを出す機能は、将来の課題にする。
- 「共有に出し忘れた」状態が起きる。Publish していない件数を、画面に表示する。

### 4.1 Fetch を自動にする(確定: 利用者の方針、2026-11-23)

Git を知らない人に「取り込む」操作を覚えさせないため、Fetch は自動にする。Publish(自分の版をチームに出す)は、途中経過の秘密を守るため(§4)、これまでどおり利用者が押す。

自動にしてよい理由: Fetch は、他の人の記録とチャンクを**自分のローカルの履歴ストアへ写すだけ**で、文書の本体には触れない(本体は Drive for desktop が従来どおり同期する)。§2 の手順のとおり、参照先が揃わない記録は保留にするので、途中で走っても壊れた履歴を作らない。何度走っても結果は同じ(取り込み済みはハッシュで分かる)。

いつ走らせるか(案):

- アプリの起動時。
- 履歴フォルダの `log/` の変化を監視して、変化があったとき(Drive for desktop が他の人の記録を届けたとき)。変化が続くあいだは数秒待ってまとめる。
- 右クリックの「過去のバージョンを確認」(§7.2)で版の画面を開いたとき。
- 念のための定期実行(例: 数分おき)。`log/` の監視が Drive の仮想ドライブで確実に届くかは未検証のため(§6 の検証 10)。

見せ方:

- 成功しても通知しない。版の一覧に、他の人の版が増えているだけにする。
- 保留(チャンクが未着)は、利用者に再実行を求めない。次の自動実行で取り直す。長く保留が続く版だけ、版の画面に「まだ Google ドライブから届いていない版があります」と出す(§7.3)。
- ストリーミング(オンライン専用)で読めないときも、自動では催促しない。版の画面を開いたときに、取得の案内を出す。

## 5. 守るべき不変条件(案)

- 保存のたびの処理は、共有フォルダに書かない。
- 各端末は、自分の `log/<deviceId>/` 以外のファイルを書き換えない。
- チャンクは、書いた後に変更しない。
- 記録が参照するチャンクが、記録より先に存在する(Publish が保証し、Fetch が確認する)。
- 読み手は、不完全な状態を壊れた履歴として扱わない。保留として待つ。
- 履歴が無い、または壊れていても、文書本体は読み書きできる。

## 6. 実装前に実機で確かめること(未検証)

1. Drive for desktop が、先頭ドットの名前や隠し属性のフォルダを同期するか。同期しない場合の名前の付け方。
2. 2 台以上で Publish したとき、チャンクと記録の届く順序、遅延、重複の出方。
3. ストリーミング(オンライン専用)の設定で、書いたファイルと、一時名からの改名が、他の端末にどう見えるか。
4. 実保存の Office 文書での、展開してからの分割の節約率とチャンク一覧のコスト。ZIP の再圧縮が原本とバイト列で一致するか(調査 §6)。**一部済み(2026-11-23、[計測メモ](./non-engineer-office-delta-measurement.md)):** 本物の Excel 2 ファイルで、zlib では元の圧縮データを再現できず、preflate-rs の補正データ(元の 1.8〜5.3%)を持てば 1 バイトも違わずに戻せた。1 文字の編集の模擬で、展開してから分割する方式の新しいバイトは 0.1〜0.6%。Word と、実際に保存し直した前後の版は未計測。
5. 共有フォルダの権限が閲覧のみの人が Publish したときの振る舞い。
6. 利用者が履歴フォルダを誤って削除した場合の検出と、復旧(ローカルのストアから再 Publish できる)。
7. 監視しているフォルダの中のファイルを書き出しで置き換えたとき(§7.1)、Drive for desktop が同じファイルの新しい版として同期するか(共有リンクと Drive の版履歴が保たれるか)。そのまま書き込む場合と、一時名で書いて改名する場合の両方で確かめる。
8. Drive for desktop がアップロードを済ませたファイルかどうかを、アプリから判定できるか(§7.2)。あわせて、Drive for desktop が足す右クリックの項目と、このアプリの項目の並び。
9. Windows 11 の最初の短い右クリックメニューに、管理者権限なしで項目を出せるか(パッケージの身元と署名の要否。§7.2)。
10. 履歴フォルダの `log/` の変化を、Drive for desktop の仮想ドライブ上で監視できるか(他の人の記録が届いたときに、変化の通知が来るか。§4.1)。

## 7. 既知の制限と、利用者に伝えること

- 共有フォルダに入れる人は、**Publish された分の履歴**を全員が読める。削除した内容や、機密を含む過去の版も、Publish した連鎖に含まれていれば読める。PDF の増分更新で黒塗りが復元された事故と同じ性質である。履歴から外すファイルの除外リストは、計画では後回し(`non-engineer-oss-plan.md` §6.4)だが、共有の前に優先して検討する。
- 本体ファイルを共有フォルダの外に持ち出す(メール添付など)と、履歴は付かない。持ち出し用の書き出しは別の明示操作で、共有とは別機能にする。
- 拡張機能を入れていない人は、履歴を作ることも読むこともできない。共有フォルダの文書は、従来どおり読み書きできる。
- ローカルの履歴ストアは端末ごとで、Publish していない履歴は、その端末が壊れると失われる。

### 7.1 書き出しで同名のファイルがあるとき(確定: 利用者の方針、2026-11-22)

過去の版をファイルとして書き出す(持ち出し用の書き出し、版の復元先の指定)とき、書き出し先に同じ名前のファイルがある場合の扱い。

**方針: 利用者からは、同じファイルに差分が重なっているように見せる。** 名前を変えた別のファイルを増やさない。ファイルは 1 つのまま、その履歴に版が 1 つ増える。

経緯: 最初は Adobe Lightroom Classic の書き出しの「既存のファイル」の設定(確認する・ハイフンと番号を付けた別名 `IMG_0001-2.jpg`・警告せずに上書き・スキップ)をまねる案で進めた(2026-11-21)。その後、利用者が「Lightroom 方式そのものが、思い描いていた姿と違っていた」と取り下げた(2026-11-22)。Lightroom の方式は、書き出したものを**別々のファイル**として並べる考え方で、ここで求めているのは**1 つのファイルの版が積み重なる**見え方である。そのため、Lightroom に関わる決定(初期値「一意の名前」、番号の上限 `-99`、表示名を Lightroom に寄せる)は、すべて無効とする。

#### 同じファイルに版として重ねる

書き出し先に同じ名前のファイルがあるとき、そのファイルの中身を書き出す内容に置き換え、置き換えたことを**そのファイルの新しい版として履歴に記録する**。元の中身は 1 つ前の版として残るので、いつでも戻せる。

- 似た前例: Google Drive のウェブで同名のファイルを上げると、「既存のファイルを更新する(新しい版にする)」か「別々のファイルとして残す」かを聞かれる。【記憶による。画面の表記は本調査では確認していない】ここで採るのは前者である。
- 過去の版を同じファイルへ書き出すこと(実質の復元)も、**履歴を巻き戻さず、上に新しい版を重ねる。** エンジニア版の「保存すると、いまの内容が新しい記録になる」(`design-policy.md` の巻き戻しの節)と同じ考え方である。

守ること(不変条件):

- **置き換える前に、いまの中身が履歴にあることを確かめる。** 最後の記録の後に、監視が拾う前の変更がある(あるいは監視が止まっていた)なら、置き換えの前に、いまの中身を 1 つの版として記録する。記録できなければ置き換えない。これが無いと「重ねる」のつもりで中身が消える。
- **新しい版には、書き出しで作られたことを記録する。** 例: 「書き出し: 11/20 15:30 の版から」。利用者が自分で保存した版と見分けられるようにする。監視が同じ書き込みを拾って、版を 2 つ作らないようにする(内容のハッシュが同じなら 1 つにまとめる。§4 の表の、取り込んだ本文の扱いと同じ)。
- **書き出す内容が、いまの中身と同じなら、何もしない。** 版を増やさない。
- **そのファイルを別のアプリ(Word など)が開いていて書けないときは、置き換えず、閉じてから再実行するよう伝える。** 開いたまま置き換えると、そのアプリが古い内容で保存し直して、書き出しが上書きされることがある。
- 【未検証】置き換えの書き方(そのまま書き込むか、一時名で書いて改名するか)で、Drive for desktop が「同じファイルの新しい版」として同期するか、「消して新しく作った別のファイル」として扱うかが変わりうる。後者だと、Drive 側の共有リンクや Drive 自身の版履歴が切れるおそれがある(§6 の検証 7)。

未決:

- **書き出し先が履歴の対象の外**(デスクトップ、USB メモリなど)にあるときの扱い。そのファイルには履歴が無いので、そのままでは重ねられない。**段階 1 では対象を Drive にアップロードされたファイルに限る(§7.2)ので、後回しにする。** 対象を広げるときに決める。案: 置き換える前に、いまの中身をローカルの履歴ストアに記録し、以後そのファイルも履歴の対象にする(重ねる見え方を保てる)。別案: 同名があれば書かずに場所を選び直させる。
- 書き出しの操作の名前(例: 「この版を書き出す」「この版に戻す」)。入口は §7.2 の版の画面に置く。

採らなかった案:

- **Lightroom Classic の方式(別名 `名前-2.拡張子` で並べる。確認・上書き・スキップを選ばせる)**: 書き出すたびにファイルが増え、どれが最新か分からなくなる。利用者が思い描いていたのは、1 つのファイルに版が重なる姿だった(上の経緯)。
- **日時を付けた別名(`報告書_20261121-1530.docx`)**: 同じく別々のファイルが増える。
- **黙って上書きする(履歴に残さない)**: 元の中身が消える。

### 7.2 過去の版を見る入口と、対象のファイル(確定: 利用者の方針、2026-11-22)

**入口: ファイルを右クリックすると「過去のバージョンを確認」が出て、押すとそのファイルの版の情報が見られる。**

- 版の画面には、そのファイルの版の一覧(日時、自分の保存か、書き出しで作られたか、チームの他の人の版か)を出す。言葉は §7.3 に従う。§7.1 の書き出し・戻す操作は、この画面から行う。画面の中身(差分の見せ方など)は未決。
- 右クリックの項目は、**対象のファイルにだけ出す**(対象外のファイルに出して、押したら「履歴がありません」とするより分かりやすい)。
- 項目の名前は、Windows に元からある「以前のバージョンの復元」(ファイル履歴・復元ポイントの機能)と取り違えやすい。名前を変えるか、アプリ名を前に付けるか(例: 「verEve: 過去のバージョンを確認」)は未決。【一般的な知識であり、本調査では確認していない】
- 【一般的な知識であり、本調査では確認していない。実機で確かめる】Windows 11 の右クリックメニューは、最初に出る短いメニューと、「その他のオプションを表示」の奥の従来のメニューに分かれている。最初の短いメニューに出すには、`IExplorerCommand` を実装し、アプリに「パッケージの身元」(MSIX、または外部の場所を使うまばらなパッケージ)を持たせる必要がある。従来のメニューだけなら、利用者単位のレジストリ(`HKCU\Software\Classes\*\shell`)で足り、管理者権限が要らない(§9.4 の方針に合う)。非エンジニアは奥のメニューを開かないことが多いので、最初の短いメニューに出すことを目標にし、配布の形(§9.4 の署名)と合わせて決める。対象のファイルにだけ出す判定も、`IExplorerCommand` の状態の問い合わせ(`GetState`)で行える見込み。
- 【未検証】Drive for desktop も右クリックメニューに項目を足している。並びと名前が紛らわしくならないか、実機で確かめる。

**対象のファイル: 段階 1 では、Google Drive にアップロードされたファイルだけから始める。**

- 具体的には、共有フォルダ F(§3)の中にあり、Drive for desktop がアップロードを済ませたファイル。それ以外(デスクトップ、USB メモリ、F の外のフォルダ)は、段階 1 では履歴を取らず、右クリックの項目も出さない。
- 【未検証】「アップロード済み」をどう判定するか。Drive for desktop はエクスプローラーに同期の状態を示すアイコンを出しているが、アプリからその状態を読む方法は確かめていない。読めない場合は「F の中にあるファイル」を対象とみなす案に落とす。§6 の検証に加える。
- これにより、§7.1 の「履歴の対象の外への書き出し」は段階 1 では起きない場面として後回しにできる。

### 7.3 画面と言葉の原則(確定: 利用者の方針、2026-11-23。表の言葉も同日に案のまま採用。ただし個々の文言は、実際の画面で調整してよい)

対象は Git の使い方を知らない人である。**大事なのは、GUI だけで版の管理が完結すること**で、Git のコマンドや概念を再現することではない。

- **利用者がすることは、普段どおりファイルを保存することだけ。** 版は保存のたびに自動でできる。版に名前やメッセージを付けることは求めない(付けたい人のための任意の欄は、後で検討してよい)。
- **版を見る・戻す・書き出す・共有する操作は、すべて画面のボタンとメニューで行う。** 入口は右クリックの「過去のバージョンを確認」(§7.2)。コマンド入力や設定ファイルの手編集を求めない。
- **画面に Git の言葉を出さない。** この文書の内部の呼び名と、画面に出す言葉を分ける。画面の言葉は案で、表示名は未決。

| この文書の内部の呼び名 | 画面での見せ方(案) |
|---|---|
| 記録、スナップショット記録 | 版(バージョン)。日時で呼ぶ(例: 「11/20 15:30 の版」) |

## 8. 採らなかった案と理由

- **保存のたびに共有フォルダへ書く**: 順序と重複の問題が頻繁に起き、途中経過の秘密も共有される。利用者が明示操作を望んだ。
- **Drive API で履歴を持つ(appDataFolder)**: 共有できないので、他のユーザーとの共有に使えない。
- **Drive API で共有フォルダに履歴を書く(drive.file)**: 他の人が作ったファイルを自動で見つけられない可能性がある。審査とクォータの運用も増える。
- **Drive の revisions に任せる**: 約 30 日、非固定が 100 個を超えると消え、固定は 200 個まで。
- **GitHub のようなバージョン管理ソフトを別に作る**: 利用者が commit や push を覚えることになる。ここで採る Publish / Fetch は、押す操作が 2 つだけで、版の管理を利用者に求めない。
- **履歴を本体ファイルに埋め込む**: 形式ごとの実装が要り、他のアプリが再保存で消すリスクがある。Word と Google Docs で customXml が残るかが未検証。

## 9. 導入時の確認とチュートリアル(案)

利用者の前提: Drive for desktop を知らない非エンジニアが多い。導入の流れの中で、存在確認と案内を行う。

### 9.1 方針

- **ローカルの記録は Drive for desktop が無くても動く。** 確認の結果が「無い」でも、インストールを止めず、記録は始める。必要になるのは Publish と Fetch だけである。最初の Publish を押したときに、再度確認して案内する。
- 案内は**アプリの中に画面で出す**。長い文書を読ませない。手順の正本は Google の公式ヘルプとし、このアプリでは**手順を複製せず**、公式ページへ誘導する。Google の画面や名称は変わるため、複製すると古くなる。

### 9.2 確認する項目

「入っているか」だけでは足りない。Publish と Fetch が成り立つ条件を順に確認する。

| 確認 | 見方(案) | 結果が悪いときの案内 |
|---|---|---|
| 1. Drive for desktop がインストールされているか | 標準のインストール先、または実行中のプロセスを探す。【未検証】公式ヘルプで確認できたのは、データの置き場 `AppData\Local\Google\DriveFS`(Windows)と `~/Library/Application Support/Google/DriveFS`(macOS)まで | インストールの案内(§9.3) |
| 2. 起動していて、サインイン済みか | 同上のデータの置き場、またはマウント先の有無。【未検証】 | 起動とサインインの案内 |
| 3. 共有フォルダが、この PC 上のフォルダとして見えているか | 利用者に選んでもらったフォルダが、Drive for desktop の配下にあるか | 「共有フォルダをこの PC に出す」案内(§9.3) |
| 4. そのフォルダが、オンライン専用でなく、手元にあるか | 公式ヘルプのストリーミングとミラーリングの違い | 「このフォルダはオフラインでも使えるようにする」の案内 |
| 5. 自分にそのフォルダへの書き込み権があるか | 試しに専用フォルダを作れるか | 管理者に編集権限を依頼する文面を出す |

- 確認 1〜2 の見つけ方(標準のインストール先、プロセス名、マウント先のパス)は、公式ヘルプで確認できていない。実機で調べて、このファイルに追記する。
- フォルダを選ぶ画面を用意し、**利用者に Drive のフォルダを指定してもらう**。パスを自動で推測するより確実である。

### 9.3 チュートリアルの内容(案)

- インストール、サインイン、共有フォルダを自分の PC に出す、の 3 つの場面を、画面付きの短い手順にする。細かいボタン名は公式ヘルプに任せる。
- 「これは何のために要るのか」を一言で説明する。例: 「チームの人と履歴を共有するために、Google Drive をこのパソコンで使えるようにします。個人で使うだけなら、今はスキップできます」。
- 管理者が入れる場合のため、情報システム担当に渡す依頼文のひな形を用意する。
- 端末の種類に合わせて出し分ける(Windows と macOS)。

### 9.4 アプリの形(確定): 独立したアプリ(.exe)

利用者が確定させた。VS Code の拡張機能ではなく、独立した Windows アプリとして配布する。1 節の「専用の拡張機能」は、この専用アプリを指すものと読み替える。

この形が決めること(案):

- **導入時の確認は、セットアップウィザードまたは初回起動の画面で行う。** 9.2 の 5 項目を、アプリ自身が画面で順に確認できる。
- **常駐する監視プロセスとして動かす。** フォルダを監視して保存ごとに記録する(計画の置き場 C の「監視プロセス」に当たる)。Windows のログオン時に自動起動し、タスクトレイに状態を出す。起動していない間の保存は記録されない。この制限を、画面で伝える。
- **インストールは利用者単位にする(管理者権限を求めない)。** 企業の端末では、管理者権限が取れないことが多いため。【推測】実機と運用で確認が要る。
- **配布時の署名。** 署名のない .exe は、Windows の警告画面(SmartScreen)で止まりやすい。非エンジニアには強い障害になる。コード署名の入手と運用を、配布の前に決める。【一般的な知識であり、本調査では確認していない】
- **macOS は対象外とする。** .exe は Windows 専用である。macOS 版を作るかは未決。作る場合、Drive for desktop の置き場(`~/Library/Application Support/Google/DriveFS`)は公式ヘルプで確認できているので、検出は別に実装する。
- エンジニア版(VS Code 拡張、`src/` 以下)とは別の実行体になる。共有してよいのは、ストアや履歴形式のコードを、ライブラリとして切り出せた場合だけ。エンジニア版の `refs/microgit` とは混ぜない(計画 §6.4)。

### 9.5 未決

- Windows で Drive for desktop の存在を調べる具体的な方法(登録情報、標準のインストール先、プロセス名、ドライブ文字の有無)。公式ヘルプで確認できておらず、実機で調べる。
- 企業の管理下で、Drive for desktop の導入が制限されている場合の案内。
- 公式ヘルプのどのページを正本として案内するか(選定と、変更への追従)。
