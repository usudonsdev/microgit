# 非エンジニア版: Google Drive 共有フォルダでの履歴共有(設計メモ・案)

2026-10-18。調査の根拠は [non-engineer-history-storage-survey.md](./non-engineer-history-storage-survey.md)。非エンジニア版の全体計画は `origin/docs/release-5.1.0` の `docs/non-engineer-oss-plan.md`(このブランチには無い)。ここに書くのは**案**であり、未実装・未検証の前提を含む。実装の正本にはしない。

## 1. 前提(利用者が確定させたもの)

- 相手に Git を入れさせない。
- 共有の相手は、同じ会社やチームの人で、**Google Drive の共有フォルダ**で文書を共有する。
- 全員が、この OSS(専用の拡張機能)と Google Drive(Drive for desktop)を入れている。それ以外のソフト(Word、Excel、PDF ビューアなど)は問わない。
- 現行の MicroGit(エンジニア版)は、履歴を親リポジトリの `refs/microgit/<branch>/*` に載せ、本体と同じリモートで運ぶ(`design-policy.md` §4)。非エンジニア版も「本体と履歴を同じ共有の仕組みで運ぶ」点を引き継ぐ。ただし運び手が Git ではなく Drive になる。

## 2. 結論(案)

**運び手は Drive for desktop(ファイルシステムの同期)に任せ、拡張機能は Drive API を使わない。** 履歴は、共有フォルダの中の専用フォルダに、拡張機能が普通のファイルとして書く。

理由:

- 調査した範囲で、Drive API の `drive.file` スコープは「アプリが作ったファイル」と「利用者が開いたファイル」に限られる(公式本文)。【推測】A さんの拡張機能が作った履歴ファイルを、B さんの拡張機能が一覧で見つけるには、Picker で開く操作が要りそうで、自動同期には向かない。実機で未検証。
- appDataFolder は共有できない(公式本文)。他のユーザーとの共有には使えない。
- ファイルシステム経由なら、OAuth、スコープの審査、クォータの課金方針の未確定を、すべて避けられる。
- 全員が Drive for desktop を入れているという前提が、ここで効く。

代償:

- 履歴フォルダが共有フォルダ内に見える。これは「二つ目のもの」だが、アプリが自動で作って更新し、利用者は触らない前提にする。名前は専用の固定名にし、隠し属性または先頭ドットを付ける。ただし Drive for desktop がドットや隠しファイルを同期するかは**未確認**(§6 の検証 1)。
- 順序と重複の問題を、拡張機能の側で防ぐ必要がある(§4)。

## 3. 構成

共有フォルダ F の中に、次を置く。

```
F/
  (利用者の文書: Word、Excel、PDF など。Drive for desktop が従来どおり同期)
  .microgit-history/            ← 拡張機能が作る専用フォルダ
    chunks/<hash 先頭2桁>/<hash>    内容アドレス型の不変チャンク
    log/<deviceId>/<連番>-<hash>    その端末だけが書く追記専用のスナップショット記録
```

- **チャンク**: 展開した文書の中身(ZIP 形式なら部品ごと)を内容定義チャンク分割し、ハッシュで名付ける。一度書いたら変更しない。同じ内容は誰が書いても同じファイルになるので、重複しても害がない。
- **スナップショット記録**: 保存の時点のフォルダ F の木(ファイルパスと、チャンクの一覧)を表す。親の記録のハッシュを持つ。各端末は**自分の `log/<deviceId>/` にだけ**書き、他の端末の記録は書き換えない。
- 書き込み規則: チャンクを全部書き終えてから、最後にスナップショット記録を書く。記録は、一時名で書いて名前を変える(完成した記録だけが読み手に見えるようにする)。

## 4. 同期で起きる問題と対策

調査で、同期サービス上のリポジトリでは、競合ではなく**順序と重複の問題**が起きると分かった(restic フォーラム、rclone の Drive 文書)。

| 問題 | 対策(案) |
|---|---|
| スナップショット記録がチャンクより先に届く | 読み手は、記録が参照する全チャンクの存在を確認する。足りなければ「保留」として扱い、後で再確認する。見つからないまま長く経つ場合だけ警告する |
| 書きかけのファイルが見える | 一時名で書いてから改名する。読み手は、一時名を無視する。ハッシュと名前が一致しないチャンクは捨てて再取得する |
| 重複ファイルや競合コピー(`... (1)` など) | 書き手が 1 端末に限られるので、同じ名前を 2 台が書くことはない。それでも出た重複は、ハッシュが同じなら無視し、違えば警告する |
| 2 人が同時に保存して履歴が分岐する | 分岐は記録に残し、統合しない。現行の `importFromParentRefs` が分岐を `diverged` として扱う考え方に合わせる(`design-policy.md` §4)。表示で両方の枝を見せる |
| 削除と、端末をまたぐロック | 段階 1 では、チャンクと記録を**削除しない**。容量が問題になるまで、削除(古い履歴の整理)は作らない。restic の prune が使う排他ロックは、Drive では信頼できない |
| 他の人の編集を、自分の保存と誤認して二重に記録する | Drive が同期して来た変更を、自分の端末の監視が検知する。内容のハッシュが、既に誰かの記録にあれば、新しい記録を作らず「観測済み」とする(内容アドレスなので判定できる) |
| Drive for desktop のストリーミング(オンライン専用)で、未ダウンロードのファイルがある | 読む前に取得を促す。取得できない間は保留にする |

## 5. 守るべき不変条件(案)

- 各端末は、自分の `log/<deviceId>/` 以外のファイルを書き換えない。
- チャンクは、書いた後に変更しない。
- 記録が参照するチャンクが、記録より先に存在する。
- 読み手は、不完全な状態を壊れた履歴として扱わない。保留として待つ。
- 履歴のフォルダが無い、または壊れていても、文書本体は読める。本体への書き込みは行わない(現行の「記録しないものは触らない」方針と同じ)。

## 6. 実装前に実機で確かめること(未検証)

1. Drive for desktop が、先頭ドットの名前や隠し属性のフォルダを同期するか。同期しない場合の名前の付け方。
2. 2 台以上で、チャンクと記録を書いたとき、届く順序、遅延、重複の出方。
3. Drive for desktop のストリーミングで、書いたファイルと一時名からの改名が、他端末にどう見えるか。
4. 展開してからの分割の、実保存の Office 文書での節約率と、チャンク一覧のコスト。ZIP の再圧縮が原本とバイト列で一致するか(調査 §6)。
5. 共有フォルダの権限(閲覧のみの人)で、履歴を書けない場合の振る舞い。
6. 利用者が履歴フォルダを誤って削除した場合の検出と、復旧の手順。

## 7. 既知の制限と、利用者に伝えること

- 共有フォルダの権限がある人は、全員が履歴の全内容を読める。削除した内容や、機密を含む過去の版も読める。PDF の増分更新で黒塗りが復元された事故と同じ性質の問題になりうる。履歴に入れないファイルの除外リストは、計画では後回しになっている(`non-engineer-oss-plan.md` §6.4)。共有では、優先度を上げて検討する。
- 本体ファイルを共有フォルダの外に持ち出す(メール添付など)と、履歴は付かない。書き出しは別の明示的な操作として考える。
- 拡張機能を入れていない人は、履歴を作れず、読むこともできない。共有フォルダの文書は、従来どおり読み書きできる。

## 8. 採らなかった案と理由

- **Drive API で履歴を持つ(appDataFolder)**: 共有できないので、他のユーザーとの共有に使えない。個人の端末間だけなら使える。
- **Drive API で共有フォルダに履歴を書く(drive.file)**: 他の人が作ったファイルを自動で見つけられない可能性がある(§2)。審査、クォータ、OAuth の運用も増える。
- **Drive の revisions に任せる**: 約 30 日、非固定が 100 個を超えると消え、固定は 200 個まで。
- **GitHub のようなバージョン管理ソフトを別に作る**: 利用者が commit や push を覚えることになる。「ユーザーが管理するファイルを本体と履歴の二つにしない」要件と逆になる。
- **履歴を本体ファイルに埋め込む**: 形式ごとの実装が要り、他のアプリが再保存で消すリスクがある。Word と Google Docs で customXml が残るかが未検証。共有の主経路にはしない。
