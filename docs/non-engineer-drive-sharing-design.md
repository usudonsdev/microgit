# 非エンジニア版: Google Drive 共有フォルダでの履歴共有(設計メモ・案)

2026-10-18。調査の根拠は [non-engineer-history-storage-survey.md](./non-engineer-history-storage-survey.md)。非エンジニア版の全体計画は `origin/docs/release-5.1.0` の `docs/non-engineer-oss-plan.md`(このブランチには無い)。ここに書くのは**案**であり、未実装・未検証の前提を含む。実装の正本にはしない。

## 1. 前提(利用者が確定させたもの)

- 相手に Git を入れさせない。
- 共有の相手は、同じ会社やチームの人で、**Google Drive の共有フォルダ**で文書を共有する。
- 全員が、この OSS(専用の拡張機能)と Google Drive(Drive for desktop)を入れている。それ以外のソフト(Word、Excel、PDF ビューアなど)は問わない。
- **保存のたびの版管理は、ローカル環境だけで行う。** Drive への履歴のアップロードは、**利用者が明示的に押したときだけ**行う。
- 現行の MicroGit(エンジニア版)も同じ形である。保存のたびにローカルへ記録し、共有は `Publish Micro History` と `Fetch Micro History` の明示操作で行う(`design-policy.md` §4、README)。非エンジニア版も、この操作の対応を引き継ぐ。運び手が Git ではなく Drive になる。

## 2. 結論(案)

- **ローカルの履歴ストア**は、共有フォルダの外(OS のユーザー領域)に置く。保存のたびに自動で記録する。Drive には一切触れない。
- **Publish(共有に出す)** を押したときだけ、履歴のうち共有フォルダに無い分を、共有フォルダ内の専用フォルダへ普通のファイルとして書く。Drive for desktop が従来どおりそれを同期する。
- **Fetch(共有から取り込む)** を押したときだけ、他のメンバーが Publish した履歴を、自分のローカルの履歴ストアへ取り込む。
- **拡張機能は Drive API を使わない。** 運び手は Drive for desktop(ファイルシステムの同期)である。

Drive API を使わない理由:

- appDataFolder は共有できない(公式本文で確認)。
- `drive.file` は「アプリが作ったファイル」と「利用者が開いたファイル」に限られる(公式本文)。【推測】A さんの拡張機能が作った履歴を、B さんの拡張機能が自動で見つけるには、Picker で開く操作が要りそうで、使いにくい。実機で未検証。
- ファイルシステム経由なら、OAuth、スコープの審査、クォータの課金方針の未確定を、すべて避けられる。

## 3. 構成

ローカル(共有フォルダの外):

```
<OS のユーザー領域>/microgit/<フォルダのフルパスから決めた名前>/
  履歴ストア(保存ごとに更新。形式は計画 §7 の置き場 C に従う)
```

共有フォルダ F の中(Publish が書く):

```
F/
  (利用者の文書。Drive for desktop が従来どおり同期)
  .microgit-history/
    chunks/<hash 先頭2桁>/<hash>      内容アドレス型の不変チャンク
    log/<deviceId>/<連番>-<hash>      その端末だけが書く、追記専用のスナップショット記録
```

- **チャンク**: 展開した文書の中身(ZIP 形式なら部品ごと)を内容定義チャンク分割し、ハッシュで名付ける。一度書いたら変更しない。誰が書いても同じ内容は同じファイルになるので、重複しても害がない。
- **スナップショット記録**: 保存の時点のフォルダの木(パスとチャンクの一覧)。親の記録のハッシュを持つ。各端末は**自分の `log/<deviceId>/` にだけ**書き、他の端末の記録は書き換えない。
- Publish の手順: ①共有フォルダに無いチャンクを書く。②全チャンクが書けたことを確認する。③記録を一時名で書いて改名する。この順序は、最後の記録が見えた時点で、参照先が揃っていることを保証するためである。
- Fetch の手順: ①他端末の `log/` の記録を読む。②参照先のチャンクが全部あることを確認する。無ければその記録は「保留」にして、取り込まない。③揃った記録とチャンクを、ローカルのストアへコピーする。他端末の履歴は、その端末の系列として別に表示する。

## 4. 明示操作にしたことで変わること

- **同期の順序と重複の問題は、Publish と Fetch の瞬間に限られる。** 保存のたびに共有フォルダを書く案より、起きる回数がずっと少ない。残る問題への対策は次のとおり。

| 問題 | 対策(案) |
|---|---|
| 記録がチャンクより先に届く | Fetch は、参照先が全部あることを確認する。足りなければ保留にして、利用者に「同期の完了を待ってから再実行」と伝える |
| 書きかけのファイルが見える | 一時名で書いてから改名する。Fetch は一時名を無視する。ハッシュと一致しないチャンクは捨てる |
| 重複ファイルや競合コピー(`... (1)` など) | 書き手が 1 端末なので同名を 2 台が書かない。出た重複は、ハッシュが同じなら無視し、違えば警告する |
| 2 人が同じ文書を別々に編集して分岐する | 統合しない。系列ごとに別の枝として見せる。現行の `diverged` の扱いに合わせる(`design-policy.md` §4) |
| 古い履歴の整理 | ローカルのストアは自由に整理できる。共有側は追記のみで、段階 1 では削除しない。restic の prune が使う排他ロックは、Drive では信頼できない |
| 取り込んだ他人の本文を、自分の保存と誤認する | 本体の文書は Drive が従来どおり同期する。自分の端末の監視が、その変更をローカルの保存として記録する。内容のハッシュが、取り込み済みの他端末の記録に既にあれば、新しい記録を作らず参照だけにする |
| ストリーミング(オンライン専用)で未ダウンロード | Fetch の前に取得を促す。取得できない間は保留にする |

- **途中経過の秘密はローカルに留まる。** 下書きの途中、消した内容、機密を含む過去の版は、Publish を押すまで共有フォルダの人に見えない。ただし Publish は、前回の Publish 以降の連鎖を丸ごと出すので、途中の版も共有される。選んだ版だけを出す機能は、将来の課題にする。
- 「共有に出し忘れた」状態が起きる。Publish していない件数を、画面に表示する。

## 5. 守るべき不変条件(案)

- 保存のたびの処理は、共有フォルダに書かない。
- 各端末は、自分の `log/<deviceId>/` 以外のファイルを書き換えない。
- チャンクは、書いた後に変更しない。
- 記録が参照するチャンクが、記録より先に存在する(Publish が保証し、Fetch が確認する)。
- 読み手は、不完全な状態を壊れた履歴として扱わない。保留として待つ。
- 履歴が無い、または壊れていても、文書本体は読み書きできる。

## 6. 実装前に実機で確かめること(未検証)

1. Drive for desktop が、先頭ドットの名前や隠し属性のフォルダを同期するか。同期しない場合の名前の付け方。
2. 2 台以上で Publish したとき、チャンクと記録の届く順序、遅延、重複の出方。
3. ストリーミング(オンライン専用)の設定で、書いたファイルと、一時名からの改名が、他の端末にどう見えるか。
4. 実保存の Office 文書での、展開してからの分割の節約率とチャンク一覧のコスト。ZIP の再圧縮が原本とバイト列で一致するか(調査 §6)。
5. 共有フォルダの権限が閲覧のみの人が Publish したときの振る舞い。
6. 利用者が履歴フォルダを誤って削除した場合の検出と、復旧(ローカルのストアから再 Publish できる)。

## 7. 既知の制限と、利用者に伝えること

- 共有フォルダに入れる人は、**Publish された分の履歴**を全員が読める。削除した内容や、機密を含む過去の版も、Publish した連鎖に含まれていれば読める。PDF の増分更新で黒塗りが復元された事故と同じ性質である。履歴から外すファイルの除外リストは、計画では後回し(`non-engineer-oss-plan.md` §6.4)だが、共有の前に優先して検討する。
- 本体ファイルを共有フォルダの外に持ち出す(メール添付など)と、履歴は付かない。持ち出し用の書き出しは別の明示操作で、共有とは別機能にする。
- 拡張機能を入れていない人は、履歴を作ることも読むこともできない。共有フォルダの文書は、従来どおり読み書きできる。
- ローカルの履歴ストアは端末ごとで、Publish していない履歴は、その端末が壊れると失われる。

## 8. 採らなかった案と理由

- **保存のたびに共有フォルダへ書く**: 順序と重複の問題が頻繁に起き、途中経過の秘密も共有される。利用者が明示操作を望んだ。
- **Drive API で履歴を持つ(appDataFolder)**: 共有できないので、他のユーザーとの共有に使えない。
- **Drive API で共有フォルダに履歴を書く(drive.file)**: 他の人が作ったファイルを自動で見つけられない可能性がある。審査とクォータの運用も増える。
- **Drive の revisions に任せる**: 約 30 日、非固定が 100 個を超えると消え、固定は 200 個まで。
- **GitHub のようなバージョン管理ソフトを別に作る**: 利用者が commit や push を覚えることになる。ここで採る Publish / Fetch は、押す操作が 2 つだけで、版の管理を利用者に求めない。
- **履歴を本体ファイルに埋め込む**: 形式ごとの実装が要り、他のアプリが再保存で消すリスクがある。Word と Google Docs で customXml が残るかが未検証。

## 9. 導入時の確認とチュートリアル(案)

利用者の前提: Drive for desktop を知らない非エンジニアが多い。導入の流れの中で、存在確認と案内を行う。

### 9.1 方針

- **ローカルの記録は Drive for desktop が無くても動く。** 確認の結果が「無い」でも、インストールを止めず、記録は始める。必要になるのは Publish と Fetch だけである。最初の Publish を押したときに、再度確認して案内する。
- 案内は**アプリの中に画面で出す**。長い文書を読ませない。手順の正本は Google の公式ヘルプとし、このアプリでは**手順を複製せず**、公式ページへ誘導する。Google の画面や名称は変わるため、複製すると古くなる。

### 9.2 確認する項目

「入っているか」だけでは足りない。Publish と Fetch が成り立つ条件を順に確認する。

| 確認 | 見方(案) | 結果が悪いときの案内 |
|---|---|---|
| 1. Drive for desktop がインストールされているか | 標準のインストール先、または実行中のプロセスを探す。【未検証】公式ヘルプで確認できたのは、データの置き場 `AppData\Local\Google\DriveFS`(Windows)と `~/Library/Application Support/Google/DriveFS`(macOS)まで | インストールの案内(§9.3) |
| 2. 起動していて、サインイン済みか | 同上のデータの置き場、またはマウント先の有無。【未検証】 | 起動とサインインの案内 |
| 3. 共有フォルダが、この PC 上のフォルダとして見えているか | 利用者に選んでもらったフォルダが、Drive for desktop の配下にあるか | 「共有フォルダをこの PC に出す」案内(§9.3) |
| 4. そのフォルダが、オンライン専用でなく、手元にあるか | 公式ヘルプのストリーミングとミラーリングの違い | 「このフォルダはオフラインでも使えるようにする」の案内 |
| 5. 自分にそのフォルダへの書き込み権があるか | 試しに専用フォルダを作れるか | 管理者に編集権限を依頼する文面を出す |

- 確認 1〜2 の見つけ方(標準のインストール先、プロセス名、マウント先のパス)は、公式ヘルプで確認できていない。実機で調べて、このファイルに追記する。
- フォルダを選ぶ画面を用意し、**利用者に Drive のフォルダを指定してもらう**。パスを自動で推測するより確実である。

### 9.3 チュートリアルの内容(案)

- インストール、サインイン、共有フォルダを自分の PC に出す、の 3 つの場面を、画面付きの短い手順にする。細かいボタン名は公式ヘルプに任せる。
- 「これは何のために要るのか」を一言で説明する。例: 「チームの人と履歴を共有するために、Google Drive をこのパソコンで使えるようにします。個人で使うだけなら、今はスキップできます」。
- 管理者が入れる場合のため、情報システム担当に渡す依頼文のひな形を用意する。
- 端末の種類に合わせて出し分ける(Windows と macOS)。

### 9.4 アプリの形(確定): 独立したアプリ(.exe)

利用者が確定させた。VS Code の拡張機能ではなく、独立した Windows アプリとして配布する。1 節の「専用の拡張機能」は、この専用アプリを指すものと読み替える。

この形が決めること(案):

- **導入時の確認は、セットアップウィザードまたは初回起動の画面で行う。** 9.2 の 5 項目を、アプリ自身が画面で順に確認できる。
- **常駐する監視プロセスとして動かす。** フォルダを監視して保存ごとに記録する(計画の置き場 C の「監視プロセス」に当たる)。Windows のログオン時に自動起動し、タスクトレイに状態を出す。起動していない間の保存は記録されない。この制限を、画面で伝える。
- **インストールは利用者単位にする(管理者権限を求めない)。** 企業の端末では、管理者権限が取れないことが多いため。【推測】実機と運用で確認が要る。
- **配布時の署名。** 署名のない .exe は、Windows の警告画面(SmartScreen)で止まりやすい。非エンジニアには強い障害になる。コード署名の入手と運用を、配布の前に決める。【一般的な知識であり、本調査では確認していない】
- **macOS は対象外とする。** .exe は Windows 専用である。macOS 版を作るかは未決。作る場合、Drive for desktop の置き場(`~/Library/Application Support/Google/DriveFS`)は公式ヘルプで確認できているので、検出は別に実装する。
- エンジニア版(VS Code 拡張、`src/` 以下)とは別の実行体になる。共有してよいのは、ストアや履歴形式のコードを、ライブラリとして切り出せた場合だけ。エンジニア版の `refs/microgit` とは混ぜない(計画 §6.4)。

### 9.5 未決

- Windows で Drive for desktop の存在を調べる具体的な方法(登録情報、標準のインストール先、プロセス名、ドライブ文字の有無)。公式ヘルプで確認できておらず、実機で調べる。
- 企業の管理下で、Drive for desktop の導入が制限されている場合の案内。
- 公式ヘルプのどのページを正本として案内するか(選定と、変更への追従)。
