## 1. 何のための仕組みか

#32 で記録（コミット）を速くしたあと、「次は fsync を減らそう」と考えていた。ところが、保存 1 回の処理全体を段階ごとに計ってみると、記録は **全体の 5%** にすぎなかった。

| 段階（Windows、保存 200 回の最後の 20 回の p50） | ms |
|---|---|
| ブランチの確認 | 30.6 |
| 記録（コミット） | 20.6 |
| 層の作成 | 125.4 |
| timeline.log の生成 | 57.6（履歴とともに伸びる） |
| Overlay の状態の更新 | 29.7 |
| 画面の更新 | 136.0 |
| 合計 | 405.5 |

fsync を減らしても、全体は数 ms しか変わらなかったはずだ。**部分だけを計って最適化すると、効かない所を磨いてしまう。**

---

## 2. 仕組み

### 2.1 段階ごとに時間を取る

保存のイベントが起きた時刻から数え、処理の区切りごとに「直前の印からここまで」をその段階の時間として足す（`SaveTimer.mark`）。合計だけでなく、利用者にとって意味のある 2 つの時点も記録する。

- **記録が終わるまで**（recorded）：保存してから、履歴に残るまで
- **その時点に戻れるまで**（restorable）：層ができて、過去に戻る操作ですぐ使えるまで

1 回ごとの値を残し、中央値（p50）と遅い側（p95）を見る。平均だけだと、たまに起きる遅い回が隠れる。

### 2.2 記録と関係のない仕事は、列の外へ

保存の処理は列（キュー）で 1 つずつ行う。列の中に重い後片付け（画面の更新・ログの生成）があると、**次の保存がその分待たされる**。

```
変更前：[保存1: 記録 → 層 → 画面 → ログ] [保存2: 記録 → 層 → 画面 → ログ] ...
変更後：[保存1: 記録 → 層] [保存2: 記録 → 層] ... (落ち着いたら) [画面 → ログ を 1 回]
```

保存が続いている間は後片付けを後ろへずらし、300 ms 落ち着いてから 1 回だけ行う（デバウンス）。画面の表示は少し遅れるが、記録は待たない。親のリポジトリへの publish も同じやり方をしていた。

### 2.3 知っていることを捨てない

層の作成は、保存 1 回で Git を 3 回起動していた（親を調べる、変わったファイルを調べる、中身を読む）。ところが、その直前の記録の処理は、**親・変わったファイル・中身をすべてメモリに持っていた**。それをいったん Git に書き、Git に聞き直していた。

記録の結果に「親からの変化」（delta）を載せ、層の作成にそのまま渡すようにした。125 ms → 32 ms。

ただし、知っていることを使う近道には **使える条件** がある。今回は「変わったのが保存したファイル 1 つだけで、消えたファイルが無く、親の層がもうある」とき。それ以外は、今までどおり Git から作る（遅いが確実な道を残す）。近道が正しいことは、差分テストで「delta が `git diff-tree` の結果と一致する」ことを毎回確かめている。

### 2.4 ほかのものも、ファイルを読めば済む

ブランチの確認は、保存のたびに Git を起動して今のタグを調べていた（`git tag --points-at HEAD`）。HEAD とタグのファイルを直接読めば同じ答えが出る。同じ答えになることは、実物の Git と比べる単体テストで確かめた（タグなし、同じコミットに複数、packed-refs、detached など）。

### 2.5 再現しない遅さ

計測の途中で 1 回だけ、記録の時間が保存を重ねるごとに 40 ms から 300 ms まで伸びた。速い記録の中で Git の起動や履歴の読み直しが起きていないこと（統計）を確かめ、同じ条件で 2 回測り直したが、再現しなかった。PC 側の要因と考えるが、原因は特定できていない。**確かめきれなかったことは、そう書いて残す**（学習用 09 の §2.5）。

## 3. 結果

| | 前 | 後 |
|---|---|---|
| 保存 → 記録が終わるまで | 52.3 ms | 24.9 ms |
| 保存 → その時点に戻れるまで | 180.1 ms | 56.9 ms |
| 保存 1 回の処理全体 | 405.5 ms | 57.2 ms |
| 1 秒に追いつける保存 | 約 2.5 回 | 約 17 回 |

（Windows 11、VS Code 1.140.0、カーネル版、保存 200 回の最後の 20 回の p50）

## 6. もっと知りたいとき

- 「Amdahl's law（アムダールの法則）」：全体のうち速くした部分の割合で、全体の速さの上限が決まる
- 「debounce」「throttle」：続けて起きる出来事をまとめる 2 つのやり方
- 「tail latency」：平均ではなく遅い側（p95・p99）を見る理由
