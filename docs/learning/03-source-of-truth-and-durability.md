## 1. 何のための仕組みか

MicroGit の履歴は、次期メジャーで 3 か所に現れる。

```
shadow の Git（.git/microgit/repos/<branch>.git）
Node 版の層とビュー（.microgit_overlay/）
カーネル版の層（最小ゲストのメモリ、または Linux の一時ディレクトリ）
```

同じ情報が何か所にもあると、「食い違ったらどれを信じるか」「どれが消えたら困るか」を決めておかないと、あとで必ず混乱する。

---

## 2. 仕組み

### 2.1 正本とキャッシュ

- **正本**（source of truth）：これが正しい、と決めた 1 か所。失うと取り返しがつかない
- **キャッシュ**：正本から作り直せる写し。速くするために持つ。消えても作り直せばよい

MicroGit では **shadow の Git を正本** にし、層とビューはすべてキャッシュにした（ADR-0001）。これで次のことが言える。

| 起きること | 影響 |
|---|---|
| 仮想マシンを再起動した（ゲストのメモリの層が消えた） | 必要になったとき Git から作り直す |
| Node 版の層の形式を変えた（#21 のレイヤ形式 v2） | 古い層を捨てて作り直す。移行の処理は要らない |
| ゲストが乗っ取られた・壊れた | ゲストの中に正本は無いので、履歴は無事 |
| 別のパソコンで同じリポジトリを開いた | 同じ Git から、そのパソコンのバックエンドで層を作る |

この考え方は、身近なところにもある。ビルドの成果物（`out/`）はソースから作り直せるキャッシュで、ソース（Git）が正本である。だから `out/` は Git に入れない。

### 2.2 キャッシュを作り直せることの代償

正本（Git）が表せないものは、キャッシュにも入れられない。Git は「空のディレクトリ」や「ディレクトリごと消した」を記録しないので、OverlayFS が本来持っているディレクトリの意味論（ゴールデンテストの N-1・N-2）は使えない。MicroGit の目的（ファイルの履歴）には影響しないので、これを引き受けた。

### 2.3 「保存した」はどこまで確かか：ページキャッシュと fsync

プログラムがファイルに書き込んでも、データはすぐにはディスクに届かない。

```
プログラム ──write()──→ OS のメモリ（ページキャッシュ）──（あとで）──→ ディスク
                           ↑ ここで「書けた」と返ってくる
```

| 何が起きたか | ページキャッシュのデータ |
|---|---|
| プログラム（VS Code）が落ちた | 残る。OS があとでディスクに書く |
| OS が落ちた・電源が切れた | 消える |

確実にディスクに届けるには `fsync()` を呼んで、「ディスクに届くまで待つ」必要がある。待つ分だけ遅くなる。

### 2.4 Git の既定は fsync しない部分がある

Git の既定（`core.fsync=committed,-loose-object`）では、MicroGit が保存のたびに作る **ばらのオブジェクト** と **ref** を fsync しない。電源断のあとに困るのは、次のような順番の崩れである。

```
1. オブジェクト（コミットの中身）を書く   ← まだページキャッシュ
2. ref（micro-history）をそのコミットに向ける ← まだページキャッシュ
（電源断）
ディスクには 2 だけ届いていた → ref が存在しないオブジェクトを指す → リポジトリが壊れる
```

`core.fsync=loose-object,reference` にすると、オブジェクトも ref もディスクに届くのを待つ。`core.fsyncMethod=batch` は、ばらのオブジェクトの書き出しをまとめ、最後に 1 回だけディスクのキャッシュを空にさせて待ち時間を減らす。

### 2.5 測ってから決める

「fsync は遅い」とよく言われるが、どのくらい遅いかは環境しだいなので、測った（`scripts/bench-durability.mjs`）。

| | 保存 1 回（中央値） |
|---|---|
| Git の既定 | 約 100 ms |
| fsync する | 約 102〜107 ms |

差は計測のばらつきと同じくらいだった。それより目立ったのは、**保存 1 回に約 100 ms かかり、そのほとんどが Git のプロセスを 4 回起動する時間だった** ことである。カーネル版の OverlayFS のコミットは 0.1 ms ほどなので、速さを気にするなら、OverlayFS ではなく Git の呼び出し方を見直すべきだと分かった。**推測で最適化せず、測ってから決める**。

### 2.6 積み重ねの上限（コンパクション）

OverlayFS の層は無限には積めない（最大 500 層、mount のオプション文字列は 4096 バイトまで）。そこで、層の深さが 32 を超えたら、差分ではなく「そのコミットの完全な写し」の層を作る（ADR-0003）。

この考え方は、ほかの分野にもある。

- データベースの **スナップショット＋差分ログ**：差分だけだと復元に時間がかかるので、ときどき全体の写しを取る
- 動画の **キーフレーム**：前のフレームとの差分だけを持ち、ときどき完全な 1 枚を入れる

MicroGit では、正本の Git に全部の履歴があるので、写しの層を作っても履歴は減らない。

## 4. 手を動かして確かめる

1. **自分の PC で測る**：`node scripts/bench-durability.mjs`。HDD や USB メモリの上のフォルダで測ると、差が大きく出るかもしれない
2. **Git の既定を読む**：`git help config` で `core.fsync` を探し、「default」の行を読む
3. **設定を切り替える**：VS Code の設定で `microgit.durability` を `process` にして、MicroGit の出力（`MicroGit Output`）に「永続性を変更: process」と出ることを確かめる
4. **キャッシュを消しても大丈夫なことを確かめる**：MicroGit を使っているワークスペースで VS Code を閉じ、`.microgit_overlay/` を丸ごと消してから開き直し、過去のマイクロコミットに戻る。層とビューが作り直される
