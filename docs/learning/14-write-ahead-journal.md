## 1. 何のための仕組みか

MicroGit は、保存 1 回ごとに Git のファイルを 7 つ書く（中身の blob、フォルダの tree 3 つ、commit、ブランチ、タグ）。既定の設定（`microgit.durability=power`）では、停電しても記録を失わないように、7 つそれぞれを **fsync**（OS のメモリにある書き込みを、ディスクに書き終わるまで待つ）していた。

fsync は「ディスクが書き終わった」と言うまで返ってこないので、遅いディスクでは時間の大半になる。#45 で測ると、記録の時間のうち fsync の割合は CI の Windows で 69%（7 回で 50.5 ms）、macOS で 56% だった。

利用者の方針は次のとおり。

> 非常時の復元は遅くても復元が可能であればそれでいい。大切なのは復旧が可能であることと、通常時に高速でマイクロコミットが可能であること。

つまり「ふだんの保存は速く、停電のあとは遅くてもよいから必ず元に戻せる」。これはデータベースが何十年も使っている **write-ahead log（WAL、先に書く記録）** の考え方そのものだ。

## 2. 仕組み

### 2.1 「確定」は 1 か所でよい

停電で困るのは、「保存した」と利用者に見せたのに、あとで記録が消えていること。7 つのファイルを全部確定させなくても、**7 つ全部を作り直せる情報が 1 か所に確定していれば**、記録は失われない。

```
ふだん（保存 1 回）
  1. 書くものをメモリに集める（オブジェクトの中身、ref の「前の値 → 新しい値」、HEAD の向き）
  2. それを 1 つの記録にしてジャーナルの末尾に追記 → fsync（ここで 1 回だけ待つ）
  3. Git のファイル（オブジェクト・index・HEAD・ref）を、fsync せずに書く

停電のあと（次に起動したとき）
  ジャーナルを先頭から読み、Git のファイルが足りない・壊れていたら、記録から作り直す
```

### 2.2 順番がいちばん大事

2 と 3 の順番を逆にすると何が起きるか考えてみる。Git のファイルを先に書いて、ジャーナルを確定させる前に停電すると、

- 名前はあるのに中身が途中までの blob が残りうる（OS は名前の書き込みと中身の書き込みの順番を守るとは限らない）
- ジャーナルにはその記録が無いので、作り直せない
- 次に同じ中身を保存すると、MicroGit は「この blob はもうある」と判断し、壊れた blob を指すコミットを作ってしまう

**先にジャーナルを確定させれば、ディスクにある Git のファイルはどれも、確定した記録から作り直せる**。これが「write-*ahead*」の意味。

### 2.3 書きかけの最後の記録

ジャーナルへの追記そのものの途中で停電することもある。そこで記録 1 つを次の形にしている。

```
'MGJ1'（4 バイト） | 長さ（4 バイト） | 中身（JSON） | 中身の SHA-256（32 バイト）
```

読むときは先頭から順に、形と SHA-256 が合う記録だけを使い、合わなくなったところで止める。最後の記録が途中で切れていたら、その保存は「記録されなかった」ことになる。Git のファイルはジャーナルの後に書くので、その保存の Git のファイルもまだ無い（はず）。ディスクの状態と食い違わない。

### 2.4 作り直すとき：ref は「誰が書いたか」を見分ける

オブジェクトは簡単だ。ハッシュが中身から決まるので、「無いか、展開してハッシュが合わなければ書き直す」だけでよい。

難しいのは ref（ブランチやタグが指すコミット）。停電のあと、ブランチが記録の途中の値を指していたとする。理由は 2 つ考えられる。

| 理由 | どうするべきか |
|---|---|
| 書き込みが失われ、途中の値が残った | 記録の最後の値に進める |
| ほかの処理（過去に戻る操作）が、ちょうどその値に戻した | 触らない（利用者がした操作を消してはいけない） |

最初の実装は「記録ごとに、今の値が記録の前の値と同じなら進める（compare-and-swap）」だった。停電を模した試験で、ブランチを 5 つ前に戻す操作のあとの停電を試すと、戻したブランチが最後の値まで進み直してしまった。5 つ前のコミットは、ジャーナルの 16 番目の記録の「前の値」でもあるからだ。**値だけでは 2 つを見分けられない**。

そこで次の 2 つで守っている。

1. **MicroGit 自身が ref を書き換える前に、ジャーナルを空にする**（チェックポイント、2.5）。過去に戻る前、ブランチの shadow を切り替える前、Git のコマンドでの記録に切り替える前。ジャーナルが空なら、作り直しが上書きすることはない
2. **それでも残る場合（別の窓や、手で Git を使った場合）は、ref のファイルの更新時刻で見分ける**。MicroGit が途中の値を書いたのは、その ref の最後の記録より前。ほかの処理が書いたのは、最後の記録より後

### 2.5 後片付け（チェックポイント）

ジャーナルは放っておくと伸び続け、中身は Git のファイルと二重になる。保存が 300 ms 途切れたとき（画面の更新と同じ予約）と、記録が 64 件か 8 MiB たまったときに、

1. 次のジャーナルのファイルを裏で作る（その間の保存は今のファイルへ）。できたら切り替える（以後の保存はそちらへ）
2. 古いジャーナルの記録で書いた Git のファイルを、まとめて fsync する（非同期、保存を待たせない）
3. 古いジャーナルを消す

途中で停電しても、古いジャーナルは消す前なので作り直せる。

### 2.6 ジャーナルに入れないもの

- **index**：Git でも index はキャッシュ扱いで、HEAD の tree から作り直せる。ただし作り直さないと危ない。停電で index が古いまま残ると、次の保存で「最後の数回分の変更が消えた tree」ができる。そこで ref を進めたときは `git read-tree HEAD` で作り直す
- **reflog**（ref の変更の履歴）：fsync しないので、行が途中で切れたり、無いオブジェクトを指したりしうる。`git fsck` はこれをエラーにする。作り直しのときに、壊れた行を取り除く（最初の試験で見つけた）

### 2.7 名前も確定させる（ディレクトリの fsync）

Linux や macOS では、ファイルの中身を fsync しても、そのファイルの**名前**は確定しない。名前は「ディレクトリ」という別のファイルの中身だからだ。新しく作ったジャーナルの名前が停電で消えると、中身が確定していても見つけられない。

そこで、新しいジャーナルを作ったら `microgit-journal/` を fsync し、チェックポイントでは Git のファイルが入っているディレクトリも fsync してから古いジャーナルを消す。次のジャーナルはチェックポイントの中で裏で作ってから切り替えるので、保存のときに払うのは起動して最初の記録だけ（作業の外で下ごしらえする、[13 回](./13-do-the-prep-when-needed.md) の逆の向き：使う前の暇なときに作っておく）。

## 3. 結果

手元の Windows（SSD）で、ファイル 50、保存 200 回（最初の 20 回を除いた平均、2 回測った）：

| | ジャーナルなし | ジャーナルあり |
|---|---|---|
| 保存 1 回の fsync の回数 | 7 | **1** |
| fsync の時間 | 9.8 ms | 1.1 ms |
| 記録全体 | 30.5 / 32.6 ms | **22.2 / 24.4 ms** |

この PC の fsync は 1 回約 1.4 ms と速いので、差は約 8 ms。fsync が遅い環境（CI の Windows で 1 回約 7.2 ms）ではもっと効くはず。

**次の壁**も見えた。fsync をしなくても、Windows では Git のファイルを作るだけで保存 1 回に約 17 ms かかる（オブジェクト 9.4 ms、ref 4.5 ms、index 2.1 ms）。ファイルを 1 つ作るたびに、NTFS のメタデータの更新とウイルス対策の検査が入るためと考えられる。ボトルネックを 1 つ外すと、次のボトルネックが見える（[12 回](./12-measure-the-whole-path.md)）。

## 5. 手を動かして確かめる

```sh
npm run compile
# 停電を模した 4 つの場面（失われた書き込み、書きかけの最後の記録、ほかの処理の書き換え、チェックポイントのあと）

# 段階ごとの時間を、ジャーナルあり・なしで比べる

```

試してみること：

- `src/fastGit/journal.ts` の `decideRef` で、更新時刻を見る行を消して（いつも `'advance'` を返す）、`micro-commit-crash.mjs` を走らせる。external の場面が失敗するのを確かめる
- `applyTxn` で、ジャーナルへの追記をオブジェクトの書き込みの後に動かすと、どんな停電で何が壊れるかを紙に書いてみる（2.2）
- `simulateLoss` が、書き込みを失わせるときに更新時刻も前の値に戻している理由を考える（ヒント：2.4 の見分け方）

## 6. もっと知りたいとき

- **WAL**：SQLite の「Write-Ahead Logging」のページ（sqlite.org/wal.html）。チェックポイントの考え方が同じ
- **ARIES**：データベースの復元の古典的な論文（Mohan ほか、1992）。「先に記録を確定させる」規則（WAL protocol）の出どころ
- **ファイルシステムのジャーナル**：ext4 の `data=ordered`。メタデータのジャーナルと、中身を書く順番の関係
- **fsync の落とし穴**：「Files are hard」（Dan Luu）。ファイルの作成と名前の変更を確定させる難しさ
- **Git の場合**：`git config core.fsync` と `core.fsyncMethod=batch` の説明（`git help config`）。Git 自身も、fsync の回数をまとめて減らす工夫をしている
