## 1. 何のための仕組みか

カーネル版のバックエンドでは、過去のコミットの姿を仮想マシンの中（ゲスト）で組み立て、その一覧と中身をホスト（あなたの PC）が受け取って、ワークスペースに書く。

ゲストは **信用しない**（SR-1）。ゲストの中のカーネルや agent に不具合があるかもしれないし、細工されたリポジトリのファイルでゲストが乗っ取られるかもしれない。乗っ取られたゲストが「`.git/hooks/post-checkout` にこの中身を書いて」と返してきたら、何も考えずに書くと、次に Git を使ったときにその中身がプログラムとして実行されてしまう。

だから、ゲストから受け取ったものは **ワークスペースに書く前に、ホストが必ず確かめる**。それが Boundary Guard（境界の見張り番）である。ゲストの中で確かめても意味がない。乗っ取られたゲストは、確かめる処理ごと書き換えられるからだ。

## 2. 仕組み

### 2.1 パストラバーサル：外に出るパス

```
../../.ssh/authorized_keys
/etc/passwd
C:\Windows\System32\...
```

`..`（親へ戻る）や絶対パスを含むパスは、ワークスペースの外を指す。これを使って本来書けない場所に書く攻撃を **パストラバーサル** という。Boundary Guard は、`/` 区切りの相対パスで、空・`.`・`..` の段が無いものだけを通す。Windows では `\` も区切りになるので、`\` を含むパスも通さない。

### 2.2 `.git` を狙う攻撃と、名前の「ゆらぎ」

ワークスペースの `.git/` は Git の管理領域で、特に `.git/hooks/` の中身は Git がプログラムとして実行する。ここに書かせないことが一番大事。ところが「`.git` という名前」の判定は、見た目より難しい。

| 名前 | なぜ `.git` と同じになるか |
|---|---|
| `.GIT`、`.Git` | Windows と macOS の既定の FS は大文字小文字を区別しない |
| `.git.`、`.git ` | Windows は名前の末尾のドットと空白を無視する |
| `GIT~1` | Windows（NTFS）は古いプログラムのために、長い名前に 8.3 形式の短い別名を付ける。`.git` の短い名前は `GIT~1` |
| `.g‌it`（見えない文字入り） | macOS の HFS+ は、名前の比較で一部の見えない Unicode 文字を無視する |

2014 年、Git 自身がこの種の攻撃を受けた（CVE-2014-9390）。細工したリポジトリを clone させると、`.GIT/hooks/` などに書かせて任意のプログラムを動かせた。Git はこれ以来、上の表の名前をすべて `.git` として扱って拒否している。Boundary Guard も同じ範囲を弾く（`isGitDirSegment()`）。

### 2.3 ホストの FS で表せない名前（O-14）

Linux のゲストの中では作れても、ホストでは作れない名前がある。

| ホスト | 表せないもの |
|---|---|
| Windows | 予約名（`CON`、`NUL`、`COM1`、`LPT1` などは、拡張子を付けて `con.txt` にしても使えない）、`< > : " | ? *` と制御文字、末尾のドットと空白 |
| Windows・macOS | 大文字小文字だけが違う 2 つの名前（`A.ts` と `a.ts`）は、同じファイルを指してしまう |
| macOS | Unicode の正規化形だけが違う 2 つの名前（「が」を 1 文字で書いたものと、「か」＋濁点で書いたもの）は、同じファイルを指してしまう |

最後の 2 つを見逃すと、2 つめのファイルを書いたときに 1 つめを黙って上書きしてしまう。Boundary Guard は、同じものを指す名前をそろえた「鍵」（`collisionKey()`）で比べ、ぶつかったら後のほうを弾いて知らせる。

### 2.4 中身が一覧と合っているか

ゲストは「ファイルの一覧（パスと sha256）」と「ファイルの中身」を別々に返す。受け取った中身の sha256 を計算し直し、一覧の値と一致しなければ書かない（`verifyContent()`）。一覧と中身が食い違うのは、ゲストが壊れているか、嘘をついているかのどちらかである。

### 2.5 リンクをたどってワークスペースの外に出る

ワークスペースの中に、外を指すリンク（シンボリックリンク、Windows のジャンクション）があると、`escape/pwned.txt` に書いたつもりが、実際には外のフォルダに書いてしまう。

```
ワークスペース/
  escape  →（リンク）→ C:\Users\あなた\大事なフォルダ
```

Boundary Guard は、書く前に途中のディレクトリを 1 つずつ見て、リンクがあれば書かない。リンクでないディレクトリも、実体のパス（realpath）がワークスペースの中にあるかを確かめる（`isInsideWorkspace()`）。書き込みの最後の要素がリンクなら、リンクの先に書かないよう、リンクそのものを消してから普通のファイルを置く。

このチェックと実際の書き込みのあいだに、別のプログラムがリンクを作る（TOCTOU：確かめた時と使う時の差）攻撃は防げない。ワークスペースはあなた自身のフォルダなので、そこまでは想定しない（脅威モデル §7）。

### 2.6 消してよいものは限る

過去に戻ったとき、今あって過去には無いファイルは消す必要がある。ただし消すのは、**MicroGit が記録したことのあるファイル**（shadow の履歴に出てきたもの）だけ。MicroGit を使わずに置いたファイルは、一覧に無くても消さない。利用者のディレクトリを丸ごと消すこともしない。

### 2.7 途中で相手が落ちても、半端な状態を残さない

最初の下書きは「消す → 中身を取ってくる → 書く」の順だった。これだと、中身を取ってくる途中でゲスト（仮想マシン）が落ちると、**消しただけで書けていない** 半端な状態がワークスペースに残る。

そこで順番を変えた。

```
1. 一覧を検証する            ← ワークスペースは読むだけ
2. 消すもの・取ってくるものを決める  ← 読むだけ
3. 中身を全部受け取り、sha256 を確かめる ← ここで相手が落ちたら、何もせずにやめる
4. 消す
5. 書く
```

相手とのやりとりが全部終わるまで、ワークスペースには一切手を付けない。これは「失敗するかもしれない部分を先に済ませ、確実に終わる部分を後に回す」という、トランザクションの考え方の小さな形である。4 と 5 の途中で PC の電源が切れる場合は防げないが、そのときも正本（shadow の Git）は無事なので、もう一度過去に戻る操作をすれば直る。

## 3. このリポジトリではどこにあるか

| やっていること | 関数 |
|---|---|
| パスの形 | `checkPathShape()` |
| `.git`・作業フォルダ・Windows の名前 | `checkPathPolicy()`、`isGitDirSegment()` |
| 大文字小文字・正規化のぶつかり | `collisionKey()`、`validateViewEntries()` |
| 一覧の検証（種類、sha256 の形、弾いたディレクトリの下も弾く） | `validateViewEntries()` |
| 中身の照合 | `verifyContent()` |
| リンクでの脱出 | `isInsideWorkspace()` |
| 検証したものだけを反映（消す → 書く） | `syncWorkspaceFromGuest()` |
