ファイルを保存するたびに裏で自動コミットを作り、あとから好きな時点に戻せる VS Code / Cursor 拡張「**MicroGit**」を、大学で個人開発しています。

次の版（5.0.0）で、この拡張機能の中に **小さな Linux を同梱** しました。中身は Linux カーネルと、Go で書いた 3 MB ほどのプログラム 1 つだけです。Windows でも Mac でも、その中で Linux の OverlayFS（フォルダを重ねて 1 つに見せる仕組み）を動かし、「過去の時点に戻る」操作を Windows で約 8 倍、Linux で約 6 倍速くしました。

:::message
**この記事で書くこと**
- なぜ VS Code 拡張に Linux カーネルを入れることになったのか
- 「Linux 環境まるごと」ではなく「OverlayFS という機能 1 つだけ」を持ち込む設計
- Windows で 1 MiB を送ったら中身が壊れた話、Mac で 64 KiB を超えると止まった話
- 本物の OverlayFS と比べてみたら、既存の実装のバグが次々に見つかった話
- 普通の `git checkout` の 20 倍以上遅かった「過去に戻る」が、Git と並ぶまで

VS Code 拡張でネイティブな機能を配りたい人、OS ごとの違いに悩んでいる人、仮想化の仕組みに興味がある人向けです。OS や仮想化の専門知識は前提にしません。
:::

## MicroGit とは

Ctrl+Z で少し前のコードまで戻して、そこから別の書き方を試し始めると、戻る前に書いていたコードは消えてしまいます。MicroGit はこれを防ぐための拡張機能です。

- ファイルを保存するたびに、普段の `.git` とは別の隠しリポジトリへ自動でコミットする（以下、この細かい履歴を **マイクロ履歴** と呼びます）
- サイドバーのグラフから、好きな保存点へ戻れる
- 過去に戻ってから書き換えると、そこから枝分かれして両方の履歴が残る

これまでの経緯は、以前の記事に書きました。

- [Ctrl+Z で消えるコードを残す VS Code 拡張を作った](https://zenn.dev/usudonsdev/articles/release2_0_0_branch)（v2.0.0）
- [Git 高速化の論文を読んで、保存ごとに履歴を残す拡張を作った](https://zenn.dev/usudonsdev/articles/article-zenn-microgit-overlaygit)（v4.0.0）

## Windows では、過去に戻るのに 1.4 秒かかっていた

保存のたびにコミットするので、履歴はすぐ数百件になります。そして、グラフの点をクリックして過去に戻るたびに、その時点のファイルをワークスペースに書き戻す必要があります。

v4 までは、この「過去の時点のフォルダを組み立てる」処理を、Linux の OverlayFS の考え方をまねて Node.js で書いていました。保存ごとの差分を「層」として積み、戻るときはその層を重ねて過去の姿を作ります。前回の記事では、**OS の mount は使わず Node.js 一本にする** と書きました。どの OS でも同じように動かすためです。

ただ、ファイル 200 個・保存 40 回の履歴で測ると、過去に戻る操作の中央値はこうでした。

| 環境 | Node.js 版 |
| --- | --- |
| Linux（WSL2） | 127 ms |
| Windows 11 | 1,426 ms |

Windows で 1.4 秒。保存のたびに履歴を増やし、気軽に行き来するツールとしては重すぎます。ファイルシステムの動きを JavaScript で再現する方式には、どうしても速さの上限があります。

一方で、OverlayFS は Linux カーネルに最初から入っています。MicroGit の「層を積んで、重ねて見せる」という設計は、OverlayFS とほぼ同じ形です。**本物を使えれば速い。でも Linux にしか無い。** 5.0.0 は、この問題に正面から取り組んだ版です。

## Linux 環境ではなく、「機能 1 つ」だけを持ち込む

Windows や Mac で Linux の機能を使う方法は、すでにたくさんあります。WSL2、Docker Desktop、Lima などです。ただ、どれも「Linux 環境まるごと」を用意するもので、拡張機能を入れた人全員に「まず Docker を入れてください」とは言えません。

そこで、提供する範囲を **OverlayFS という 1 つのカーネル機能だけ** に絞りました。

```
┌──────────── あなたの PC（ホスト） ────────────┐
│  VS Code ── MicroGit（TypeScript）            │
│                 │ 1 行 1 JSON の命令           │
│  QEMU（Windows） / Virtualization.framework（Mac） │
└─────────────────┼─────────────────────────────┘
                  ▼
┌──────────── 仮想マシンの中（ゲスト） ─────────┐
│  Linux カーネル 6.18（最小構成）               │
│    └ OverlayFS                                │
│  agent（Go で書いた 1 ファイル）＝ 命令を実行する係 │
│    └ 層はメモリ上（tmpfs）に置く               │
└───────────────────────────────────────────────┘
```

仮想マシンの中に入っているのは、Linux カーネルと agent の 2 つだけです。

- **シェルを入れない。** agent が起動直後の準備（`/proc` などの mount）も自分でやり、そのまま命令を待ちます。任意のプログラムは動かせません
- **ネットワークの仕組みを入れない。** カーネルの `CONFIG_NET` 自体を無効にしました。ホストとのやりとりは virtio-console という仮想の線だけで、ネットワーク関連の脆弱性がまるごと関係なくなります
- **命令は OverlayFS の操作だけ。** 「この層の上にこの変更を積む」「この層の姿を見せる」「このファイルを読む」といった、少数の単純な命令です

こうして削った結果、カーネルと agent を合わせたゲストは、圧縮して **3.6 MB 以下** になりました。拡張機能に同梱して配れる大きさです。

OS ごとの動かし方は次のとおりです。

| 環境 | 動かし方 |
| --- | --- |
| Linux x64 / arm64 | 仮想マシンなし。`unshare -Urm` で同じ agent を直接起動する（カーネル 5.11 以降） |
| Windows x64 | 同梱の QEMU で最小の Linux を起動する。管理者権限は不要 |
| Apple silicon Mac | macOS 標準の Virtualization.framework で最小の Linux を起動する |
| Intel Mac、Windows on Arm など | 従来の Node.js 版 |

Linux では本物のカーネルがすでにあるので、仮想マシンは使いません。Linux・Windows・Mac のどれでも、中で動く agent は同じバイナリで、同じ命令を受け取ります。

そして、**どの環境でも、使えなければ黙って Node.js 版に切り替わります。** 起動できそうに見えても、実際に agent を起動し、小さな層を 1 枚作って捨てるところまで試してから使います。Ubuntu 23.10 以降のように、セキュリティのために非特権のユーザー名前空間が止められている環境では、ここで失敗して Node.js 版になります。

## つまずいたこと

### Windows：1 MiB を送ったら中身が壊れた

Windows 版の QEMU では、最初は標準入出力（stdio）で仮想マシンと命令をやりとりしていました。仕組みを確かめるための小さなテストは、これで全部通っていました。

困ったのは、実際の大きさのファイルを流したときです。

| 1 回に送る中身 | stdio | 名前付きパイプ |
| --- | --- | --- |
| 16 KiB | 1,251 ms | 4 ms |
| 256 KiB | 20,139 ms | 3 ms |
| 1 MiB | 78 秒後に **中身が壊れて失敗** | 26 ms |
| 16 MiB | — | 2,308 ms |

速さに直すと、毎秒 13 KB ほどしか出ていませんでした。256 KiB のファイルを 1 つ保存しただけで、その保存を仮想マシンに伝えるのに 20 秒かかります。

この版の目的は「Windows で 1.4 秒かかっていた、過去に戻る操作を速くする」ことでした。それなのに、ちょっと大きめの JSON やテストデータを保存するだけで、**元の Node.js 版よりずっと遅くなる**。1 MiB では 78 秒待ったあげく、中身が壊れて失敗しました。壊れたまま使われることはなく、失敗すれば Node.js 版に戻りますが、それでは大きなファイルを扱う人ほど速くならないうえに、待たされるだけです。何のために仮想マシンまで持ち込んだのか分からなくなります。

しかも、小さな命令しか送らないテストでは、一度も表に出ませんでした。Node.js 版と結果を比べるテストで、実際の大きさのファイルを流して初めて見つかっています。

Windows の名前付きパイプに切り替えたら、同じ 1 MiB が 26 ms になりました。パイプの名前は、起動のたびに 128 ビットの乱数で作っています。

### Mac：64 KiB を超える 1 行で止まった

Mac の Virtualization.framework では、逆に「止まる」問題が出ました。virtio-console に約 64 KiB を超える JSON を 1 行で流すと、仮想マシンの中の agent が行の終わりを受け取れず、そこで応答が返ってこなくなります。

64 KiB は、思ったより小さい数字です。ファイルの中身は base64 にして送るので、1.33 倍にふくらみます。48 KiB ほどのソースファイルを 1 つ保存するだけで、この線を越えます。つまり Mac では、**少し長めのファイルを保存した瞬間に、仮想マシンが黙り込む** ことになります。

厄介だったのは、エラーが出ないことです。何かが失敗したのではなく、ただ返事が来ない。自分のコードの読み書きの問題かと思い、ホスト側の通り道を stdio から Unix ドメインソケットに替えてみましたが、同じところで止まりました。ここでようやく、自分の側ではなく、Mac の virtio-console の経路の制限だと切り分けられました。

対策として、Mac のときだけファイルの中身を 24 KiB ずつに分けて送り、受け取るときも分けて読むようにしました。やりとりの回数が増えるので、ほかの OS では使っていません。3 MiB のファイルや 700 個のファイルを含む 15 のシナリオで、126 回の過去移動を試して確かめています。

### 実機テストで、古い部品が混ざっていた

公開前の最後の確認として、配布する Mac 用のパッケージそのものを Apple silicon の実機に入れて試しました。2 日前に、このパッケージの候補で「4 つのテストがすべて通った」と記録していたものです（あとから見ると、そのときは開発用の経路で動いていた可能性が高いのですが、確かめきれていません）。

結果は 4 つのうち 3 つが通過。保存も、過去に戻る操作も、日本語の名前のファイルも、3 MiB のファイルも問題なく動きました。落ちたのは「どちらのバックエンドで動いているかを確かめる」テストだけでした。

中身を見ると、状態の表示には `active=kernel`（カーネル版で動いている）と出ているのに、**カーネル版で過去に戻る操作が一度も成功していません**。原因は、パッケージに入っていたのが 4 日前に作った古い Linux のイメージ（1 つ前の版の agent 入り）だったことでした。カーネル版がうまく動かず、そのたびに裏で Node.js 版が肩代わりしていたので、保存や復元は普通にできていたわけです。開発中のテストは別の場所から新しい agent を読み込んでいたので、この混在に気づけませんでした。

もしこのまま公開していたら、Mac の利用者の画面には「カーネル版で動いている」と表示され、機能もちゃんと動く。それなのに、誰の Mac でも速くなっていない。**表示だけ速い版になっているのに、誰も気づけない** 状態で配るところでした。機能が動くかだけでなく、「どちらで動いたか」まで確かめるテストを 1 つ入れていたことに救われました。

それ以来、公開の判定には手元で組み合わせたものを使わず、CI で一から作り直したパッケージだけを実機で試すことにしています。

## 仮想マシンの中は信用しない

仮想マシンの中の agent は、ワークスペースに直接書き込めません。agent が返した「ファイルの一覧と中身」は、必ずホスト側の検査（Boundary Guard）を通してから反映します。

- `.git` の中には書かない（大文字小文字の違い、末尾のドット、Windows の短い 8.3 形式の名前、macOS が無視する文字なども含めて弾く）
- `..` やシンボリックリンクで、ワークスペースの外に出ない
- 消してよいのは、MicroGit が記録したことのあるファイルだけ
- 中身をすべて受け取って検査し終えるまで、ワークスペースには触らない

仮想マシンの中に検査を置かないのは、中が乗っ取られたら検査ごと書き換えられるからです。

もう 1 つ決めたのが、**履歴の正本は、これまでどおりホストの Git** にすることです。仮想マシンの中の層は、Git からいつでも作り直せるキャッシュにすぎません。仮想マシンが落ちても、中身がおかしくなっても、捨てて作り直せば済みます。既存の利用者の履歴を変換する必要もありませんでした。

## 本物と比べたら、自分のバグが見つかった

カーネル版を作るにあたり、「Node.js 版と本物の OverlayFS が同じ結果を返すか」を比べるテストを作りました。同じ操作の列を両方に流し、できあがったフォルダを Git のツリーと突き合わせます。

目的はカーネル版の確認でしたが、先に見つかったのは **Node.js 版のバグ** でした。比べるテストで 4 つ、その作業の途中のスモークテストでもう 1 つです。

| 見つかった不具合 | 起きること |
| --- | --- |
| 日本語のファイル名（スモークテストで発見） | Git の既定設定だと名前がエスケープされて層に入らず、過去に戻っても中身が復元されない |
| ファイルを同名のディレクトリに置き換える | 保存時に例外で止まり、壊れたファイルが残る |
| ディレクトリを同名のファイルに置き換える | 保存時・過去に戻る時に例外になる |
| `.wh.` で始まる名前のファイル | ファイルが消える（OverlayFS の「削除の印」と区別できていなかった） |
| ファイル ⇔ ディレクトリを置き換えた時点へ戻る | ワークスペースへの反映が例外で止まる |

どれも、カーネル版と関係なく、v4 の利用者にも起きうるものでした。日本語のファイル名は特に痛いです。自分で作った「OverlayFS のまね」が、本物とどこで違うのかは、本物と並べてみるまで分かりませんでした。5.0.0 では、この 5 つをすべて直しています。

逆に、直せない違いも 2 つはっきりしました。空のディレクトリと、中身を消したあとに残る空ディレクトリの扱いです。Git はディレクトリを記録しないので、履歴の正本を Git にしている限り、本物の OverlayFS と同じにはできません。これは仕様として受け入れました。

## どれくらい速くなったか

ファイル 200 個・保存 40 回・行き来 30 回で測った中央値です。

| 環境 | 保存 1 回ぶんの層を作る | 過去に戻る | カーネル版の起動 |
| --- | --- | --- | --- |
| Linux（WSL2、仮想マシンなし） | 36.9 ms → **10.8 ms** | 127.4 ms → **21.6 ms** | 29 ms |
| Windows 11（QEMU） | 271.0 ms → **135.0 ms** | 1,425.8 ms → **169.7 ms** | 902 ms |

過去に戻る操作は、Linux で約 6 倍、Windows で約 8 倍速くなりました。Windows の起動には約 0.9 秒かかりますが、最初の保存のときに裏で起動を始めるので、待たされることはほとんどありません。

### 普通の Git と比べると

「6 倍、8 倍」と言われても、元が遅かっただけかもしれません。そこで、いちばん身近な基準である **普通の `git checkout`** と比べてみました。

同じ Mac で、同じ形の履歴（ファイル 200 個に保存 40 回）を普通の Git リポジトリにも作り、同じ 2 つの時点を `git checkout` で 30 回行き来しました。やっていることは同じ、「作業フォルダを過去の姿に切り替える」です。

| 過去に戻る操作（中央値、Apple M5・macOS 26.5.1） | 1 回目 | 2 回目 |
| --- | --- | --- |
| 普通の Git（`git checkout`、Git 2.50.1） | 30.0 ms | 28.6 ms |
| MicroGit v4（Node.js 版） | 685.4 ms | 703.1 ms |
| **MicroGit 5.0.0（カーネル版）** | **22.3 ms** | **22.4 ms** |

v4 までの MicroGit は、普通の Git の **20 倍以上遅かった** ことになります。グラフの点をクリックしてから、ファイルが戻るまで 0.7 秒。Git なら一瞬で終わる切り替えに、毎回ひと呼吸待たされていました。

5.0.0 では、それが **普通の Git と同じくらい、むしろ少し速い** ところまで来ました。しかも MicroGit は、切り替えのたびに仮想マシンから受け取った中身を検査してからワークスペースに書いています。そのぶんの手間を足しても、Git の checkout と並べて遜色ありません。

ただし、「Git より何倍も速い」わけではありません。今回の履歴は小さく、Git のほうもオブジェクトをまとめた（`git gc` した）状態では 24.8 ms まで縮みます。言えるのは、**保存のたびに履歴を残す道具が、普段の Git と同じ感覚で過去を行き来できるようになった** ということです。v4 までの「便利だけど、戻るのが少し重い」が、5.0.0 で「戻るのも Git 並み」になりました。

## いまの状態

5.0.0 は、まだ Marketplace に公開していません。公開の条件を「設計で対象にしたすべての OS（Linux x64・Linux arm64・Windows x64・Apple silicon Mac）で、カーネル版が実際に動くこと」と決めていて、Node.js 版への切り替えで動いただけでは合格にしていません。

Windows と Linux は GitHub Actions で、配布するパッケージそのものを VS Code に入れて毎回確かめています。Mac は GitHub の実行環境では仮想化が使えないため、実機で確かめます。その実機の確認が 2026 年 9 月 30 日に通り、すべての OS で条件がそろいました。

<!-- TODO：公開したら、公開日とインストール方法（Marketplace のリンク）をここに書く -->

公開されたら、設定は何も要りません。どちらで動いているかは、コマンド `MicroGit: Overlay Status` の先頭（`active=kernel` / `active=nodejs`）で確かめられます。カーネル版を使いたくない場合は、設定 `microgit.overlayBackend` を `nodejs` にしてください。

## おわりに

前回の記事で「OS の mount は使わず Node.js 一本にする」と書いたとき、理由は「拡張機能としてどの OS でも動かすのが難しいから」でした。今回やったのは、その難しさを避けずに、**持ち込む範囲を機能 1 つまで削る** ことで越えることです。

削ったおかげで、ゲストは 3.6 MB 以下に収まり、シェルもネットワークもなく、ホストとの境界は少数の命令だけになりました。そして何より、本物と並べて比べられるようになったことで、自分の実装のバグにも気づけました。

MicroGit は研究・開発段階のプロトタイプです。大事なプロジェクトでは、普段どおり Git でコミットしてから使ってください。
