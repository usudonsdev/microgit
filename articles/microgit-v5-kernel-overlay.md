ファイルを保存するたびに裏で自動コミットを作り、あとから好きな時点に戻せる VS Code 拡張「**MicroGit**」を、大学で個人開発しています（VS Code をもとにしたエディタの Cursor でも動きます）。

試行錯誤の途中をこまめに残したいとき、普通の Git には 2 つのストレスがあります。1 つは、残すたびに手が止まること。`git add` して、コミットメッセージを考えて、`git commit` する。数分おきにやる気にはなれません。MicroGit は、これを最初から Ctrl+S だけにしていました。

残っていたのが、もう 1 つのストレスです。**戻るたびに待たされる。** v4 までの MicroGit は、過去の保存点に戻るのに、Mac で約 0.7 秒、Windows では約 1.4 秒かかっていました。普通の `git checkout` の 20 倍以上です。気軽に行き来するための道具が、行き来するたびにひと呼吸待たせていました。

次の版（5.0.0）では、ここを普通の Git と同じくらい（Mac で 0.02 秒）まで縮めました。

使ったのは、Linux に最初から入っている **OverlayFS** という仕組みです。複数のフォルダを「層」として重ね、1 つのフォルダに見せる機能で、Docker もこれを使っています。保存ごとの変更を層として積んでおけば、過去のある時点の姿は「その時点までの層を重ねる」だけで作れます。

ただ、OverlayFS は Linux にしかありません。そこで、Windows や Mac でも使えるように、拡張機能の中に **小さな Linux を同梱** しました。中身は Linux カーネルと、Go で書いた 3 MB ほどのプログラム 1 つだけです。

:::message
**この記事で書くこと**
- 保存ごとの自動コミットを「ストレスなく」使うための 3 つの条件と、5.0.0 でどこまで満たせたか
- 普通の `git checkout` の 20 倍以上遅かった「過去に戻る」が、Git と並ぶまで
- そのために、VS Code 拡張に Linux カーネルを入れた理由と、「OverlayFS という機能 1 つだけ」を持ち込む設計
- Windows で 256 KB のファイル 1 つに 20 秒かかった話、Mac で少し長いファイルを保存すると黙り込んだ話
- 保存 1 回の記録も、Git のプログラムを起動せずに書くようにして、普通の Git のコミットより速くした話（停電への備えつき）

試行錯誤の履歴を気軽に残したい人、VS Code 拡張でネイティブな機能を配りたい人向けです。OS や仮想化の専門知識は前提にしません。
:::

## MicroGit とは

Ctrl+Z で少し前のコードまで戻して、そこから別の書き方を試し始めると、戻る前に書いていたコードは消えてしまいます。MicroGit はこれを防ぐための拡張機能です。

- ファイルを保存するたびに、普段の `.git` とは別の隠しリポジトリへ自動でコミットする（以下、この細かい履歴を **マイクロ履歴** と呼びます）
- サイドバーのグラフから、好きな保存点へ戻れる
- 過去に戻ってから書き換えると、そこから枝分かれして両方の履歴が残る

この記事では、v4 までの「OverlayFS の動きを JavaScript でまねた方式」を **旧方式**、5.0.0 で入れた「本物の OverlayFS を使う方式」を **新方式** と呼びます。5.0.0 は、新方式が使える環境では新方式で、使えない環境では旧方式で動きます。

これまでの経緯は、以前の記事に書きました。

- [Ctrl+Z で消えるコードを残す VS Code 拡張を作った](https://zenn.dev/usudonsdev/articles/release2_0_0_branch)（v2.0.0）
- [Git 高速化の論文を読んで、保存ごとに履歴を残す拡張を作った](https://zenn.dev/usudonsdev/articles/article-zenn-microgit-overlaygit)（v4.0.0）

## ストレスなく残して戻るための 3 つの条件

保存のたびに履歴を残す道具が「使っていて気にならない」ためには、次の 3 つが要ると考えています。5.0.0 の時点の状態と一緒に並べます（数字は同じ Mac で何十回か測った、真ん中の値です）。

| 条件 | 普通の Git | MicroGit 4（前の版） | MicroGit 5.0.0 |
| --- | --- | --- | --- |
| **残すのに手を止めない** | `git add` とメッセージが要る | Ctrl+S だけ | Ctrl+S だけ |
| **残すのを待たない** | コミットが終わるまで待つ（約 0.05 秒） | 裏で記録、編集は止まらない | 裏で記録、編集は止まらない |
| **戻るのを待たない** | 約 0.03 秒 | **約 0.7 秒** | **約 0.02 秒** |

1 つ目と 2 つ目は、v4 までに満たしていました。保存の記録は裏の列で順番に処理するので、Ctrl+S を押したあと、エディタが記録の終わりを待つことはありません。

足りなかったのが 3 つ目です。5.0.0 は、この 3 つ目を普通の Git と並ぶところまで持ってきた版です。

## 戻るたびに、ひと呼吸待たされていた

保存のたびにコミットするので、履歴はすぐ数百件になります。そして、グラフの点をクリックして過去に戻るたびに、その時点のファイルを、VS Code で開いている作業フォルダ（以下、ワークスペース）に書き戻す必要があります。

v4 までは、この「過去の時点のフォルダを組み立てる」処理を、OverlayFS の考え方をまねて Node.js で書いていました（旧方式）。保存ごとの差分を「層」として積み、戻るときはその層を重ねて過去の姿を作ります。以前の記事では、**OS の機能（OverlayFS のマウント）は使わず Node.js 一本にする** と書きました。OverlayFS は Linux にしかないので、どの OS でも同じように動かすためです。

ただ、ファイル 200 個・保存 40 回の履歴で測ると、過去に戻るのにかかる時間（何十回か測った真ん中の値）はこうでした。

| パソコン | 過去に戻るまでの時間（前の版） |
| --- | --- |
| Linux（Windows の中で動かす Linux） | 約 0.13 秒 |
| Windows 11 | **約 1.4 秒** |

Windows で 1.4 秒。グラフの点をクリックしてから、ファイルが戻るまでに 1 秒以上かかります。「さっきの書き方とどっちがよかったかな」と何度か行き来するだけで、そのたびに手が止まります。気軽に行き来するための道具としては重すぎました。ファイルシステムの動きを JavaScript で再現する方式には、どうしても速さの上限があります。

一方で、OverlayFS は Linux カーネルに最初から入っています。MicroGit の「層を積んで、重ねて見せる」という設計は、OverlayFS とほぼ同じ形です。**本物を使えれば速い。でも Linux にしか無い。** 5.0.0 は、この問題に正面から取り組んだ版です。

## Linux 環境ではなく、「機能 1 つ」だけを持ち込む

Windows や Mac で Linux の機能を使う方法は、すでにたくさんあります。WSL2（Windows の中で Linux を動かす仕組み）、Docker Desktop、Lima などです。ただ、どれも「Linux 環境まるごと」を用意するもので、拡張機能を入れた人全員に「まず Docker を入れてください」とは言えません。

そこで、提供する範囲を **OverlayFS という 1 つのカーネル機能だけ** に絞りました。

```
┌──────────── あなたの PC（ホスト） ────────────┐
│  VS Code ── MicroGit（TypeScript）            │
│                 │ 1 行 1 JSON の命令           │
│  QEMU（Windows） / Virtualization.framework（Mac） │
└─────────────────┼─────────────────────────────┘
                  ▼
┌──────────── 仮想マシンの中（ゲスト） ─────────┐
│  Linux カーネル 6.18（最小構成）               │
│    └ OverlayFS                                │
│  agent（Go で書いた 1 ファイル）＝ 命令を実行する係 │
│    └ 層はメモリ上（tmpfs）に置く               │
└───────────────────────────────────────────────┘
```

図の「ホスト」はあなたの PC、「ゲスト」はその中で動かす小さな仮想マシンです。QEMU はオープンソースの仮想マシンソフト、Virtualization.framework は macOS に標準で入っている仮想マシンの仕組みです。

仮想マシンの中に入っているのは、Linux カーネルと、命令を受け付けて実行するプログラム（以下 agent）の 2 つだけです。

- **シェルを入れない。** コマンドを打ち込む仕組みそのものがありません。起動直後の準備も agent が自分でやり、そのまま命令を待ちます。任意のプログラムは動かせません
- **ネットワークの仕組みを入れない。** カーネルの `CONFIG_NET` 自体を無効にしました。ホストとのやりとりは virtio-console という仮想の線だけで、ネットワーク関連の脆弱性がまるごと関係なくなります
- **命令は OverlayFS の操作だけ。** 「この層の上にこの変更を積む」「この層の姿を見せる」「このファイルを読む」といった、少数の単純な命令です

こうして削った結果、カーネルと agent を合わせたゲストは、圧縮して **3.6 MB 以下** になりました。拡張機能に同梱して配れる大きさです。

OS ごとの動かし方は次のとおりです。

| パソコン | どう動くか |
| --- | --- |
| Linux | 仮想マシンは使わない。Linux に最初から入っている OverlayFS を、管理者権限なしでそのまま使う |
| Windows（ふつうの Intel・AMD の PC） | 拡張機能に入っている小さな Linux を、裏で起動して使う。管理者権限は要らない |
| Mac（M1 以降の Apple のチップ） | macOS に最初から入っている仮想マシンの仕組みで、小さな Linux を起動して使う |
| それ以外（Intel の Mac、Arm の Windows など） | 前の版と同じ旧方式で動く |

Linux では本物のカーネルがすでにあるので、仮想マシンは使いません。Linux・Windows・Mac のどれでも、中で動く agent は同じバイナリで、同じ命令を受け取ります。

そして、**どの環境でも、使えなければ黙って旧方式に切り替わります。** 起動できそうに見えても、実際に agent を起動し、小さな層を 1 枚作って捨てるところまで試してから使います。Ubuntu 23.10 以降のように、セキュリティのために「管理者権限なしで隔離された空間を作る機能」（非特権のユーザー名前空間）が止められている環境では、ここで失敗して旧方式になります。

## つまずいたこと

### Windows：1 MB を送ったら中身が壊れた

Windows 版の QEMU では、最初は標準入出力（stdio：プログラムの入力と出力の通り道）で仮想マシンと命令をやりとりしていました。仕組みを確かめるための小さなテストは、これで全部通っていました。

困ったのは、実際の大きさのファイルを流したときです。

| 1 回に送るデータの大きさ | 最初の通り道（標準入出力） | 直した通り道（名前付きパイプ） |
| --- | --- | --- |
| 16 KB | 1.3 秒 | 0.004 秒 |
| 256 KB | **20 秒** | 0.003 秒 |
| 1 MB | 78 秒待ったあと **中身が壊れて失敗** | 0.03 秒 |
| 16 MB | （試していない） | 2.3 秒 |

速さに直すと、毎秒 13 KB ほどしか出ていませんでした。256 KB のファイルを 1 つ保存しただけで、その保存を仮想マシンに伝えるのに 20 秒かかります。

この版の目的は「Windows で 1.4 秒かかっていた、過去に戻る操作を速くする」ことでした。それなのに、ちょっと大きめの JSON やテストデータを保存するだけで、**元の旧方式よりずっと遅くなる**。1 MB では 78 秒待ったあげく、中身が壊れて失敗しました。壊れたまま使われることはなく、失敗すれば旧方式に戻りますが、それでは大きなファイルを扱う人ほど速くならないうえに、待たされるだけです。何のために仮想マシンまで持ち込んだのか分からなくなります。

しかも、小さな命令しか送らないテストでは、一度も表に出ませんでした。旧方式と結果を比べるテストで、実際の大きさのファイルを流して初めて見つかっています。

Windows の名前付きパイプ（プログラム同士がデータをやりとりするための、Windows の仕組み）に切り替えたら、同じ 1 MB が 0.03 秒になりました。パイプの名前は、起動のたびに 128 ビットの乱数で作っています。

### Mac：64 KB を超える 1 行で止まった

Mac の Virtualization.framework では、逆に「止まる」問題が出ました。virtio-console に約 64 KB を超える JSON を 1 行で流すと、仮想マシンの中の agent が行の終わりを受け取れず、そこで応答が返ってこなくなります。

64 KB は、思ったより小さい数字です。ファイルの中身は base64（データを文字だけで表す形式）にして送るので、1.33 倍にふくらみます。48 KB ほどのソースファイルを 1 つ保存するだけで、この線を越えます。つまり Mac では、**少し長めのファイルを保存した瞬間に、仮想マシンが黙り込む** ことになります。

厄介だったのは、エラーが出ないことです。何かが失敗したのではなく、ただ返事が来ない。自分のコードの読み書きの問題かと思い、ホスト側の通り道を stdio から別の仕組み（Unix ドメインソケット）に替えてみましたが、同じところで止まりました。ここでようやく、自分の側ではなく、Mac の virtio-console の経路の制限だと切り分けられました。

対策として、Mac のときだけファイルの中身を 24 KB ずつに分けて送り、受け取るときも分けて読むようにしました。やりとりの回数が増えるので、ほかの OS では使っていません。3 MB のファイルや 700 個のファイルを含む 15 のシナリオで、126 回の過去移動を試して確かめています。

### 実機テストで、古い部品が混ざっていた

公開前の最後の確認として、配布する Mac 用のパッケージ（拡張機能の配布ファイル）そのものを Apple silicon の実機に入れて試しました。2 日前に、このパッケージの候補で「4 つのテストがすべて通った」と記録していたものです（あとから見ると、そのときは開発用の経路で動いていた可能性が高いのですが、確かめきれていません）。

結果は 4 つのうち 3 つが通過。保存も、過去に戻る操作も、日本語の名前のファイルも、3 MB のファイルも問題なく動きました。落ちたのは「新方式と旧方式のどちらで動いたかを確かめる」テストだけでした。

中身を見ると、状態の表示には `active=kernel`（新方式で動いている）と出ているのに、**新方式で過去に戻る操作が一度も成功していません**。原因は、パッケージに入っていたのが 4 日前に作った古い Linux のイメージ（1 つ前の版の agent 入り）だったことでした。新方式がうまく動かず、そのたびに裏で旧方式が肩代わりしていたので、保存や復元は普通にできていたわけです。開発中のテストは別の場所から新しい agent を読み込んでいたので、この混在に気づけませんでした。

もしこのまま公開していたら、Mac の利用者の画面には「新方式で動いている」と表示され、機能もちゃんと動く。それなのに、誰の Mac でも速くなっていない。**表示だけ速い版になっているのに、誰も気づけない** 状態で配るところでした。機能が動くかだけでなく、「どちらで動いたか」まで確かめるテストを 1 つ入れていたことに救われました。

それ以来、公開の判定には手元で組み合わせたものを使わず、GitHub Actions の自動ビルド（CI）で一から作り直したパッケージだけを実機で試すことにしています。

ただし、実際に公開したパッケージは、実機で試したものの後に作り直したものです（その間に、記録の処理を速くする変更を入れたため）。手元に Mac が無かったので、実機での試し直しはしていません。代わりに、Mac 用の部品を実機で合格したものと 1 バイトずつ比べました。違いは、Go が agent に自動で埋め込む「ビルドしたときのコミット番号と時刻」と、それに連動する値だけで、仮想マシンの中身は同じでした。次の版からは、この埋め込み自体をやめて、比べやすくするつもりです。

## 仮想マシンの中は「間違えうるもの」として扱う

仮想マシンの中の agent は、ワークスペースに直接書き込めません。agent が返した「ファイルの一覧と中身」は、必ずホスト（あなたの PC）の上で検査してから反映します。

- `.git` の中には書かない（大文字小文字の違い、末尾のドット、Windows の `PROGRA~1` のような短い別名、macOS が無視する文字などで `.git` に化けるものも弾く）
- `..` やシンボリックリンクで、ワークスペースの外に出ない
- 消してよいのは、MicroGit が記録したことのあるファイルだけ
- 中身をすべて受け取って検査し終えるまで、ワークスペースには触らない

最初は「仮想マシンの中は攻撃者になりうるので信用しない」という考えで、この検査を置きました。作り進めるうちに、この前提を見直しています。仮想マシンの中にネットワークは無く、届くのは自分が保存したファイルだけです。同じファイルは、VS Code や Git、ほかの拡張機能が、PC の上で先に読んでいます。仮想マシンだけを特別に疑う理由は小さい、と考えました。

一方で、**間違いは実際に起きました。** 前の節に書いたとおり、Windows では中身が壊れ、Mac では黙って止まり、古い部品が紛れ込みました。そこで今は、仮想マシンの中を「悪意は無いが、間違えうるもの」として扱っています。検査はそのまま残し、壊れた結果がワークスペースに書かれるのを止める役目にしています。検査は、過去に戻る操作全体の 0.02 秒の中に収まるくらい軽いので、外す理由もありません。

もう 1 つ決めたのが、**履歴の正本（いちばん正しい記録の本体）は、これまでどおりホストの Git** にすることです。仮想マシンの中の層は、Git からいつでも作り直せるキャッシュにすぎません。仮想マシンが落ちても、中身がおかしくなっても、捨てて作り直せば済みます。既存の利用者の履歴を変換する必要もありませんでした。

## 本物と比べたら、自分のバグが見つかった

新方式を作るにあたり、「旧方式と本物の OverlayFS が同じ結果を返すか」を比べるテストを作りました。同じ操作の列を両方に流し、できあがったフォルダを、Git に記録されたその時点のファイル一覧と突き合わせます。

目的は新方式の確認でしたが、先に見つかったのは **旧方式のバグ** でした。比べるテストで 4 つ、その作業の途中の簡単な動作確認（スモークテスト）でもう 1 つです。

| どんなとき | 起きていたこと |
| --- | --- |
| 日本語の名前のファイル | 過去に戻っても、中身が元に戻らなかった（Git が日本語の名前を記号の列にして出力するのを、そのまま名前として使っていた） |
| ファイルを、同じ名前のフォルダに置き換えて保存した | 保存が途中で止まり、壊れたファイルが残った |
| フォルダを、同じ名前のファイルに置き換えた | 保存や、過去に戻る操作が途中で止まった |
| 名前が `.wh.` で始まるファイル | ファイルが見えなくなった（OverlayFS が「消した」という印に使う名前と区別できていなかった） |
| ファイルとフォルダを置き換えた時点へ戻った | 戻す途中で止まった |

どれも、新方式と関係なく、v4 の利用者にも起きうるものでした。日本語のファイル名は特に痛いです。自分で作った「OverlayFS のまね」が、本物とどこで違うのかは、本物と並べてみるまで分かりませんでした。5.0.0 では、この 5 つをすべて直しています。

逆に、直せない違いも 2 つはっきりしました。空のディレクトリと、中身を消したあとに残る空ディレクトリの扱いです。Git はファイルだけを記録し、空のディレクトリは記録しないので、履歴の正本を Git にしている限り、本物の OverlayFS と同じにはできません。これは仕様として受け入れました。

## 戻るときの待ち時間は、どれくらい減ったか

### 普通の Git と比べると

いちばん身近な基準は、普通の `git checkout` です。同じ Mac で、同じ形の履歴（ファイル 200 個に保存 40 回）を普通の Git リポジトリにも作り、同じ 2 つの時点を 30 回行き来しました。やっていることは同じ、「作業フォルダを過去の姿に切り替える」です。

| 過去に戻るのにかかった時間（Mac） | 1 回目の計測 | 2 回目の計測 |
| --- | --- | --- |
| 普通の Git（`git checkout`） | 0.030 秒 | 0.029 秒 |
| MicroGit 4（前の版） | 0.685 秒 | 0.703 秒 |
| **MicroGit 5.0.0** | **0.022 秒** | **0.022 秒** |

（Apple M5・macOS 26.5.1・Git 2.50.1。30 回行き来した、真ん中の値）

v4 までは、Git なら一瞬で終わる切り替えに、毎回 0.7 秒待たされていました。5.0.0 では、それが **普通の Git と同じくらい、むしろ少し速い** ところまで来ました。しかも MicroGit は、切り替えのたびに仮想マシンから受け取った中身を検査してからワークスペースに書いています。そのぶんの手間を足しても、Git の checkout と並べて遜色ありません。

ただし、「Git より何倍も速い」わけではありません。今回の履歴は小さく、Git のほうもオブジェクトをまとめた（`git gc` した）状態では 0.025 秒 まで縮みます。言えるのは、**保存のたびに履歴を残す道具が、普段の Git と同じ感覚で過去を行き来できるようになった** ということです。

### OS ごとの変化

ほかの OS でも、同じ条件（ファイル 200 個・保存 40 回・行き来 30 回の真ん中の値）で測っています。

| パソコン | 過去に戻るのにかかる時間（前の版 → 5.0.0） | 最初の 1 回だけかかる準備 |
| --- | --- | --- |
| Linux（Windows の中で動かす Linux。仮想マシンは使わない） | 0.13 秒 → **0.02 秒**（約 6 倍速い） | 0.03 秒 |
| Windows 11（拡張機能に入っている小さな Linux を使う） | 1.4 秒 → **0.17 秒**（約 8 倍速い） | 0.9 秒 |

Windows では、1 秒以上待たされていたものが 0.2 秒を切りました。最初の準備（小さな Linux の起動）には約 0.9 秒かかりますが、最初の保存のときに裏で起動を始めるので、待たされることはほとんどありません。

## 記録の処理も、普通の Git より速くした

戻る速さがそろったあとに残っていたのは、保存 1 回を記録する処理です。5.0.0 の途中までは、同じ Mac で保存 1 回の記録に約 0.15〜0.16 秒 かかっていました。普通の `git add` → `git commit`（約 0.05 秒）の 3 倍ほどです。

| 保存 1 回の記録にかかっていた時間（Mac、直す前） | 時間 |
| --- | --- |
| Git のコミットを作る（Git のプログラムを 4 回起動していた） | 約 0.10 秒 |
| 過去に戻るための準備（変わったファイルを、差分として積む） | 約 0.05 秒 |

エディタは記録の終わりを待たないので、使っていて手が止まるわけではありません。ただ、保存が続くと記録が追いつかなくなります。それに、「記録の中身は Git のコミットそのものだから、Git より速くはならない」と思い込んでいたのは間違いでした。

### Git のコマンドを使わずに、Git の形式で書く

`git commit` が中でしていることは、突き詰めると 4 種類のファイルを書くことです。

| 書くもの | 中身 |
| --- | --- |
| ファイルの中身 | 圧縮して、中身から計算した名前で置く |
| フォルダの一覧 | フォルダの中にあるファイルの名前と、その中身の名前 |
| コミット | どの一覧か、1 つ前のコミット、時刻、メッセージ |
| ブランチの指す先 | ブランチがいまどのコミットを指しているか |

MicroGit は、これを拡張機能の中で、**Git とまったく同じ形式で直接書く** ようにしました。Git のプログラムを起動しないので、起動にかかる時間（Windows では 1 回あたり数十ミリ秒）が丸ごと消えます。前回の記録の状態はメモリに持っておき、保存された 1 ファイルの分だけを計算し直します。

形式が同じなので、普通の Git でそのまま履歴を読めます。それを保証するために、同じ保存の列を「Git のコマンドで記録する版」と「直接書く版」の両方に流し、毎回の結果が 1 ビットも違わないこと、Git の整合性の検査（`git fsck --strict`）が通ることを、自動テストで毎回確かめています。

この作業の途中で、もう 1 つ大きな問題も見つかりました。保存のたびに「この中身は前にもあったか」を調べるため、履歴全体を読み直していたのです。Windows では、履歴が 1,000 回になると保存 1 回に 2.4 秒かかっていました。履歴の索引を一度だけ作り、あとは足していく形に直しています。

### 停電への備えを、7 回の待ちから 1 回に

Git のプログラムを起動しなくなると、次に大きかったのは **fsync** でした。書いたファイルは、すぐにはディスクに届かず、いったん OS のメモリに溜まります。fsync は「ディスクに書き終わるまで待つ」命令です。MicroGit は既定で、電源が落ちても記録を失わないように、保存 1 回で書く 7 つのファイルをそれぞれ fsync していました。GitHub Actions の Windows では、記録の時間の 7 割がこの待ちでした。

そこで、データベースが昔から使っている「先に書く記録（ジャーナル）」の方式にしました。

1. 保存 1 回で書くものを全部 1 つの記録にまとめ、ジャーナルというファイルの末尾に足す。**待つのはここの 1 回だけ**
2. Git のファイルは、待たずに書く
3. 保存が落ち着いたら、裏でまとめてディスクに確定させ、ジャーナルを消す

停電したら、次に起動したときに、ジャーナルから足りない分を作り直します。ジャーナルが先に確定しているので、Git のファイルがどう壊れていても作り直せます。この順番を逆にすると、壊れたファイルが「記録の無いまま」残りえます。

停電を模した試験（書き込みを失わせる、ジャーナルの最後を途中で切る、など）で、作り直したあとの履歴が正しいことを確かめています。作っている途中では、作り直しが「利用者がわざと過去に戻した操作」まで元に戻してしまう落とし穴にもはまりました（ファイルの更新時刻で見分けるようにしています）。

### 結果

普通の Git と同じ条件（ファイル 200 個、電源が落ちても失わない設定を両方でそろえる）で、保存を 300 回記録しました。

| 保存 1 回を記録する時間（Windows 11） | 時間 |
| --- | --- |
| 普通の Git（`git add` → `git commit`） | 0.107 秒 |
| **MicroGit 5.0.0** | **0.025 秒** |

（AMD Ryzen 7 5700X の PC。最後の 20 回の真ん中の値）

GitHub の自動テスト用の 5 台のパソコンでも、公開したものと同じ拡張機能を VS Code に入れて測っています（ジャーナルを入れる前 → 後）。

| パソコン（GitHub の自動テスト用） | 保存 1 回を記録する時間（直す前 → 後） |
| --- | --- |
| Windows | 0.070 秒 → **0.021 秒** |
| Mac（この PC では仮想マシンを使えないため、旧方式で動作） | 0.019 秒 → **0.012 秒** |
| Linux（Ubuntu、3 台） | 約 0.006 秒 → **約 0.003 秒** |

**記録の中身は Git のコミットそのものなのに、普通の Git より 4 倍ほど速く** なりました。Git が遅いわけではありません。Git はどんな使い方にも対応するため、毎回プログラムを起動し、設定を読み、作業フォルダの状態を確かめ直します。MicroGit は「いま保存されたのは、この 1 ファイルだけ」と分かっているので、その手間を省けます。

まだ残っているのは、Windows でファイルを作るたびにかかる時間です（保存 1 回で約 0.017 秒）。保存が落ち着いてからまとめて書く方式を検討しています。

## いまの状態

5.0.0 は、2026 年 10 月 2 日に、Cursor などが使う拡張機能のストア **Open VSX** に公開しました。Cursor の拡張機能の画面で「MicroGit」を検索すると入れられます。VS Code Marketplace への公開は準備中です。

公開の条件は「設計で対象にしたすべての OS（Linux x64・Linux arm64・Windows x64・Apple silicon Mac）で、新方式が実際に動くこと」と決めていて、旧方式への切り替えで動いただけでは合格にしていません。Windows と Linux は GitHub Actions で、配布するパッケージそのものを VS Code に入れて毎回確かめています。Mac は GitHub の実行環境では仮想化が使えないため、実機で確かめました（公開したパッケージとの関係は、上の「実機テストで、古い部品が混ざっていた」に書いたとおりです）。

設定は何も要りません。どちらで動いているかは、コマンド `MicroGit: Overlay Status` の先頭（`active=kernel` / `active=nodejs`）で確かめられます。新方式を使いたくない場合は、設定 `microgit.overlayBackend` を `nodejs` にしてください。

## おわりに

試行錯誤の履歴は、残すのが面倒でも、戻るのが重くても、使われなくなります。MicroGit は v1 から「残すのに手を止めない」を目指してきましたが、戻るたびに待たされるのでは、せっかく残した履歴を気軽に見に行けませんでした。

5.0.0 では、そのために Linux カーネルごと持ち込みました。持ち込む範囲を OverlayFS という機能 1 つまで削ったので、ゲストは 3.6 MB 以下に収まり、シェルもネットワークもありません。その結果、戻る速さが普通の Git と並びました。本物と並べて比べられるようになったおかげで、自分の実装のバグにも気づけました。記録の処理では、Git の形式は変えずに、Git のプログラムを使わずに書くことで、普通の Git より速くできました。

残すのに手を止めない。残すのを待たない。戻るのも待たない。3 つがそろって、ようやく「保存するだけで、あとは気にしなくていい」道具に近づいたと思っています。記録の処理も、普通の Git のコミットより速くなりました。

MicroGit は研究・開発段階のプロトタイプです。大事なプロジェクトでは、普段どおり Git でコミットしてから使ってください。
