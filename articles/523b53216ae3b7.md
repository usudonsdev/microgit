## はじめに

大学で個人開発をしている usudon です。いま、ファイルを保存するたびに裏で Git のコミットを自動で作る VS Code 拡張機能「MicroGit」を作っています。

その開発中に、**自分のプロジェクトの `.git` フォルダが丸ごと消えました。** コミットの手間をなくすツールを作っていたら、コミット履歴そのものを失ったわけです。

:::message
**この記事で書くこと**
- `.git` が消えた原因は、Node.js の `child_process` に渡した `cwd`（実行ディレクトリ）がずれて、別のリポジトリで破壊的な git コマンドが走ったこと
- 対策は、`cwd` に頼らず `git -C <絶対パス>` で対象リポジトリを明示すること
- 復旧できたのは、GitHub に push してあったから

Node.js から git コマンドを呼ぶツールを作っている人向けです。
:::

## 1. MicroGit とは

MicroGit は、Git でコミットする前の「ちょっとした試行錯誤」を自動で記録するための VS Code 拡張です。普段使っている Git（メインのリポジトリ）とは別に、隠しフォルダの中に専用のリポジトリ（以下、シャドウリポジトリ）を持ち、保存のたびにそちらへコミットします。

開発の動機は、Gitでコミットする前の「ちょっとした試行錯誤」を自動で記録したいという思いでした。

```text
 [保存(Ctrl+S)]  -->  [MicroGit]  -->  [自動コミット]
                                          |
 [任意地点へ復元] <--  [履歴ツリー表示] <---  [シャドウリポジトリ]
```

- **全自動シャドウコミット**: 保存をトリガーに、本体を汚さず `.microgit_shadow` 領域へ自動記録。
- **非線形な履歴管理**: 過去に戻って別の修正を始めたら、自動で「新しい世界線（mb-1, mb-2...）」として分岐。
- **直感的なUI**: 専用Webviewで、分岐したマイクロ履歴を視覚的に確認。

本家リポジトリの履歴を汚すことなく、ローカルでの試行錯誤を「Undo Tree」のように管理できるツールを目指していました。

## 2. `.git` が消えた原因

v1.0.1 のテスト中に起きました。
VS Code上のファイルがすべて「未追跡（Untracked）」になり、**`.git`フォルダそのものが削除されていました。**

### なぜ実行ディレクトリが狂ったのか
調査の結果、Node.jsの `child_process` で指定する `cwd`（実行ディレクトリ）に起因する問題であることが分かりました。

当初、Windows環境でフォルダ名に「研究室関係」という日本語が含まれていたため、文字化けが原因だと推測していました。しかし真因は、**パス解決の不備でディレクトリ移動に失敗した際、実行場所が想定外の場所（メインプロジェクトのルート）に固定されてしまったこと**にありました。

### 暴発した破壊的コマンド
本来は、バックアップ領域であるシャドウリポジトリの掃除のために実行されるはずだった破壊的な操作が、移動の失敗によってメインプロジェクト側で実行されてしまいました。
```bash
# 本来は .microgit_shadow 内で実行されるはずが、ルートで暴発
git rm -rf --cached . 
```
これでインデックスが消えただけでなく、`.git` ディレクトリ自体も消え、リポジトリがただのフォルダになりました。

`.git` が消えるということは、それまでのコミット履歴もブランチも全部なくなるということです。ファイルは手元に残っていても、「いつ、何を、なぜ変えたか」は二度と取り出せません。しかも原因は自分のツールです。気づかずに配っていたら、入れてくれた人のリポジトリでも同じことが起きうる状態でした。

### 対策：`cwd` に頼らず、対象を明示する
この失敗から、Git操作を自動化する際は実行ディレクトリ（`cwd`）の暗黙の挙動に頼らず、Gitの **`-C "絶対パス"` オプション** で対象リポジトリを明示するのがよさそうだ、と考えるようになりました。
`-C` なら、どのリポジトリを相手にするかがコマンド自体に書いてあるので、実行場所の取り違えは起きにくくなります。ただし、これだけで全部防げるわけではありません。破壊的なコマンドの前に、いまいる場所が想定どおりかを確かめることも要ります。

## 3. 復旧：リモートに push してあった
復旧に使えたのは、リモートに残っていた履歴でした。

幸いなことに、開発中のコードを定期的にGitHubへプッシュ（リモート同期）していたため、ネット上の履歴からプロジェクトを救出することができました。
```bash
git init
git remote add origin <URL>
git fetch
git reset --hard origin/master
```
おなじみの手順により、わずか数分で開発環境を元通りに再構築できたのです。

## おわりに
今回いちばん皮肉だったのは、コミットの手間を減らすツールを作っていた本人が、こまめな push のおかげで助かったことです。

復旧できたのは、開発中のコードを定期的に GitHub へ push していたからです。自動化ツールを作る側でも、通常の Git でのコミットと push は省けない、というのが今回の結論です。
