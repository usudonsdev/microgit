作りたい家具を文章で入力すると、AI が 3D モデルを組み立ててくれるサービス「[DIY-Agent](https://zenn.dev/usudonsdev/articles/article-zenn-diy-cad-aws-architecture)」を個人で作っています。AI（Amazon Bedrock）が CAD ソフト FreeCAD 用のプログラムを書き、それを AWS 上で実行して形を作ります。出来たモデルが「ちゃんと 1 つの塊として繋がっているか」を検査してから返し、部品がバラバラなら不合格にして作り直させる。素直な仕組みのつもりでした。

コードを読み直して、そうではないことに気づきました。検査は不合格を出す前に、**離れている部品を最大 30mm 引き寄せ、それでもくっつかなければ直径 4mm の柱を生やして**繋げていました。AI の失敗作を、自分のコードがこっそり整形して「合格」にしてユーザーに返していたわけです。

もっと悪いのはその次でした。**この書き換えが何件起きているのか、本番のログを見ても分かりませんでした。** 通知が stderr にしか出ておらず、しかもその stderr を、成功したジョブでは捨てていたからです。

AI が失敗したとき、全部作り直させるのではなく壊れた箇所だけ直させたい。そう思って調べ始めたら、その手前にこれが埋まっていました。この記事は、その修正ループを作るまでに何を直したかの記録です。

:::message
**この記事で書くこと**
- 成功したジョブのログだけが消えていた 3 つの原因
- 失敗を文字列ではなく型で扱い、「AI に直させる失敗」と「直させない失敗」を分けた方法
- 「数秒かかる」と思っていた処理を測ったら 0.055 秒で、設計を 1 つ丸ごと捨てた話

生成 AI の出力を検査・修正する仕組みを作っている人向けです。対象は DIY-Agent の v3.1.0 です。
:::

---

## 見えていなかった 3 つの穴

### 穴 1：成功したジョブのログが 1 行も残っていない

コンテナの入口が logging を設定していませんでした。Python の root ロガーの既定は WARNING なので、実行側が出していた `log.info` は**すべて捨てられていました**。

「部品 3 点、干渉なし」も「検査結果は合格」も、本番のログには存在しませんでした。動いているものは見なくていい、と無意識に思っていたぶん、気づくのが遅れました。

### 穴 2：成功したときだけ、通知の経路が塞がっていた

実行側は「終了コードが 0 以外のときだけ」エラーログを出す作りでした。ところが冒頭の自動接続は stderr にしか通知を出しません。

**つまり「救われた」ことが伝わる経路は、成功したときに限って塞がっていた**ことになります。冒頭の「何件書き換えられているか分からない」は、穴 1 とこれが重なった結果です。

### 穴 3：失敗位置を、渡す前に捨てていた

AI が書いたスクリプトは `compile(script, "<freecad_job_script>", "exec")` で実行しているので、例外の traceback には何行目で落ちたかが入っています。ところが例外を整形する関数が、最後の 1 行だけ残して捨てていました。

あとで差分修正をやるうえで一番欲しい「何番目の操作で落ちたか」が、**最初から手元にあったのに捨てられていた**わけです。

## 直し方：記録は検査側に貯め、ファイルで渡す

3 点セットで直しました。

| 層 | 変更 |
| --- | --- |
| 検査（FreeCAD 側） | 発火した書き換えを貯め、JSON ファイルに書き出す |
| 実行（外側） | 成功時も stderr を出す。発火していたら **WARNING** で出す |
| コンテナ入口 | DynamoDB に検査結果・自動接続の有無・内訳を残す |

設計として意識したのは 3 点です。

**検査側から AWS を触らせない。** 記録は FreeCAD 側で貯めてファイルで渡します。可視化のために既存の分担を崩したくありませんでした。

**発火は WARNING で出す。** INFO は環境次第で消えることが、まさに穴 1 で分かったばかりです。同じ理由で消える経路に、同じ情報を流すわけにはいきません。

**合格したジョブにも必ず書く。** 率を出すには分母が要ります。不合格だけ記録していると「何件救われたか」は永遠に分かりません。

記録の失敗でジョブは落としません。成果物の正しさには関わらないためです。

## 失敗を、文字列から構造に変える

差分修正を入れる前に、もう 1 つ直す必要がありました。

不合格は日本語のメッセージ付き `ValueError` だけで、コンテナの入口は**そのメッセージの文字列一致**でリトライ可否を決めていました。「干渉しています」が含まれるか、といった判定です。検査の文面を 1 つ直すとリトライが黙って止まり、ユーザーには「失敗」とだけ出ます。

そこで失敗を型にしました。

```python
class ValidationFailure(ValueError):
    code: str                 # disconnected_solid / interference / ...
    parts: list[str]          # 関係する部品名
    measured: dict            # ギャップ mm・干渉体積 mm3・超過 mm
    script_line: int | None   # 何番目の操作で落ちたか
    repairable: bool          # 差分修正で直せる種類か
    message_ja: str           # 既存のユーザー向け文面
```

`ValueError` を継承したのは、既存の `except ValueError` をそのまま効かせるためです。おかげで 17 箇所を一度に書き換えずに済みました。

一方で、テンプレート経路に残る 9 箇所は **あえて素の `ValueError` のまま**にしています。あれは「ユーザーが寸法を変えるしかない」入力エラーで、AI に直させる対象ではありません。全部を新しい型に揃えるほうが綺麗ですが、揃えると「直せない失敗」まで直そうとしてしまいます。

### 「直せない」側に倒したもの

以下では、AI に書かせる差分の修正コードを **patch** と呼びます。

| code | 理由 |
| --- | --- |
| `script_error` | patch は「元スクリプト → patch」の順で当てる。**元が落ちるなら patch を足しても同じ行で落ちる** |
| `not_inspectable` | 形状が壊れて判定自体ができない。部分修正より作り直しが速い |
| `empty_model` | 何も出来ていない。直す対象が無い |
| `motion_spec` | 可動定義は手前の Lambda が載せる。CAD 側の patch では変えられない |
| `unknown` | 何が起きたか分からないものを AI に投げても直らない |

タイムアウトも対象外にしました。重い解析や Spot インスタンスの遅さが原因のことがあり、形状を直させると無関係な改変を招きます。

### テストが教えてくれた 2 つの不足

実機のコンテナで 100mm 離した箱を通すと、狙いどおり「ギャップ 100mm / 許容 30mm」まで取れました。スクリプトが落ちるケースでは、何行目で落ちたかも拾えています。

一方で、テストが 2 つ穴を見つけました。

**どの部品が離れているか言えなかった。** 自動接続は名前を持たない塊を相手にするので、部品名が空のままでした。修正を書かせるとき、AI が部品を掴む手段は名前しかありません。これでは入力になりません。融合する前の名前付きオブジェクトどうしで測り直すようにしました。

**スクリプトが落ちると状態が空だった。** モデルは生成関数の中で作られるので、例外が飛ぶと呼び出し元から掴めません。**FreeCAD は落ちても直前までの部品が残る**という利点を、自分で捨てていたことになります。作った時点で登録するようにして、落ちる前に出来ていた分が残るようになりました。

## 測ったら、設計が 2 か所ひっくり返った

ここまで来て、ようやくループ本体に着手できます。その前に、計画段階で「分からない」と書き残していた点をコンテナで測りました。

| 分からなかったこと | 計画時の想定 | 実測 |
| --- | --- | --- |
| 検査側から AWS SDK が見えるか | 見えない見込み | **見えない**（FreeCAD 側 3.11.14 / 外側 3.10.12） |
| FreeCAD の再起動 | 数秒 | **0.08 〜 0.11 秒** |
| スクリプトの再実行 | 数秒 | **0.055 秒** |
| モデルの保存 / 再オープン | 未測定 | **0.005 / 0.007 秒**・12KB |

想定が 1 桁以上外れていました。そしてこの数字で、2 つの判断が変わりました。

**プロセスを分ける設計が「安い」ことが確定した。** 検査側から Bedrock は呼べないので、検査側が終了コードで合図して外側が Bedrock を呼ぶ、という分担が要ります。プロセスを分ける以上コストを覚悟していましたが、再起動が 0.1 秒ならほぼ無視できます。AWS SDK を FreeCAD 側に持ち込む工夫は不要でした。

**状態を保存して再構築を省く計画が、丸ごと要らなくなった。** 3 段棚相当のスクリプトを最初から実行し直しても 0.055 秒です。保存したモデルから開き直せば 0.007 秒ですが、この差のために状態管理を増やしても、Bedrock 1 回（数秒）の前では誤差でしかありません。

**そこで、このフェーズは目的を「失敗した形を残す」に振り替えました。** 不合格で終わったときだけモデルを S3 に置きます。5.2KB、保存 5ms。なぜ不合格になったかを FreeCAD で開いて目で見られるほうが、数値の羅列より速い。AI が何を直そうとしたのかも一緒に残しています。

速くするために作ろうとしていたものが、測ったら速度には効かず、デバッグには効いた。**捨てずに目的を差し替えられたのは、先に測ったからでした。**

## ループをタスクの中に閉じる

コストの内訳を見ると、1 回のリトライは 3 層に分かれていました。

| 層 | 中身 | 差分修正で消えるか |
| --- | --- | --- |
| Fargate タスク起動 | 数 GB のイメージ取得 + FreeCAD 起動 | **タスク内に閉じれば消える（最大）** |
| AI の全文再生成 | スクリプト全体の書き直し | 差分プロンプトで消える |
| モデルの再構築 | スクリプトを最初から実行 | 消せるが **0.055 秒**＝誤差 |

当初は 2 番目を狙っていましたが、**時間と金額の大半は 1 番目**でした。狙うべきはプロンプトの改善ではなく、ループの置き場所です。

### 終了コード 42

```text
検査側（FreeCAD の python）            実行側（外側の python）
  検査に不合格
    → 失敗の内容と現在の状態を書き出す
    → 終了コード 42                ──→  42 を見たら Bedrock に patch を要求
  patch を受け取って再実行         ←──  patch を書いて FreeCAD を再起動
    → 元スクリプト → patch の順に実行
    → 同じ検査へ
```

通常の失敗（終了コード 1）と区別できないと、実行側は「直せる失敗」と「作り直すしかない失敗」を取り違えます。直せるかどうかの判定は検査側で済んでいるので、**それを 1 ビットの合図として外に出すだけ**で足ります。

### patch は積み上げる

2 回目の修正は「元スクリプト → patch1 → patch2」の順で当てます。毎回 patch を 1 枚に作り直させると、1 回目で直った部分まで書き直させることになり、直った所を壊しかねません。AI には既に当てた修正を履歴として見せ、その続きだけを書かせます。

### 打ち切り条件

| 条件 | 値 |
| --- | --- |
| 最大試行 | 2 回（タスク内）→ その後は従来どおり全再生成 |
| 同一失敗 | 失敗の種類と部品が前回と一致したら即打ち切り |
| 予算 | 残り 10 秒未満で打ち切り（既定 240 秒） |
| patch 無し | AI が使える修正を返さなかった |
| 情報無し | 42 なのに失敗の内容が書き出されていない |

「同じ場所で同じ間違い」を検知したら即やめる、というのが効きます。文脈を変えないと直らない失敗を、同じ入力で繰り返させても時間を使うだけです。

打ち切ったら例外になり、**そこから先は従来の全再生成にそのまま落ちます**。段階フォールバックを新設したのではなく、既存の経路の手前に 1 段挟んだだけです。合わせて、タスクを立ち上げ直す回数の上限を 2 から 1 に下げました。タスク内で 2 回直すようになったぶんです。

## プロンプトの中心は「掴めるのは名前だけ」

patch からは元スクリプトのローカル変数（`body`, `handle` …）が見えません。掴めるのは `doc.getObject("名前")` だけで、その名前は失敗時に書き出した状態ファイルに入っています。

この制約をプロンプトの先頭近くに明記し、テストでも「その一文があること」を確認しています。全再生成用の文面と内容は近いのですが、**あちらは「書き直せ」、こちらは「今の座標をこう動かせ」**なので、流用せず書き直しました。

返ってきたコードは 8 パターンで弾きます（import / 新規ドキュメント作成 / ファイル操作 / OS 操作 / 動的実行 / 書き出し / モデルを触らない / 壊れた Python）。**弾いたときは例外にします。** 無言で空を返すと「修正したが直らなかった」と区別がつかなくなり、冒頭で潰したのと同じ種類の穴になります。

ここでもテストが弱点を見つけました。**BOM 付きで返されると構文解析が「壊れています」と言って落ちます。** 中身は正しいのに構文エラーに見え、原因が分かりにくい。BOM と全角空白を落としてから解析するようにしました。

### Bedrock を呼ばずに配線を確かめる

環境変数でダミーの修正コードを差し込めるようにしました。終了コード、patch の当て方、予算の配線を、AI の当たり外れと切り離して実機確認するための差込口です。

| シナリオ | 結果 |
| --- | --- |
| 直る修正 | **コンテナを立て直さずにモデル生成まで復帰** |
| 何も変えない修正 | 同一失敗として 1 回で打ち切り |
| 上限 0 | 即打ち切り |
| 修正コード自体が落ちる | patch のエラーとして分類 → もう 1 回試して打ち切り |

## IAM が無いと 1 回も動かない

デプロイで一番効いたのは、地味ですが権限でした。**CAD タスクのロールに `bedrock:InvokeModel` が付いていませんでした。** ここが無ければ、差分修正は 1 回も動きません。

ポリシーは既存の `Resource: "*"` に倣わず、推論プロファイルと基盤モデルの ARN に絞りました。クロスリージョン推論プロファイルは**プロファイル本体と、その裏の各リージョンのモデル本体の両方**に権限が要るので、実際の ARN を確認してから書いています。

`iam simulate-principal-policy` を使えば、**Bedrock を 1 回も呼ばずに**権限の実効性を確認できます。3 本すべて allowed を確認してからデプロイしました。

## まだ確かめていないこと

ここは正直に書いておきます。

**Bedrock を実際に呼んだ差分修正は、まだ本番で 1 件も通っていません。** 配線・終了コード・patch の適用・打ち切りは実機で確認しましたが、**プロンプトが実際に直せる修正コードを返すかどうかは別の話**です。デプロイ済みであることと、動くことが確認済みであることは違います。

部品を勝手に寄せた回数も、まだ数字が出ていません。可視化を入れたばかりで、いま集めているところです。この数字が出たら、30mm という閾値を見直します。頻度が高いなら、寄せる前に AI に直させるほうが筋がいい。ほぼ 0 なら、そもそもこのループの優先度が下がります。

**閾値を決め打ちしないために可視化を先にやった**ので、ここは待つのが正しい順序だと思っています。

## 学んだこと

**動いているものほど、見ていない。** 失敗のログは真っ先に整備しましたが、成功したジョブのログは 1 行も残していませんでした。しかも「黙って形を書き換えて合格にする」という一番知りたい挙動が、まさにその成功側の経路に隠れていました。

**率を出すには分母が要る。** 不合格だけ記録していると、何件救われたのかは永遠に分かりません。合格したジョブにも書く、という判断がこの記事の出発点でした。

**測ってから決めると、フェーズが 1 つ消える。** 「数秒かかる」と思っていた処理が 0.055 秒でした。速くするために作る予定だったものは不要になり、代わりにデバッグ用として残りました。作る前に測っていなければ、要らないものを作って「速くならない」と悩んでいたはずです。

**無言で失敗させない。** 危険なコードを弾いたときに例外を投げるのも、修正が空なら打ち切り理由を残すのも、根は同じです。最初に潰した穴は、結局ずっと同じ形で出てきます。
