Googleマップを開けば、最短・最速の道はすぐ出てくる。
でも散歩でほしいのは、むしろその逆だ。

少し寄り道して、公園や商店街や小さなカフェに触れてからゴールに着く。そんなルートを提案する Web アプリ「お散歩マップ」を、個人開発でつくっている。スタートとゴールと歩きたい時間を入れると、途中に立ち寄りたくなる場所を挟んだ散歩ルートを返してくれる。

:::message
**この記事で書くこと**
- 月3ドルという予算を先に決めたら、技術選定がどう決まったか（Google Maps を使わず、無料の地図データ OpenStreetMap と AWS のサーバーレスで組む）
- 生成 AI（Amazon Bedrock）に存在しない店をでっち上げさせないための工夫
- 実際に歩いてみて見つかった「実装が設計に追いついていなかった」箇所

地図アプリや生成 AI を使ったサービスを、低予算で作りたい人向け。
:::

> **この記事は 2026-08-23 時点の記録。**
> 直後に「寄り道価値による足切り」「通過点のドラッグ編集」「Bedrock の 2 モデル併用」が入り、見どころの選び方と AI の使い方が変わった。差分は末尾の「その後」にまとめてある。

この記事では、実装の細部よりも、**最初に決めておいた設計の芯**を残しておく。

---

## プロダクトの一言

スタート・ゴール・所要時間を入れると、好みに合う見どころを挟んだ散歩ルートを2〜3本返す。

対象はまず東京23区と川崎・横浜。好みは「散歩診断」でもよいし、スキップして「自然 / 食べ歩き / お買い物」の3択でもよい。どちらも同じエンジンに流す。

やらないことも最初に決めた。共同プラン、歴史テーマ、全国展開は後回し。MVPは「一人で、今日の散歩を決められる」まで。

---

## 設計を縛ったもの: 月3ドル

技術選定の前に、予算を固定した。**月額およそ3ドル**。

この数字があると、迷う選択肢がかなり減る。

- Google Maps / Places は使わない
- 常時起動のサーバは置かない
- AIは「毎回フル生成」しない

代わりに、無料またはほぼ無料で組める部品を選ぶ。

| 役割 | 採用 |
|------|------|
| フロント | React + TypeScript |
| 地図表示 | MapLibre + 無料タイル |
| 地名検索 | Nominatim（OSM） |
| 道に沿った線 | OSRM（公開デモサーバ）※失敗時は直線フォールバック。ただし徒歩用ではなかった（「その後」に追記） |
| 見どころの文章 | Bedrock（安いモデル）※後に用途で 2 モデル併用に変更 |
| API / DB | Lambda + DynamoDB |
| 配信 | S3 + CloudFront |

「高機能な地図APIを買わない」と決めた瞬間に、アプリの顔もはっきりした。最短ナビの模倣ではなく、散歩専用のシンプルな画面でよい、と。

---

## 判断1: フロントは React

MVPは一人用だ。それでもフロントに React を選んだのは、地図とサイドパネルが連動する画面を、状態とコンポーネントを分けて組み立てたかったから。

ロードマップには、複数人で同じ散歩プランを作り、好みを折衷する共同ルートがある。その先に、経由点をみんなで編集する体験を足すかもしれない。ただ、いまはまだ同期も共同編集もない。React を選んだのは、そういう画面を足すときに画面側の作りを変えずに済むかもしれない、という見込みで、確かめたわけではない。

---

## 判断2: 「通る場所」と「線の形」を分ける

最初のプロトタイプでは、スタート・見どころ・ゴールを直線で結んでいた。見た目は地図アプリなのに、道を無視して空を飛んでいる感じになる。

ここでやりがちなのが、タイル画像から道路をトレースするような凝った処理だ。精度も保守も重いので、MVPでは捨てた。

代わりに役割を分けた。

1. **waypoints** … どこを通るか（論理）
2. **徒歩ルーティング** … 道に沿った折れ線（見た目）
3. **MapLibre** … その折れ線をそのまま描く

アプリ側は「きれいな線を自分で計算する」必要がない。外部のルートAPI（OSRM の公開デモサーバ）に渡して、帰ってきた座標列を描くだけにする。APIが落ちたときだけ、直線にフォールバックする。

散歩アプリの肝は、ここだと感じている。**楽しさはwaypointsで決め、納得感はgeometryで担保する。**

---

## 判断3: AIに店名をでっち上げさせない

見どころの紹介文や並びはLLMに任せたい。一方で、存在しない店を自信満々に出されると、散歩アプリとしては致命傷になる。

なので生成は2段にした。

```
OSM（Overpass）で実在POIを取る
    ↓
Bedrockで選別・並べ替え・紹介文
    ↓
ルートに組み込む
```

LLMの仕事は「ゼロから場所を考える」ことではない。すでに存在する候補の中から、テーマに合うものを選び、散歩者向けの短い文を書くことだ。

コスト面でも同じ方向を向いている。同じエリア・同じ好みの再リクエストは、DynamoDBのキャッシュから返す。Bedrockはミスったときだけ。月3ドルの前提では、キャッシュはオプションではなく必須条件に近い。

---

## 判断4: 地図まわりは全部プロキシする

地名検索も地図クリック時の逆ジオコーディングも、ブラウザから無料APIを直叩きしたくなる。実際にはCORSや利用規約、レート制限があるので、Lambda側に薄いプロキシを置いた。

ユーザーから見ると「検索して選ぶ」か「地図をタップする」かの違いだけ。内部ではどちらも同じ地点データに正規化する。UIは二つ、データモデルは一つ、というだけの話だが、ここを雑にするとあとで必ず二重管理になる。

---

## 判断5: 配信は Amplify ではなく CloudFront

フロントの置き場所は、最初から Amplify Hosting も候補だった。git push でビルド・配信まで面倒を見てくれるし、個人開発ではいちばん楽な道だ。

それでも **S3 + CloudFront を CDK で明示する**方を選んだ。いちばん正直な動機から書くと、**もともと立てている別サイトが Amplify 採用**で、配信まわりの感覚はそちらで足りている。だからこのプロジェクトでは、Amplify の裏で動いているのと同系統の CDN を、**自分で組み立てる側から見てみたかった**。速さや「CDNが強いから」ではない。

そのうえで、お散歩マップ向きでもあった理由が次だ。

**1. アプリ全体を一枚の設計図に載せたかった**

本番は静的フロントだけではない。API Gateway、Lambda、DynamoDB、Bedrock の IAM まで含めて初めて動く。Amplify にフロントだけ預け、API は別管理、という二系統にすると、デプロイ手順も権限も環境変数も二重になる。既存サイト側で Amplify の楽さは知っているので、こちらは CDK でフロント配信から API・DB・AI 権限まで `infra/` に並べる実験にした。月3ドルで部品を増やしすぎないプロジェクトほど、入口は一つにしたい。

**2. コストの見え方を自分で縛りたかった**

Amplify は便利なぶん、何がいくらなのかがぼやけやすい。こちらは最初から「S3 と CloudFront はだいたいこれくらい」と予算表に載せたうえで組んでいる。請求の単位が設計図と同じ語彙で読めると、Bedrock のキャッシュや Lambda の呼び出しと並べて判断しやすい。ホスティングに魔法を期待するより、安い部品を明示した方が、この予算感には合う。

**3. このアプリに Amplify の便利さが、まだ必要ではなかった**

ブランチごとのプレビュー URL や Console 上の環境変数は魅力的だ。ただ MVP のフロントは Vite でビルドした SPA を配るだけなので、git 連携のビルド基盤がなくても困らない。地図の操作感はホスティング方式と無関係で、MapLibre はブラウザと API さえあれば動く。あとから CI で `build` → `deploy` を自動化すればよく、最初から Amplify に寄せる必然は薄かった。

対比だけ書くと、だいたいこうなる。

| | Amplify Hosting | お散歩マップ（CDK + CloudFront） |
|--|--|--|
| デプロイ | git push で自動ビルド | 手元または CI で `build` → `cdk deploy` |
| インフラ | 裏で S3/CloudFront 等が立つ | `infra/` に全部書いてある |
| フロントと API | 分かれやすい | 同じスタックに同居 |
| コストの見え方 | ホスティング単位でまとまりやすい | S3 / CloudFront / Lambda を個別に読める |
| CDN | CloudFront 系統 | 同じ系統 |

覚え方はシンプルだ。Amplify = ホスティングが面倒を見る（既存サイトはこちら）。CDK + CloudFront = 設計図を自分で書いて、配信も含めて同じ帳面に残す。慣れた道を一度やめて、組み立て側を試した、ということでもある。

---

## キャッシュを「1日鮮度」にする

キャッシュは必須だが、永久保存だと OSM 上の店の開閉が反映されない。かといって、毎日すべてのキーを Bedrock で作り直すと月3ドルが溶ける。

なので鮮度はこう付ける。

- 書き込みから **24時間** でソフト期限切れ
- 期限切れでも定時ジョブは回さない
- **次にそのエリアがリクエストされたときだけ** OSM + Bedrock で更新
- 誰も触らない古いキーは DynamoDB TTL で消す（掃除用 Lambda は置かない）

「1日に1回更新したい」気持ちは、先回り再生成ではなく、**鮮度の上限を1日にする**ことで満たす。利用があるキーだけ課金されるので、予算の向きと合う。

---

## 判断6: 天気は見せるが、ルートはまだ変えない

歩きやすさには天気が効く。ただ、雨のたびに見どころ生成をやり直すと Bedrock が走る。月3ドルの前提では、そこまで高くつけたくない。

なので最初は **表示と一言の助言だけ**にした。Open-Meteo を Lambda からプロキシし、出発時刻の時間帯の気温・降水・風を出す。ルートの中身は今までどおり。自転車メニューも、同じ天気APIを後から共有する前提で置いてある。

地名検索と同じ型だ。無料の外部APIはブラウザから直叩きせず、薄いプロキシの後ろに置く。

---

## あえて後回しにしたもの

認証はいま自前JWTだが、本番らしい仕組みはPhase 2でCognito Liteに移す前提で書いてある。個人開発の規模なら無料枠に収まりやすいし、最初からAuthに時間を溶かすより、ルートの質を上げた方がプロダクトらしい。

同様に、共同お散歩やリアルタイム編集も面白いが、一人用が動いてからの話にした。フロントの土台だけ先に React で置き、同期や折衷ロジックは後から足す。先に欲張ると、画面もデータも一気に増える。

## その後: 芯は正しかったが、実装が届いていなかった

ここまでが 2026-08-23 時点の記録だ。実際に自分で歩いてみると、**芯の立て方は間違っていなかったが、実装がそこに追いついていない**箇所がいくつも出てきた。書き残しておく。

### 「所要時間」を一度も見ていなかった

一番恥ずかしいものから書く。ルートを組み立てる `buildRouteProposal` が、`targetDurationMinutes` を**一度も参照していなかった**。30分と入れても180分と入れても、同じルートが返っていた。

冒頭の「プロダクトの一言」に「スタート・ゴール・所要時間を入れると」と書いておきながら、3つ目が効いていない。所要時間の予算内にスポットを詰める `fitSpotsToDuration` に置き換えて直した。

似た話がもう一つある。地図に写真が一度も出ていなかった。MediaWiki の `generator=geosearch` はパラメータの接頭辞に `g` が1つ増えて `ggs*` になるのだが、`gs*` のまま送っていて `missingparam` で常に0件だった。同じ間違いが `wikipedia-landmarks.ts` にもあり、**「必ず候補に残すランドマーク」も一度も取れていなかった**。

設計の芯を先に文章で固めるのは有効だ。ただ、**芯が実装されているかどうかは、まったく別の話**だった。文章にした時点で、できた気になっていた。

### 「珍しい」と「寄り道する価値がある」は別の軸だった

判断3で「AIに店名をでっち上げさせない」と書いた通り、候補は OSM の実在 POI から取っている。問題は候補の作り方ではなく、**並べ替え**のほうだった。

```
computePoiPickScore = themePriority*2 + localCharacter*0.9 + uniqueness*0.6
```

`computeUniqueness()` は「ブランドが無い」「名前が固有」を高く評価する。個人経営の**整骨院**はまさにこれに当てはまり、チェーンのカフェより高いスコアが付いていた。不動産屋も同じだ。散歩の見どころとして整骨院が出てくる。

希少度の設計自体が間違っていたわけではない。**「珍しい」と「寄り道する意味がある」は別の軸だった**、というだけだ。前者を計算していて、後者を計算していなかった。

案は3つ考えた。希少度の重みを下げる案は、順位が下がるだけで候補の少ないエリアでは結局出てくる。Bedrock のプロンプトで「選ぶな」と書く案は、実際にそう書いていたが守られないことがあるし、Bedrock 障害時のフォールバックには効かない。

採用したのは、**ランキングより前に足切りの段を作る**案だ。`detour-value.ts` で医療・金融・行政・クルマ・美容・宿泊を候補から落とす。日本の OSM はタグが粗く、**整骨院が `shop=massage` になっている**ようなことが普通にあるので、タグだけでなく名称でも弾く。逆に `historic` や `leisure=park` のような訪問価値タグを持つものは救済する。Overpass の `shop` クエリ自体も allowlist に絞った。

ランキングの最後にカテゴリのラウンドロビンも入れた。寺が9件続く並びを崩すためだ。

閉店の扱いも足した。`disused:` / `was:` / `abandoned:` タグを持つ POI を除外し、`opening_hours` から出発時刻と到着目安で営業中かどうかを判定する。解釈できない書式は `unknown` を返す。**誤って「営業中」と言わない**ことを優先した。

ただし限界がはっきりしている。高円寺〜阿佐ヶ谷の200件を実測したところ、`opening_hours` の収録率は6%、`check_date` は0%。しかも記載があるのはほぼ全国チェーンで、**このアプリが優先する個人店には付いていない**。OSM で閉店判定はできない。表示は「あれば出す」に留め、確実な確認は Google マップ検索リンクという導線でユーザーに委ねた。確実にやるなら Google Places API が要るが、それは「Google Maps / Places は使わない」という月3ドルの前提を崩す。ここはやらない側に倒した。

### モデルは1つに決めなくてよかった

記事では「Bedrock（安いモデル）」と一括りにしていた。安く済ませるなら1つに決めるべきだと思っていたからだ。実際には、**読ませる文章の質が足りなかった**。

品質差が一番わかりやすかったのは、中目黒の銭湯「光明泉」だ。Haiku は「自然の泉」と書いた。名前から推測している。Sonnet は「煙突と青いタイルが路地に突然あらわれる下町銭湯」と書いた。

そこで用途で分けた。

| 経路 | モデル | 実測 | 理由 |
|------|--------|------|------|
| `POST /routes`（ルート生成） | Claude Haiku 4.5 | 紹介文1件 4.4秒 | 30秒以内に返す必要がある。選定と短い一言には十分 |
| `GET /spots/preview`（ホバー詳細） | Claude Sonnet 4.6 | 6〜7秒 | ユーザーがじっくり読む文章。ここだけ質を優先 |

Sonnet は Haiku の約3倍の単価だが、プレビューは1件ずつで、生成済みは再生成しない。月3ドルへの影響は限定的だと判断した。**全部を良いモデルにするのではなく、ユーザーが文字を読む時間が長い場所だけ良いモデルにする。** 一覧は一言（`highlight`）、詳細は本文（`description`）の2段構成にして、本文は「具体物・できること・感覚」の3点必須、定型句は禁止句として弾くようにした。

このとき、時間予算の付け方も間違えていたことがわかった。Bedrock 呼び出しには「この秒数を超えたら打ち切ってフォールバック文を使う」という中断時間を置いている。Sonnet を試したあと Haiku に戻すとき、この中断時間を**8秒固定**に戻したのだが、戻しすぎだった。8件分の生成は Haiku でも8秒では終わらず、`/routes` が常にフォールバック文を返していた（実測: OSM 約5秒 + Bedrock 8秒で中断 = 14.2秒で `manual`）。

使う人から見ると、どのルートを出しても、見どころの紹介がすべて AI の書いたものではない予備の定型文になっていた、ということだ。モデルを 2 つに分けてまで文章の質を上げようとしていたのに、その文章が 1 件も画面に出ていなかった。

モデルごとに秒数を決め打ちするのをやめ、**ルート生成全体の時間予算（25秒）から残りをそのまま渡す**形に変えた。「モデルが速いか遅いか」ではなく「**あと何秒使えるか**」で決めるほうが、モデルを差し替えても壊れない。

日次の Bedrock 呼び出し上限も、環境変数 `MAX_DAILY_BEDROCK_CALLS`（既定20）に出した。この切り分けのとき一時的に60に上げて「日次上限が原因ではない」ことを確認できたので、**コスト防衛の値をハードコードしないのは、デバッグのためにも効く**とわかった。

### 判断2が効き、判断5は変えていない

通過点をマウスホールドで動かせるようにした。判断1で触れた、画面側で経由点を扱う作りの第一歩だ。離す前にトレードオフ（距離と時間の差、寄れるようになる見どころと外れる見どころ）をライブ表示し、元の位置60m以内に戻して離すと変更が取り消される。

ここで効いたのが判断2だった。**通る場所（waypoints）と線の形（geometry）を分けてあった**ので、ドラッグ中は直線近似で計算し、確定してから実際の徒歩経路を取り直せばいい。毎フレーム OSRM を叩く必要がない。動かしているのは論理側の waypoints だけだ。役割を分けておいたおかげで、あとから編集機能を足すのが素直だった。

一方、判断5の「Amplify ではなく CDK + CloudFront」は**変えていない**。本番配信は `OsanpoMapWebStack`（S3 + CloudFront）のままだ。

ただしフロントと API のスタックを分離し、`amplify/` に Amplify Gen2 の backend 定義を置いて、**API だけなら Amplify 側からも立てられる**状態にはした。`defineData` / `defineAuth` は使わず、既存の Hono API と自前JWTをそのまま流用する形にしてある。Amplify のオピニオン付きバックエンドに乗り換えると、判断5で挙げた「アプリ全体を一枚の設計図に載せる」が崩れるからだ。

一度やめた慣れた道を、選択肢として戻せる状態にはしておく。それくらいの温度感で置いてある。

### 「徒歩の線」は、徒歩の道ではなかった（2026-10-07 追記）

この記事では OSRM の公開デモサーバを「徒歩ルーティング」として使うと書いた。コードも `/route/v1/foot/` で呼んでいる。ところが公開デモサーバは、URL に foot と書いても車用の道路データで答えるらしい。確かめるため、東京都内の同じ2点を `foot` と `driving` で問い合わせたところ、どちらも距離 2,691 m・所要 398 秒と完全に同じ値が返ってきた。徒歩なら 30 分以上かかる距離で、時速に直すと約 24 km。**歩く速さではない**。

つまり今の「道に沿った線」は、車が通れる道に沿っていて、歩行者専用の道や階段は拾えていない可能性がある。散歩アプリとしては痛い。コードに「本番は OpenRouteService 等へ差し替え予定」とだけ書いて、プロトタイプのまま気づいていなかった。徒歩用のデータを持つサーバーに替えるのが直し方で、まだ直していない。

## いまの感触

「最短を出さない」と言うのは簡単で、実際にやるとうまくいく条件が狭い。

- 見どころが実在すること
- 線が道に乗っていること
- 同じ条件で何度も課金しないこと
- Googleマップのコピーに見えないこと

「その後」に書いた通り、この 4 つは満たしていても **「実在するが、寄り道する意味がない」** という 5 つ目の条件が抜けていた。整骨院は確かに実在する。

月3ドルという制約は厳しいが、おかげで構成が素直になった。無料の地図データ、薄いAPI、必要なときだけAI、あとはキャッシュ。フロントは React、配信は Amplify に任せきりにせず CloudFront を設計図に残した。派手さはないが、散歩アプリにはちょうどいい厚みだと思う。

次はソフトTTLを本番に載せつつ、ルート生成の安定化と保存・認証まわりを少しずつ寄せていく。同じエリアを歩いても「今日はこっち」と思える候補が、古くなりすぎず安定して出るようにしたい。
